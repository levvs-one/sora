# Sora для Apple-платформ: архитектура, таргеты и границы платформы

Дата: **20.10.2026**. Статус: **исследовательский/архитектурный документ**,
не код. Зона ответственности — подотдел исследований и архитектуры
департамента Apple-клиентов. Документ фиксирует решения, с которыми
сверяются подотделы кода; где факт не подтверждён источником, так и
написано: **не подтверждено**.

Требование владельца: «все системы, исключений нет». Этот документ
честно разделяет три вещи, которые нельзя смешивать:

1. что **разрешает API** Apple (самая широкая граница);
2. что **может собрать текущий тулчейн** и **примет App Store** в 2026
   (самая узкая практическая граница для сторного канала);
3. что **умеет актуальный libbox** ветки sing-box 1.14 (граница движка).

Итоговый таргет — это пересечение всех трёх, а не минимум одной из них.
Для каждого сегмента вне пересечения ниже дано письменное обоснование
и вариант (legacy-таргет / ограниченный режим / документированный
отказ), а не молчаливое исключение.

Внутренние источники репозитория (не веб):

- `packaging/engines/engines.lock` — пин движков: sing-box
  **1.14.3-lx.22** (форк `Leadaxe/sing-box-lx`), Xray v26.10.17,
  mihomo v1.19.32. В lock-файле есть только Linux/Windows-бинарники
  sing-box; **Apple-сборки libbox (Libbox.xcframework) в lock нет** —
  это отдельный пробел поставки, см. §2.4.
- `core/engine/singbox/render.go` — эталонная семантика рендера
  sing-box-конфига в Go-ядре (§2.2).
- `core/engine/plan.go` — engine-независимая модель `Plan` (протоколы,
  транспорты, TLS, DNS, TUN, группы, правила), от которой зеркалится
  Swift-контракт (§3.3).
- `docs/android-vpnservice.md` — зафиксированные требования к
  библиотечному (in-process) встраиванию движка: внешний бинарник на
  мобильной платформе невозможен, нужен embedded-драйвер, protect-бридж
  сокетов, системный kill switch вместо самодельного файрвола. Apple-
  дизайн ниже этим требованиям **не противоречит** и повторяет их
  структуру: libbox в процессе расширения, платформенный бридж,
  kill switch средствами системы + конфига, а не пакетами/правилами ОС.

## 1. Deployment targets и покрытие старых систем

### 1.1. Граница API: Network Extension / NEPacketTunnelProvider

- Packet tunnel provider (`NEPacketTunnelProvider`,
  `com.apple.networkextension.packet-tunnel`) — механизм, на котором
  строится TUN-клиент на обеих платформах. По вторичному источнику
  (разбор чужого PacketTunnel-проекта) API требует **macOS 10.11+**,
  «as this is when the NEPacketTunnelProvider API was introduced»
  [S1]. Для iOS тот же класс выводов в поиске даёт «Network Extension
  framework (introduced in iOS 9)» [S2]. **Оговорка честности:**
  первоисточник Apple (страница доступности `NEPacketTunnelProvider`
  в документации) в этой волне напрямую не вычитан; цифры iOS 9 /
  macOS 10.11 помечаются как **подтверждено вторичными источниками,
  не первоисточником Apple**.
- Практический вывод: сама по себе граница NE (iOS 9 / macOS 10.11)
  **не является** ограничителем таргета в 2026 году. Ограничители —
  тулчейн, App Store и libbox (§1.2–§1.4). Ссылаться на «NE не умеет»
  для отказа сегментам iOS 12–14 / macOS 10.13–10.15 **нельзя** — это
  было бы выдуманным обоснованием.

### 1.2. Граница движка: libbox ветки 1.14

- Официальная страница клиентов sing-box для Apple фиксирует
  требования официальных клиентов SFI/SFM/SFT:
  **iOS 15.0+ / macOS 13.0+ / tvOS 17.0+** [S3] (страница открыта и
  вычитана целиком в этой волне).
- Тот же пол подтверждается разбором сборочной системы sing-box:
  Apple-сборка libbox целится в `ios, iossimulator, tvos,
  tvossimulator, macos` с требованиями **iOS 15.0+, macOS 13.0+,
  tvOS 17.0+** (`cmd/internal/build_libbox/main.go`) [S4]; зеркальный
  разбор CI повторяет: «Apple: Generates a unified Libbox.xcframework
  targeting iOS (15.0+), macOS (13.0+), and tvOS (17.0+)» [S5].
- Changelog 1.14.0 подтверждает, что ветка 1.14 — актуальная линия
  (iOS/tvOS-клиенты вернулись в App Store, Hysteria2: BBR profile,
  hop interval randomization, gecko obfs и т.д.) [S6]. Рендер sora уже
  опирается на 1.14-семантику (см. `render.go`: `http_clients` вместо
  deprecated `download_detour`, Hysteria2 `bbr_profile`/
  `hop_interval_max` — «sing-box 1.14»).
- Сторонний (не официальный и не lx) Swift-пакет libbox старой ветки
  заявлял iOS 12.0 / macOS 11.0 [S7]. Это **не** основание для таргета:
  пакет относится к v1.11.8, не к пиннутой 1.14.3-lx.22, и не является
  ни официальным клиентом, ни нашим форком. Приводится только как
  доказательство, что *старые* ветки libbox технически собирались под
  более низкие полы — это важно для legacy-варианта в §1.6.
- **Не подтверждено:** публикует ли форк `Leadaxe/sing-box-lx`
  (1.14.3-lx.22) собственный `Libbox.xcframework` и с какими именно
  `-iosversion`/`-macosversion` он собран. В `engines.lock` Apple-
  артефактов нет. До подтверждения подотдел сборки обязан либо
  собирать libbox из исходников форка самостоятельно (тогда полы
  задаём мы флагами gomobile, но не ниже полов используемых API
  sing-box), либо зафиксировать новый пин. Заявлять «lx.22 libbox =
  iOS 15/macOS 13» без проверки артефакта **нельзя**.
- gomobile как инструмент: флаг `-iosversion` задаёт минимальную
  версию iOS для компиляции, значение по умолчанию — **13.0**;
  `-macosversion` по умолчанию не задан [S8]. То есть сам gomobile
  не запрещает пол ниже 15/13 — пол задаёт код sing-box и его
  зависимости, а не биндинг-инструмент.

### 1.3. Граница тулчейна и App Store при сабмите в 2026

Подтверждено страницей Apple «Upcoming Requirements» [S9]:

- С **28.04.2026** загрузки в App Store Connect должны быть собраны
  **Xcode 26+** с SDK семейства 26 (iOS 26 / iPadOS 26 / tvOS 26 /
  visionOS 26 / watchOS 26). Это требование к **SDK сборки**, а не к
  runtime-таргету пользователей [S9][S10].
- С **09.09.2026** приложения iOS/iPadOS при загрузке должны таргететь
  **iOS 13 или новее** [S9].
- С **апреля 2027** (анонсировано): минимум таргета iOS/iPadOS —
  **iOS 15+**, SDK — семейства 27 [S10].

Практическая граница жёстче формальной: по сводке о поддержке Xcode,
**Xcode 26 перечисляет deployment targets iOS от 15**, Xcode 27 —
также от 15 [S10]; независимый разбор SDK-полов даёт для Xcode 26
SDK floor iOS 12.0 / macOS 10.13, а для Xcode 27 — iOS 15.0 /
macOS 12.0 [S11]. Источники здесь расходятся в том, что считать
«полом» (список в UI Xcode против SDK floor), поэтому честная
формулировка:

- **Не подтверждено до проверки на реальной машине сборки**, можно ли
  Xcode 26, которым обязаны собирать для App Store, выставить
  deployment target iOS 12–14 так, чтобы бинарь прошёл загрузку.
  Сходящиеся вторичные источники указывают, что поддерживаемый
  диапазон Xcode 26 начинается с **iOS 15** [S10][S12].
- Следствие для прямого (не-сторного) канала macOS: Developer ID-
  сборку можно собирать **старым Xcode параллельно** — App Store-
  правила на неё не распространяются. Для iOS такого канала без
  джейлбрейка/enterprise-сертификата не существует: TestFlight и
  App Store идут через App Store Connect и тот же Xcode-гейт.

### 1.4. Граница UI: SwiftUI по версиям

- SwiftUI базовый: **iOS 13+ / macOS 10.15+** [S13][S14].
- `NavigationStack`/`NavigationSplitView`: **iOS 16+** (и macOS 13+);
  на iOS ≤15 единственный вариант — deprecated, но компилирующийся
  `NavigationView` [S15][S16].
- `MenuBarExtra` (SwiftUI-сцена меню-бара macOS): относится к
  поколению iOS 16 / macOS 13 API; точная страница доступности Apple
  в этой волне не вычитана — **не подтверждено первоисточником**,
  в коде обращаться только через `@available(macOS 13, *)` с
  фолбэком на `NSStatusItem` (AppKit).
- WidgetKit: введён на WWDC 2020 с iOS 14 [S17] (вторичный источник);
  интерактивные виджеты — через AppIntents, поколение iOS 17 —
  **не подтверждено** в этой волне, проектировать как enhancement.
- AppIntents: фреймворк прибыл с **iOS 16** (2022), заменив SiriKit
  для новых интеграций [S18][S19].
- `SMAppService` (ServiceManagement, регистрация login item/демона из
  бандла): поколение **macOS 13 Ventura** — подтверждается
  контекстом источников о Login Items Ventura и пометкой API как
  нового перехода от legacy launchd-плистов [S20]; точная страница
  доступности Apple — **не подтверждено первоисточником**. На
  macOS ≤12 фолбэк — `SMLoginItemSetEnabled` (deprecated) или
  LaunchAgent-плист, с честной пометкой legacy в UI.

### 1.5. Архитектуры и 32-бит

- iOS: поддержка 32-битных приложений прекращена в **iOS 11** (2017)
  [S21][S22]. Любой современный таргет — arm64 only; «32-битный iOS-
  сегмент» не существует как запускаемая цель для нового приложения.
- macOS: **10.15 Catalina полностью удалила 32-бит** [S21][S23];
  10.14 — последняя версия с 32-битными приложениями. Наш код —
  64-битный (arm64 + x86_64 universal для macOS-таргетов, где это
  применимо); сегмент «32-битный macOS» закрывается не таргетом, а
  тем, что сама ОС его не запускает при ≥10.15, а при ≤10.14 см.
  legacy-обоснование §1.6.
- macOS 26 (Tahoe) по вторичному источнику «Requires Apple Silicon;
  Intel Macs are no longer supported» [S24] — **не подтверждено
  первоисточником Apple в этой волне**; на таргеты ≤ macOS 13 это не
  влияет, влияет только на верхнюю границу тестирования universal-
  бинарников в будущем.

Это пересечение: официальный пол libbox/SFI/SFM (§1.2) = пол,
который уверенно поддерживает обязательный Xcode 26 (§1.3).

## 2. Движок: libbox как ядро обоих клиентов

### 2.1. Модель встраивания

На Apple, как и на Android (`docs/android-vpnservice.md` §1.6, §2),
исполняемый бинарник движка как отдельный процесс из песочницы
невозможен как штатная модель продукта: ядро — **libbox в процессе
PacketTunnel-расширения** (`Libbox.xcframework`, gomobile-бридж,
`BoxService` + `PlatformInterface`-колбэки в терминах sing-box).
Основное приложение движок не запускает; оно управляет
`NETunnelProviderManager`, а расширение владеет libbox-инстансом.
Следствия, зеркалящие Android-спецификацию:

- Сокеты движка к серверам не должны попадать обратно в TUN:
  на Apple это решается маршрутизацией расширения (underlying
  interface) и libbox platform-бриджем, а не `VpnService.protect()`;
  эквивалентность требования фиксируем, механизм — платформенный.
- TUN-fd libbox получает от `NEPacketTunnelFlow`, а не создаёт сам;
  в sing-box это штатный Apple-путь официальных клиентов [S3].
- Лимит памяти расширения — проектное ограничение первого класса:
  Apple-доктрина для NE-провайдеров — жёсткий верхний предел буферов
  и flow control вместо «сколько влезет» [S27]. Конкретная цифра
  лимита iOS в этой волне **не подтверждена** первоисточником —
  числа из вторичных источников в документ не вносим.

### 2.2. Как конфиг libbox зеркалит `core/engine/singbox/render.go`

Swift-`LibboxConfigBuilder` (SoraCore, §3.3) обязан производить тот
же JSON, что Go-`Render`/`renderVersioned` для того же `Plan`.
Построчно по `render.go`:

| Блок render.go | Семантика Go-ядра | Зеркало в Apple/libbox |
|---|---|---|
| `log` (`logConfig`) | `silent→disabled`, `warning/""→warn`, timestamp off | Идентично; логи расширения не должны содержать секретов (см. маскирование ниже) |
| Inbound `mixed` (`mixed-in`) | Только если `LocalProxy.Enabled`; listen 127.0.0.1 (0.0.0.0 при AllowLAN), порт из runtime, опц. users | Идентично для proxy-режима (в т.ч. legacy 10.15 без TUN). В TUN-режиме на iOS loopback-порт расширения не является пользовательским системным прокси — UI не должен обещать его как на десктопе |
| Inbound `tun` (`tun-in`) | `address` из `Tun.Addresses()`, `auto_route` (на Linux — false, роутингом владеет core; **не-Linux — true**), `strict_route`, MTU: план или **1500** (не jumbo 9000 — обоснование PMTUD в `tunDefaultMTU`), `stack` только для движков <1.15 (для 1.14-пина — `mixed` по умолчанию), `route_address`, пакеты include/exclude — **только Android** | На Apple `auto_route=true`-семантика: маршрутами владеет система через `NEPacketTunnelNetworkSettings`, а не core. MTU 1500 и логика выбора — идентичны. `stack`: пин 1.14.3 → эмитить как Go для <1.15. `include_package/exclude_package` на Apple **не эмитятся**: per-app на iOS — не список пакетов, см. PARITY (split tunnel) |

| Kill switch | В Go-ядре kill switch **не рендерится в sing-box-конфиг**: это внешний файрвол службы (nftables/WFP), который ставится **до** старта ядра и держится после его падения (`docs/architecture.md`, `docs/security.md`) | На Apple внешнего файрвола у приложения нет. Эквивалент собирается из трёх слоёв, и документ запрещает называть любой из них в одиночку «kill switch»: (1) `route.final`/правила — при строгом режиме final ведёт не в `direct`, а в block/drop-исход (в sing-box — outbound типа block; в рендере sora block-семантика уже есть как action reject для правил); (2) системный слой — `includeAllNetworks`/`enforceRoutes` у NE-настроек (термины по вторичному обзору NE [S28], точная доступность по версиям — проверять в SDK при реализации); (3) on-demand правила (§4.2), не дающие трафику «окна» между сетями. Честное ограничение: при убитом системой расширении (jetsam) слой (1) умирает вместе с ним — десктопной гарантии «файрвол жив после смерти ядра» на iOS **нет**, UI обязан формулировать kill switch как «строгий режим туннеля», а не абсолют |

### 2.3. Split tunneling в терминах движка

Десктопная модель плана: правила route (домены/IP/процессы/порты) +
TUN include/exclude приложений (на десктопе приложения маршрутизируются
process-правилами). Зеркало на Apple:

- Домен/IP/порт/geo-правила — полностью, через route (§2.2).
- Per-app: iOS не даёт пользовательскому VPN произвольного списка
  «приложение → туннель/мимо» в десктопном смысле; per-app VPN —
  MDM-функция [S29]. В SoraCore контракт `Tun.IncludeApps/
  ExcludeApps` для Apple-таргетов **не заполняется** (как render.go
  не эмитит package-фильтры вне Android), а UI показывает честное
  состояние §5, а не неработающие тумблеры.

### 2.4. Риски движкового слоя

1. **Артефакт libbox форка lx не зафиксирован** (§1.2) — главный
   открытый риск волны. Владелец решения: подотдел сборки.
2. **Naive/AmneziaWG 3.1/masquerade**: render.go требует особых
   билд-тегов/возможностей форка (naive — `with_naive_outbound`;
   AWG masquerade умеет только sing-box-lx). Присутствие этих тегов
   в Apple-сборке — **не подтверждено**; фич-гейтинг на Apple должен
   повторять десктопный `catalog.go`-подход: фича отсутствует в
   сборке → план отклоняется честно, а не рендерится молча хуже.
3. **Дрейф зеркал**: Go↔Swift рендеры обязаны сходиться на общем
   корпусе планов (тот же принцип, что уже принят в проекте для
   Go↔Dart зеркал: паритет тестом, не глазами).
4. **Обновления libbox** не могут подгружаться в обход App Store
   (код расширения — часть бандла); цикл обновления движка = цикл
   релиза приложения. На direct-macOS канале то же ограничение
   мягче (свой релизный поезд), но не исчезает.

### 3.2. Границы модулей

- **SoraCore** — чистый Swift: модели (§3.3), парсинг ссылок и
  подписок, `LibboxConfigBuilder`, хранение профилей, capability-
  реестр (§5.1). Запрещены импорты UI-фреймворков и NetworkExtension:
  пакет тестируется без симулятора и переиспользуется обоими
  приложениями и (через общие типы) провайдером. Libbox как бинарная
  зависимость в SoraCore **не линкуется** — только в PacketTunnel.
- **Apps/iOS, Apps/macOS** — UI и платформенные адаптеры: управление
  `NETunnelProviderManager`, системный прокси (macOS), login item,
  меню-бар, навигация. Различия платформ живут здесь и в адаптерах
  §5, не в SoraCore.
- **PacketTunnel** — один Swift-код провайдера на обе платформы:
  `NEPacketTunnelProvider`-подкласс, libbox-жизненный цикл,
  platform-бридж, применение сетевых настроек из плана, обработка
  sleep/wake и сообщений от приложения (§4). Платформенные различия
  внутри провайдера — только за capability-проверками, не копиями
  файлов.
- **Widgets/Intents** — отдельные extension-таргеты; общаются с
  приложением только через App Group-состояние (§3.4), не через
  процессные вызовы.

### 3.3. API-контракт (зафиксирован, задан родителем подотделам кода)

Имена и состав — контракт; этот документ его фиксирует и отмечает
риски, а не переизобретает.

- `ServerProfile` — один сервер профиля/подписки: стабильный `id`,
  отображаемое имя, `protocol: ProxyProtocol`, адрес/порт, секреты
  (только через Keychain-ссылку, не значением в Codable-модели —
  риск: Codable-копии профилей в App Group не должны содержать
  паролей/UUID открытым текстом; в UserDefaults/Shared-контейнере
  лежат метаданные и keychain references).
- `ProxyProtocol` — зеркало `engine.Protocol` из `plan.go`:
  `vless, vmess, trojan, shadowsocks, hysteria2, tuic, wireguard,
  socks5, http, anytls, direct` (+ служебные `bypass`,
  `xray-profile` — на Apple обязаны отклоняться гейтом, а не
  падать: bypass = zapret-семантика, xray-profile = Xray-движок,
  которого в libbox-мире нет).
- `TLSSpec` — зеркало `engine.TLS`: enabled, serverName, alpn,
  fingerprint (uTLS), insecure, ECH {enabled, config, queryServerName},
  REALITY {publicKey, shortID, mldsa65Verify?, keyShare?}. Риск:
  `RealityMLDSA65Verify` и `KeyShare` в Go помечены как Xray/mihomo-
  специфика, sing-box их не рендерит; Swift-контракт хранит поля
  (импорт не должен терять данные), билдер — не эмитит и помечает
  фичу отсутствующей, как `catalog.go`.
- `TransportSpec` — зеркало `engine.Transport`: type
  (tcp/ws/grpc/h2/httpupgrade/xhttp), path, host, service, headers,
  earlyData (+header name), XHTTP mode и xmux/padding поля.
  Риск: xmux/padding в Go рендерит только mihomo — на Apple (sing-box)
  поля хранятся, не эмитятся, гейтятся честно (как в Go).
- `LibboxConfigBuilder` — `Plan` (Swift-зеркало `engine.Plan`) →
  sing-box JSON `Data`; детерминированность (сортировка ключей/
  правил как в Go там, где Go сортирует: DNS policy patterns),
  ошибки — типизированные, с указанием outbound/правила, как ошибки
  `render.go` («singbox: outbound %s: …»). Паритет — корпусным
  тестом против Go-`Render` на общих фикстурах (§2.4.3).
- `ProfileStore` — CRUD профилей и подписок поверх App Group-
  контейнера + Keychain (§3.4); подписки: форматы — по PARITY.md;
  обновление подписок выполняет **приложение**, не расширение
  (расширение получает готовый план/конфиг).

## 4. Network Extension: поведение

### 4.1. Жизненный цикл провайдера

`startTunnel` → прочитать конфиг из App Group → `setTunnelNetworkSettings`
(адреса из плана, маршруты, `NEDNSSettings`, MTU) → старт libbox →
completion. `stopTunnel` — гасить libbox до completion, не после.
`sleep`/`wake` провайдера — отдельные колбэки жизненного цикла:
на sleep движок не убивается, на wake — перевыпуск сессий (§4.2).
Общий принцип из NE-практик: провайдер обязан переживать сон/пробуждение
восстановлением состояния и держать нужное для восстановления в
App Group-хранилище [S30].

### 4.2. Смена сетей, сон/пробуждение, on-demand

Требуемое поведение (спроектировано; статус — в PARITY.md):

- **Смена сети (Wi-Fi↔Cellular, смена SSID, captive portal):**
  система переоценивает on-demand правила при смене интерфейса, IP
  и DNS-конфигурации [S31]; провайдер на wake/сетевом событии
  обязан: перечитать underlying-интерфейс, перезапустить
  «застрявшие» исходящие сессии libbox (эквивалент десктопного
  «служба раз в 2 с смотрит интерфейсы и закрывает соединения
  старого пути», `docs/architecture.md` — но событийно, не поллингом:
  поллинг в расширении запрещён экономией батареи и NE-практикой).
  iOS-специфика: временная остановка туннеля системой при потере
  сети (temporary shutdown) с переоценкой правил при восстановлении
  [S31] — UI показывает «переподключение», а не «ошибка».
- **On-demand правила** (`NEOnDemandRule`: Connect/Disconnect по
  interface type, SSID, DNS, probe URL — состав полей подтверждается
  libbox platform-интерфейсом sing-box [S32]): продуктовая лестница —
  выкл / всегда при любой сети / только не-доверенные SSID /
  кроме домашних SSID. Сетевые профили sora (F5, десктоп) на Apple
  реализуются именно on-demand правилами + сменой выбранного
  профиля, а не собственным мониторингом сетей.
- **Сон/пробуждение macOS:** как §4.1; после wake — та же процедура,
  что при смене сети. **iOS-сон:** on-demand не активен во сне;
  пробуждение по сетевой активности поднимает туннель заново [S33] —
  это платформенное поведение, UI не обещает «туннель жив во сне».
- **Captive portal:** при строгом kill switch портал не откроется
  (та же честная оговорка, что в десктопном `docs/security.md`):
  состояние UI — «сеть требует входа: временно отключите строгий
  режим», а не молчаливый провал.

### 4.3. Канал приложение ↔ провайдер

Статус, выбор сервера (fast switch), статистика — через
`sendProviderMessage`/`handleAppMessage`, не через сетевой Clash API
наружу. Fast switch на Apple = новый конфиг в App Group + сообщение
провайдеру «перечитай» с перезапуском только libbox-сессии; системный
туннель при этом не пересоздаётся (эквивалент десктопного мгновенного
SelectServer по инварианту, не по механизму).

### 4.4. Виджеты и Shortcuts/AppIntents (спроектированные поверхности)

Статус обеих поверхностей: **спроектировано** (не «потом»):

- **Виджеты (WidgetKit, iOS 14+ [S17] / macOS 11+):** состояние
  туннеля, текущий сервер/профиль, действие connect/disconnect.
  На таргетах без интерактивных виджетов виджет — только отображение
  + тап открывает приложение (§5-лестница). Данные — из App Group-
  снимка состояния, который пишет провайдер/приложение; виджет сам
  в сеть не ходит.
- **AppIntents (iOS 16+ / macOS 13+ [S18]):** интенты Connect,
  Disconnect, SwitchServer, SwitchProfile; на системах без
  AppIntents фолбэк — legacy SiriKit/Shortcuts-действия через
  `INIntent` там, где это оправдано, либо честное отсутствие
  поверхности (§5), а не краш/пустой экран Shortcuts.

## 5. Адаптивность по версиям (усиление мандата владельца)

### 5.1. Принцип

**Capability-проверки в рантайме вместо жёстких веток по версии.**
Версия ОС — вход для реестра возможностей, а не разбросанные
`if os == …` по коду. SoraCore держит `Capability` enum и пробы:

- `@available` + наличие класса/символа (compile-time ветка с
  рантайм-гардом) — для SwiftUI/API поверхностей;
- runtime-пробы результата (API существует, но поведение зависит
  от конфигурации/канала) — для NE-настроек и login item.

Конкретные пары «новая поверхность → проба → фолбэк»:

| Поверхность | Проба | Фолбэк |
|---|---|---|
| `NavigationStack` (iOS 16/macOS 13) | `@available` | `NavigationView`-адаптер с тем же роутером состояния |
| `MenuBarExtra` (macOS 13) | `@available(macOS 13, *)` | `NSStatusItem` + AppKit-меню, тот же view model |
| `SMAppService` (macOS 13) | `@available` + статус регистрации | `SMLoginItemSetEnabled`/LaunchAgent, пометка legacy в настройках |
| AppIntents (iOS 16/macOS 13) | `@available` + регистрация шорткатов | INIntent-действия или отсутствие поверхности с честным состоянием |
| WidgetKit (iOS 14/macOS 11) | наличие extension-таргета | Виджета нет; функции доступны в приложении (не деградация туннеля) |
| Интерактивные виджеты (поколение iOS 17) | `@available` — **граница не подтверждена первоисточником** | Виджет открывает приложение для действия |
| NE on-demand расширенные поля | проба по факту применения правил | Базовые Connect/Disconnect-правила |

### 5.2. Лестница graceful degradation (на сегмент)

Для каждой фичи и сегмента лестница одна: **полная фича →
ограниченный режим → честное состояние в UI**. Отказ и краш в
лестнице отсутствуют как ступени.

- **iOS 15 (основной таргет, но ниже AppIntents):** туннель полный;
  Shortcuts — ограниченный режим (INIntent/ручные действия);
  навигация — полная (`NavigationStack` нет, но `NavigationView`-
  адаптер даёт те же экраны); виджет — отображение + открытие
  приложения для действий.
- **macOS 11–12 (legacy):** туннель полный (старый libbox);
  меню-бар — `NSStatusItem` (ограниченный, равный по функциям,
  беднее по анимациям); автозапуск — legacy login item с пометкой;
  виджетов/интентов — честное состояние «недоступно на этой системе»
  в настройках, без пустых экранов.
- **macOS 10.15 (legacy, ограниченный режим):** нет TUN в продукте
  первой итерации → системный прокси; UI показывает постоянный
  баннер режима и список того, что режим не покрывает (приложения
  без proxy-awareness, UDP). Это честное состояние, а не тихая
  «работает как везде».
- **iOS 13–14 (legacy, условный):** как iOS 15, минус виджеты на 13
  (WidgetKit с 14) — состояние в UI; на 13 виджет-ступень лестницы
  пропускается целиком.
- **Сегменты отказа (§1.6):** лестница заканчивается не приложением,
  а документированным отказом — это тоже «честное состояние»,
  только на уровне продукта, а не экрана.

## 6. Подпись и распространение: таблица решений

Факты канала: Developer ID-подпись + нотаризация — обязательный
путь для direct-macOS: Gatekeeper требует подписанное Developer ID
приложение, нотаризация — сканирование Apple с «билетом», который
степлером прикрепляется к бандлу [S34][S35]; нотаризация обязательна
для ПО вне Mac App Store начиная с macOS 10.15 [S36]. Для App Store/
TestFlight нотаризация не применяется — там App Review и свои
сертификаты распространения; требования к сборке — §1.3 [S9].

| Вопрос | iOS | macOS App Store | macOS Direct (Developer ID) |
|---|---|---|---|
| Сертификат | Apple Distribution | Apple Distribution | Developer ID Application |
| Нотаризация | Нет | Нет | **Да** + Hardened Runtime + stapling [S34][S36] |
| PacketTunnel | App Extension в бандле | App Extension в бандле | Network Extension (system-extension форма для direct-канала) + явное одобрение пользователем в System Settings |
| System Extension vs NE | Не применимо (только NE app extension) | NE app extension | На 11+ — System Extension-хостинг NE; на 10.15 NE уже штатная замена kext (kext deprecated в 10.15, ряд KPI unsupported с 11) [S25][S26] — **kext-путь не проектируется вообще** |
| Entitlements | §3.5 | §3.5 | §3.5 + Hardened Runtime exceptions минимально, каждое — с обоснованием в релизных нотах |
| Обновления | App Store/TestFlight | App Store | Свой механизм поверх нотаризованных сборок; libbox обновляется только с приложением (§2.4.4) |
| Legacy-сегменты | Сторный канал под вопросом (§1.3) | — | Реалистичный канал для legacy-macOS (§1.6) |
| Решение волны | Основной канал: App Store + TestFlight | Допустим, но не первичен (двойная ревью-поверхность) | **Первичный для macOS** (прецедент официального SFM: standalone + Homebrew [S3]) |

TestFlight при этом — бета-канал обоих сторных продуктов, с тем же
Xcode/SDK-гейтом, что и App Store [S10].

## 8. Стандарт мелочей (единый источник для ревью коммитов)

Владелец: внимание самым мелким деталям — стандарт, а не вкус.
Этот раздел — чек-лист ревьюера для каждого коммита приложений
iOS/macOS: несоответствие любому пункту — замечание ревью, как
несоответствие контракту §3.3. Все значения живут в одном месте —
`DesignTokens` в SoraCore/UI-слое (spacing, motion, typography,
colors); экран, хардкодящий число/цвет/строку в обход токенов, не
проходит ревью независимо от того, «выглядит нормально» или нет.

### 8.1. Сетка и отступы

- База **4pt**, шаг **8pt**: все spacing/padding/margin — только
  кратные значения из `DesignTokens.Spacing` (`4, 8, 12, 16, 24, 32`),
  ни одного литерала в экранах.
- Межэкранная ритмика одна: горизонтальный инсет контента, зазоры
  секций и списков берутся из тех же токенов на iOS и macOS;
  платформенная разница — только там, где её требует HIG, и она
  оформляется вариантом токена, а не локальным числом.
- Выравнивание по сетке проверяется скриншотом ревью, а не глазом
  автора: ревьюер вправе запросить скриншот экрана из коммита.

### 8.2. Анимации

- Длительности — только именованные константы
  `DesignTokens.Motion` (базовый набор волны: `fast 0.20`,
  `medium 0.30`; кривые — `easeInOut` для переходов состояния и
  стандартный `spring` для интерактивных откликов). Магические
  числа длительностей/кривых в экранах запрещены.
- Честная сверка с десктопом: у Flutter-приложения свой набор —
  класс `Motion` в `app/lib/src/design/theme.dart` (`fast 160ms`,
  `medium 180ms`, `slow 220ms`, кривая `Cubic(0.2, 0.9, 0.25, 1)`).
  Apple-токены **не обязаны** совпадать с ним по числам (другая
  платформенная моторика), обязаны совпадать по принципу: один
  набор на приложение, ноль литералов. Расхождение чисел
  зафиксировано здесь, чтобы ревьюер не «исправлял» одно под другое.
- `Reduce Motion` (системная настройка доступности): анимации
  заменяются мгновенными переходами/затуханием по capability-пробе
  (§5.1), а не игнорируются.

### 8.3. Типографика и терминология (глоссарий)

- Шрифт — системный (SF Pro через системные text styles), размеры —
  только семантические стили Dynamic Type (`headline`, `body`,
  `caption`…), не числовые размеры в экранах.
- **Один термин = одно слово во всех строках.** Глоссарий составлен
  по строкам основного приложения (`app/lib/l10n/app_ru.arb`,
  ключи в скобках) и обязателен для Apple-строк:

  | Термин (RU / EN) | Ключ десктопа | Запрещено |
  |---|---|---|
  | сервер / server | `servers`, `serverAuto` | «нода», «точка», «хост» (в UI; в технических полях адреса допустим «адрес сервера») |
  | подписка / subscription | `subscription`, `addSubscription` | «конфиг-ссылка», «профиль провайдера», «фид» |
  | ссылка на подписку / subscription link | `subscriptionLink` | «конфиг-ссылка», «URL конфига» |
  | ядро / engine | `engine` | «движок» в UI (в документации допустим как синоним-пояснение, в строках — нет) |
  | подключение / connection (состояние) | `stateConnected` и др. | «туннель поднят», «сессия активна» в пользовательских состояниях |
  | состояния: «Не подключено», «Подключение», «Подключено», «Переподключение», «Отключение» | `stateOff/Connecting/Connected/Reconnecting/Disconnecting` | вольные перефразирования по экранам |
  | «Интернет только через VPN» | `killSwitch` | литеральный «kill switch» в RU-строках; «аварийный выключатель» |
  | «Без сервера» / bypass-режим | `serverBypass`, `sectionNoServer` | «обход без VPN», «прямой режим» |
  | «Самый быстрый» (автовыбор) | `serverAuto` | «авто», «умный выбор» по разным экранам |
  | журнал / logs | `logs` | «логи» в RU-строках |
  | соединения / connections | `connections` | «коннекты», «сессии» |
  | маршруты / routes | `routes` | «роутинг» в RU-строках |
  | тема: «Как в системе / Светлая / Тёмная» | `themeSystem/Light/Dark` | иные формулировки тех же трёх значений |
  | ошибки — человеческим текстом по образцу `err*` («Что-то пошло не так», «Сервер не ответил вовремя») | `errGeneric`, `errTimeout`… | сырые коды/строки исключений пользователю (стандарт проекта: в топовом UI нет «красных ошибок») |

- EN-строки сверяются с `app_en.arb` тем же правилом: термин EN —
  перевод термина RU из этой таблицы, а не отдельный выбор.
- Новая сущность сначала получает термин здесь и ключ в arb,
  потом — экран. Ревьюер проверяет дифф строк на синонимы из
  колонки «Запрещено».

### 8.4. Accessibility

- У **каждого** интерактивного элемента — accessibility label
  (VoiceOver), у иконок-кнопок без текста — обязательно; состояние
  (подключено/нет, выбран/нет) — traits/value, а не только цвет.
- Dynamic Type: вёрстка не ломается на максимальных размерах —
  списки перестраиваются (стек вместо строки), ничего не обрезается
  в нечитаемый хвост; проверка — скриншот на `accessibilityXXXL`
  в ревью экранов со списками.
- Контраст и различимость состояний — не только цветом: подключено/
  отключено/ошибка различаются также иконкой и текстом состояния
  (§8.3, состояния).
- Полная навигация с клавиатуры на macOS и Switch Control/VoiceOver
  на iOS для главных действий (подключить, отключить, сменить
  сервер) — часть приёмки экрана, а не отдельный «a11y-эпик потом».

### 8.5. Длинные строки и обрезка

- Переполнение запрещено как класс: ни один текст не выходит за
  контейнер и не сдвигает соседей.
- Имена серверов и названия подписок — **tail truncation**
  (многоточие в конце) в одну строку в списках.
- Адреса/хосты/URL/ключи (то, где значимы обе стороны строки) —
  **middle truncation**: начало и конец видны, середина — «…».
- Полное значение обрезанного текста доступно: на iOS — на экране
  деталей/долгим нажатием (копирование), на macOS — tooltip +
  детали; обрезка — только отображение, данные не теряются.
- Числа и единицы — как в arb десктопа: «{value} мс», «{value}
  Мбит/с», байты Б/КБ/МБ/ГБ (`milliseconds`, `speedMbps`, `bytes*`):
  один формат на приложение, без «ms/Mbps» в RU-строках.

### 8.6. Темы и цвета

- Тёмная и светлая темы — **паритет по каждому экрану**: коммит
  экрана без скриншотов обеих тем не проходит ревью.
- Цвета — только семантические токены (`DesignTokens.Color`:
  фон, поверхность, текст первичный/вторичный, акцент, успех,
  предупреждение, ошибка, разделитель), резолвящиеся по теме и
  системному виду. Литеральные `Color(red:…)`/hex в экранах
  запрещены; новый цвет сначала становится токеном с именем по
  смыслу, не по оттенку («danger», не «red2»).
- «Как в системе» — значение по умолчанию (§8.3, тема).

### 8.7. Иконки и изображения

- Иконки — SF Symbols там, где символ существует; размеры — по
  HIG-ступеням платформы и из токенов, не произвольные числа.
- Растр не растягивается и не сжимается неквадратно; пользователь-
  ские изображения — только в своих аспектах, с обрезкой по
  контейнеру (crop), не деформацией. AppIcon и ассеты — из
  `Assets/` (ARCH §3.1), каждый размер — отдельным честным
  рендером, не апскейлом меньшего.

### 8.8. Как ревьюер применяет стандарт

Проверка коммита экранов: (1) grep диффа на литералы spacing/
duration/цветов вне `DesignTokens`; (2) дифф строк — на глоссарий
§8.3; (3) скриншоты: светлая+тёмная, обычный+максимальный Dynamic
Type, самая длинная строка корпуса (длинное имя сервера/подписки);
(4) VoiceOver-проход главных действий. В PARITY.md этот стандарт
отмечается по строкам пометкой «детали: проверено/нет».
