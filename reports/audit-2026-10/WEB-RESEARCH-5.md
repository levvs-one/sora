## TIER S — критично, действовать сейчас

### S1. sing-box-lx ушёл с lx.14 на lx.21; в lx.15 — критичный gRPC-фикс и фикс REALITY-«random» против Xray ≥26.9.8
**Факт.** Верхний релиз Leadaxe/sing-box-lx на 2026-10-20 — **1.14.3-lx.21**;
sora пинит **lx.14** (`engines.lock`). Между ними, по релиз-нотам форка:
- **lx.15 (security):** `google.golang.org/grpc` v1.79.1 → v1.83.1 по
  **GHSA-p77j-4mvh-x3m3** (critical, обход авторизации по `:path`; плюс
  HTTP/2 DATA-fragmentation OOM и ещё три фикса) и `go-jose/v4` → v4.1.4
  (паника JWE). Нота прямо говорит: upstream sing-box старые версии
  по-прежнему пинит — фикс есть только в lx-линии.
- **lx.15:** `fingerprint: "random"`/`"randomized"` ломали REALITY-ноды
  против **Xray ≥ v26.9.8** до рестарта процесса: `randomized` независимыми
  «монетами» решал группу X25519MLKEM768, гибридный key share и ALPN —
  без share сервер Xray ≥26.9.8 отвечает `reality verification failed`,
  без ALPN не поднимаются gRPC/XHTTP поверх h2 (работало ~25% процессов);
  в пул `random` входили `edge`/`ios` без гибридного share (мёртв в 2 из 5
  процессов). Фикс: `randomized` всегда несёт ALPN и X25519MLKEM768,
  `random` выбирает только из `chrome`/`firefox`/`safari`.
- **lx.15:** urltest пробовал ноды раз в 2×`interval` (при дефолте 3 мин —
  раз в 6 мин; смерть удерживаемой ноды замечалась до 2× позже); failover
  теперь уходит и с деградировавшей (>2× медленнее лучшей) ноды.
- **lx.15:** uTLS/REALITY-соединения отпускают handshake-state после
  TLS 1.3: −18…−25 КБ на соединение (Chrome 42.1→16.6 КБ).
**Источник:** https://github.com/Leadaxe/sing-box-lx/releases (ноты lx.15;
даты отдельных lx-релизов из рендера GitHub не извлекаются, порядок версий
и содержание — по нотам, проверено 2026-10-20).
**Что значит для sora.** (1) Бамп `engines.lock` sing-box lx.14 → lx.21
(или минимум lx.15) — это уже не «фичи», а закрытие critical gRPC-адвайзори
в поставляемом бинаре. (2) До бампа: в sora `core/engine/fingerprint.go`
`random`/`randomized` валидны для sing-box-пути — на пине lx.14 связка
«sing-box-lx клиент → свой/чужой Xray ≥26.9.8 REALITY-сервер» с этими
фингерпринтами частично мертва; stealth-подсказка должна предупреждать
именно про эту связку, а не только про «randomized не похож на браузер».
(3) После бампа Xray (проход 4, S1) до ≥26.9.8 требование гибридного share
становится обязательным и для Xray-пути: любой кастомный/сторонний
фингерпринт без X25519MLKEM768 в key shares к новому Xray REALITY
не подключится — валидатор обязан это проверять.

### S2. Hysteria2 stall-after-upload: QUIC жив, все TCP-стримы мертвы; серверный фикс — PR, клиентский фикс Xray в v26.10.17 НЕ подтверждён
**Факт.** Colitu Lab (публикация 2026-10-15) воспроизвела на официальном
Hysteria server **v2.11.0** + Xray 26.10.10: после upload-speedtest'а
(~50–60 с) соединение перестаёт нести новый TCP-трафик навсегда, хотя QUIC
жив (ACK, control-пакеты, UDP-датаграммы/DNS продолжают идти). Механизм:
цель upload'а перестаёт читать, но не закрывает соединение → сервер
перестаёт читать из стрима → непрочитанные данные держат
connection-level flow-control window (дефолты Hysteria: 8 МБ/стрим,
20 МБ/соединение) → клиент не может слать ни по одному стриму; Xray-клиент
стрим не отпускает. Патч Colitu (~37 строк, write-deadline 10 с на запись
в TCP-цель + закрытие цели при конце стрима): восстановление 7.8 с против
«никогда за 30 с». 2026-10-16 заведены Hysteria issue #1702 и PR #1703
(конфигурируемый stall-timeout, интеграционный тест) и Xray-core issue
#7169 (клиентская половина: `CancelWrite`/`RESET_STREAM` освобождает окно
даже на непатченых серверах; контрибьютор воспроизвёл на main и планирует
фикс). **Статус на 2026-10-20: слияния PR #1703 и фикса #7169 в первоисточниках
не видно; утверждение «stall-фикс вошёл в v26.10.17» — НЕ ПОДТВЕРЖДЕНО**
(тело релиза v26.10.17 на GitHub вообще без changelog — только спонсоры;
compare v26.10.10...v26.10.17 рендер GitHub не отдаёт).
**Источники:** https://lab.colitu.com/research/hysteria2-stall-after-upload ;
https://dev.to/colitu/our-hysteria2-connections-died-after-every-upload-speed-test-the-fix-was-37-lines-2n81 ;
https://github.com/XTLS/Xray-core/releases/tag/v26.10.17
**Что значит для sora.** (1) Это прямой ответ на пункт задания про
«stall-фикс в 26.10.17»: его там честно нет (или недоказуемо) — не писать
в changelog sora обратное. (2) Собственный speedtest sora через hy2-туннель
(фича из раунда 1) — ровно триггер бага: health-check/FreezeDetector обязан
различать «QUIC жив, стримы мертвы» (проба новым TCP-стримом, а не
ICMP/UDP) и переподключать hy2, а не объявлять ноду живой по датаграммам.
(3) One-click deploy Hysteria2-сервера: заложить stall-timeout-патч уровня
PR #1703 в образ ноды или мониторить слияние PR; непропатченый стоковый
v2.11.0+ сервер sora будет терять hy2 после каждого пользовательского
upload-теста.

### S3. Пин sing-box-lx lx.14 для Windows 7 сломан на старте; чинит lx.16
**Факт.** Нота lx.16: «Windows 7 build starts again: since lx.14 it failed
at startup with `watch registry key … The parameter is incorrect`» —
причина: DNS-change watcher из sing-tun v1.14.3 использует флаг
реестровых нотификаций, существующий только с Windows 8; lx.16 повторяет
регистрацию без флага на Win7. Там же lx.16 добавил `lxd update`
(самообновление ядра на Linux с проверкой суммы, атомарной подменой
и откатом), а lx.17/lx.19 чинят гонку TUNSETIFF при рестарте/апдейте.
**Источник:** https://github.com/Leadaxe/sing-box-lx/releases (ноты lx.16–lx.19)
**Что значит для sora.** `engines.lock` поставляет для `win7-386` именно
**sing-box 1.14.3-lx.14** — то есть win7-вариант sing-box-пути sora на
целевой ОС, судя по нотам форка, падает при старте. Для продукта, у которого
sora-legacy/старые системы — заявленная аудитория, это Tier S: бамп lx
(см. S1) одновременно чинит win7-старт; до бампа win7-пользователям
sing-box-путь честно не обещать.

### S4. Go-тулчейн sora core не запинен на security-патч: Go 1.27.2 (2026-10-08, 15 CVE)
**Факт.** Go 1.27.2 и 1.26.9 вышли 2026-10-08 с 15 security-фиксами
(net/http, crypto/tls — включая ECH-кейс CVE-2026-97031, cmd/go, os —
включая CVE-2026-56857, обход os.Root через Windows junction, фикс
в 1.27.2/1.26.9). Отдельно: CVE-2026-56865 (обход интегритети module
proxy, CVSS 8.4) закрыт в Go 1.25.13/1.26.6 и `golang.org/x/mod` v0.40.0.
**Источники:** https://seclists.org/oss-sec/2026/q4/101 ;
https://linuxsecurity.com/news/server-security/go-security-update-15-flaws ;
https://integsec.com/blog/cve-2026-56865-go-module-proxy-integrity-bypass-what-it-means-for-your-business-and-how-to-respond
**Что значит для sora.** `core/go.mod`: `go 1.27` без `toolchain`-пина —
сборка может идти тулчейном 1.27.0/1.27.1 со всеми 15 CVE в stdlib
поставляемого core. Действие: запинить `toolchain go1.27.2` в core
(service/sync уже на `go 1.26.9` — security-линия 1.26, там ок).
`golang.org/x/mod` в core — v0.41.0 indirect, выше порога 0.40.0 по
CVE-2026-56865, действия не требует. Заодно: бинари lx-форка собраны
Go 1.26.8 (ноты lx.20) — на один security-патч позади 1.26.9; это остаточный
риск апстрима, мониторить, не чинить самим.

## TIER A — важно, в бэклог с приоритетом

### A1. Что реально внутри Xray v26.10.17 — честный статус по трём пунктам задания
**Факт.** Тело релиза v26.10.17 на GitHub changelog не содержит (проверено
открытием страницы тега 2026-10-20); список релизов подтверждает только

извлечь не удалось, НЕ ПОДТВЕРЖДЕНО (известный sora факт остаётся прежним:
`core/engine/registry/registry.go` требует mihomo ≥1.19.32 как мост для
Xray TUN); **гибридный key share с 26.9.8** — подтверждён, но это не

X25519MLKEM768 share Xray ≥26.9.8 отвечает `reality verification failed`
(ноты lx.15, см. S1). Плюс из нот v2rayN (см. A5): актуальные сборки Xray
удалили `allowInsecure` — sora это уже обработала (парсер принимает,
Xray-рендер не эмитит, есть тест в `core/engine/xray/render_test.go`
и объяснение в справке приложения) — действия не требует, рассинхрона нет.
**Источники:** https://github.com/XTLS/Xray-core/releases/tag/v26.10.17 ;
https://github.com/Leadaxe/sing-box-lx/releases (ноты lx.15)
**Что значит для sora.** Перед бампом пина Xray (проход 4, S1) родителю —
один ручной проход по compare/коммитам 26.10.10→26.10.17 на машине
с полным GitHub-доступом; из публичного рендера содержание релиза, кроме
`hellochrome_155` (проход 4), не устанавливается.

### A2. mihomo: пин 1.19.32 — по-прежнему верхний; но upstream заявляет AWG 3.0/3.1, а матрица sora говорит «mihomo не умеет AWG 3.1»
**Факт.** Страница релизов MetaCubeX/mihomo на 2026-10-20: верхний —
**v1.19.32** (тот, что запинен у sora). В его линии: 1.19.30 —
`feat: support AmneziaWG v3.0` и `feat: support AmneziaWG v3.1`,
`chore: update quic-go to 0.61.0`, `fix: CVE-2026-56862 for crypto/tls`
(KeyUpdate-DoS в Go crypto/tls, CVSS 7.5 по Red Hat); 1.19.31 —
`fix: RandomPaddingAddition and DisableCookies for AmneziaWG v3`,
конвертер REALITY ML-KEM-опций; 1.19.32 — AnyTLS idleSession race fix,
`xhttp extra.headers` в конвертере, дефолтный TUN-стек `mips`,
load-balance `hash-key` по inbound user.
**Источники:** https://github.com/MetaCubeX/mihomo/releases ;
https://access.redhat.com/security/cve/cve-2026-56862
**Что значит для sora.** Расхождение, которого не было в проходах 1–4:
`core/engine/d24_awg3_test.go` утверждает «mihomo must miss amneziawg3
for a 3.1 plan», а запиненный mihomo 1.19.32 несёт AWG 3.1 с 1.19.30.
Либо sora зря отказывает mihomo-пути для AWG 3.1-планов (теряется
failover-маршрут), либо поддержка mihomo частичная (не все поля 3.1) —
нужен аудит полей по рендеру mihomo, а не по памяти. Заодно: справка
приложения («Новые параметры AWG 3.x ещё не импортируются») и тесты
про 3.1 в core противоречат друг другу — привести к одному знаменателю.

### A3. Ломающее изменение lx.18: у MASQUE-outbound удалён ключ `network`
**Факт.** lx.18: legacy-ключ `network` у outbound `masque` больше не
принимается — конфиг с ним падает на загрузке (`unknown field "network"`),
лечение — переименовать в `vhttp` (`h3`/`h2`/`auto`); список tcp/udp —
`network_list`. Плоские TLS-алиасы (`sni`, `skip_cert_verify`, `fragment*`)
пока живут с deprecation-warning.
**Источник:** https://github.com/Leadaxe/sing-box-lx/releases (ноты lx.18)
**Что значит для sora.** При бампе lx (S1) генератор MASQUE-профилей
sing-box-пути обязан эмиттить `vhttp`, а импортер чужих sing-box JSON —
переписывать `network`→`vhttp` для masque-outbound'ов, иначе профили,
рабочие на lx.14, перестанут загружаться после обновления движка.
В текущем рендере sora совпадений по masque-outbound не найдено —
проверить путь полных JSON-профилей провайдеров, а не только свой рендер.

### A4. AWG 3.1: финальная документация Amnezia — и противоречие в нотах lx-форка
**Факт.** Официальная документация AmneziaWG теперь описывает 3.1 как

последовательности, тайминги и часть метаданных протокола, чтобы ломать
статистический анализ сессий (а не отдельные сигнатуры). Клиент
AmneziaVPN: AWG 3.1 support — 5.0.1.5 (2026-08-21), свежий клиент —
5.0.3.0 (2026-09-18, TProxy), новее релизов нет. При этом standing-список
фич в нотах sing-box-lx по-прежнему пишет «AmneziaWG **2.0** (`with_awg`)»,
хотя тесты sora утверждают, что lx `with_awg` несёт 3.1-план.
**Источники:** https://docs.amnezia.org/documentation/amnezia-wg/ ;
https://github.com/amnezia-vpn/amnezia-client/releases ;
https://github.com/Leadaxe/sing-box-lx/releases
**Что значит для sora.** До маркетинга «AWG 3.1 через sing-box» — полевая

HeaderProtectionKey и т.д.) реально уходят на провод, а не только проходят
валидацию плана; документация форка и его поведение здесь расходятся

### A6. Цензура: механизма «ковровых» бань подсетей — телеметрия RU-приложений; бюджет ТСПУ и цель 92% к 2030; Иран — рассекреченный план

20+ крупнейших интернет-компаний собирать данные об использовании VPN
клиентами; по RKS Global, ≥30 крупнейших RU-приложений собирают такую
информацию, включая IP-адреса VPN-сервисов, — и она, по эксперту RKS,
использовалась в недавней атаке на инфраструктуру VPN. Это недостающее
звено механики прохода 4 (S3/B5): подсети бьются не только сканами, а по
телеметрии с устройств. (2) Документы ГРЧЦ/Верстка (октябрь 2026):
целевая «средняя эффективность ограничения VPN по сигнатурам» — **92%
к 31.12.2030**, 98% трафика через ТСПУ, пропускная способность 831 Тбит/с;
бюджет ГРЧЦ на 2027 — рост ~20 → 31.8 млрд руб. (+60%). (3) Иран:
2026-10-13 рассекречен 32-пунктный план Верховного совета по киберпространству:
разблокировка иностранных платформ увязана с усилением борьбы со средствами
обхода. Новых **технических** практик по BY/KZ/CN и новых волн RU после
2026-10-20 поиском по первоисточникам НЕ ПОДТВЕРЖДЕНО (сегодня 2026-10-20,
окно дельты — часы).
**Источники:** https://www.hrw.org/news/2026/09/24/russia-crackdown-on-bypassing-online-censorship ;
https://vpnlab.io/en/russia-doubles-internet-blocking-vpn-budget-2026-2619 ;
https://digiato.global/news/iran-32-point-unblocking-plan-disclosed/
**Что значит для sora.** (1) В threat model one-click деплоя добавить:
IP ноды, засвеченный в телеметрии популярных RU-приложений (клиенты
коммерческих VPN), умирает вместе с подсетью — аргумент за self-hosted
«тихие» ноды и разнообразие ASN (усиление, а не повтор вывода прохода 4).
(2) Цель 92%/2030 — в стратегический горизонт censorship intelligence
рядом с ИИ-пунктом прохода 4 (A4): сигнатурный детект — финансируемая
государственная метрика, ставка на поведенческую мимикрию подтверждается

### A7. quic-go CVE-2026-40898: фикс 0.59.1 — не новый; новая работа — карта форков по движкам sora
**Факт.** CVE-2026-40898 (HTTP/3 QPACK trailer expansion → memory

**Источники:** https://github.com/quic-go/quic-go/releases/tag/v0.59.1 ;
https://security.snyk.io/vuln/SNYK-WOLFILATEST-TELEPORT18-17195140 ;

## TIER B — полезно знать / точечные действия

### B1. lx.21: TrustTunnel (AdGuard) — новый outbound/inbound в пинуемом форке
**Факт.** lx.21 добавляет `trusttunnel` outbound и inbound: HTTP/2 over TLS
или HTTP/3 over QUIC к настоящему домену, внутри — proxy CONNECT с Basic
auth, UDP кадрами `CONNECT _udp2`; интероп с официальными endpoint 1.1.0
и клиентом 1.1.11 в обе стороны. Честные ограничения от самого форка:
паддинга нет (TLS-in-TLS виден), нет ICMP, UDP только на IP. На H2
рекомендован uTLS `chrome` (SETTINGS/окно сессии уже хромовые); с
`quic: true` uTLS — ошибка старта.
**Источник:** https://github.com/Leadaxe/sing-box-lx/releases (ноты lx.21)
**Вердикт: в наблюдение, не в Tier A.** Протокол свежий, полевых данных
по RU/ТСПУ нет; кандидат в транспорты sing-box-пути после бампа lx —
дёшево (рендер одного outbound), но обещать как антицензурный нельзя.

### B2. lx.14 (текущий пин) уже содержит XHTTP session-параметры и MTU-выравнивание цепочек — проверить парсер sora, а не движок
**Факт.** Нота lx.14 (SPEC 119): часть `path` после первого `?` уходит
дословно как query запроса (как в Xray), а **session, seq и padding
query-параметры добавляются поверх** неё во всех режимах и на
HTTP/1.1/2/3; без этого Cloudflare-Worker реле (edgetunnel) теряли
`proxyip` и CF-сайты падали с 502 через 20–60 с. Там же `lx.mtu_align`:
hysteria2/TUIC поверх MASQUE/WARP получают `initial_packet_size`
1232 (IPv6)/1252 (IPv4) и отключённый PMTUD — без этого IPv6-hy2 через
WARP молчал. Парсеры ссылок LxBox/лаунчера при этом срезают `?…`-хвост
xhttp-path на своей стороне.
**Источник:** https://github.com/Leadaxe/sing-box-lx/releases (ноты lx.14)
**Что значит для sora.** Движок на пине умеет; риск — на стороне sora:
импорт xhttp-ссылок с `path=/?proxyip=…` и построение цепочек
hy2-over-WARP должны сохранять query-хвост и полагаться на mtu_align
форка, а не выдумывать свой MTU. Точечная проверка `validate_xhttp`
и chain-рендера, не бамп.

### B3. uTLS/JA4/PQ: дельты нет — зафиксировано честно
**Факт.** Тегированного релиза uTLS новее v1.8.2 по-прежнему нет;
HelloChrome_156 не существует в публичных источниках; Chrome 156 stable
назначен на 2026-10-20 (Chromium Dash), на момент проверки stable —
155/early 156; в release notes 156 TLS/ClientHello-изменений нет.
JA4: новостей нет. PQ: гибрид X25519MLKEM768 — дефолт браузеров
(Chrome 131+, Firefox 132+) и Go crypto/tls с Go 1.24 при nil
CurvePreferences; нового с прохода 4 не появилось, кроме серверного
требования REALITY из S1.
**Источники:** https://github.com/refraction-networking/utls/releases ;
https://chromestatus.com/release-notes/156 ;
https://www.qntonsol.com/learn/try-post-quantum-tls-today-openssl-browsers-cloudflare.html
**Что значит для sora.** Parrot-watch не ускорять; JA4-эталон 155 валиден
и для 156 до фактической перепроверки после роллаута (1–2 недели).

### B4. AnyTLS: mihomo не шлёт `client-metadata` по умолчанию — образец приватного дефолта
