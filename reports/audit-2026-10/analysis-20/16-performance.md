# Аналитик №16: производительность

Репозиторий: `~/workspace/bug-hunt/sora`, ветка `bugfix/audit-2026-10-19`.
Зона: горячие пути Go (рендер конфигов, probe, counters/connections), Dart UI (перестройки, списки серверов, старт), память, батарея.
Метод: read-only анализ кода, без изменений. Эффекты оценены порядком величины, где возможно — с расчётом.

---

## Вердикт

Код в целом написан с оглядкой на производительность: троттлинг нотификаций проб (300 мс), стриминговые RPC вместо поллинга там, где это важно, виртуализация списков, ограниченные кэши, бюджеты сокетов. Это сильная база.

Но есть **два высокоприоритетных дефекта** и несколько средних, которые реально бьют по UX именно в целевых сценариях («тысячи серверов», «старт < 0.3 с», «экран соединений»):

1. **Глобальный probe падает целиком при >256 серверах** — клиент шлёт все серверы одним запросом, ядро режет лимитом. Для больших подписок измерение латентности не работает вообще.
2. **Сортировка списка серверов делает `DateTime.now()`/`sqrt`/`pickMember` внутри компаратора** — O(n log n) дорогих вызовов на UI-потоке при каждом тике проб (300 мс) и каждом нажатии клавиши в поиске. В режимах `smart`/`speed` при ~3000 серверов это десятки миллисекунд джанка за сортировку.
3. **Экран соединений дважды в секунду тянет весь список соединений**: `readStats()` → `Counters()` делает полный `GET /connections` с декодом всего JSON, и тут же `listConnections` делает второй такой же. При тысячах активных соединений — мегабайты мусорного JSON в секунду.
4. **Холодный старт**: `await Settings.load()` и `await desktop.start()` выполняются до `runApp()` — первый кадр откладывается на дисковый I/O + инициализацию window manager/D-Bus/нотификаций. Цель <0.3 с под угрозой без сплэша.

Плюс серия средних/мелких: поиск без дебаунса, ре-сорт соединений каждую секунду, непрореживаемые карты измерений, `jsonDecode`/`DateFormat` на каждый нотифай в десктоп-интеграции.

Ниже — сильные стороны (что не трогать), затем слоп/проблемы с оценкой эффекта, затем ранжированные рекомендации.

## Сильные стороны (проверено, держать)

- **Троттлинг нотификаций проб**: `app/lib/src/sora.dart:1567` — `_probeNotifyInterval = 300ms`; без него сотни серверов = сотни полных перестроек UI. Комментарий честно ссылается на аудит M20.
- **Стримы вместо поллинга там, где важно**: `WatchEvents` (`core/control/server.go:702`), `ProbeServers` (`core/control/server.go:1095`), `watchSubscriptions`/`watchEvents` на клиенте (`app/lib/src/sora.dart:762` и далее). Поллинг остался только там, где осознанно (см. проблемы №3, №6).
- **Нет глобального поллинга статистики**: `readStats()` (`app/lib/src/sora.dart:330`) вызывается только по требованию, с гардом `_readingStats` от overlapping-запросов; комментарий ссылается на аудит M17.
- **Виртуализация списков**: `SliverList.separated` в `app/lib/src/ui/servers.dart`, `ListView.builder` в `app/lib/src/ui/connections.dart` — ряды строятся только для видимой области. Заголовок файла честно фиксирует: «building only visible server rows».
- **Мемоизация группировки**: `_groupedEntries` через `Expando` (`app/lib/src/groups.dart:77`) — Unicode-regex на имя сервера выполняется один раз на объект состояния, а не при каждой перестройке (комментарий прямо описывает, зачем кэш: тики проб каждые 300 мс).
- **Probe-бюджеты в Go**: глобальный пул сокетов (`slots`), `MaxConcurrentRequests = 4`, `MaxEndpoints = 256`, короткие таймауты (`core/probe/probe.go:33-41`) — один тяжёлый замер не роняет остальные.
- **Ограниченные кэши**: логи Go — 20000 записей / 8 МБ с вытеснением старых (`core/logs/logs.go:90-91`); парсер ограничен `MaxInputSize` и лимитом айтемов с дедупликацией через map (`core/parser/parser.go:256-329`) — один проход, без O(n²).
- **Диск не дёргается в горячем пути**: `historySaveInterval = 30s` для `probe/history.json` (`core/probe/bandwidth.go:56`); `_saveBandwidth()` — один раз за бенчмарк-ран, а не на сэмпл (`app/lib/src/sora.dart:1799`).
- **mihomo hot-reload**: `ReloadPayload` (`core/engine/mihomo/engine.go:113-132`) применяет план без рестарта процесса и без потери соединений; sing-box/xray честно документированы как restart-only (`core/engine/singbox/engine.go:3`, `core/engine/xray/engine.go:120-121`).
- **Анимация орба gated**: тикер `Glow` стартует только при `busy && energy > 0 && Motion.enabled` (`app/lib/src/design/glow.dart:84-98`) — в покое батарею не ест.

## Слоп/проблемы

Формат: файл:строки — что не так — оценка эффекта.

### HIGH

**P1. Глобальный probe целиком отваливается при >256 серверах.**
`app/lib/src/sora.dart:1577-1595` — `probe()` без `subscriptionId` кладёт `servers` (все подписки, дедуплицированные) в один `ProbeServersRequest`. Ядро режет: `if total > MaxProbeEndpoints` → `ResourceExhausted` (`core/control/server.go:1104-1107`), лимит `MaxProbeEndpoints = 256` (`core/control/plan.go:39`). Клиентского чанкинга нет (проверено поиском по `sora.dart` — нет разбиения на батчи). Эффект: при подписке/сумме подписок >256 серверов кнопка «измерить всё» и автопроб при открытии десктоп-панели (`servers.dart:57-66`) **не измеряют ничего** — ошибка уходит в `reportFailure`, результаты остаются «неизвестными». Это прямо противоречит сценарию «списки на тысячи строк» из постановки задачи: сортировка по пингу/скорости для таких подписок мертва.

**P2. Дорогой компаратор сортировки списка серверов на UI-потоке.**
`app/lib/src/ui/servers.dart:270-283` (`_sortEntries`) + `app/lib/src/sora.dart:2076-2151` (`freshBandwidthOf`, `smartScoreOf`, `compareAutoSelect`) + `app/lib/src/sora.dart:2048-2069` (`pickMember`):
- режимы `speed`/`smart`: компаратор вызывает `freshBandwidthOf` → `DateTime.now()` на каждое сравнение; `smart` — дважды `smartScoreOf`, т.е. **4× `DateTime.now()` + 2× `sqrt` + обращения к `reliabilityOf` на одно сравнение**;
- `keyOf` для групп вызывает `pickMember(entry, …)` — O(members) **на каждое сравнение**, итого O(n log n · m) для списков с группами;
- режим `name` (в `_sortEntries:273`) делает `a.name.toLowerCase()` — аллокация строки на каждое сравнение.
Сортировка запускается при каждом throttled-нотифае проб (каждые 300 мс во время замера), каждом нажатии клавиши в поиске (`servers.dart:49`), каждом обновлении подписки (`servers.dart:180`). Расчёт: n=3000 → ~35 тыс. сравнений; при ~1–2 мкс на сравнение в `smart` — **30–70 мс на UI-потоке за одну сортировку, до ~3 раз в секунду во время проба**. Это видимый джанк именно в момент, когда пользователь смотрит на обновляющиеся пинги. В дефолтном режиме `ping` компаратор дешёвый (два map lookup) — проблема проявляется в `smart`/`speed`.

**P3. Двойной полный `GET /connections` каждую секунду на экране соединений.**
`app/lib/src/ui/connections.dart:61` — `_read()` каждую секунду (`_every = 1s`, строка 30) вызывает и `sora.readStats()`, и `link.stub.listConnections(...)`. `GetStats` → `Engine.Counters` → `clashapi.Client.Counters` (`core/engine/clashapi/ops.go:107-117`), который делает **полный `GET /connections` и декодирует весь список соединений** ради трёх чисел (`downloadTotal`, `uploadTotal`, длина списка). `ListConnections` (`core/control/logs.go:329-347` → `ops.go:53-79`) делает второй такой же запрос тут же. Эффект: при N активных соединений — 2 HTTP round-trip + 2 JSON-декода всего списка в секунду, почти всё выбрасывается. При 2–5 тыс. соединений это сотни КБ–единицы МБ JSON в секунду впустую: CPU на декод, аллокации тысяч структур `connection`, лишние GC-паузы, батарея. Комментарий в `ops.go:23-24` («the polled HTTP source») фиксирует, что источник по дизайну поллится, — но ничто не мешает кэшировать.

### MEDIUM

**P4. Холодный старт: два `await` до `runApp()`.**
`app/lib/main.dart:22-26`: `await Settings.load()` (создание `SharedPreferencesWithCache` — чтение XML/JSON с диска, плюс `_migrate`) и `await desktop?.start(hidden: …)` (`app/lib/src/desktop/desktop.dart:87-112`: `windowManager.ensureInitialized`, `setPreventClose`, D-Bus watch трея, инициализация нотификаций, `syncLaunchAtLogin`, подписки на диплинки) — всё до первого кадра. Сплэша нет: окно пустое, пока это не завершится. Эффект: на Linux инициализация window manager + D-Bus легко даёт +100–300 мс к первому кадру; цель «<0.3 с» труднодостижима без выноса за первый кадр. `sora.run()` при этом уже правильно `unawaited` (строка 24) — тяжёлый линк к ядру первый кадр не блокирует.

**P5. Поиск по серверам без дебаунса: полная перестройка на каждое нажатие.**
`app/lib/src/ui/servers.dart:49` — `_search.addListener(() => setState(() {}))`. Каждое нажатие: `build()` → `_visibleEntries` (O(n), `servers.dart:254`), `_matching` (O(n) + `toLowerCase` на каждую запись, `:245`), `_sortEntries` (O(n log n) с компаратором из P2, `:270`). При 3000 серверов и быстрой печати «vless» — 5 полных циклов фильтр+сорт подряд, в `smart`-режиме каждый по десятки мс. Эффект: залипание ввода на больших списках; лечится дебаунсом 150–250 мс (один цикл на слово вместо одного на букву).

**P6. Экран соединений ре-сортирует и перегруппировывает каждую секунду.**
`app/lib/src/ui/connections.dart:74-77` — `..sort((a,b) => b.start.seconds.compareTo(a.start.seconds))` на весь список при каждом полле (1 Гц). `_groupedList` (`:175-213`) при каждом `build` заново строит `Map<process, List>` и сортирует группы через `_traffic` (сумма байт по всем соединениям — O(n) на группу, вызывается O(g log g) раз внутри сортировки). Эффект: при тысячах соединений — миллисекунды CPU ежесекундно впустую + батарея; порядок «сначала новые» можно поддерживать инкрементально (список с сервера дописывается, а не перемешивается), а группировку мемоизировать по составу ID.

**P7. Карты измерений (`latency`, `bandwidth`, `probeStats`) никогда не чистятся.**
`app/lib/src/sora.dart:1674` (`bandwidth`), `:532`/`:1596` (`latency`), `:1712` (`probeStats`). `_watchSubscriptions` (`:762`) заменяет состояния подписок целиком, но записи об удалённых/исчезнувших серверах остаются навсегда. `probeStats` затухает per-id, но сами id не удаляются. Эффект: медленная утечка памяти на протяжении жизни приложения при регулярных обновлениях подписок (сотни–тысячи мёртвых записей); `_saveBandwidth()` (`:1699`) сериализует и персистит в SharedPreferences весь мусор целиком — растёт и JSON в настройках, и время его парса при старте (`_loadBandwidth`, `:102`).

**P8. `Desktop._changed()` делает лишнюю работу на каждый нотифай (в т.ч. тики проб 300 мс).**
`app/lib/src/desktop/desktop.dart:278-283`: на каждый `notifyListeners` — `_updateTray()` (нативный `setTooltip` каждые 300 мс во время проба), `_warnAboutSubscriptions()` (цикл по подпискам + `subscriptionWarning` с `Intl.verifiedLocale` и конструкцией `DateFormat` на подписку), `_syncProxy()` с `jsonDecode(sora.settings.proxySnapshot)` на каждый тик. Эффект: мелкий, но системный — десятки лишних нативных вызовов и парсов JSON в секунду во время замеров; `_syncProxy`/`_warnAboutSubscriptions` достаточно дёргать при смене phase/подписок, а не при каждом тике.

### LOW

**P9. `tls.Config` на каждый замер.**
`core/probe/probe.go:190` — `tlsConfig(host)` аллоцирует новый `tls.Config` на каждый `dial`. Горячим путём это не является (замеры идут секундами, лимит 256 эндпоинтов), но кэш по host убрал бы аллокации совсем.

**P10. Квадратичные worst-case в рендерах, ограниченные константами.**
`assignTags`/`unique` (`core/engine/singbox/render.go:121-136`) — цикл `for n := 2; r.used[tag]; n++` даёт O(n²) при массовых дублях имён; `remoteRuleSet` (`:541-554`) — линейный скан `r.ruleSets` на правило. На практике n ограничен `MaxOutbounds = 5000` (`core/engine/plan.go:12`), дублей имён мало — не править без профилировки, просто не ухудшать.

**P11 (замечание, не дефект).** Ветка `name` внутри `Sora.compareServers` (`app/lib/src/sora.dart:1822-1826`) вызывает `displayNameOf` → `nameOf` (`:574-580`), а `nameOf` строит весь `servers` (O(N) с Set) и делает `firstWhere` — O(N) **на сравнение**. Сейчас из `_sortEntries` эта ветка недостижима (ранний return для `name`), но метод публичный — футган для будущих вызовов. При использовании — предвычислить ключи.

**Проверено и признано нормой (не слоп):** `_Elapsed` в `home.dart:316` — таймер 1 с, но перестраивает один `Text`; `Screen`/`kit.dart:141` — без вложенных скроллов; `updates.dart:255` — таймер 12 ч; `connect()`/`Apply` — рендер конфига один раз за подключение, O(n) с map-lookup (`core/control/plan.go:167-314`).

## Ранжированные рекомендации

1. **Чанкинг проба >256 (P1).** В `Sora.probe()` (`sora.dart:1569`) резать `all` на батчи ≤256 и слать последовательно/параллельно (2–3 в полёте), склеивая стрим результатов; либо поднять `MaxProbeEndpoints` с сохранением потоковой выдачи. Эффект: возвращает к жизни измерение пинга для больших подписок — сейчас оно молча не работает вообще. Приоритет наивысший: без этого бессмысленны сортировки по пингу/скорости на тысячах серверов.
2. **Decorate-sort-undecorate для списка серверов (P2).** В `_sortEntries` (`servers.dart:270`) один раз на запись предвычислить: для групп — `pickMember` один раз (а не в компараторе), для `smart`/`speed` — числовой скор/ключ один раз за текущие `DateTime.now()`, для `name` — `toLowerCase()` один раз; затем сортировать по готовым ключам. Эффект: ~35 тыс. дорогих сравнений → O(n) дешёвых предвычислений + O(n log n) сравнений чисел; 30–70 мс джанка → единицы мс на 3000 записей.
3. **Убрать двойной `/connections` (P3).** Вариант А (дешёвый): в `clashapi.Engine` кэшировать результат `Counters()` на ~250–500 мс — `readStats()` и `listConnections`, приходящие в один тик, делят один fetch. Вариант Б (правильный): totals-only эндпоинт (`/traffic` у sing-box/mihomo) для `Counters()`. Эффект: −50% (А) до −95% (Б) CPU/трафика поллинга экрана соединений.
4. **Первый кадр раньше настроек (P4).** В `main.dart`: `runApp()` немедленно с лёгким сплэшем; `Settings.load()` и не-критичную часть `desktop.start()` (нотификации, `syncLaunchAtLogin`, D-Bus watch) — после первого кадра (`addPostFrameCallback`/`unawaited`). Критично для цели <0.3 с: сейчас первый кадр ждёт диск + window manager + D-Bus.
5. **Дебаунс поиска серверов (P5).** 150–250 мс после последнего нажатия перед `setState`; плюс предвычисление lowercase имён один раз на набор записей. Эффект: N нажатий → 1 цикл фильтр+сорт вместо N.
6. **Не ре-сортить соединения вслепую (P6).** В `connections.dart`: поддерживать порядок «сначала новые» инкрементально (merge по `start`/id, а не полный `sort` в секунду); группировку по процессам мемоизировать по множеству id. Эффект: убрать ежесекундные O(n log n)+O(n·g) на экране, который и так поллит.
7. **Чистка карт измерений (P7).** При обновлении/удалении подписки (`_watchSubscriptions`) удалять из `latency`/`bandwidth`/`probeStats` id, которых больше нет ни в одной подписке и ни в custom-серверах; опционально кап размера. Эффект: нет медленной утечки, `_saveBandwidth` перестаёт персистить мусор, старт чуть быстрее.
8. **Тихий `_changed()` (P8).** В `desktop.dart:278`: `_updateTray` — только при смене phase/тултипа; `_warnAboutSubscriptions` и `_syncProxy` — по смене подписок/phase, а не на каждый нотифай; `proxySnapshot` распарсить один раз и кэшировать. Эффект: убрать десятки нативных вызовов и `jsonDecode` в секунду во время проб.
9. **Мелочи (P9–P11):** кэш `tls.Config` по host в probe; не трогать квадратичные worst-case рендеров без профилировки; либо удалить, либо обезопасить `name`-ветку `compareServers` предвычислением ключей.

### Что намеренно не предлагаю

- Переписывать поллинг `listConnections`/`readStats` на стримы ядра: Clash API — pull-модель, WebSocket `/traffic` есть не у всех движков; 1 Гц только при открытом экране — приемлемо после P3/P6.
- Кэширование `Render()` конфигов: рендер — раз за подключение, O(n), аллокации не в горячем пути; мемоизация конфигов с секретами — риск, не выгода.
- Уменьшение `DefaultMaxEntries` логов / `historySaveInterval`: текущие границы разумны.
