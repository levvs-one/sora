# Аналитик №19: релизный пайплайн

Read-only анализ ветки `bugfix/audit-2026-10-19` (sora). Дата анализа: 2026-10-20.
**Важно:** ветка живая — параллельные агенты правили эту зону прямо во время анализа
(коммиты `2b2631a` APP_VERSION в CI, `73d845d` документирование ручной подписи SHA256SUMS).
Ниже — состояние на момент проверки каждой находки; исправленное уже — помечено.

## Вердикт

Пайплайн спроектирован честно (fail-closed везде, где надо; версии прошиваются из тега;
манифест релиза парсится строго), но **прямо сейчас он сломан в самом главном месте**:
Windows-установщик не может собраться в CI вообще — ни на PR, ни по тегу.
Гейт «неподписанный установщик не должен собраться случайно» (коммит `5fa5b7a`, SORA-L5)
добавил в `sora.iss` безусловный `SignTool=soraSign`, а определение тулкита в вызов
`iscc` в workflow не прокинули. По официальной документации Inno Setup это ошибка
компиляции. Итог: тег `v*` сегодня даёт только Linux-пакеты, Windows-артефакт —
пустой, а шаг «Build the installer» красный на каждом PR.

Второй по важности разрыв — между моделью безопасности и реальностью на Windows:
`SHA256SUMS.minisig` скачивается апдейтером, но на Windows его подпись никто не проверяет
(проверка есть только в Linux-хелпере `sora-update`, под root). Пока нет ни key ceremony
(minisign), ни Authenticode-сертификата — оба действия владельца — релиз фактически
нельзя ни установить, ни раздать как автообновление. Это честно закодировано
(fail-closed), но это и главный блокер принципа «легко выпустить обнову».

Безупречного качества здесь нет: один критический дефект (сломанная сборка Windows),
один высокий (непроверяемая подпись на Windows-пути обновления), плюс набор средних
мелочей про воспроизводимость, rollback и рассогласование источников версии.

## Сильные стороны

1. **Fail-closed подписи релиза.** Ключ minisign — плейсхолдер
   `REPLACE-ME-AFTER-KEY-CEREMONY` (`packaging/install/install.sh:30`,
   `packaging/install/install.ps1:80`, `packaging/linux/sora-update:43`), и все три
   скрипта отказываются работать, пока он не заменён (`install.sh:77`,
   `install.ps1:85`, `sora-update:48`). Сообщения об ошибке честно говорят, что делать
   (key ceremony, FIX-PLAN.md раздел 9), а не притворяются, что всё хорошо.
2. **Подпись обязательна для автообновления.** `app/lib/src/updates.dart:389`:
   `release.asset('SHA256SUMS.minisig')` бросает `UpdateFailure.release`, если ассета
   нет, — неподписанный релиз даже не предлагается. На Linux хелпер перепроверяет
   подпись под root до доверия любому хешу (`packaging/linux/sora-update:117`).
3. **Строгий разбор релиза.** `SoraRelease.parse` (`updates.dart:66-88`): только
   не-драфт, не-prerelease, строго трёхкомпонентная версия; URL каждого ассета обязан
   совпадать с `releases/download/$tag/$name` (защита от подмены через API);
   `expectedHash` требует ровно одну строку манифеста на файл (защита от
   дубликатов/теневых записей); лимиты `contentLength`/size на скачивание.
4. **Версия прошивается из тега, а не из головы.** `SORA_VERSION=${GITHUB_REF_NAME#v}`
   (`.github/workflows/repository.yml:204-207`, `:405-407`); Go — `-X main.buildVersion`
   с `-trimpath`; не-теговые сборки получают честную `0.0.0.<run>` / `0.0.0~<run>`.
   `APP_VERSION` для гейта расширений теперь тоже тянется автоматически из
   `pubspec.yaml` (коммит `2b2631a`, workflow `:203-209`, `:473-479`) — пустого гейта
   в релизах больше нет.
5. **Контракт имён пакетов сходится.** Имена, которые ждёт апдейтер
   (`updates.dart:133-137`: `sora-core_${v}_amd64.deb`, `sora-core-${v}-1.x86_64.rpm`,
   `sora-core-${v}-1-x86_64.pkg.tar.zst`), совпадают с дефолтами nfpm
   (см. замечание №7 ниже про неявный `release`).
6. **CI гоняет настоящий цикл установки.** Каждый PR: сборка установщика, установка
   через `install.ps1`, проверка службы, живые тесты трафика через туннель, удаление;
   Linux: `install.sh` на Ubuntu + Fedora/Arch в контейнерах. Редкий уровень для
   проекта такого размера.
7. **Движки пинованы.** `packaging/engines/engines.lock` — версии + SHA-256,
   `fetch.sh` падает при несовпадении; `engines.sig` — проверка апстрим-подписей
   с fail-closed (`SORA-M3`).
8. **Честность в доках для пользователя.** `docs/faq.md:23` прямо говорит: установщик
   не подписан сертификатом, SmartScreen покажет предупреждение, подлинность — по
   `SHA256SUMS`. Не прячется.
9. **Драфт только после всех джоб** (`needs: [workflow, proto, go, app, windows, linux-packages]`),
   с `--verify-tag` (workflow `:563`).

## Слоп / проблемы

Формат: файл:строка — суть.

### Критично

- **`packaging/windows/sora.iss:36` + `.github/workflows/repository.yml:221`** — релизный
  пайплайн сломан. `sora.iss` требует `SignTool=soraSign` безусловно, а CI вызывает
  `ISCC.exe /DAppVersion=... packaging\windows\sora.iss` без `/SsoraSign=...`.
  Официальная документация Inno Setup: имя Sign Tool «have to be defined in the
  compiler IDE … or on the compiler command line (via the "/S" parameter), else an
  error will occur». Шаг «Build the installer» падает на каждом PR и каждом теге —
  Windows-артефакта в релизе нет вообще. Источник: коммит `5fa5b7a` добавил гейт,
  не тронув workflow. Заголовок `sora.iss:1-8` дополнительно документирует ту же
  сломанную команду как инструкцию по сборке.

### Высоко

- **`app/lib/src/updates.dart:389,398` (Windows-путь)** — подпись `SHA256SUMS.minisig`
  скачивается и кладётся в рабочую папку, но на Windows её никто не проверяет.
  Проверка есть только в Linux-пути (`packaging/linux/sora-update:117`, под root).
  Windows-путь (`updates.dart:416` → `desktop.dart:176`, прямой запуск Inno-установщика)
  сверяет лишь хеш установщика с `SHA256SUMS`, а сам манифест аутентифицирован только
  TLS GitHub. Это противоречит заявленной модели (`docs/security.md:32`: подпись
  minisign проверяется до доверия хешам). В Dart уже есть верификатор minisign
  (`app/lib/src/ext/verifier.dart`, для расширений) — его не переиспользовали.
  Смягчение: без ассета `.minisig` релиз не предлагается вообще, так что «тихая»
  подмена требует ещё и скомпрометированного TLS/релиза; но defense-in-depth здесь
  дырявый именно там, где выше риск (Windows, самая массовая платформа).

### Средне

- **`docs/development.md` (раздел «Выпуск», шаги 1–4)** — не упоминает обязательные
  ручные шаги: подписать `SHA256SUMS` ключом релиза и загрузить `SHA256SUMS.minisig`
  в драфт. Коммит `73d845d` задокументировал это только в комментарии workflow
  (`.github/workflows/repository.yml`, блок перед `gh release create`). Буквальное
  следование dev-доке даёт опубликованный, но неустанавливаемый релиз
  (апдейтер требует `.minisig`, скрипты — валидную подпись).
- **Релизные заметки — `--notes ""`** (workflow `:563`). Полностью ручные, связи с
  `CHANGELOG.md` нет: ничто не заставляет notes соответствовать changelog'у
  (который ведётся добросовестно, до 1.0.12). Качество анонса — на совести владельца
  в момент публикации; легко выпустить «пустой» релиз.
- **Два источника версии.** `SORA_VERSION` — из тега (workflow), `APP_VERSION` — из
  `app/pubspec.yaml` (`grep '^version:' … | cut -d+ -f1`, workflow `:203-209`).
  Процедура требует поднять оба, но CI не проверяет `tag == pubspec`. Расхождение
  даст: апдейтер сравнивает по версии тега, а гейт расширений `min_app_version`
  (`store_screen.dart:186`) — по версии pubspec. Молчаливый дрейф.
- **Нет staged rollout и rollback.** `updates.dart`: опрос `/releases/latest` каждые
  12 часов — все клиенты получают релиз одновременно; `newerRelease` — только
  «вперёд». Отозванный (удалённый) релиз нельзя откатить у тех, кто успел
  обновиться; единственный путь — новый тег с версией выше. «Staged updates» из
  F7 — это стадии одного обновления (checking→downloading→verifying→installing),
  а не поэтапный rollout.
- **Сборки не воспроизводимы** (заявлений об этом нет — честно, но для
  проекта-витрины с «transparent signing» это дыра): Go — `-trimpath` есть, но нет
  `-buildvcs=false` (в бинарник вшивается VCS-штамп); Flutter и Inno встраивают
  таймстампы; nfpm — без фиксации `mtime`; zapret собирается из вендоренного дерева
  `third_party/zapret` без зафиксированного апстрим-коммита в репозитории
  (в `third_party/README.md` зафиксированы хешами только отдельные `.a`/`.o`-блобы).
  Независимая перепроверка «собрано из этого коммита» невозможна.

### Низко / мелкий слоп

- **Три рецепта `APP_VERSION` в доках** — `packaging/linux/README.md:32`,
  `packaging/windows/README.md:20`, `docs/development.md:134` (везде захардкоженный
  пример `1.0.6`), плюс `docs/extensions.md:87` (формула из pubspec). CI теперь
  делает правильно автоматически; доки стоит свести к одной ссылке на workflow.
- **`packaging/linux/nfpm.yaml` / `nfpm-app.yaml`: поле `release` не задано.**
  Имя `sora-core-${v}-1.x86_64.rpm`, которое ждёт апдейтер, держится на дефолте
  nfpm (`release=1`). Работает, но неявно — зафиксировать `release: 1` явно.
- **Проверено, не проблема:** `sha256sum -- * > SHA256SUMS` (workflow, шаг
  «Checksums») корректно исключает сам `SHA256SUMS` — glob раскрывается до создания
  файла редиректом. Порядок шагов (скрипты → checksums → draft) правильный.

## Ранжированные рекомендации

1. **Починить сборку Windows-установщика в CI (блокер всего).**
   `sora.iss`: обернуть `SignTool`/`SignedUninstaller` в условие наличия определения,
   напр. `#ifdef SoraSign … #endif`, либо в CI передавать throwaway-тестовый
   `/SsoraSign=` для PR-сборок. Fail-closed должен падать только на *релизной*
   сборке без сертификата, а не на каждой сборке вообще. Сейчас пайплайн мёртв —
   это №1 без вариантов.
2. **Довести Windows-путь обновления до модели безопасности:** проверять подпись
   `SHA256SUMS.minisig` в Dart до запуска установщика (переиспользовать
   `ext/verifier.dart`), как это делает `sora-update` на Linux. Иначе
   `docs/security.md:32` врёт про Windows.
3. **Закрыть действия владельца — это главный блокер «легко выпустить обнову»:**
   key ceremony (minisign) + Azure Trusted Signing для Authenticode. Пока их нет,
   любой релиз неустанавливаем/необновляем по дизайну. После церемонии —
   автоматизировать: шаг workflow, подписывающий `SHA256SUMS` ключом из секретов
   (или задокументированный ручной ритуал прямо в `docs/development.md`, а не
   только в комментарии workflow).
4. **Дописать раздел «Выпуск» в `docs/development.md`:** шаги подписи
   `SHA256SUMS`, загрузки `.minisig` в драфт, написания notes из `CHANGELOG.md`.
   Сегодня там 4 шага, из которых шаг 4 («написать текст и опубликовать») скрывает
   самую ответственную часть.
5. **Одна истина версии:** в CI сверять `tag == версия pubspec` (fail-fast на
   расхождении) либо выводить `APP_VERSION` из `SORA_VERSION`. Убрать три
   разошедшихся рецепта из README/дokов.
6. **Генерировать notes драфта из `CHANGELOG.md`** (шаг workflow извлекает секцию
   версии), вместо `--notes ""`. Убирает класс «пустой релиз по забывчивости».
7. **Staged rollout + аварийный тормоз:** метка/поле в релизе (напр. процент или
   `rollout: paused`), которую уважает апдейтер; документированная процедура
   отзыва (удаление тега/релиза + новый тег-фикс). Сейчас релиз — это «всем сразу,
   назад дороги нет».
8. **Шаги к reproducible builds:** `-buildvcs=false` + `SOURCE_DATE_EPOCH` для Go,
   фиксация `mtime`/`release` в nfpm, запись апстрим-коммита zapret
   (напр. `third_party/zapret.VENDOR`), документированный отказ от
   воспроизводимости Inno/Flutter — или принятие этого как есть, но явно.
9. **Мелочь:** зафиксировать `release: 1` в обоих `nfpm*.yaml`; свести рецепты
   `APP_VERSION` в доках к одному.

## Что уже исправлено параллельными агентами (не дублировать)

- `2b2631a`: CI прокидывает `--dart-define=APP_VERSION` из `pubspec.yaml`
  (Windows `:203-216`, Linux `:473-486`) — гейт расширений в релизах больше не пустой.
- `73d845d`: комментарий в workflow о ручной подписи `SHA256SUMS` и загрузке
  `.minisig` в драфт (но не в `docs/development.md` — см. рекомендацию 4).
- `98794f1`: починка CI-контракта после fail-closed H1 (minisign-тестовые ключи в
  CI через `SORA_MINISIGN_PUBKEY`, `SORA_DIST`) — самопроверка пайплайна скриптами
  работает.
