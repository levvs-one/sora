# Ревью SW3 Go-часть: пакет `core/select` (коммит 43aaa3c)

Дата: 2026-10-19. Ревьюер: swarm-review (независимый).
Проверено: `score.go`, `reliability.go`, `pick.go`, `advisor.go`, `select.go` + 4 тестовых файла.
Проверки: `go build ./select/`, `go vet ./select/`, `go test -race -count=1 ./select/` — всё зелёное (45 тестов: 38 авторских + 7 ревьюерских).

## Вердикт

**Принять с мелкими исправлениями (уже внесены).** Математика скоринга корректна,
Beta-posterior адекватен, анти-флэппинг продуман (окна подтверждений + кулдаун +
сброс счётчика при восстановлении), ранкинг детерминирован, объяснения честны.
Найдено 5 реальных дыр — все закрыты коммитом ревью (см. «Исправлено»).
Критических проблем нет. Осталось 4 замечания/вопроса (см. «Осталось») — ни одно
не блокирует.

## Найденные дыры и исправления

Все 5 сначала воспроизведены падающими тестами (`core/select/review_test.go`,
тесты остались как регрессионные), затем исправлены.

1. **NaN в конфиге → NaN в скоре, ломается ранкинг.** `clampFloat(NaN)` возвращал
   NaN (сравнения с NaN ложны). `ScoreConfig{WeightPing: NaN}` давал `Total: NaN`,
   а компаратор сортировки (`a.Total != z.Total` истинно, `>` ложно при NaN) —
   недетерминированный порядок. Исправлено: `clamp01`/`clampFloat` мапят NaN →
   0/lo (`select.go`). Бонус: NaN в `reliability`-входе `Score()` тоже больше не
   протекает в `Breakdown`.
2. **Переполнение uint32 в `pingScore` при «чужом» контексте.** Если кандидата
   скорят против `ScoreContext`, построенного не по его множеству
   (`LatencyMs < MinLatencyMs`), `c.LatencyMs - ctx.MinLatencyMs` враппалось и
   кандидат получал 0 вместо 1. Исправлено: вычитание во float64, `clamp01`
   держит результат (`score.go`).
3. **Документолгано vs код: «pruned on save».** Комментарий к `ReliabilityConfig.TTL`
   обещал чистку протухших записей при сохранении, код этого не делал — файл
   `probe/reliability.json` копил мёртвые записи до 1МБ-лимита, после чего
   `load()` **выбрасывал всю историю целиком** (медленная потеря данных).
   Исправлено: `saveLocked` больше не пишет протухшие записи (`reliability.go`).
   Поведение `Rate`/`Stats` не изменилось (они и так игнорировали протухшее).
4. **`AdvisorConfig{LatencyFactor: NaN}` → мусор в лимите.** `time.Duration(NaN)` —
   implementation-defined, сравнение `byFactor > latLimit` непредсказуемо.
   Исправлено: NaN трактуется как «не задано» → дефолт, как и 0 (`advisor.go`).
   Аналогично для `ErrorRate`.
5. **Нет теста на конкурентный доступ**, хотя `ReliabilityStore` заявлен
   «safe for concurrent use». Добавлен hammer-тест под `-race` — гонок нет,
   мьютекс покрывает `Record`/`Rate`/`Stats`/`Prune`/`saveLocked`.

Дополнительно добавлен тест, фиксирующий задокументированную семантику строгого
`>` на порогах (`TestReviewExactThresholdNotDegraded`): деградация ровно на
пороге — не деградация. Квантование окон делает точные попадания частым случаем
(напр. 2/4 == 0.5 при `ErrorRate: 0.5`), поведение осознанное и совпадает с докой
(«exceeds», «more than»).

## Что проверено и признано корректным

- **Нормализация скоринга:** пинг относительный (min→1, max→0, вырожденный
  span→1), bandwidth — доля от максимума, freshness — линейный распад к TTL,
  веса нормируются к сумме 1, all-zero → дефолты. Деления на ноль нет.
- **Beta-posterior:** `(s+α)/(s+f+α+β)`, α=β=1 по умолчанию; неизвестный/протухший
  сервер → prior mean 0.5. Счётчики насыщаются вместо враппинга (uint32).
- **Fail-safe персистентности:** битый/гигантский файл → дропается, никогда не
  фатально; атомарная запись (tmp+rename); 0o600/0o700 — та же конвенция, что в
  `probe` (проверено, расхождений нет).
- **Advisor:** `ConfirmWindows` последовательных окон + сброс при одном здоровом
  окне + `MinSwitchInterval` между советами; кулдаун «держит» счётчик, совет
  срабатывает сразу по истечении, без новой серии подтверждений; `Switched`
  (ручной тоже) стартует кулдаун. Флэппинга нет. p95 — корректный nearest-rank
  (`ceil(0.95n)-1`).
- **Детерминизм:** тай-брейки полный порядок (has-latency → latency → has-bw →
  bw → id); `sort.SliceStable`; мапы только для lookup'ов. Свежесть зависит от
  часов — при фиксированном `Now` воспроизводимо полностью.
- **Честность объяснений:** `Reason` для пина и для скоринга соответствуют
  реальному пути выбора; бонус движка применён до сортировки и отражён в
  показанном `Total`; `Rejected` содержит всех отфильтрованных с причинами.
- **API:** разделение чистое (скоринг / журнал / выбор / советник), конфиги
  клампятся, zero value везде usable. Лишнего («слопа») не найдено: `Stats`,
  `Prune`, `Armed` — легитимное публичное API журнала/советника, оставлены
  (в дереве пока нет вызывающего кода — интеграция с сессией предстоит).

## Осталось (не блокирует, решения за владельцем)

1. **`resolveGate`: неизвестный `Kind` (нет в `engine.Catalog`) → тихое отсутствие
   гейта (fail-open).** Кандидат с любым протоколом проходит. Это «попробовать и
   упасть на коннекте» (журнал надёжности потом научится), а не дыра в
   безопасности, но умолчание неочевидное. Предложение: либо явно документировать
   fail-open, либо реджектить с причиной `unknown engine kind "..."` (fail-closed).
   Не менял — решение про поведение.
2. **Два ручки приора:** `ScoreConfig.PriorSuccess/PriorFailure` и
   `ReliabilityConfig.PriorSuccess/PriorFailure`. Picker использует первые только
   в fallback'е при `rel == nil`. Работает корректно, но пара на одну сущность —
   кандидат на упрощение при интеграции.
3. **`Observe` возвращает `reason == ""`** и для «окно ещё не набралось», и для
   «здорово». Косметика; при желании — различать («warming up»).
4. **`Record` → запись файла на каждый исход коннекта.** Для VPN-клиента норма
   (одно событие на connect/disconnect), но при интеграции не вызывать в горячих
   циклах.
5. **Замечание про окружение (не код):** во время ревью другой агент правил
   `core/engine` прямо в дереве — одна сборка упала на несуществующем уже через
   минуту `validate_tuning.go`. Итоговые `build`/`vet`/`test -race` — зелёные,
   но перед мержем ветки стоит прогнать полный `go build ./...` по `core`.
