# Анализ цензуры №06 — Детект VLESS / VMess / Trojan

Аналитик: №6/50. Дата: 2026-10-20. Статус: анализ, код не тронут, коммитов нет.
Источники: te-st.org «Разбор №37» (30.09.2026, полевые тесты), USENIX Security 2023 (Wu et al., passive detection FEP), RaccoonLine Global VPN Blocking Report 2026, Project Atlas, Geedge leak analysis (censoredplanet.org, 2026), OpenGFW, liuylv/trojan-prober, ISOC Pulse (Иран), XTLS docs. Слухи помечены как слухи.

---

## 1. Что детектится и как проявляется

Три протокола в разной степени устойчивы, но **все три детектятся при определённых условиях**. Проявления (РФ):

- **Тихий дроп (silent drop)**: ТСПУ пропускает TLS-handshake + первые ~16 КБ, затем перестаёт маршрутизировать сессию. Клиент «висит» до тайм-аута. Паттерн зафиксирован в февральской волне 2026.
- **Активный RST-инжект**: ТСПУ подделывает TCP RST обеим сторонам, сессия обрывается сразу.
- **Отказ handshake на 443**: майская волна 2026 — блокировка процесса TLS-handshake VLESS на 443, при этом SSH к тем же серверам работал.
- **Блок подсети целиком**: августовская волна 2026 — бан по IP-диапазонам хостинговых AS, независимо от протокола.
- **Режим «белых списков»** (мобильные операторы РФ): разрешён только IP из списка разрешённого — любой VPN-протокол мёртв по определению.

В Китае доминирующий вектор — **пассивный детект полностью зашифрованного трафика** (USENIX 2023: entropy/exemption эвристики, ~0.6% допустимого коллатерала) + активное пробирование. В Иране — ML-DPI + активное пробирование + периодические протокольные вайтлисты (вплоть до «только DNS/HTTP/HTTPS», stealth blackout, середина 2025).

## 2. Где: регион, операторы, условия

**Россия (ТСПУ/РКН), хронология волн по VLESS:**
- Ноябрь 2025 — первые сигнатурные блокировки VLESS (исследователь Пётр Лосев: «система научилась вычленять именно этот протокол»).
- 17 февраля 2026 — от прямой сигнатуры к **косвенным признакам**: SNI ≠ инфраструктура IP, паттерны нетипичны для браузинга. Раскатано на проводных операторах «Дом.ру», SkyNet, «Ростелеком». Били связку VLESS+Reality.
- 21 мая 2026 — тестирование блокировки TLS-handshake VLESS на 443 в Сибири, ДВ, Москве; SSH к тем же узлам работал (то есть блок протокольный, не IP).
- Август 2026 — переход к блокировке **целых подсетей** хостеров (несколько десятков AS, по данным «Новой Газеты Европа» при участии крупных ИТ-компаний как источника статистики по IP).
- Режим «списков разрешённого» на мобильных сетях: доступ только по IP из списка.

Тесты te-st.org (сентябрь 2026, ноды Москва/СПб, дата-центры и ШПД): их собственные конфиги VLESS от VPN Generator блокировок не показали (9/9 успешных handshake), при том что у других пользователей проблемы были. Вывод: обновления ТСПУ раскатываются **неравномерно по операторам и регионам**; РКН бьёт по подсетям (AS) и TLS-фингерпринтам известных провайдеров, а не по протоколу «вообще».

**Китай (GFW):**
- С 6 ноября 2021 — пассивный детект полностью зашифрованных протоколов (Shadowsocks, VMess, Obfs4) по entropy/exemption-эвристикам (USENIX 2023).
- Активное пробирование подозрительных узлов — штатный вектор.
- По RaccoonLine 2026: **VMess сломан в 2025** — DPI-обновления научились детектить его по **характеристикам тайминга пакетов**. Единственный протокол, который «операторы и исследователи последовательно сообщают как выживший» в Tier-3 DPI (Китай, Иран, КНДР) в 2026 — **VLESS + REALITY**. Но фиксированные endpoint'ы со временем банятся по поведенческим сигналам.
- Project Atlas: в Китае «CDN + VMESS + WS работает, но технически детектится; Trojan работает, но фингерпринт может быть идентифицирован; VLESS с TLS или XTLS — сильная опция».

**Иран:**
- ISOC Pulse (источники 2024): SSH/VMESS фильтруется в течение **дня** после подключения, VLESS — от **недели до месяца**.
- Середина 2025: stealth blackout — централизованный border gateway, **protocol whitelisting** (только DNS/HTTP/HTTPS), DPI TLS-handshake с резетом по SNI.
- RaccoonLine 2026 относит Иран к Tier 3 (ML-DPI + active probing).

## 3. Как технически: векторы детекта по протоколам

### 3.1. VLESS

Протокол минималистичен: в handshake **UUID пользователя передаётся открытым текстом** (version=1 байт + 16 байт UUID + остальное). Следствия:

1. **Кластеризация по UUID**: один и тот же UUID в тысячах сессий на один IP — детерминированный идентификатор, позволяющий коррелировать соединения даже без расшифровки. Это не «сигнатура», это коррелятор. *(Технический факт из спецификации VLESS; факт использования этого ТСПУ/GFW — не подтверждён публично, но вектор очевиден.)*
2. **Entropy первых килобайт**: февральская волна 2026 в РФ — ТСПУ анализирует ~16 КБ после handshake на «случайность» и несоответствие профилю HTTP/2-браузинга. VLESS поверх bare TLS без маскирующего транспорта — идеальная мишень для этого теста.
3. **SNI ↔ инфраструктура mismatch**: февраль 2026 — сверка заявленного SNI с AS/IP-принадлежностью. SNI=google.com на IP рядового VPS-хостера = автоматическое расхождение.
4. **XTLS-Vision**: добавляет собственный handshake поверх TLS (структура фиксированного размера). Публичных подтверждений его сигнатурного детекта нет, но фиксированная структура handshake — кандидат в сигнатуру. **Слух/требует проверки.**
5. **VLESS Encryption** (опциональное шифрование payload, без TLS): защищает содержимое, но **не даёт вида обычного HTTPS** — сама документация XTLS прямо указывает, что для обхода цензуры он непригоден.

### 3.2. VMess

- **AEAD-шифрованный handshake** — сигнатуры в открытом виде нет. Но:
- **Китай, ноябрь 2021+**: пассивный детект как «fully encrypted protocol» по entropy/exemption-эвристикам USENIX 2023 (доля установленных битов, доля и позиция печатных ASCII-символов, фингерпринты известных протоколов как исключения).
- **Китай/Иран, 2025** (RaccoonLine 2026): VMess детектится по **таймингу и распределению размеров пакетов** даже поверх TLS — «размерный/временной профиль» не совпадает с обычным браузингом.
- **Активное пробирование**: VMess-сервер без корректного fallback отвечает на неавторизованные подключения отлично от веб-сервера.
- Итог: VMess в 2025–2026 в Tier-3 — **сломан**, работает только как «слишком мелкий, чтобы было дело» или за CDN.

### 3.3. Trojan

- Handshake поверх TLS: первый payload — **56-байтный hex SHA-224 пароля + CRLF + SOCKS5-адрес**. Фиксированная длина первого пакета — слабое место для length-based эвристик.
- **Активное пробирование — главный вектор.** liuylv/trojan-prober (Go): 5 типов проб — H1-Close, H1-Incomplete, Overbuffer-Incomplete, H1-ALPN-h2, Short-ALPN-h2. Trojan-сервер без fallback ведёт себя отлично от nginx/Caddy при: быстром закрытии, неполных запросах, переполнении буфера, ALPN-mismatch. Именно так GFW исторически подтверждал Trojan-узлы; август 2025 в РФ (по dev.to-источнику, менее надёжен) — «активное пробирование стало массовым, Trojan упал до ~90% детекта». **Помечаю dev.to-цифры как слух** — анекдотальные проценты одного оператора.
- Пассивно поверх корректного TLS Trojan почти неотличим от HTTPS — но **только если fallback настроен на реальный сайт**. Без fallback — детект за 1–2 пробы.

### 3.4. Общее для всех трёх (маскирующие транспорты)

- **uTLS-фингерпринт клиента**: GFW умеет отличать TLS-библиотеку VPN-клиента от Chrome/Firefox. Обход — `fingerprint: chrome` и т.п. Но: **post-quantum KEM** (X25519MLKEM768, уже в Chrome) — клиент без него на фоне реальных браузеров 2026 года выглядит устаревшим. Xray это учитывает (reality.go детектит PQ KEM).
- **Активное пробирование vs REALITY**: REALITY перенаправляет неавторизованные подключения на реальный dest (например, learn.microsoft.com:443). Пробер получает настоящий сайт — классификация «прокси» не срабатывает. **Но**: dest должен быть (а) реально доступен с сервера, (б) поддерживать TLS 1.3, (в) не быть заблокированным в регионе цензуры.
- **SpiderX-механизм** (Xray): клиент при провале REALITY-верификации ведёт себя как краулер dest-сайта. Это защита от «цензор притворяется клиентом», но сам паттерн краулинга — аномалия, теоретически детектируемая. **Требует проверки.**

## 4. Надёжность известных обходов

| Обход | Надёжность | Ограничения (проверено) |
|---|---|---|
| **VLESS + REALITY** | Высокая — лучший из известных в 2026 (RaccoonLine; gist-анализ 04.2026: «нет публично известной DPI, надёжно детектящей VLESS Reality») | Не защищает от: бана IP/подсети (август 2026), SNI↔infra mismatch (февраль 2026), режима белых списков; требует корректного dest и fallback; фиксированный endpoint со временем палится по поведению |
| **Trojan + fallback на реальный сайт** | Средняя-высокая | Критична идеальность fallback (5 типов проб trojan-prober); фиксированная длина первого пакета; IP-репутация |
| **VLESS/VMess/Trojan + WS/gRPC за CDN** | Средняя | CDN IP — тоже банятся; gRPC/WS-паттерны «технически детектятся» (Project Atlas про VMESS+WS в Китае) |
| **XHTTP / SplitHTTP** | Потенциально выше WS (таблица XTLS: obfuscation High, CDN-friendly, multiplex xmux) | Мало полевых данных 2025–2026; сложность настройки; лимиты reverse proxy (nginx 128 streams) |
| **VLESS Encryption без TLS** | Низкая для цензуры | Сам XTLS: не даёт вида HTTPS, для обхода непригоден |
| **VMess AEAD без маскировки** | Низкая (2025+) | Пассивный entropy-детект + timing-детект |

Ключевой вывод из gist-анализа (04.2026): «классификатору не нужно знать, какой у тебя протокол — ему достаточно знать, что ты не браузишь». Побеждает не «шифрование сильнее», а **протокольная мимикрия**: реальный TLS к реальному домену, трафик внутри application layer.

**REALITY не панацея** (v2ray22.com, 2026): «не undetectable; не чинит заблокированный адрес; паттерны трафика, доступность dest, сетевые политики и отличия конфигурации влияют на результат».

## 5. Что неизвестно / требует проверки

1. Точные пороги entropy-теста ТСПУ (~16 КБ окно — эмпирика te-st; сам алгоритм закрыт).
2. Использует ли ТСПУ/GFW **кластеризацию по открытому UUID VLESS** — вектор очевиден, публичных подтверждений нет.
3. Эксплуатируется ли **timing side-channel REALITY** (разница задержки ответа REALITY-сервера vs настоящего dest) — в литературе есть направление, полевых подтверждений применения цензорами нет. **Слух.**
4. Сигнатурность **XTLS-Vision handshake** — фиксированная структура, публичных сигнатур нет. Требует реверса/теста.
5. Детект **XHTTP/SplitHTTP** ML-моделями Tier-3 — полевых данных почти нет.
6. Масштаб использования **SNI↔infra mismatch** как автоматического правила (февраль 2026 — по косвенным признакам).
7. Детектируемость **SpiderX-краулинга** как аномалии.
8. Точный механизм «накопления статистики по IP при участии крупных ИТ-компаний» (август 2026, «Новая Газета Европа») — как именно вычисляются «подозрительные» AS.

## 6. Проблемы для тех-агентов

- **P06-1. Открытый UUID в handshake VLESS** — детерминированный коррелятор сессий. Требуется: (а) оценить переход на VLESS Encryption или ротацию UUID; (б) проверить, кластеризует ли ТСПУ/GFW по UUID (полевой тест).
- **P06-2. Политика выбора decoy-SNI для REALITY**: запрет SNI крупных брендов (Google/Microsoft/Apple) на VPS-IP; требование infra-консистентности — идеально собственный сайт-прикрытие на том же IP/хостинге. Нужен чекер «SNI ↔ ASN/IP» в пайплайне выпуска конфигов.
- **P06-3. Fallback при активном пробировании**: сервер обязан отвечать как настоящий веб-сервер на все 5 классов проб trojan-prober (H1-Close, H1-Incomplete, Overbuffer, ALPN-mismatch, minimal H2). Нужен self-test harness, гоняющий эти пробы против наших инбаундов.
- **P06-4. IP/ASN-репутация и ротация**: августовская волна 2026 бьёт по подсетям целиком. Нужны: диверсификация AS, мониторинг бана по /24, процедура быстрого переезда, подписная ссылка вместо статичных конфигов.
- **P06-5. uTLS-фингерпринт клиента**: обязательный `fingerprint: chrome` (или актуальный), с поддержкой post-quantum KEM (X25519MLKEM768), иначе клиент выделяется на фоне браузеров 2026. Проверить, что дефолтные конфизы sora это выставляют.
- **P06-6. Профиль «не-браузинга»**: entropy-тест ~16 КБ + HTTP/2-профиль. Сырой VLESS/TLS без маскирующего транспорта — под ударом. Дефолт для РФ/Китая/Ирана — только REALITY или XHTTP/WS за TLS с реалистичным ALPN (h2).
- **P06-7. XTLS-Vision**: верифицировать, имеет ли vision-handshake детектируемую сигнатуру (реверс Xray + захват трафика + сравнение с обычным TLS). До вердикта — не рекомендовать как primary для Tier-3.
- **P06-8. Выбор транспорта**: XHTTP (xmux, CDN-friendly, obfuscation High по таблице XTLS) — кандидат на primary вместо WS; нужны полевые A/B-тесты XHTTP vs WS vs gRPC на ТСПУ/GFW-подобных стендах (OpenGFW как тестовый таргет).
- **P06-9. Режим белых списков (мобильные РФ) и protocol-whitelist (Иран-2025)**: никакой протокол не проходит. Требуется отдельный план: meek-подобные транспорты через разрешённые CDN-домены, либо честная индикация «недоступно» вместо молчаливых ретраев.
- **P06-10. Доменная зависимость конфига**: если домен из ключа заблокирован по SNI/DNS — ключ мёртв независимо от протокола. Нужны: DNS-over-HTTPS/TLS по дефолту, запасные SNI/домены в подписке, вариант конфига «по IP».
- **P06-11. Зонд мониторинга по методике te-st.org**: два уровня (сырой TCP + полный handshake), серия запросов 2–3 минуты с интервалом ~20с (часть блокировок срабатывает с задержкой), ноды на «Ростелеком», МТС, «ЭР-Телеком»/«Дом.ру», «Билайн» + 2–3 мобильных оператора, алерты в Tg-бота. При сбое сначала исключать IP-блок (проверка SSH), затем перебирать SNI/фингерпринт.
- **P06-12. SpiderX и dest-доступность**: dest для REALITY обязан быть TLS 1.3, доступен с сервера, не заблокирован в регионе; оценить, палит ли SpiderX-краулинг клиент (аномальный паттерн) — тест.
- **P06-13. Trojan: длина первого пакета** (56-байт hex + CRLF) — оценить, применяется ли length-based эвристика; fallback-тесты по P06-3 покрывают и это частично.
- **P06-14. VMess**: считать скомпрометированным для Tier-3 (timing-детект 2025). Не использовать как primary; оставить только как fallback для «мелких» сетей либо за CDN.
