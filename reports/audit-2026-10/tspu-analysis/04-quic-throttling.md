# 04. QUIC/UDP-троттлинг (ТСПУ)

Аналитик №4. Дата: 2026-10-20. Веб-поиск: 8 запросов (RU+EN), приоритет 2025–2026, плюс полный разбор ключевого источника (FOCI'26). Перекрёстные ссылки: отчёты 12 (Discord/Telegram), 13 (ECH), 29 (фрагментация), 50 (матрица обходов).
Статус: только анализ, код не тронут, коммитов нет.

Маркировка достоверности: **[П]** — проверено ≥2 независимыми источниками или прямые измерения из рецензируемой работы; **[S]** — один источник / вывод из механики, требует перепроверки; **[слух]** — недостоверно, в технические решения не закладывать.

## 1. Что блокируется / как проявляется

### YouTube — SNI-троттлинг QUIC с 18.07.2024 [П]
- QUIC-троттлинг YouTube стартовал **к 18.07.2024 — через неделю после TLS-троттлинга** (~11.07.2024) [П — FOCI'26 §2.3, со ссылкой на форумные измерения ntc.party]. Триггер — SNI `.googlevideo.com` / `youtube.com` в QUIC Initial.
- Скорости с 01.08.2024: **128 кбит/с по TCP и 512 кбит/с по QUIC** [П — Meduza, цит. по Wikipedia «Замедление YouTube в России (с 2024)»]. Проявление: видео не выше 240p, 4K — вечная буферизация. Механизм по расследованиям июля 2024: идентификация по SNI + искусственное ограничение скорости отбрасыванием пакетов [П — Wikipedia со ссылкой на аналитиков кибербезопасности].
- Эскалация: **08.08.2024 — полная SNI-блокировка YouTube по TLS** [П — FOCI'26]; **по QUIC — к 18.04.2025** [П — FOCI'26, форумные данные]. Т.е. «троттлинг» для YouTube — пройденный этап, сейчас это блокировка; но механика policer'а актуальна для других целей (см. Cloudflare, Telegram-медиа).
- Важно: **TCP дросселировался сильнее QUIC (128 vs 512 кбит/с)** — принудительный TCP-fallback для YouTube был не обходом, а ухудшением [П].

### Cloudflare — 16 КБ на соединение с 09.06.2025 [П]
- С 09.06.2025 провайдеры режут трафик к Cloudflare: **первые ~16 КБ соединения проходят, дальше — обрыв**. Затронуты **все протоколы, включая HTTP/3 over QUIC** [П — developers.cloudflare.com/support, обновлено 23.04.2026; Cloudflare blog «Russian Internet users are unable to access the open Internet»].
- Пик 13–15.06.2025: падение трафика к Cloudflare на ~50% [П — redteamnews.com]. Техники: packet injection + блокировки → таймауты соединений [П — Cloudflare via securityonline.info]. Те же меры — против Hetzner, DigitalOcean, OVH [П].
- Проявление: сайт либо не грузится вообще (ассет >16 КБ), либо отдаёт только шапку HTML. Это не «замедление», а **объёмный лимит на соединение** — качественно иной policer, чем у YouTube.

### Международный QUIC в целом — только SNI-цензура, не троттлинг [П]
- Период B (03.2022–06.2022): поголовный дроп всего международного QUIC (первый пакет ≥1001 байт + version `0x00000001`) [П — FOCI'26]. Снят 03.06.2022 (трафик QUIC к Cloudflare вырос на 38% за день).
- Период C (с 05.2022–07.2023 переход, далее): **только SNI-зависимая цензура**, поголовного троттлинга QUIC нет [П — FOCI'26]. **QUICv2 не цензурируется вообще** — парсер ТСПУ его не понимает [П].
- Discord: QUIC-соединения с SNI `discord.com` показывают доменно-специфичное поведение (см. §3.5) [П — FOCI'26 Fig.4]. Сам Discord заблокирован с 08.10.2024 (см. отчёт 12); голосовой RTC — UDP высоких портов.

### Что НЕ зафиксировано
- Поголовного шейпинга всего UDP/443 «до X Мбит/с» вне конкретных кампаний (YouTube, Cloudflare) измерения не показывают [П — FOCI'26: незаблокированные домены по QUIC ходят свободно].
- Слухи о «троттлинге всего UDP оптом» относятся к регионам белых списков (см. матрицу п.25) — отдельный режим, не предмет этого отчёта.

## 2. Где: регион, операторы, условия

- **Покрытие**: вся РФ, где стоят ТСПУ. Масштаб (10.2025): 1406 узлов, 132.3 Тбит/с суммарной нагрузки; цель — 954 Тбит/с к 2030 [П — отчёт 12/CIL 09.2026]. Разбивка Минцифры (05.2026): 1207 узлов ШПД, 135 узлов мобильных сетей, 86 трансграничных [П — habr.com/ru/amp/publications/1014590].
- **Операторы** (подтверждены для Cloudflare-кампании): Ростелеком, Мегафон, Вымпелком, МТС, МГТС [П — Cloudflare]. Для YouTube/QUIC-SNI — все крупные (инфраструктура ТСПУ едина) [П — FOCI'26: поведение идентично в трёх городах].
- **Uniformity**: Москва, СПб, Новосибирск — идентичное поведение QUIC-цензуры [П — FOCI'26]. Исключение: **в Москве 22% системных портов (1–1023) не под QUIC-цензурой**; в СПб и Новосибирске цензура покрывает **все UDP-порты до 65535** [П — FOCI'26 §3]. QUIC-релевантные порты (443, 853/DoQ) цензурируются везде.
- **Направленность**: только **исходящий** трафик из РФ; входящий не цензурируется никогда [П — FOCI'26]. Локализация по TTL-замерам: цензура между 3-м и 4-м хопом от Москвы; TLS- и QUIC-цензура — на одном хопе (одно устройство ТСПУ) [П].
- **Условие деградации цензуры**: при перегрузке ТСПУ уходит в **bypass (fail-open)** — трафик идёт без фильтрации. Март 2026: источники Forbes в телекоме — ТСПУ не справляется, заблокированные сервисы периодически «оживают»; устройство RDP.RU ~100 Гбит/с [S — dev.ua; habr/tadviser; РКН официально отрицает — учитывать как неподтверждённое]. Для sora: троттлинг/блокировки **не детерминированы во времени** — возможны окна прохождения.

## 3. Как технически

### 3.1. Детект QUIC: расшифровка Initial [П — FOCI'26 §3]
1. ТСПУ отслеживает **первый пакет каждого UDP-flow** (4-tuple: src IP, src port, dst IP, dst port).
2. QUIC Initial расшифровывается **публичными ключами** (RFC 9001: initial keys выводятся из публичного salt'а QUICv1 — цензор реализует тот же вывод, что и Wireshark).
3. Из расшифрованного payload извлекается **TLS ClientHello → расширение SNI**.
4. SNI сверяется с блоклистом. **Блоклисты TLS и QUIC совпадают**: из Tranco Top-100k все 2644 домена, цензурируемые по TLS, цензурируются и по QUIC, и наоборот [П — измерения 03–04.2026].
5. Исторический детект (Period B): эвристика «первый пакет ≥1001 байт + 4-байтный version `0x00000001`» [П].

### 3.2. Механика блокировки: drop + residual censorship 420 с [П]
- При совпадении SNI: **дропается Initial и все последующие пакеты того же 4-tuple в течение 420 секунд**. Каждый новый пакет **сбрасывает таймер** — активные ретраи клиента самопродлевают бан [П — FOCI'26 §3, Fig.2].
- **Residual clearance**: если первый пакет НЕ триггернул цензуру — flow больше **не анализируется вообще** («первый пакет решает») [П]. Это архитектурная брешь, см. §4.
- Цензура **однонаправленная и in-path**: только drop, без инъекций (control-пакеты QUIC зашифрованы — подделать CONNECTION_CLOSE/RST цензор не может) [П].

### 3.3. Механика троттлинга: policer (SNI-III) [П — отчёт 12 / CIL 09.2026]
- Таксономия ТСПУ: **SNI-III = policer: дроп пакетов сверх rate limit**. Именно этот режим = троттлинг (в отличие от SNI-I/II — инъекции RST и дропы).
- YouTube: лимит 128 кбит/с (TCP) / 512 кбит/с (QUIC) по SNI `.googlevideo.com`. Точная реализация policer'а (token bucket? per-flow state? окно измерения?) **не реверсирована** — см. §5.
- Cloudflare: лимит **16 КБ на соединение**, затем обрыв (не rate, а **объёмный** лимит). Техники: packet injection + drop → таймауты [П — Cloudflare].

### 3.4. Отличия от TCP-цензуры
| Аспект | TCP/TLS | QUIC/UDP |
|---|---|---|
| Парсинг SNI | plaintext ClientHello, тривиально | требуется AEAD-расшифровка Initial (дороже CPU) |
| Реакция | RST-инъекция (on-path возможна), drop | **только in-path drop** — инъекции невозможны (всё зашифровано) |
| Состояние | 5-tuple + отслеживание handshake | 4-tuple UDP, «первый пакет решает», residual 420 с |
| Порты | обычно 80/443 | **любые UDP-порты** (до 65535; искл. — часть системных в Москве) |
| Направленность | оба направления (RST — обеим сторонам) | только исходящий из РФ |
| Троттлинг | drop ломает congestion control предсказуемо | QUIC восстанавливается быстрее (нет head-of-line blocking) — возможно, поэтому лимит для QUIC выставляли выше (512 vs 128) [S — гипотеза] |

### 3.5. Доменно-специфичные аномалии [П — FOCI'26 §3, Fig.4]
- `discord.com` по QUIC: **не цензурируется, если на том же 4-tuple ранее прошли «нецензурные» данные** — residual clearance срабатывает раньше, чем проверка SNI. Но «цензура незатронутых доменов всё равно включает residual censorship, перезаписывающий clearance» — поведение нестабильно и зависит от порядка пакетов.
- Некоторые домены блокируются **только на порту 443**, на других портах — нет.
- Предположение авторов: сложные конфиги / несколько ТСПУ с разными настройками на пути. Для sora: **поведение ТСПУ неоднородно даже внутри одного города** — стратегии обхода нужно валидировать per-destination, а не один раз.

## 4. Насколько надёжен известный обход

### 4.1. QUIC-десинхронизация fake-пакетами (zapret) — частично, деградирует [П — конфиги; S — эффективность]
Механика (дефолт `def-cfg.sh`): `--filter-udp=443 --dpi-desync=fake --dpi-desync-repeats=6 --dpi-desync-fake-quic=quic_initial_www_google_com.bin` — перед настоящим Initial шлётся 6 фейковых QUIC Initial с «чистым» SNI (`www.google.com`); DPI принимает фейк за первый пакет flow → residual clearance → настоящий Initial не инспектируется [П — deepwiki remittor/zapret-openwrt].
ALT-варианты (Flowseal/zapret-discord-youtube): `fake,disorder2`, `repeats=8`, `--dpi-desync-udplen-pattern=0xCAFEBABE` [П].
Оценка надёжности:
- Работает, пока ТСПУ смотрит **строго первый пакет** flow. Если DPI начнёт смотреть N первых пакетов / реассемблировать — умрёт сразу.
- Полевые данные анекдотичны: «на МТС/Билайн ещё помогает, на Ростелеком/Мегафон — уже нет» [слух — tenchat.ru, дек 2025, блог с промо VPN]. Как планировочный сигнал — слабый, как факт — не годится.
- Риски: фейк создаёт мусорное QUIC-соединение на сервере (расход CID, возможный Retry); disorder-варианты могут ломаться о QUIC Retry от сервера (второй Initial после Retry — новый «первый пакет» для DPI? см. §5).
- Вывод: **базовый приём держать, но считать деградирующим** (согласуется с матрицей п.47: «смерть zapret как бесплатного обхода»).

### 4.2. Принудительный TCP-fallback (резка UDP/443) — механически надёжен, но часто вреден [П]
Блокировка UDP/443 (reject/ICMP-unreachable) заставляет Happy Eyeballs/Chromium откатиться на TCP+TLS [П — zenn.dev/lafine: ICMP port-unreachable → мгновенный fallback без ожидания таймаута].
Но:
- Обходит только **QUIC-специфичную** обработку. SNI-цензура по TCP — та же (блоклисты TLS=QUIC), троттлинг YouTube по TCP был **жёстче** (128 vs 512 кбит/с) [П].
- Для доменов, троттлируемых/блокируемых именно по QUIC-SNI (редкий случай, учитывая равенство блоклистов) — рабочий. В общем случае — **не обход, а смена лимита на худший**.
- Вывод: fallback — не стратегия обхода, а **диагностический инструмент** («по TCP идёт, по QUIC нет» → проблема в QUIC-ветке ТСПУ).

### 4.3. QUIC connection migration — не обход блока, но сброс 420-с бана [S — вывод из механики]
- Residual censorship привязан к 4-tuple. Смена source port / IP (миграция по CID, без разрыва соединения) = новый flow для ТСПУ = **выход из 420-секундного бана** [S — следует из §3.2, полевыми тестами не подтверждено].
- Но новый flow = новая инспекция первого пакета → SNI снова виден → снова блок. Как **обход блокировки — не работает**; как **восстановление после ложного/устаревшего бана — работает**.
- Комбинация «миграция + shadow handshake» (§4.4) — теоретически полный обход блокировки; не тестировалась.

### 4.4. Shadow handshake (decoy Initial с чистым SNI первым) — подтверждено точечно [П — FOCI'26 Fig.4; S — обобщаемость]
Суть: на том же 4-tuple первым отправляется валидный QUIC Initial с невинным SNI → ТСПУ фиксирует residual clearance → затем идёт настоящий трафик, уже не инспектируемый. Сервер демультиплексирует по CID, оба Initial'а живут как отдельные соединения — серверной поломки нет.
- Подтверждено для `discord.com` [П]. Но поведение **доменно-специфично**, для большинства доменов из выборки не проверялось/не сработало.
- Вывод: самый дешёвый потенциальный обход (один лишний Initial, без фейковых разрывов), но **требует полевой валидации** на целевых SNI (P04-3).

### 4.5. QUICv2 — теоретический обход, практически неприменим [П — FOCI'26; S — применимость]
Парсер ТСПУ понимает только QUICv1; QUICv2 (RFC 9368/9369) проходит мимо цензуры [П]. Но серверная поддержка QUICv2 у крупных сервисов практически нулевая → клиентом не форсится. Фиксировать как «окно на будущее», не как план.

### 4.6. Фрагментация ClientHello внутри Initial — против ТСПУ ненадёжна [П]
Против GFW фрагментация ClientHello — рабочий обход [П — Zohaib et al. 2024, цит. по FOCI'26]. Против ТСПУ **минимум один вариант фрагментации провален** (payload no. 8, Appendix B) [П — FOCI'26]. QUIC Initial и так фрагментируется на уровне дейтаграмм редко (Initial обычно в одном UDP-пакете) — поле для манёвра уже, чем в TCP. См. отчёт 29.

## 5. Что неизвестно / требует проверки

1. **Реализация policer'а YouTube**: token bucket vs selective drop, per-flow или per-SNI state, окно измерения, порог срабатывания по времени/объёму. Без этого нельзя спроектировать «шейпинг-френдли» режим (например, pacing под лимит).
2. **Почему лимиты TCP/QUIC различались** (128 vs 512 кбит/с): два разных policer'а или артефакт методологии Meduza? Ответ определяет, есть ли смысл в тонкой настройке протокола под лимит.
3. **Актуальный статус YouTube-троттлинга в 2026**: после полной блокировки (08.2024 TLS, 04.2025 QUIC) policer может быть демонтирован или, наоборот, переиспользован для других SNI. Нужны свежие замеры скорости, а не факта доступности.
4. **Окно инспекции**: строго первый UDP-пакет flow или первые N байт/пакетов? Критично для fake-десинхронизации (repeats=6 может быть как избыточным, так и недостаточным).
5. **QUIC Retry**: серверный Retry → клиент шлёт второй Initial с новыми ключами. Видит ли ТСПУ второй Initial как «первый пакет»? Ломает ли это fake-десинхронизацию (фейк уходит до Retry, настоящий Initial — после)?
6. **0-RTT / resumption**: пакеты 1-RTT без Initial на новом 4-tuple — инспектируются ли? (У ТСПУ нет ключей 1-RTT → вероятно, пропускаются; тогда долгоживущий resumed QUIC — потенциальный обходной канал.)
7. **ECH over QUIC**: при ECH SNI скрыт. Детектит ли ТСПУ ECH-ClientHello внутри Initial и что делает: пропуск / дроп / шейпинг? (См. отчёт 13 по ECH-блокировкам Cloudflare с 11.2024 — но там про TLS.)
8. **GQUIC (Q043/Q046)**: старые версии, которые исторически использовал YouTube в Android-приложении (pcap с SNI `*.googlevideo.com` в GQUIC CHLO — форум opnsense). Парсит ли их ТСПУ или они идут мимо?
9. **Московская аномалия портов**: почему 22% системных портов 1–1023 не под цензурой — конфиг, другой вендор ТСПУ или баг? Воспроизводимо ли для обхода (DoQ/853 покрыт везде — нет, но другие порты?)
10. **Статус 16-КБ лимита Cloudflare в 2026**: ослаблен, усилен или заменён? Cloudflare docs обновлены 04.2026 — лимит ещё описан как действующий [П], но свежих независимых замеров объёма нет.
11. **Мобильные PGW-шейперы**: есть ли у мобильных операторов собственный UDP/QUIC-шейпинг поверх ТСПУ (жалобы «VPN плохо передаёт QUIC/UDP» — vpn-rating.space 10.2026 [S])? Разделить эффекты ТСПУ и операторского QoS.
12. **Детект «VPN поверх QUIC»**: MASQUE/QUIC-туннели (Mullvad 2025.9, матрица п.48) выглядят как обычный QUIC — попадает ли такой трафик под SNI-проверку Initial (у MASQUE Initial настоящий, SNI прокси-сервера)? Если SNI прокси чист — это рабочий транспорт поверх QUIC-цензуры.

## 6. Проблемы для тех-агентов

- **P04-1. QUIC Initial-парсер для самодиагностики.** Реализовать в Go (core): расшифровка Initial публичными ключами (RFC 9001), извлечение SNI. Нужно клиенту, чтобы отличать «убил ТСПУ» (нет ответа после Initial с конкретным SNI) от «сеть плохая». Без этого любая QUIC-стратегия слепа.
- **P04-2. Автотюнинг fake-QUIC десинхронизации.** Параметры (repeats, fake vs fake+disorder2, udplen-pattern, выбор fake-SNI) сейчас захардкожены в zapret-конфигах. Нужен механизм подбора по паре (оператор, регион) + детект «стратегия перестала работать» с фолбэком. Опора на §5 п.4.
- **P04-3. Валидация shadow handshake.** Полевыми тестами проверить обобщаемость decoy-Initial за пределами discord.com: целевые SNI (googlevideo.com, cloudflare-домены, vpn-sni). Если работает широко — это обход стоимостью в один пакет; если нет — зафиксировать границы.
- **P04-4. Port-rotation для выхода из residual-бана.** 420 с бана с самопродлением при ретраях: клиент должен при детекте бана (P04-1) менять UDP source port с экспоненциальным backoff'ом, а не долбить тот же 4-tuple. Специфицировать для QUIC-транспортов (Hysteria2 и т.п.).
- **P04-5. Различение «блок» vs «шейпинг».** Активный throughput-probe: короткий замер скорости по QUIC и TCP на контрольных SNI → классификация (drop / policer-128 / policer-512 / объёмный лимит 16 КБ / чисто). От классификации зависит выбор стратегии; сейчас клиент их не различает.
- **P04-6. Матрица «протокол × SNI → ожидаемое качество».** Запретить слепой TCP-fallback: для YouTube он ухудшает (128 < 512 кбит/с). Решение клиента должно учитывать измеренную матрицу, а не эвристику «TCP надёжнее».
- **P04-7. Нестандартные UDP-порты.** Проверить воспроизводимость московской аномалии (22% системных портов без цензуры) и поведение на высоких портах в других городах. Если найдётся стабильно «слепой» порт — использовать для DoQ/DNS и сигнальных каналов. (Осторожно: FOCI показывает покрытие до 65535 в СПб/Новосибирске — эффект может быть точечным.)
- **P04-8. Покрытие QUIC Retry в десинхронизации.** Убедиться, что fake-стратегия переживает серверный Retry (второй Initial): либо фейки повторяются после Retry, либо клиент детектит Retry и перезапускает десинхронизацию.
- **P04-9. ECH-over-QUIC.** Оценить реакцию ТСПУ на ECH-ClientHello в Initial (пропуск/дроп/шейпинг). Если пропуск — ECH+QUIC становится транспортом, скрывающим SNI от policer'а; связать с отчётом 13.
- **P04-10. Сигналы для CENSORSHIP-METER.** В `CENSORSHIP-METER-SPEC.md` добавить QUIC-метрики: скорость QUIC vs TCP на контрольных SNI, факт residual-бана (по P04-1), время до восстановления, объёмный лимит (16-КБ паттерн), версия QUIC сервера. Без этого метр не видит половину картины.
- **P04-11. QUIC внутри VPN-туннелей.** Проверить жалобы «VPN плохо передаёт QUIC/UDP»: не применяет ли ТСПУ эвристический шейпинг к UDP внутри туннелей (по размеру/таймингам пакетов), даже не видя SNI. Если да — нужен TCP-инкапсуляция QUIC (XHTTP/stream-one уже есть в стеке — оценить).
- **P04-12. 16-КБ лимит Cloudflare — зафиксировать как необходимый локально.** Объёмный лимит рвёт любое соединение независимо от SNI/протокола; клиентский обход невозможен — только смена egress (VPN) или дробление на подсоединения <16 КБ (костыль уровня приложения). Не тратить ресурсы на «умный» обход, честно показывать пользователю причину.
