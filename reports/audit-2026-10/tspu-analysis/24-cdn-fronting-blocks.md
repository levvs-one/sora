# 24. Блокировки CDN-фронтинга

Аналитик №24, отдел анализа ТСПУ/блокировок. Дата: 2026-10-20.
Только анализ, код не затронут. Проверенное — как факт; слухи помечены.

## 1. Что блокируется

**Классический домен-фронтинг (SNI ≠ Host) мёртв на всех крупных CDN.** Закрыт не цензором, а самими провайдерами:

- Cloudflare — запрещён с 2015 (проверка соответствия SNI и Host, иначе 403).
- Google — апрель 2018; AWS CloudFront — апрель 2018 (проверка связки SNI / Host / сертификат / distribution / аккаунт, ответ 421 при mismatch).
- Microsoft Azure Front Door / CDN — политика запрета с марта 2021.
- Akamai — также затронут.

То есть попытка фронтинга на крупной CDN сегодня отваливается на стороне CDN, до цензора дело не доходит.

**Наследники фронтинга и их статус:**

1. **ECH (Encrypted Client Hello), RFC 9849 (март 2026)** — «санкционированный фронтинг»: внешний ClientHello с публичным SNI, внутренний (с реальным именем) зашифрован. Ключ — через DNS HTTPS/SVCB-запись. Статус по странам: Россия — блокируется с ноября 2024 (см. раздел 3); Китай — блокируется «гибким» способом: режут DNS-маршруты для получения ECH-конфига, из-за чего ECH не может стартовать вообще (исследование CDT, 2025); Иран — та же тактика, блокировка bootstrap-DNS. Единственный крупный провайдер ECH долгое время — Cloudflare; в 2026 появилась самостоятельная реализация (OpenSSL 4.0, NGINX 1.29.4).
2. **«Тихий» фронтинг на мелких CDN / self-hosted reverse proxy** — по данным русскоязычного сообщества (MiraclePtr, пересказ в Habr-статье про XHTTP, 02/2026), *некоторые* CDN до сих пор допускают SNI/Host mismatch. Список таких CDN публично не верифицирован — считать слухом до проверки. У такого подхода нет главного преимущества классики — «не заблокируешь без колоссального collateral damage».
3. **Meek (Tor)** — исторически работал через крупные CDN; по плану Tor Project: переход Snowflake/Moat на Fastly, удаление Meek из встроенных опций (письмо anti-censorship-team). Фактически meek как массовый транспорт свёрнут.
4. **«Легитимный» CDN-трафик (свой домен на CDN, SNI == Host)** — это не фронтинг, а маскировка под обычный HTTPS-трафик CDN. Работает до тех пор, пока цензор не режет саму CDN (см. раздел 3: Россия режет Cloudflare целиком с июня 2025).
5. **XHTTP-сплит (Xray-core)** — наследник идеологии, а не техники: в режимах packet-up/stream-up потоки «туда» и «обратно» идут независимыми HTTP-сессиями, которые можно развести по разным транспортам (QUIC/HTTPS), IP-версиям, адресам, серверам, провайдерам, странам и доменам. Цензор видит два некоррелируемых «легитимных» потока.

## 2. Где: известные случаи

- **Россия, апрель 2018** — РКН заблокировал миллионы IP Google и AWS, чтобы остановить фронтинг Telegram; в ответ Google (14.04) и Amazon (27.04) отключили фронтинг у себя.
- **Россия, ноябрь 2024** — ТСПУ начал дропать соединения с ECH на Cloudflare: условие — SNI `cloudflare-ech.com` + присутствие ECH-расширения в ClientHello. РКН подтвердил; 7 ноября 2024 ГРЧЦ предписал российским операторам сайтов отключить ECH или переехать на отечественные CDN («расширение ограничено ТСПУ и нарушает закон»); повтор в апреле 2025.
- **Россия, март 2025** — региональные тесты разрыва соединений с Cloudflare. Замеры показали *селективную* блокировку ECH в связке с условиями Cloudflare, но не тотальную.
- **Россия, 9 июня 2025** — начало систематического троттлинга Cloudflare: первые 16 КБ проходят, дальше соединение рвётся. Затронуты HTTP/1.1, HTTP/2 (TCP+TLS) и HTTP/3 (QUIC), включая серверы за пределами РФ. Одновременно — блокировки диапазонов Hetzner, OVH, DigitalOcean. Cloudflare официально подтвердил, что троттлинг идёт со стороны российских ISP (Ростелеком, Мегафон, Вымпелком, МТС, МГТС) методами packet injection/blocking.
- **Россия, 2025–2026 (по открытым репортам)** — блокировки DoH/DoT (Google и Cloudflare DNS); февраль 2026 — удаление youtube.com и доменов WhatsApp из НСДИ (DNS-уровень поверх DPI-троттлинга).
- **Россия, февраль 2026 (community-репорт)** — для WARP-подключений к российским ДЦ Cloudflare: блокировка по паре SNI+IP (mailfence.com, tuta.com, mullvad.net и др.); к февралю 2026 mailfence «почти полностью заблокирован» — подключение к его IP с чужим SNI тоже не проходит в большинстве случаев. Признак эскалации от SNI-уровня к IP-уровню.
- **Китай** — DNS-отравление `edgecastcdn.net` (EdgeCast/Verizon) из-за «зеркал collateral freedom» Greatfire; GFW расшифровывает QUIC Initial для SNI-фильтрации (USENIX Security '25); ECH душится через блокировку DNS bootstrap, а не DPI handshake.
- **Иран** — блокировка DNS-маршрутов, нужных для получения ECH-конфига (CDT, 2025).
- **Слух (не верифицировано независимо):** коммерческий блог anyproxy.site (10/2026) сообщает о блокировке фингерпринтов VLESS в РФ «с декабря 2025» и о 400+ заблокированных VPN в 2026. Относиться как к неподтверждённому.

## 3. Как технически

### 3.1. Как цензор отличает фронтинг

1. **Видимость SNI — центральный механизм.** ТСПУ инспектирует TLS ClientHello и извлекает SNI; это первичный механизм селективной блокировки/троттлинга (пример: троттлинг `googlevideo.com` с августа 2024). Приказная практика РКН требует от операторов CDN **сохранять видимость SNI выше по цепочке** (TSPU-and-You, §3.2). То есть регулятор давит не только на сеть, но и на саму CDN-инфраструктуру.
2. **SNI/Host mismatch цензору отличать не нужно** — это уже делает CDN (403/421). Цензору остаётся ловить случаи, где CDN mismatch допускает (мелкие CDN) — там работает обычная связка SNI-блоклист + IP-блоклист.
3. **ECH детектируется в лоб:** пара (SNI=`cloudflare-ech.com`, ECH-расширение в ClientHello) → дроп. Это точечная сигнатура, а не блокировка всего ECH (AdGuard, 11/2024). GREASE ECH (фиктивное расширение для выравнивания fingerprint) существует именно против такого детекта — поведение ТСПУ против GREASE неизвестно.
4. **Корреляция SNI+IP:** наблюдения 2025–2026 показывают блокировки на уровне пары (SNI, IP назначения) с последующей эскалацией до блокировки IP целиком. Для обхода это значит: смена SNI при сохранении IP — временная мера.
5. **QUIC:** GFW (Китай) расшифровывает QUIC Initial и фильтрует по SNI внутри crypto-фрейма; у ТСПУ троттлинг Cloudflare покрывает и QUIC (июнь 2025).
6. **Таксономия блокировок ТСПУ (Xue et al. 2022, подтверждена практикой):** SNI-I — инжект RST; SNI-II — дроп; SNI-III — policing/шейпинг (сброс пакетов сверх лимита; так душили YouTube и так режут Cloudflare — 16 КБ, затем разрыв).

### 3.2. Блокировки IP-диапазонов CDN

- Цензор **готов** резать CDN целиком, несмотря на collateral damage: Россия-2018 (Google/AWS ради Telegram — не сработало против Telegram, ударило по банкам и приложениям), Россия-2025 (Cloudflare — троттлинг, а не полный блок: 16 КБ пропускают, чтобы «базовый HTML» работал, а медиа/туннели умирали).
- Китай предпочитает DNS-отравление имён CDN (дешевле, чем резать IP).
- Вывод: «не заблокируют CDN, слишком дорого» — больше не аксиома. Для Cloudflare в РФ она ложна с июня 2025.

### 3.3. Требования к SNI

- SNI должен быть видим (plain) — ECH объявлен вне закона для сайтов, обслуживающих РФ (предписание ГРЧЦ 11/2024, повтор 04/2025; законопроект Минцифры о запрете «протоколов шифрования, позволяющих скрывать имя сайта»).
- CDN, работающие с российскими пользователями, обязаны сохранять видимость SNI для ТСПУ (давление через реестр организаторов распространения информации: Cloudflare внесён, с требованиями хранить данные в РФ и дать доступ ФСБ).
- Практическое следствие: нельзя строить обход в расчёте на то, что «CDN скроет SNI» — регулятор требует обратного, и крупные CDN подчиняются.

## 4. Насколько надёжен известный обход

### 4.1. «Легитимный» CDN-трафик (свой домен на CDN, SNI == Host)

- **Против DPI handshake — надёжен:** соединение неотличимо от обычного HTTPS к сайту на той же CDN (тот же SNI, валидный сертификат, тот же IP anycast).
- **Против IP-троттлинга CDN — мёртв в РФ для Cloudflare:** с 09.06.2025 любой трафик через Cloudflare режется на 16 КБ независимо от транспорта (VLESS+WS, XHTTP — без разницы). Обход деградирует не из-за детекта протокола, а из-за деградации несущей.
- **Против скоринга серверов — уязвим:** по кейсу AmneziaWG (ТСПУ, лето 2025 – 2026) цензор перешёл от детекта протокола к идентификации серверов: скоринг по совокупности слабых признаков (в первую очередь объём трафика) → блокировка на уровне адреса/подсети, даже если протокол продолжает хендшейкаться. Концентрированный туннельный трафик на одном CDN-фронте попадёт под тот же скоринг.
- **Итог:** надёжность — средняя и падающая; работает, пока CDN не в прицеле и пока объём трафика не выделяется. Это обход «несущей», а не протокола.

### 4.2. XHTTP с downloadSettings и сплитом (Xray-core)

Что даёт (по Habr-обзору, 02/2026, и документации Xray-examples):

- **packet-up** — проходит почти через любой CDN/веб-сервер (куча коротких сессий вверх + одна длинная вниз); **stream-up** — по длинной сессии в каждую сторону, но требует cooperating сервер; **stream-one** — без сплита, только через nginx `grpc_pass` или Cloudflare с включённым gRPC (декой).
- **Независимая настройка направлений** (`downloadSettings`): вверх — QUIC, вниз — HTTPS; вверх — IPv6, вниз — IPv4; разные IP, разные серверы/хостинги/страны, разные домены. Корреляция двух направлений требует от цензора кросс-потокового анализа — на практике не делается.
- **Маскировка fingerprint:** сервер — реальный nginx (TLS 1.2 с настоящим fingerprint, Xray за ним); клиент — опционально browser dialer (TLS делает настоящий браузер через скрипт на странице) вместо uTLS-имитации.
- **CDN-агностичность:** работает через CDN без поддержки WebSocket/gRPC (слабое место классического VLESS+WS).

Ограничения и риски:

- **Только Xray-core.** Клиенты на sing-box XHTTP не поддерживают (статья прямо фиксирует; v2rayNG/v2raN — да). Для sora (ядро sing-box/mihomo) это архитектурный барьер, а не настройка.
- **Версии клиента и сервера должны совпадать** — иначе «странные глюки» или неработоспособность. Парк клиентов обновляется с задержкой (кейс Amnezia: 3–4 дня на app-store review в волны блокировок 2026).
- **Троттлинг CDN бьёт одинаково:** сплит через Cloudflare в РФ всё равно упрётся в 16 КБ.
- **Нет публичных замеров эффективности против актуального ТСПУ** — все заявления о «сильно усложняет блокировку» теоретические/анекдотические.
- **Скоринг по объёму** (см. 4.1) применим и здесь, если оба направления терминируются на инфраструктуре одного оператора.
- **Итог:** структурно самый сильный из известных обходов (ломает корреляцию потоков — главную опору DPI), но надёжность в проде не измерена, а в экосистеме sora упирается в отсутствие XHTTP в sing-box.

## 5. Что неизвестно / требует проверки

1. Какие именно «некоторые CDN» до сих пор допускают SNI/Host mismatch (утверждение MiraclePtr, пересказанное в Habr). Без списка это неприменимо.
2. Поддерживает ли sing-box XHTTP на октябрь 2026 (на май 2026 — нет). Если нет — какова цена портирования/обёртки xray-core.
3. Роняет ли ТСПУ ClientHello с GREASE ECH (фиктивное расширение) или только с настоящим ECH + `cloudflare-ech.com`.
4. Роняет ли ТСПУ *любое* ECH-расширение независимо от outer SNI (актуально для self-hosted ECH на nginx 1.29.4/OpenSSL 4.0).
5. Замеры: выживаемость XHTTP-сплита (все три режима) через ТСПУ 2026 — up/down через разные AS/домены. Публичных данных нет.
6. Подтверждение слухов о блокировке фингерпринтов VLESS в РФ с декабря 2025 (источник — один коммерческий блог).
7. Эволюция Cloudflare-троттлинга в 2026: остался ли лимит 16 КБ, расширился ли на другие CDN (Fastly? — критично для Snowflake/meek-наследников).
8. Реальна ли гипотеза «внутристрановой трафик не фильтруется» (Habr, 2026): первый хоп — дешёвый российский VPS, CDN — российский. Какие российские CDN пригодны и действительно ли их трафик вне DPI.
9. Детали «гибкой» блокировки ECH в Китае (что именно режут: DNS HTTPS-записи? DoH-резолверы?).
10. Умеет ли ТСПУ коррелировать разделённые потоки (up через один IP/AS, down через другой) — почти наверняка нет, но не проверено.
11. Статус ECH в TLS-стеке, используемом sora (поддержка клиентом outer/inner, доставка ECH-конфига без палевного DNS).

## 6. Проблемы для тех-агентов

- **P24-1.** Ядро sora — sing-box/mihomo; XHTTP — эксклюзив Xray-core (на 05/2026 sing-box не поддерживает). Требуется архитектурное решение: портировать XHTTP-транспорт в sing-box, держать второй core (xray) ради одного транспорта, или отказаться от XHTTP-сплита как обхода.
- **P24-2.** Любой обход на Cloudflare в РФ деградирует с 09.06.2025 (троттлинг 16 КБ → разрыв, TCP и QUIC). Нельзя проектировать «CDN-обход» с дефолтом на Cloudflare для российских пользователей; нужен выбор CDN per-region и детект троттлинга на клиенте.
- **P24-3.** Классический фронтинг (SNI ≠ Host) отклоняется самими CDN (Cloudflare 403, AWS 421, Azure policy). Реализация не должна рассчитывать на mismatch на крупных CDN — это мёртвый путь, а не «запасной».
- **P24-4.** ECH по схеме Cloudflare (`cloudflare-ech.com` + ECH extension) дропается ТСПУ с 11/2024. Если использовать ECH — только self-hosted (свой outer SNI/ключи) и только после проверки п. 5.4 (режет ли ТСПУ любое ECH-расширение).
- **P24-5.** РКН требует от CDN сохранять видимость SNI (реестр ОРИ, предписания). Обход, требующий от CDN скрывать SNI, — это ставка против регулятора, которую крупные CDN проигрывают. Проектировать исходя из видимого SNI.
- **P24-6.** Тактика РКН сместилась: от сигнатур протоколов — к скорингу серверов по объёму трафика и блеклистингу подсетей (кейс AmneziaWG 2025–2026). CDN-обход с высокой концентрацией пользователей на одном фронте будет заблокирован по IP/подсети безотносительно маскировки. Нужны: распределение нагрузки, ротация фронтов, лимиты «плотности» пользователей на endpoint.
- **P24-7.** XHTTP-сплит даёт выигрыш, только если направления реально некоррелируемы: разные IP **и** разные AS/провайдеры **и** желательно разные домены. Сплит «два IP одного хостера» — фикция против скоринга по подсети. Клиенту нужен механизм валидации некоррелируемости пары (up, down).
- **P24-8.** Режимы XHTTP имеют разную CDN-совместимость: stream-one — только nginx `grpc_pass` / Cloudflare gRPC; stream-up — не везде; packet-up — почти везде, но медленнее и шумнее (множество коротких сессий). Нужен авто-фолбэк между режимами при смене CDN/сервера, а не один захардкоженный режим.
- **P24-9.** XHTTP требует совпадения версий Xray на клиенте и сервере; рассинхрон парка (app-store review 3–4 дня) в волну блокировок = простой. Нужна либо версионная независимость протокола, либо механизм удалённого переключения транспорта без обновления клиента.
- **P24-10.** Проверить гипотезу «российский first hop + российская CDN»: действительно ли внутристрановой CDN-трафик не подвергается DPI ТСПУ; какие отечественные CDN технически пригодны для проксирования (WebSocket/XHTTP-совместимость, терпимость к abuse).
- **P24-11.** Для Китая: ECH убивается через DNS (блокировка HTTPS/SVCB-записей с конфигом), а не через DPI. Любой ECH-зависимый обход для Китая обязан решать доставку ECH-конфига в обход цензорного DNS (встроенный конфиг, DoH через незаблокированный резолвер) — иначе ECH мёртв на старте.
- **P24-12.** QUIC в Китае: GFW расшифровывает QUIC Initial и фильтрует по SNI. XHTTP-режим «вверх по QUIC» светит SNI так же, как обычный TLS. Для Китая QUIC-направление требует либо ECH (см. P24-11), либо отказа от QUIC в пользу TCP+TLS.
- **P24-13.** Проверить слух о блокировке фингерпринтов VLESS в РФ (12/2025). Если подтвердится — одной маскировки «под легитимный HTTPS» недостаточно: клиенту нужен уровень имитации TLS не хуже browser dialer (реальный браузерный TLS), а uTLS-профилей может не хватить.
- **P24-14.** Исследовать GREASE ECH как способ прохождения точечной сигнатуры ТСПУ (ECH extension + конкретный outer SNI): дропает ли ТСПУ ClientHello с фиктивным ECH-расширением; можно ли на нём построить «серый» ECH-транспорт.
