## 1. Эволюция zapret: tpws → nfqws / winws / dvtws, что изменилось

**tpws (transparent proxy, L7, stream-level).** Исторически первый движок zapret. Работает как прозрачный TCP-прокси: принимает соединение целиком, модифицирует поток на уровне приложения и проксирует дальше.
- HTTP: `--hostcase`, `--hostdot`, `--hosttab`, `--hostpad` (игры с регистром Host, точкой в конце, табуляцией, паддингом).
- TLS: `--tlsrec` (разрез TLS-записи), `--mss`, `--oob` (out-of-band данные), `--disorder` (перестановка сегментов), `--fix-seg`.
- Плюсы: работает на любой платформе с сокетами, не требует root (кроме macOS, где нужен root для PF).
- Минусы: выше задержка и CPU (полный прокси потока), невозможна точная попакетная манипуляция.

**nfqws (Linux, NFQUEUE) — главный движок с ~2019 и поныне.** Работает на уровне отдельных пакетов L3/L4 через netfilter NFQUEUE: пакет перехватывается, обрабатывается в userspace, возвращается в стек с вердиктом (ACCEPT/DROP/модифицированный).
- Не собирает TCP-поток целиком: L7-диссекция (HTTP Host, TLS SNI, QUIC Initial) делается по первым пакетам без полной реассембли.
- Ниже задержка и CPU, чем у tpws; точная манипуляция сегментацией, порядком, IP-фрагментацией, таймингом.
- Требования: root, правила iptables/nftables, гонящие трафик в очередь (`--qnum`).

**winws (Windows)** — тот же код nfqws, собранный под Windows, перехват через драйвер WinDivert (свой фильтр-язык, уровень `WINDIVERT_LAYER_NETWORK`). Нужны права администратора, часты конфликты с антивирусами (WinDivert детектируется). Не перехватывает форвардящийся трафик — только локальный.
**dvtws (FreeBSD/OpenBSD)** — тот же код, divert-сокеты (`IPPROTO_DIVERT`).
**macOS** — только tpws (root, PF). **Android** — только tpws через сторонние обёртки (VPN API); пакетного уровня нет.

**zapret2 (2025–2026, репозиторий bol-van/zapret2).** Новое поколение: стратегии десинхронизации задаются цепочками Lua-функций (`--lua-desync`), скрипт `zapret-auto.lua` — оркестрация и детект сбоев. Бинарники `nfqws2`/`dvtws2`/`winws2`. Появилась концепция **циклической ротации стратегий** (`circular:fails=3:maxtime=60`) как ответ на пере-блокировки. Классический синтаксис `--dpi-desync=` сохранён для совместимости, но развитие идёт в Lua-сторону.

Ключевая концептуальная рамка из официальной документации, актуальная для всех поколений: **passive DPI** (слушает, инжектит RST/редиректы, дропать не может) vs **active DPI** (in-line, может дропать). zapret атакует именно дешёвую модель DPI: десинхронизирует его трекинг соединения, а конечный сервер при этом корректно реассемблирует поток.

## 2. Где применяется / против кого

zapret применяется **только там, где DPI обязан увидеть handshake/начало потока, чтобы классифицировать соединение**: SNI в TLS ClientHello, Host в HTTP, SNI/DCID в QUIC Initial, STUN/Discord-voice сигнатуры.

Проверенные (полевые данные 2025–2026) кейсы:
- **YouTube**: замедление через ТСПУ (2024→2026). Работает десинхронизация handshake к `youtube.com`, `googlevideo.com`, `ggpht.com`, `youtubei.googleapis.com` — как по TCP 443, так и по QUIC/UDP 443.
- **Discord**: блокировка с 10.2024 — текст/медиа (TCP 443, Cloudflare-fronted) и голос (UDP 50000–50099, STUN-подобный трафик). Для голоса — фейковые UDP-пакеты.
- Любой SNI-блок веба: instagram, twitter/x, rutracker и т.д. — через hostlist-профили.
- Игровой/прочий UDP-трафик: `--dpi-desync-any-protocol`, fake unknown UDP.

Где zapret **неприменим в принципе**:
- Блокировка по IP-адресу назначения (routing blackhole / null-route) — десинхронизация не меняет destination IP.
- DNS-подмена/спуфинг без DPI на соединении (лечится DoH, не zapret).
- Активный in-line DPI, который дропает **весь** поток по IP/паттерну после классификации — см. раздел 4.

Позиция команды zapret (wiki.zapret.moe, дословно по смыслу): *универсального рецепта не существует; успех зависит от провайдера; провайдер обновляет ТСПУ — ранее рабочая стратегия становится "видимой" и перестаёт работать; обновления zapret старых стратегий не ломают, только добавляют новые.* Это важно: подбор стратегии — всегда per-ISP.

## 3. Как технически: ключевые стратегии

### 3.1. Трёхфазная модель nfqws (из исходников nfq/desync.c, nfq/params.h)

`--dpi-desync=[mode0,]mode[,mode2]`:
- **Phase 0 (handshake):** `synack`, `syndata` — манипуляции на этапе установления (например, данные прямо в SYN).
- **Phase 1 (до оригинального пакета):** `fake`, `rst`, `hopbyhop`, `ipfrag1` — вброс пакетов-приманок, ломающих состояние DPI.
- **Phase 2 (на оригинальном пакете):** `multisplit`, `disorder`, `multidisorder`, `ipfrag2`, `udplen` — изменение структуры легитимного трафика.

Плюс **мультипрофильность**: `--new` разделяет независимые профили (фильтры L3/L4/L7 + hostlist/ipset + своя стратегия). Первый совпавший профиль применяется. Типичный набор: TCP 80 / TCP 443 / UDP 443 / UDP 50000–50099 (Discord voice).

Обрабатываются только первые N пакетов соединения (`NFQWS_TCP_PKT_OUT=6`, `NFQWS_UDP_PKT_OUT=6`, `NFQWS_TCP_PKT_IN=3`) — дальше соединение отпускается без обработки. Это осознанный трейд-офф: DPI тоже смотрит в основном начало.

### 3.2. Ключевые стратегии и параметры

| Стратегия | Механика | Против чего |
|---|---|---|
| `fake` | Вброс фейковых пакетов перед оригиналом. DPI "залипает" на фейке (например, видит безобидный SNI), настоящий пакет проходит. Сервер фейк отбрасывает | DPI, который классифицирует по первому увиденному handshake |
| `split2` / `multisplit` | Разрез L7-пейлоада (ClientHello) на 2/N TCP-сегментов в позиции `--dpi-desync-split-pos` (`1`, `2`, `3`, `midsld` — середина домена 2-го уровня). Опция `--dpi-desync-split-seqovl` — перекрытие по sequence number | DPI без TCP-реассембли |
| `disorder2` / `multidisorder` (+`fakeddisorder`) | Отправка сегментов не по порядку; DPI с линейной моделью не может собрать сообщение | Stateful DPI с упрощённой реассембли |
| `fakedsplit` | Комбинация fake + split | Более агрессивные DPI |
| `syndata` | Данные в TCP SYN | DPI, не ожидающий данных в handshake |
| `fooling=badseq` | Фейк с sequence number вне окна — сервер отбрасывает, DPI обрабатывает | Универсальный фулинг |
| `fooling=badsum` | Фейк с неверной TCP-checksum — сервер отбрасывает, DPI обрабатывает | То же; на некоторых сетях checksum проверяется раньше DPI **[требует проверки на конкретном ISP]** |
| `fooling=md5sig` | Добавление TCP-опции MD5-сигнатуры — сбивает парсеры DPI | DPI с хрупким TCP-парсером |
| `autottl` (`--dpi-desync-autottl=2..4`) | Автоподбор TTL фейка: пакет доходит до DPI, но умирает раньше сервера | Нужно, когда badseq/badsum фильтруются; чувствительность — компромисс ложных срабатываний |
| QUIC-десинхронизация | UDP 443: `--dpi-desync=fake,disorder2` (или `fake,split2`) + `--dpi-desync-fake-quic=quic_initial_www_google_com.bin` (готовый QUIC Initial), `--dpi-desync-repeats=6..10`, `--dpi-desync-udplen-pattern=0xCAFEBABE` / `--dpi-desync-udplen-increment=15` (порча UDP length) | DPI, классифицирующий QUIC по Initial (DCID/SNI) |
| `fake-tls-mod` | Генерация фейкового ClientHello на лету: `rnd` (рандомизация), `rndsni` (случайный SNI), `dupsid` (дубль session id), `padencap` (паддинг), `sni=www.google.com` (подмена SNI) | Нужен правдоподобный фейк без хранения бинарников |

Повторы: `--dpi-desync-repeats=6..11` — сколько раз слать фейк/применять десинхронизацию (надёжность против "шума").

### 3.3. Рабочие рецепты 2026 (community, Flowseal zapret-discord-youtube, StressOzz-пресеты)

Это **стартовые точки, не гарантии** (см. принцип "нет универсального рецепта"):

**Базовый general (Windows, winws):**
- TCP 80: `--dpi-desync=fake,split2 --dpi-desync-autottl=3 --dpi-desync-fooling=badseq`
- TCP 443: `--dpi-desync=syndata,split2 --dpi-desync-split-pos=2 --dpi-desync-repeats=8 --dpi-desync-fooling=md5sig --dpi-desync-fake-tls=tls_clienthello_www_google_com.bin`
- UDP 443 (QUIC): `--dpi-desync=fake,disorder2 --dpi-desync-repeats=8 --dpi-desync-udplen-pattern=0xCAFEBABE --dpi-desync-fake-quic=quic_initial_www_google_com.bin`

**FAKE TLS AUTO (агрессивный):** `--dpi-desync=fake,multidisorder --dpi-desync-split-pos=1,midsld --dpi-desync-fake-tls-mod=rnd,dupsid,sni=www.google.com --dpi-desync-repeats=11 --dpi-desync-ttl=4`

**StressOzz v1 (OpenWrt, nfqws):** TCP 443 `--dpi-desync=fake,multidisorder --dpi-desync-split-seqovl=681 --dpi-desync-split-pos=1 --dpi-desync-fooling=badseq --dpi-desync-fake-tls-mod=rnd,dupsid,sni=fonts.google.com --dpi-desync-fake-tls=tls_clienthello_www_google_com.bin`; UDP 443 `--dpi-desync=fake` ×6 с `quic_initial_www_google_com.bin`.

**Discord voice (UDP 50000–50099):** `--filter-l7=discord,stun --dpi-desync=fake`; в zapret2 есть готовые WinDivert-фильтры (`udp.DstPort 50000–50099 and PayloadLength=74`).

### 3.4. blockcheck-методика подбора стратегии

`blockcheck.sh` / `blockcheck2.sh` — штатный инструмент перебора **всех** стратегий против конкретного домена:
1. **Резолв** домена через `mdig`; при детекте DNS-спуфинга — автоматический переход на DoH (`SECURE_DNS=1`).
2. **Прогон по уровням протокола**: plain HTTP → HTTPS TLS 1.2 (`--tls-max 1.2`, `sec=1`: сертификат сервера виден DPI — самый сложный кейс) → HTTPS TLS 1.3 (`sec=2`, ServerHello зашифрован — легче) → HTTP/3 QUIC (UDP 443, отдельный таймаут).
3. Для каждого уровня перебираются сначала tpws-стратегии (`--hostcase`, `--tlsrec`, `--oob` и т.д.), затем nfqws/winws (`--dpi-desync=...`). Стратегия применяется через временные iptables-правила в очередь, тест — curl с таймаутом, признаки вмешательства DPI: RST, редиректы, таймауты, подозрительные ответы.
4. **Уровни сканирования**: `quick` (стоп на первом успехе), `standard` (все стратегии категории), `force` (всё подряд, для исследований).
5. **Отчёт**: строки вида `ipv4 youtube.com curl_test_https_tls13 : nfqws --dpi-desync=multisplit --dpi-desync-split-pos=1`; дедупликация по MD5-хэшу стратегии — выводятся только стратегии, сработавшие для **всех** тестовых доменов.

Практический вывод для sora: blockcheck — эталонная методология, но полный прогон занимает ~час; для клиентского UX нужен сокращённый эвристический вариант (см. P31-1).

## 4. Надёжность и ограничения

**Главное ограничение: mid-stream троттлинг по паттерну.** По свежему разбору механики ТСПУ (orion-int.ru, 10.2026):
- ТСПУ ведёт запись соединения по 5-tuple и **умеет собирать ClientHello из нескольких TCP-сегментов** — простой разрез `split` против такого DPI уже не работает ("после сборки фильтр получает полное имя").
- Вместо полного запрета ТСПУ может **троттлить**: (а) через очередь — пакеты ждут; (б) через дроп части пакетов — TCP видит потери как перегрузку и снижает темп (даже небольшая доля искусственных потерь сильно режет скорость); (в) **разрешить начальный объём, а дальнейшую передачу ограничить** — короткий запрос работает, видео/файл виснет.
- Все пакетные трюки zapret действуют на **фазе handshake** (первые ~6 пакетов). Если DPI классифицировал соединение любым способом (собранный ClientHello, IP сервера `googlevideo.com`/GGC, статистический паттерн потока) и дальше просто **режет скорость уже классифицированного потока** — fake/split/disorder бессильны: нечего десинхронизировать, поток уже помечен.
- Следствие для YouTube: сайт (`youtube.com`) может грузиться через десинхронизацию, а плеер (`googlevideo.com`) — висеть на бесконечной буферизации. Это не "плохая стратегия", это другой класс воздействия.

**Другие проверенные ограничения:**
- Нет универсального рецепта; стратегии протухают при обновлениях ТСПУ (заявление ZapretTeam).
- `wssize` (подмена TCP window size на handshake) — крайняя мера: замедляет **все** соединения на фильтруемых портах и не работает с hostlist.
- Часть техник ломает NAT; `badsum`-фулинг может отфильтровываться раньше DPI на некоторых сетях.
- winws требует установки драйвера WinDivert с правами администратора; конфликты с антивирусами и с VPN в TUN-режиме (TUN перехватывает трафик раньше/вместе — фейки внутри туннеля бесполезны).
- Обрабатываются только первые пакеты соединения; долгоживущие соединения после re-handshake/re-key могут переклассифицироваться.

**[слух, требует проверки]:** двухстадийная модель ТСПУ — центральный анализ и рассылка обновлённых списков каждые 5–15 минут (отсюда идея циклической ротации стратегий в zapret2); ночные реконфигурации ТСПУ (по Москве); паритет инспекции IPv6 с 03.2026. Источник — community knowledge base (rcd27/zapret2-mcp), не официальная документация.

## 5. Что неизвестно / требует проверки

1. **Глубина реассембли современного ТСПУ**: сколько сегментов/байт ClientHello буферизует DPI перед классификацией; от этого зависит, какие `split-pos`/`seqovl` ещё живы. Нужны полевые замеры через blockcheck `force` на живых ISP.
2. **Поколения fooling'а**: какие DPI уже игнорируют `badsum`/`badseq`/`md5sig` (фильтруют фейки до анализа). Данных в открытом виде нет.
3. **Точный механизм YouTube-троттлинга**: классификация по SNI `googlevideo.com`, по IP GGC-кэшей, по статистике потока — от этого зависит, лечится ли вообще на уровне пакетов или только сменой egress (другой IP/маршрут).
4. **Статус zapret2**: степень зрелости Lua-движка и `zapret-auto.lua` в проде; совместимость стратегий v1↔v2.
5. **QUIC vs TCP fallback**: как браузеры/клиенты ведут себя при десинхронизации только одного транспорта; риск петель fallback.
6. **[слух]** Цикл пере-блокировки 5–15 минут и ночные реконфигурации — подтвердить измерениями.

## 6. Проблемы для тех-агентов

Конкретные технические проблемы, требующие решения при интеграции zapret-подхода в sora:

- **P31-1. Автоподбор стратегии без часового blockcheck.** Нет универсального рецепта; стратегия — per-ISP и протухает. Нужен встроенный в sora быстрый probing-протокол (сокращённая эвристика blockcheck: HTTP/TLS1.2/TLS1.3/QUIC × топ-N стратегий) с кэшированием результата на ISP/сеть и перепроверкой при деградации.
- **P31-2. Платформенная матрица перехвата.** nfqws требует root+NFQUEUE (только Linux), winws — драйвер WinDivert с правами админа (конфликты с антивирусами), на Android/macOS пакетного уровня нет вообще (только tpws-режим). Требуется: таблица возможностей по ОС, graceful degradation, для Android — исследование реализуемости десинхронизации без NFQUEUE (userspace TCP-стек?).
- **P31-3. Корпус фейковых ClientHello.** `fake-tls-mod` (rnd/rndsni/dupsid/padencap/sni=) и бинарники `quic_initial_*.bin`/`tls_clienthello_*.bin` протухают (меняются реальные handshake'и, DPI учится отличать фейки). Нужен обновляемый генератор правдоподобных фейков, а не статичные бинарники.
- **P31-4. Автокалибровка TTL (autottl).** Дистанция до DPI в хопах разная на ISP/маршрут; неверный TTL = фейк доходит до сервера (ломает соединение) или не доходит до DPI (не работает). Нужен безопасный алгоритм автоподбора TTL без разрыва пользовательских соединений.
- **P31-5. Детект mid-stream троттлинга vs handshake-блока.** Пакетные трюки лечат только классификацию на handshake. Нужен классификатор деградации: если handshake пробит, а скорость режется дальше (паттерн "начало быстро → потом виснет") — переключаться на другую тактику (смена транспорта/egress для googlevideo, отключение QUIC, маршрутизация через прокси только медиа-потока), а не перебирать desync-стратегии вхолостую.
- **P31-6. Протухание стратегий и канал обновлений.** ТСПУ обновляется — стратегии умирают. Нужны: механизм доставки обновлённых пресетов (с подписью, см. требования к прозрачности sora) + телеметрия успешности стратегий + ротация (подход `circular` из zapret2: fails=3, maxtime=60).
- **P31-7. Согласованность QUIC и TCP стратегий.** Браузер падает с QUIC на TCP при неудаче; десинхронизация только UDP 443 или только TCP 443 даёт петли fallback и "мигающий" YouTube. Стратегии для обоих транспортов должны тестироваться и применяться парой.
- **P31-8. Бюджет пакетов и долгоживущие соединения.** zapret обрабатывает первые ~6 пакетов; видео/голос живут часами, re-handshake и re-key могут переклассифицировать поток. Нужна политика повторного применения/мониторинга состояния соединения.
- **P31-9. Hostlist-менеджмент и auto-hostlist.** Списки доменов (youtube, googlevideo, ggpht, youtubei, discord, ...) меняются; auto-hostlist требует детекта сигнатур вмешательства DPI (RST, редиректы, таймауты) без ложных срабатываний на обычные сетевые ошибки.
- **P31-10. Конфликт с TUN/VPN-режимом sora.** Фейковые пакеты внутри зашифрованного туннеля невидимы для DPI и бессмысленны; TUN-драйвер конкурирует с WinDivert/NFQUEUE за трафик. Требуется сплит: десинхронизация — только на прямом (не туннелированном) пути; чёткий приоритет и взаимоисключение режимов в UI.
- **P31-11. IPv6.** Стратегии применяются явно и отдельно; утёкший IPv6-трафик идёт мимо десинхронизации. Нужна паритетная обработка IPv6 или контролируемое отключение.
- **P31-12. Выбор fooling'а (badseq vs badsum vs md5sig) в рантайме.** Разные поколения DPI фильтруют фейки по-разному; неверный fooling = либо не работает, либо ломает легитимные соединения. Нужен A/B-подбор fooling на этапе P31-1, а не хардкод.
