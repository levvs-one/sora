# 03 — Блокировки по IP/подсетям (ТСПУ/реестр РКН)

Аналитик №3. Анализ на основе публичных источников 2025–2026 (измерения и реверсы — в приоритете, блоги — во вторую очередь). Непроверенные утверждения помечены как слухи.

## 1. Что блокируется / как проявляется

**Реестр.** «Единый реестр запрещённой информации» (eais.rkn.gov.ru, ФЗ «Об информации»): записи содержат домены, URL, реже — IP-адреса. Внесение IP в реестр «на практике происходит очень редко» (habr.com/ru/articles/1045074, 2026). Реестр обновляется 2 раза в сутки (порядок с 2012 года), выгрузка доступна операторам круглосуточно, операторы обязаны ограничить доступ в течение суток с момента внесения (tadviser, gov.tadviser.ru).

**«Ковровые» блокировки подсетей — новый доминирующий инструмент против VPN.** С августа 2026 РКН перешёл от точечных блокировок по сигнатурам к блокировке целых подсетей хостеров, где сосредоточены популярные VPN: регулятор «выявил несколько десятков автономных систем, где хостятся популярные VPN, и заблокировал относящиеся к ним подсети целиком» (te-st.org, «Разбор №37», 30.09.2026). Летом 2026 таким образом ограничена работа 20+ популярных VPN-сервисов (Paper VPN, VPN Legend, GaMMa VPN, LTVPN, ABS, FoxyBot, VPN Generator — по данным «Новой Газеты Европа»).

**Как проявляется блокировка IP/подсети для клиента:** симметричная картина — либо таймаут без ответа (ТСПУ «перестаёт маршрутизировать пакеты данной сессии», клиент висит до таймаута), либо инъекция TCP RST обеим сторонам (te-st.org, 09.2026). При троттлинге Cloudflare — проходит первые 16 КБ, затем соединение обрывается (Cloudflare, июнь 2025). Важный нюанс: многие блокировки срабатывают уже после успешного резолвинга имени — то есть на L3/L4, а не на DNS (kipo.editorum.ru, 2026).

**История:** прецедент «ковровых» блокировок — апрель 2018, Telegram: ~11 млн IP-адресов (AWS, Google Cloud и др.), массовый коллатеральный ущерб. Техника не нова, но в 2025–2026 масштабируется и систематизируется.

## 2. Где: регион, операторы, условия; различия выгрузок

- **Неравномерность по операторам и регионам — фундаментальный факт.** Измерения Cloudflare (июнь 2025): троттлинг применяли Rostelecom, Megafon, Vimpelcom, MTS, MGTS — техниками «packet injection and blocking, leading to connection timeouts». Пользовательские репорты 2025–2026 показывают различия: одни подсети недоступны на МТС, но доступны на Ростелекоме и наоборот; одни регионы — точечные тесты (март 2025 — тесты блокировки Cloudflare в отдельных регионах; Beeline — тесты DoH-блока, март 2025), другие — полный набор.
- **Выгрузки неоднородны.** Официальный реестр — это лишь один канал. RKS Global / HRW (2025): «значительная часть ограничений не отображается в официальных реестрах, а применяется операторами самостоятельно на основе технических сигнатур» — и по спискам, рассылаемым вне реестра (поручения ГРЧЦ, как в кейсе MikroTik — «первое поручение ГРЧЦ» от 11.09.2026, te-st.org). Плюс ТСПУ как централизованный контур: подписи и блокировки доводятся через ЦМУ ССОП/ГРЧЦ напрямую на оборудование ТСПУ, минуя публичный реестр. Итог: один и тот же IP может быть недоступен у одного оператора и доступен у другого.
- **Белые списки (2025–2026).** С 5 сентября 2025 Минцифры ведёт «белый список» для периодов отключений мобильного интернета: default-deny, разрешены только перечисленные сервисы; к весне 2026 — за сотню сервисов (ateo.digital, 2026). При белом списке IP-блокировка не нужна как отдельный механизм — всё, что не в allow-list, падает в никуда. Это другой режим работы тех же ТСПУ, и он делает бессмысленным «смену IP» как обход.
- **Скорость внесения.** Публичный реестр: 2 выгрузки в сутки + сутки на внедрение у оператора → до ~48 часов лаг. Внесудебные блокировки через ГРЧЦ/ТСПУ: быстрее, но точных публичных измерений скорости нет (см. раздел 5). По косвенным данным (волны блокировок VPN — конец сентября 2026, te-st.org): от идентификации до массового эффекта — дни, не недели.

## 3. Как технически: механизмы, скорость, коллатеральный ущерб

**Механизмы (подтверждено измерениями, не реверсом вендора ТСПУ):**
1. **ACL на ТСПУ/DPI на границе оператора.** ТСПУ стоит на стыках сетей операторов (декреты «суверенного рунета», с 2019). Фильтрация по destination IP / префиксу: drop (тихий, без ICMP) или TCP RST injection. Censored Planet (IMC'22) показал stateful-поведение ТСПУ: срабатывание на ClientHello с определённым SNI/IP. IP-уровень — самый дешёвый для ТСПУ (не требует разбора L7).
2. **BGP blackhole / null-route (слух/не подтверждено для цензуры).** В операторских сетях стандартная практика RTBH: next-hop на 192.0.2.1/198.18.0.0/15 с null-route, распространение через iBGP (RFC 3882). Для ТСПУ-цензуры публичных подтверждений использования BGP blackhole нет — все наблюдаемые эффекты совместимы с ACL на DPI-боксах. Но механизм технически доступен: оператор может вносить null-route на префиксы по требованию быстрее, чем переконфигурировать ACL на всём парке ТСПУ.
3. **Троттлинг как «мягкая» блокировка.** Cloudflare, июнь 2025: 16 КБ проходят, дальше обрыв. Это не чистая IP-блокировка, а rate-limit/shape на ТСПУ по IP-назначению — юридически «не блокировка», практически — недоступность.

**Коллатеральный ущерб (измерено):**
- Март 2025: массовые сбои при начале блокировок IP Cloudflare — YouTube, Duolingo, Twitch, приложение Сбербанка (HRW, 07.2025). РКН списал на «неисправность иностранной серверной инфраструктуры».
- Июнь 2025: официальный старт системного троттлинга Cloudflare; под удар также Hetzner, OVH, DigitalOcean — «network ranges associated with these services have been blocked» (securityonline.info).
- RU-CENTER: Cloudflare — ~44% CDN-делегирования .ru-доменов и ~11% .ru-сайтов (criticalinfralab.net, 2026). Блокировка подсетей Cloudflare бьёт по российскому же вебу.
- Январь 2025: сбой после обновления ТСПУ — недоступны госсайты, сервисы Google; решено обходом ТСПУ (HRW). Февраль 2024: массовый сбой мессенджеров и Госуслуг — зампред комитета ГД связал с «настройкой ТСПУ».
- Вывод для анализа: регулятор принимает коллатеральный ущерб как цену; «ковровые» блокировки 2026 года идут по тому же пути.

**Скорость внесения (оценочно):** публичный реестр — до 48 ч до эффекта у оператора; централизованные команды ТСПУ — часы–дни (по скорости волн блокировок VPN осенью 2026). Точных замеров «время от появления IP до его блокировки» в открытых источниках нет.

## 4. Насколько надёжен известный обход

- **Смена IP внутри той же подсети/AS — ненадёжна с августа 2026.** Блокируются подсети целиком (по данным te-st.org — «несколько десятков автономных систем» целиком). Смена IP помогает только против точечных блокировок отдельных адресов.
- **Смена IP на другую подсеть/AS — работает, но окно сужается.** РКН накапливает статистику по IP и выявляет новые AS (te-st.org: «при помощи крупных ИТ-компаний накопил статистику по IP-адресам»). Практика VPN-сервисов 2026: постоянная ротация пулов (ExpressVPN-подобная модель «динамические IP + замена заблокированных»). Для sora это означает: пул должен быть разнородным по AS/географии, с автоматической заменой выбывших.
- **Anycast — двойственно.** Плюсы: один IP анонсируется из многих точек; блокировка anycast-префикса бьёт по легитимному трафику CDN (Cloudflare) — регулятор колеблется (см. коллатеральный ущерб). Минусы: (а) anycast-IP легко идентифицируется как принадлежащий CDN/VPN-инфраструктуре; (б) для long-lived VPN-сессий anycast нестабилен — смена маршрута рвёт соединение (nottldr.com, 2025: «reserve anycast for short-lived or stateless transactions»); (в) РКН уже блокирует anycast-префиксы Cloudflare без колебаний с 2025. Итог: anycast — не панацея, хорош как один из слоёв (первичное подключение/дискавери), плох как транспорт долгоживущих туннелей.
- **ECMP / мультипутинг — не обход IP-блокировки.** ECMP распределяет потоки внутри одной AS между равными путями, но destination IP остаётся тем же — ACL на ТСПУ срабатывает независимо от пути. ECMP релевантен только против троттлинга/потерь на конкретных линках, не против блокировки префикса.
- **Что реально работает против IP-блокировок (по состоянию на 10.2026):**
  1. Свежие IP в «чистых» AS, ещё не попавших в статистику РКН (окно — недели/месяцы).
  2. Маскировка под легитимный трафик к незаблокированным IP (VLESS+Reality с донором): блокировка идёт не по IP сервера, а по сигнатуре — но если серверный IP уже в ковровой блокировке, не поможет.
  3. Доменные фронты на незаблокированных CDN — сужается (Cloudflare под троттлингом с 06.2025).
  4. IPv6: отдельный вектор; измерений покрытия блокировок по IPv6 в открытых источниках нет (см. раздел 5).
- **Белый список убивает все IP-обходы сразу.** При default-deny смена IP, anycast, ECMP — всё бессмысленно. Обход возможен только через адреса/сервисы из allow-list (проксирование через разрешённые CDN/домены — «обход белых списков», ateo.digital, 2026).

## 5. Что неизвестно / требует проверки

1. **Точный механизм внесения IP-блоков:** ACL на ТСПУ vs BGP null-route vs списки на BRAS/BNG операторов. Публичных реверсов/утечек конфигов ТСПУ нет. Нужны измерения: traceroute до заблокированного IP с разных операторов (где обрыв — на границе AS, внутри, на ТСПУ-хопе), ICMP-behavior (тихий drop vs unreachable), BGP looking glasses (есть ли more-specific / blackhole community).
2. **Скорость от идентификации IP до блокировки:** нет открытых замеров. Нужен эксперимент: поднять свежий IP, анонсировать как VPN-точку, замерять время до недоступности с разных операторов.
3. **Гранулярность «ковровых» блокировок:** /24? /20? целые AS? Известен факт блокировки «подсетей целиком», точные маски не публиковались.
4. **Покрытие IPv6:** блокируются ли IPv6-префиксы теми же списками? Открытых измерений нет.
5. **Различия выгрузок между операторами:** нет систематического сравнения списков (реестр vs поручения ГРЧЦ vs локальные ACL). Нужен мульти-операторский сканинг.
6. **Критерии снятия блокировки с подсети:** как AS выходит из-под «ковровой» блокировки, есть ли процедура апелляции для хостера.
7. **Роль «крупных ИТ-компаний» в сборе статистики по VPN-IP** (te-st.org, 09.2026): какие именно компании, какие данные передаются — важно для threat model (телеметрия в российских приложениях, собирающих список установленных VPN — RKS Global, весна 2026).
8. **SNI+IP связки:** community.cloudflare.com (02.2026): блокировки срабатывают на пары SNI+IP, причём смена SNI на тот же IP иногда помогала, иногда нет. Механика неясна.

## 6. Проблемы для тех-агентов

- **P03-1. Детектор IP-блокировки в клиенте.** Нужен механизм различения в рантайме: точечный сбой / блокировка IP (таймаут+RST на L3) / блокировка подсети / троттлинг (16КБ-паттерн) / белый список (всё недоступно). Без этого невозможен осмысленный фолбэк. Требуется: набор проб (TCP-handshake тайминги, ICMP, TLS ClientHello с разными SNI, замер throughput первых 64КБ), классификатор исходов.
- **P03-2. Мульти-операторский мониторинг доступности серверных IP.** Один и тот же IP доступен/недоступен в зависимости от оператора и региона (раздел 2). Нужна система проб с российских vantage points (разные операторы: МТС, Билайн, Мегафон, Ростелеком, Tele2; фиксированная + мобильная связь), иначе нельзя понять, «упал сервер» или «заблокировали у оператора X».
- **P03-3. Автоматическая ротация серверных IP/подсетей.** С августа 2026 блокируются подсети целиком; пул в одной AS выгорает разом. Требуется: разнородный пул (несколько AS, несколько гео), health-check изнутри РФ, автоматический вывод сгоревшей подсети и ввод свежих IP, желательно без пересборки клиента (конфиг/подписка).
- **P03-4. Стратегия «чистых» AS.** РКН выявляет AS по статистике VPN-трафика (te-st.org). Нужна политика выбора хостеров: избегать AS, где уже сконцентрированы VPN (они в приоритетной очереди на ковровую блокировку); предпочитать хостеров общего назначения со смешанным трафиком. Требуется исследование: какие AS уже под ударом, какие — нет.
- **P03-5. Обход при белом списке (default-deny).** Смена IP не работает. Требуется отдельный режим: туннелирование через разрешённые адреса/домены (доменный фронт на незаблокированных CDN, проксирование через IP из allow-list). Это архитектурно отдельный транспортный слой, не «ещё один IP».
- **P03-6. IPv6 как запасной канал.** Неизвестно покрытие блокировок по IPv6 (раздел 5, п.4). Требуется: измерение доступности VPN по IPv6 с российских операторов; при положительном результате — dual-stack транспорт с приоритетом IPv6.
- **P03-7. Различение троттлинга и блокировки.** Паттерн «16 КБ и обрыв» (Cloudflare, 06.2025) требует отдельной обработки: реассерт соединения, докачка чанками, мультиплексирование. Детектор из P03-1 должен отдельно классифицировать throttle.
- **P03-8. SNI+IP связки.** Блокировки применяются к парам (SNI, IP), поведение нестабильно (community.cloudflare.com). Требуется исследование: как ТСПУ коррелирует SNI и destination IP, можно ли использовать «чужой» SNI на своём IP (и не палит ли это сервер).
- **P03-9. Защита от идентификации серверных IP через телеметрию.** Российские топ-приложения собирают список установленных VPN (RKS Global, весна 2026); «крупные ИТ-компании» передают статистику по IP (te-st.org). Threat model: IP сервера может быть вычислен не по трафику, а по данным с устройства пользователя. Требуется: минимизация следов (пакет app, имя процесса), оценка риска для self-hosted сценария.
- **P03-10. Процедура восстановления после ковровой блокировки.** Когда подсеть заблокирована целиком: скрипт миграции (новые IP → обновление подписок/конфигов → уведомление пользователей), оценка времени простоя, «горячий резерв» в другой AS. Сейчас это ручная операция; нужна автоматизация.
- **P03-11. Измерение скорости блокировки новых IP (эксперимент).** Нет данных о времени от появления VPN-IP до его блокировки (раздел 5, п.2). Требуется полевой эксперимент с контрольным IP, иначе нельзя спроектировать интервал ротации (P03-3) на фактах, а не на гаданиях.
