## 1. Что блокируется / как проявляется

SNI — основной механизм селективной фильтрации HTTPS на ТСПУ. По ClientHello выносится решение: блокировать, душить или пропустить. Проявления:

- **SNI-I (по таксономии Xue et al. 2022, подтверждено в отчёте CIL 2026):** подделка пакетов server→client: ТСПУ обрезает payload и меняет TCP-флаги на RST/ACK. Клиент видит мгновенный сброс соединения. Это «фейковый RST».
- **SNI-II:** после ClientHello пропускается ещё 5–8 пакетов, затем начинается симметричный дроп пакетов в обе стороны. Симптом: handshake «зависает», таймаут, без RST.
- **SNI-III:** traffic policing — дроп пакетов выше заданного rate limit. Так душили YouTube по SNI `googlevideo.com` (август 2024; официально объявлялось 128 кбит/с). Симптом: соединение живёт, но пропускная способность искусственно низкая.
- **QUIC:** дроп пакетов с «нежелательным» SNI (см. раздел 3). Блокпейдж-редиректа для HTTPS/SNI нет — редирект на заглушку технически невозможен без MITM, ТСПУ ограничивается RST/дропом/душением. (Заглушки РКН встречаются в транзитной цензуре и на HTTP, это другой механизм.)
- **Двухслойный режим белых списков** (мобильный интернет в ряде регионов, 2025–2026; по реверсу статьи на Хабре, сканирование через Мегафон): L3 — drop пакетов к IP вне белого CIDR-списка; L7 — если IP разрешён, но SNI в чёрном списке — RST. Т.е. в whitelist-режиме SNI-фильтрация работает как вторая линия после IP-фильтра.

Скорость реакции централизованная: правила меняются ГРЧЦ без уведомления операторов; операторы не видят конфигурацию ТСПУ и не могут исключать сервисы из правил. Пример скорости: Cloudflare включил ECH по умолчанию в октябре 2024 → 5 ноября жалобы пользователей, 7 ноября РКН официально заявил о блокировке ТСПУ. Реакция — дни.

## 2. Где: регион, операторы, условия

- Покрытие: по заявлению главы РКН (окт. 2023) мобильные, ШПД и трансграничные узлы «закрыты на 100%». По данным CIL (окт. 2025): 1406 узлов связи, 132.3 Тбит/с трафика через ТСПУ. Все узлы >10 Гбит/с в зоне охвата; мелкие операторы фильтруются на ТСПУ апстрима.
- Железо: RDP.RU (дочка Ростелекома), линейка EcoFilter/EcoSGE (24–200 Гбит/с), брокер трафика EcoBalancer (P4, 2.0–6.4 Тбит/с). Оборудование — собственность государства, управляется удалённо ГРЧЦ.
- Правила НЕ едины по установкам: ресурс, заблокированный через одного оператора, может открываться через другого (практика ISP, CIL 2026).
- Whitelist-режим (drop-all): приграничные/конфликтные регионы, зоны «постоянных ограничений», стратегические военные регионы (CIL 2026). В марте 2026 — сообщения о белых списках на фиксированном ШПД в Ростове-на-Дону (оператор отрицал; пометка: не подтверждено независимо). В июне 2025 зафиксировано 655 отключений мобильного интернета.
- Транзитный эффект: фильтрация применяется к трафику, проходящему транзитом через РФ (минимум 6 российских AS, 8 стран-соседей получали российские блокпейджи — Ortwein et al. 2023).
- Условие для SNI-блока: достаточно одного ClientHello с запрещённым SNI; IP-адрес может быть любым (включая CDN/shared IP — отсюда collateral damage при блокировках по SNI на shared-инфраструктуре).

## 3. Как технически

### 3.1 Извлечение SNI из ClientHello (TLS/TCP)

- ТСПУ — inline L2-мост (не виден в traceroute). DPI (RDP.RU EcoSGE) парсит TLS ClientHello на лету на скорости линии.
- Перехват на первом пакете с ClientHello: SNI извлекается из extension `server_name` (type 0). Это триггер SNI-I/II/III.
- IP-фрагментация: ТСПУ реассемблирует до 45 IP-фрагментов, таймаут ~5 с. При перекрывающихся/дублирующихся фрагментах вся очередь дропается (строгая политика RFC 5722, применена и к IPv4). Вывод: обход через overlapping IP-фрагменты против ТСПУ не работает.
- TCP-сегментация: наивный сплит ClientHello по TCP-сегментам больше не работает — по отчёту автора BlindDPI (сентябрь 2026), современный DPI реассемблирует TCP-поток и всё равно блокирует. Работают техники десинхронизации DPI и сервера: фейковый пакет с мусором + сдвиг seq (DPI читает мусор, сервер отбрасывает), TTL-трюки (пакет с низким TTL умирает на DPI, но не у сервера — надёжность зависит от топологии), prepend фейковых TLS-записей.
- Известный рабочий набор (Ars Technica по отчёту 2024, актуален для GoodbyeDPI/zapret): сегментация ClientHello; padding extension, раздувающий ClientHello >1500 байт (больше одного пакета); фейковый скремблированный пакет ≥101 байта перед настоящим; prepend других TLS-записей (напр. change_cipher_spec); idle-ожидание сброса состояния троттлера; trailing dot в SNI (`example.com.`).
- Впрыснутые ТСПУ пакеты сохраняют оригинальный TTL потока (деталь для детекции), но ТСПУ переписывает TTL при форвардинге IP-фрагментов (Xue et al. 2022).

### 3.2 Session resumption

- TLS 1.3 resumption: ClientHello всё равно отправляется и обычно содержит SNI в открытом виде → виден и блокируется так же. Отдельного «ослабления» для resumption в измерениях не зафиксировано.
- TLS 1.2 abbreviated handshake: ClientHello с session_id, расширения (включая SNI) часто отсутствуют → теоретически может проскочить SNI-фильтр. Практических измерений обхода ТСПУ через TLS 1.2 resumption без SNI не найдено → см. раздел 5 (требует проверки).
- 0-RTT (TLS 1.3): первый flight всё равно начинается с ClientHello с SNI → не помогает против SNI-фильтра.

### 3.3 SNI в QUIC Initial

- Исторически (март 2022, OONI): на мобильных сетях (Yota AS31213) блокировался весь международный QUIC v1 + отдельный SNI-фильтр; vk.com был в исключениях.
- Новое (измерения март–апрель 2026, FOCI 2026, три города РФ): ТСПУ расшифровывает QUIC Initial-пакеты, извлекает SNI из вложенного TLS handshake в crypto-фрейме и дропает пакеты с запрещённым SNI. 2644 домена из Tranco Top-100k блокируются идентично по TLS и QUIC — списки для TLS и QUIC совпадают. Устройство цензуры — между 3-м и 4-м хопом от точки в Москве (т.е. на стороне оператора/ТСПУ).
- Практический вывод: блокировка QUIC = дроп Initial/Handshake-пакетов; «заглушить» QUIC фрагментацией crypto-фреймов теоретически возможно, измерений эффективности против актуального ТСПУ нет.

### 3.4 Списки блокировок

- Два контура: (а) официальный реестр РКН; (б) правила ТСПУ, управляемые централизованно ГРЧЦ и НЕ публикуемые. ТСПУ блокирует вне реестра: отдельные ресурсы, хостинги, VPN-протоколы. Дополнительно блокировки вносят другие ведомства (НКЦКИ) — тоже не публикуются.
- SNI-список — часть непубличных правил; точный состав неизвестен, измеряется только чёрным ящиком (shutdown.fyi: TLS-handshake с тестовым SNI изнутри РФ vs снаружи).
- ECH-блок (ноябрь 2024): условие = SNI `cloudflare-ech.com` + наличие ECH-расширения → drop. Точечно, не «весь ECH».

### 3.5 Скорость реакции

- Централизованное push-обновление правил на все установки; операторы узнают постфактум по жалобам. ECH: ~2–7 дней от включения Cloudflare до блока. YouTube-душение: решение доведено до операторов в июле 2024, троттлинг с августа 2024.
- Сбои правил тоже централизованные: 14 января 2025 мис конфиг ТСПУ дал −11% трафика MSK-IX за 20 минут (откат за 20 минут).

## 4. Насколько надёжен известный обход

| Метод | Статус vs ТСПУ (2025–2026) |
|---|---|
| Фрагментация ClientHello (TCP-сегментация) | Ненадёжна сама по себе: DPI реассемблирует поток. Работает только в связке с десинхронизацией (фейковые пакеты, сдвиг seq, TTL-трюки) — так устроены zapret/GoodbyeDPI. Ломается при смене логики DPI; требует подбора стратегии per-оператор |
| Fake SNI / подмена SNI | Работает там, где серверу всё равно, что в SNI (или SNI вообще не проверяется): Reality-подобные схемы, whitelist-обходы (`sni=ya.ru`). Против строгой проверки SNI сервером — нет. В whitelist-режиме (L3+L7) подмена SNI на разрешённый домен — основной рабочий вектор (практика VLESS-конфигов `[SNI-RU]`) |
| ECH | Частично заблокирован: комбинация `cloudflare-ech.com` + ECH extension дропается. Измерения (Москва, март 2025) показали селективность блока и наличие обходов, но не всеобщий блок ECH. ECH от не-Cloudflare провайдеров (после RFC 9849, март 2026; OpenSSL 4.0/NGINX 1.29.4) против ТСПУ не измерен. Риск: РКН готовит прямой законодательный запрет ECH |
| Domain fronting (классический) | Мёртв как массовая техника: CDN отключили fronting; плюс SNI в TLS всё равно виден, fronting прятал только Host. Наследники: ECH (см. выше), «SNI-RU»-маскировка под разрешённые домены в whitelist-режиме |
| Padding ClientHello > MTU | Рабочий приём из арсенала zapret (вынуждает DPI собирать >1 пакета), но сам по себе не панацея — см. фрагментацию |
| Trailing dot в SNI | Точечный приём; работает против наивных строковых сравнений, ломается при нормализации |
| QUIC: отключение/обход | QUIC SNI-фильтр существует и дропает Initial; надёжного измеренного обхода нет |
| DNS-уровень | zapret/GoodbyeDPI НЕ защищают DNS: с августа 2025 перехват 8.8.8.8/1.1.1.1 (UDP/53); обход — только через DoH/DoT/туннель. Важно: SNI-обход бесполезен, если DNS уже отравлен (NXDOMAIN до соединения) |

Общий вывод: SNI-обходы — это гонка реализаций. Каждый приём эксплуатирует конкретный баг/упрощение текущей версии DPI; ТСПУ обновляется централизованно и догоняет за месяцы. Долгосрочно надёжны только: (1) шифрование SNI (ECH) — пока частично заблокировано; (2) маскировка под разрешённый трафик целиком (не только SNI); (3) неуязвимость к SNI-фильтру по построению (IP/домен не в списках + протокол недетектим).

## 5. Что неизвестно / требует проверки

1. **TLS 1.2 session resumption без SNI против ТСПУ.** Теория говорит «должен проскочить», измерений нет. Проверить: abbreviated handshake к заблокированному домену, сравнить с полным handshake.
2. **Детали обходов ECH-блока из измерений марта 2025** (CIL ссылается на них, конкретики в открытых источниках мало). Что именно обходило: смена outer SNI, не-Cloudflare ECH-конфиг, GREASE ECH?
3. **ECH от провайдеров помимо Cloudflare** (самостоятельный хостинг после RFC 9849). Блокируется ли по наличию extension вообще или только по `cloudflare-ech.com`? Критично для стратегии.
4. **Порог SNI-II (5–8 пакетов)** — актуален ли для текущих версий EcoSGE; менялся ли с 2022.
5. **SNI-триггер на ClientHello внутри уже установленного туннеля** (напр. второй handshake, renegotiation — запрещён в TLS 1.3, но key update виден иначе). Для мультиплексированных протоколов важно, смотрит ли ТСПУ только на первый ClientHello потока.
6. **Поведение при фрагментированном QUIC Initial** (crypto-фрейм, разрезанный по нескольким UDP-дейтаграммам): реассемблирует ли ТСПУ QUIC-крипто? Измерений нет.
7. **Региональная вариативность SNI-правил**: карта «какой SNI где режется» устаревает за недели; нужен непрерывный мониторинг, а не разовые замеры.
8. **Слух:** «ТСПУ учится детектить VLESS по косвенным признакам» (РБК, дек. 2025, со ссылкой на источники) — не подтверждено независимыми измерениями; возможно, речь о блокировках по объёму/поведению серверов, а не о сигнатуре протокола.
9. **Слух:** «мощности ТСПУ не хватает, часть трафика идёт в bypass» (Forbes RU, март 2026) — правдоподобно (bypass-режим задокументирован), но количественно не измерено; влияет на воспроизводимость любых тестов.

## 6. Проблемы для тех-агентов

Контекст кода sora (только чтение): `core/obfs` уже умеет фрагментацию ClientHello, jitter, uTLS-фингерпринты и подмену SNI (только для соединений, инициируемых самим ядром); `core/censor` классифицирует факт вмешательства по wire-сигнатуре; движки sing-box/mihomo умеют ECH (конфиг пробрасывается) и TLS-фрагментацию sing-box.

- **P02-1. Нет стратегии против SNI-II/SNI-III как отдельных режимов.** `censor` различает RST vs stall vs throttle? Если детектор не различает SNI-I (RST), SNI-II (stall после 5–8 пакетов) и SNI-III (policing), выбор пресета обфускации слепой. Нужна классификация именно этих трёх сигнатур + маппинг на контрмеры.
- **P02-2. Фрагментация без десинхронизации — мёртвый приём.** Наивный TCP-сплит ТСПУ реассемблирует (подтверждено практикой BlindDPI, 2026). В `core/obfs/frag.go` проверить: есть ли fake-пакеты, сдвиг seq, TTL-манипуляции — или только «честная» сегментация. Если только сегментация — это не обход современного ТСПУ.
- **P02-3. Нет QUIC-обфускации.** QUIC SNI-фильтр ТСПУ дропает Initial по SNI из crypto-фрейма (измерено 2026). Если sora использует QUIC (HTTP/3, QUIC-транспорты), нужен аналог десинхронизации для QUIC Initial либо принудительный fallback на TCP при детекте QUIC-цензуры.
- **P02-4. ECH включён в конфиге, но стратегия outer SNI не проработана.** Блок РКН — по паре (`cloudflare-ech.com` + ECH ext). Использование дефолтного outer SNI Cloudflare = самоподпись для ТСПУ. Нужны: выбор непалевного public_name, GREASE ECH, измерение, какие outer SNI реально проходят.
- **P02-5. SNI-обход без DNS-обхода бесполезен.** zapret-урок 2025: перехват 8.8.8.8/1.1.1.1 убивает любые SNI-трюки (NXDOMAIN до соединения). Проверить, что все SNI-обходы в sora жёстко спарены с DoH/DoT или туннелированным DNS; иначе сценарий «обход включён, сайты не резолвятся».
- **P02-6. Нет измерения «что именно режется здесь и сейчас».** SNI-правила варьируются по операторам и меняются за дни. `censor/probe.go` делает разовый диагноз; нужен фоновый SNI-оракул: периодический TLS-handshake набором тестовых SNI (заблокированный/чистый/пограничный) для выбора рабочей стратегии per-сеть.
- **P02-7. Подмена SNI (fake SNI) ограничена соединениями ядра.** По doc `core/obfs`: fake SNI только для handshake, инициированных ядром. Пользовательский трафик через движки идёт с реальным SNI — для whitelist-режима (L7: чужой SNI → RST) это означает, что обход невозможен без SNI-маскировки на уровне движка/профиля. Нужен механизм SNI-переписывания для транзитного трафика (где протокол позволяет).
- **P02-8. Не закрыт кейс «SNI чистый, но IP в чёрном списке» и наоборот.** В whitelist-режиме порядок L3→L7: сначала drop по IP, потом RST по SNI. Диагностика должна различать эти два отказа (таймаут TCP vs RST после ClientHello), иначе неверный выбор контрмеры.
- **P02-9. Отсутствует обработка downgrade-атаки ТСПУ на обходы.** ТСПУ централизованно адаптируется (пример: ECH за дни). Нужен механизм быстрой смены стратегии без обновления клиента: профили обфускации, подтягиваемые с подпиской, + телеметрия эффективности (какой приём перестал работать — видно по росту SNI-II stall'ов).
- **P02-10. Не исследована связка «SNI-триггер + активный пробинг».** По данным CIL, РКН покупает VPN-ключи и строит отпечатки серверов по их же клиентам. SNI-маскировка прячет имя, но не спасает от активного пробинга сервера. Для тех-агентов протоколов: SNI-обход должен идти в паре с анти-пробинг мерами (не отвечать на чужие handshake, см. P01-серию если есть).
