# №28. Обход QUIC-троттлинга — что работает

Аналитик №28/50, отдел анализа ТСПУ/блокировок. Дата: 2026-10-20.
Тема: методы обхода QUIC-троттлинга/блокировок, механика, реальная работоспособность против ТСПУ РФ (октябрь 2026).

Источники: веб-поиск 6 запросов (приоритет 2025–2026) + чтение первоисточника FOCI 2026; смежные отчёты отдела №27 (SNI-обход, полевые тесты Riposte/Levelflow 08.2026, СПб), №30 (fake-пакеты), ZAPRET-EVOLUTION-SPEC. Слухи помечены явно как **[слух]**. Полевые тесты ценнее блогов — так и ранжировано.

Терминологическая рамка: в РФ против QUIC применяются **два разных воздействия** с общим SNI-триггером — (а) дроп по SNI (FOCI 2026: расшифровка QUIC Initial, извлечение SNI, дроп пакета + всего 4-tuple на 420 с), (б) троттлинг по SNI (YouTube: SNI-троттлинг googlevideo.com по QUIC с 18.07.2024, за неделю после TLS-троттлинга; 08.08.2024 — полный SNI-блок YouTube по TLS). Методы ниже закрывают оба, но проверялись в основном против (а).

## 1. Какие методы обхода QUIC-троттлинга известны

| # | Метод | Суть в одной строке | Статус против ТСПУ |
|---|-------|---------------------|-------------------|
| M1 | QUIC-десинк фейками (`--dpi-desync=fake` для UDP/443) | Подсунуть ТСПУ фейковый QUIC Initial раньше настоящего | **Работает** — основной полевой метод |
| M2 | Порча UDP-уровня (`udplen-increment`, `udplen-pattern`) | Сломать парсинг UDP-заголовка у DPI, сервер пересчитает | Условно, в связке с M1 |
| M3 | `disorder2`/`split` для UDP | Разбить/переставить дейтаграмму, SNI не в первом куске | **[слух для ТСПУ]** — community-практика, замеров нет |
| M4 | Принудительный TCP-fallback | Убить QUIC (отключить в браузере / дропнуть UDP/443 локально) → HTTP/2 по TCP | **Работает всегда**, цена — скорость |
| M5 | QUIC connection migration | Сменить 4-tuple после 1-RTT: новый «поток» без Initial/SNI | **[не проверено]** против ТСПУ; не бьёт SNI-блок хендшейка |
| M6 | Смена UDP-портов | Уйти с 443 на нестандартный порт | **Мёртв** (FOCI 2026: цензура на всех портах) |
| M7 | Фрагментация QUIC Initial на клиенте | Разбить CRYPTO/ClientHello на несколько дейтаграмм (Firefox 137, quic-go v0.52.0) | Против GFW — да; против ТСПУ **[не проверено]** |
| M8 | QUICv2 (version `0x6b3343cf`) | ТСПУ детектит только QUICv1 (`0x00000001`) | **Не цензурируется** (FOCI 2026), но нет серверной экосистемы |
| M9 | ECH поверх QUIC | Шифрование внутреннего ClientHello | В РФ давится и по QUIC (TU Dresden 2026, via №27) |
| M10 | Маскировка VPN под QUIC (MASQUE, WG-in-QUIC, ShadowQUIC) | Не обход троттлинга QUIC, а камуфляж VPN-трафика под HTTP/3 | Работает как транспорт (Mullvad 2025.9, NymVPN) |
| M11 | Hysteria2 FakeTCP / UDP-hop / WeChat-obfs | Мимикрия TCP-хендшейка поверх UDP; ротация портов по таймеру | Полевых данных против ТСПУ нет |
| M12 | Preceding UDP packet (случайный UDP перед Initial) | GFW считает первым пакетом потока мусор и игнорирует QUIC | Проверено только против GFW **[слух для РФ]** |
| M13 | Version-negotiation trick | Initial с неподдерживаемой версией → VN-пакет → цензор игнорит остаток | Проверено только против GFW **[слух для РФ]** |

Не методы обхода, но обязательный контекст: DoH/DoT (иначе домен виден в DNS раньше QUIC), удаление youtube.com из НСДИ 02.2026 (DNS-слой, см. №30 §4 — победа над DPI ≠ доступ).

## 2. Где проверено / против кого работает

### 2.1. ТСПУ РФ — полевые и измерительные данные

- **FOCI 2026** (Heitmann et al., Paderborn; замеры март–апрель 2026, три точки: Москва, СПб, Новосибирск; https://jonsnowwhite.de/files/foci_26_russia.pdf): ТСПУ расшифровывает QUIC Initial (ключи выводятся из публичных значений, RFC 9001), извлекает SNI, при запретном домене дропает пакет и **все последующие пакеты того же 4-tuple 420 секунд** (таймер сбрасывается каждым новым пакетом). Если первый пакет не триггернул — остаток соединения **residually cleared** (не анализируется). Блок-листы TLS и QUIC идентичны (2644 домена из Tranco Top 100k). Цензура **на всех портах** (тесты до 65535; в Москве 22% системных портов 1–1023 не затронуты, но 443 и 853 — везде). **QUICv2 не цензурируется.** Цензура однонаправленна: входящий в РФ трафик не трогают. Точка — 3–4 хоп от Москвы. История: Period B (03.2022) — дроп всего международного QUIC на UDP/443 (триггер: первый пакет ≥1001 байт с QUICv1-версией); Period C (05.2022–07.2023, Cloudflare: снятие широкого фильтра 03.06.2022) — переход на SNI-фильтр.
- **Полевые тесты Riposte/Levelflow, 08.2026, СПб** (via №27; https://riposte.levelflow.org/2026/08/bypasswithoutavpn/): YouTube открылся **только** через QUIC-десинк (youtubeUnblock, zapret2); ByeDPI — нет. Единственный метод из M1–M13, подтверждённый полевым тестом 2026 именно для YouTube/HTTP-3.
- **Троттлинг Cloudflare, с 09.06.2025**: «16 КБ»-троттлинг (первые 16 КБ ресурса грузятся, дальше — таймауты/потери), затрагивает **все протоколы включая HTTP/3 over QUIC**; операторы: Ростелеком, Мегафон, Вымпелком, МТС, МГТС; техники — инжекты и дропы пакетов. Это троттлинг **не по SNI, а по IP/направлению** — M1 здесь не поможет (см. §4).
- **criticalinfralab «TSPU and You», 09.2026** (via №30): ТСПУ — L2 transparent bridge in-path, TTL не декрементирует, в traceroute невидим. Важно для калибровки TTL-фейков (для TCP; для QUIC TTL-трюк обычно не применяют — см. §3 M1).
- **Roskomsvoboda «Runet 2025: Sovereignization», 06.2026** (via №30): «с 2025 GoodbyeDPI и Zapret в значительной степени перестали работать». **Конфликт** с полевыми тестами 08.2026 (№27 §4.5 помечает как спорное). Для QUIC-десинка прямых опровержений нет — но тезис «цензор переобучается» учитывать обязан.

### 2.2. Другие цензоры (переносимость на ТСПУ — ограниченная)

- **GFW (Китай)**: обходы QUIC-цензуры из отчёта GFW Report team (via https://dev.to/0trust0day/unmasking-the-great-firewall-how-i-explored-quic-censorship-and-ways-to-bypass-it-1di3): high destination ports (dst port ≥ src port — GFW игнорит), preceding random UDP packet, фрагментация Initial (реализована в Firefox 137 и quic-go v0.52.0), connection migration, ECH, version-negotiation trick; degradation-атака: флуд 1200 kpps QUIC Initial → 60% соединений с блеклист-SNI не блокируются ( random UDP того же размера эффекта не дал — узкое место GFW именно в QUIC-парсинге). **Против ТСПУ из этого списка напрямую проверено только отсутствие цензуры QUICv2 (FOCI 2026). Остальное — [слух для РФ].**
- **Коммерческие внедрения**: Mullvad 2025.9 — WireGuard-in-QUIC через MASQUE (десктоп Win/macOS, авто-переключение на QUIC при фейлах; https://reclaimthenet.org/mullvad-vpn-wireguard-quic-masque-bypass-censorship); NymVPN — QUIC transport mode для entry-hop (https://support.nym.com/hc/en-us/articles/39648047741457-What-is-QUIC-transport-mode-in-NymVPN). Это M10, не обход QUIC-троттлинга.

## 3. Как технически: механика каждого метода

### M1. QUIC-десинк фейками — разбор до винтика

**Что перехватывает:** `nfqws` (Linux, NFQUEUE — нужен root) или `winws` (Windows, WinDivert). sora сейчас запускает `tpws`, который работает **только с TCP-потоком — UDP идёт мимо** (ZAPRET-EVOLUTION-SPEC §2). Без UDP-тракта M1 в sora невозможен в принципе.

**Команда (канон из zapret-конфигов):**
```
--filter-udp=443 --dpi-desync=fake --dpi-desync-repeats=6
```
Вендорные сборки (zapret-discord-youtube `general.bat`):
```
winws.exe --wf-tcp=80,443 --wf-udp=443,50000-50100 \
  --filter-udp=443 --hostlist="lists/list-general.txt" \
  --dpi-desync=fake --dpi-desync-repeats=11 \
  --dpi-desync-fake-quic="bin/quic_initial_www_google_com.bin" --new ...
```
`NFQWS_PORTS_UDP=443,50000-50099`, `NFQWS_UDP_PKT_OUT=6(+ретраны)`, `NFQWS_UDP_PKT_IN=0` — обрабатываются только первые исходящие дейтаграммы (nfqws-keenetic).

**Механика по шагам:**
1. Клиент шлёт QUIC Initial (ClientHello с SNI внутри CRYPTO, зашифрован Initial-ключами из публичного salt — ТСПУ умеет расшифровывать, FOCI 2026).
2. nfqws/winws **раньше** настоящего пакета впрыскивает N (`--dpi-desync-repeats`, для QUIC типично 6–11 против 2 для TCP — компенсация потерь UDP) фейковых QUIC Initial из файла `quic_initial_www_google_com.bin` — структурно валидный Initial с **белым SNI** (`www.google.com`) и **чужим Connection ID**.
3. ТСПУ ведёт состояние потока по 4-tuple/CID и выносит вердикт по **первому** увиденному Initial: белый SNI → «чисто», поток помечается пропущенным; residual clearance (FOCI 2026) — если первый пакет не триггернул, остаток соединения дальше не анализируется. Настоящий Initial с запретным SNI проходит по уже «пропущенному» состоянию.
4. Сервер QUIC фейк игнорирует: Initial с неизвестным DCID/невалидным для его состояния — отбрасывается стеком (в отличие от TCP, где фейк надо убивать TTL/badseq — для QUIC TTL-трюк обычно не нужен, что упрощает; но см. P28-5 про GGC).

**Почему repeats высокий:** UDP не гарантирует порядок/доставку; фейк обязан прийти **строго раньше** оригинала. Проигрыш гонки = ТСПУ видит настоящий SNI первым → дроп 4-tuple на 420 с (таймер обновляется каждым пакетом — бан самопродлевается, пока клиент долбится ретрансмитами).

**Вариант M2 (в той же команде):** `--dpi-desync-udplen-increment=15` / `--dpi-desync-udplen-pattern=0xCAFEBABE` — порча поля длины UDP-заголовка. Часть DPI-парсеров отваливается; userspace QUIC-стек сервера длину пересчитывает/игнорирует. Работает только в связке, соло-замеров нет.

### M3. disorder2 для UDP — [слух]

Community-практика (habr, `NFQWS_OPT_DESYNC_QUIC="--dpi-desync=disorder2 --dpi-desync-repeats=6"`): дейтаграмма режется на куски, порядок инвертируется — первый увиденный ТСПУ кусок не содержит полного CRYPTO/SNI. В документации zapret набор UDP-режимов заявлен как ограниченный; вопрос из habr-комментария прямо указывает на расхождение доков и практики. Полевых замеров против ТСПУ 2025–2026 в открытых источниках **нет**. Не путать с M7 (фрагментация на клиенте — там куски валидны по QUIC, здесь — перестановка на中间боксе).

### M4. Принудительный TCP-fallback

Два варианта: (а) отключить QUIC в клиенте (Chrome `--disable-quic`, Firefox `network.http.http3.enabled=false`); (б) дропнуть исходящий UDP/443 локально (iptables/nftables/WFP) — браузер по Alt-Svc сам откатится на HTTP/2+TCP. Вариант (б) детерминирован: без него Happy Eyeballs каждый раз ждёт таймаут QUIC (медленный старт каждой сессии). Для sora задуман QUIC-probe в `core/probe`: активная проверка достижимости UDP/443 → честный сигнал движкам откатиться (ZAPRET-EVOLUTION-SPEC P0.3). Это не обход, а отказ от поля боя; YouTube по TCP работает, но медленнее и хуже переживает потери.

### M5. Connection migration — механика и предел

После завершения хендшейка (1-RTT ключи) клиент вправе сменить исходный IP/порт (RFC 9000 §9): сервер валидирует новый путь (PATH_CHALLENGE/RESPONSE), CID остаётся. Для ТСПУ это **новый 4-tuple** без Initial → SNI извлечь не из чего (ключи уже не Initial-секрет), а 420-секундный стейт старого 4-tuple не ассоциируется с новым. **Предел:** миграция не помогает, если Initial уже задропан по SNI, — до 1-RTT не дойти. Это обход **mid-connection троттлинга**, не блокировки хендшейка. Против ТСПУ не измерялось. Родственная техника — Hysteria2 `udp-hop`: ротация **серверного** порта по таймеру (другая сторона медали).

### M6. Смена портов — мёртв, с датой смерти

Исторически работало (2022–2023 ТСПУ смотрел только UDP/443). FOCI 2026 (замеры 03–04.2026): цензура QUIC на **случайных портах до 65535** во всех трёх точках; релевантные QUIC-порты 443 и 853 — везде. Метод закрыт измерением, не мнением.

### M7. Фрагментация QUIC Initial на клиенте

Клиент разбивает TLS ClientHello (CRYPTO-фреймы) на несколько QUIC-дейтаграмм так, что SNI разорван между ними. Цензор, читающий только первую дейтаграмму и не собирающий CRYPTO-поток, SNI не видит. Реализовано в Firefox 137 и quic-go v0.52.0 (по GFW Report team — против GFW работает). Против ТСПУ: неизвестно, делает ли ТСПУ реассембли CRYPTO (FOCI 2026 этого не тестировал; ТСПУ умеет расшифровывать Initial — собрать фрагменты для него технически тривиально, вопрос лишь в том, делает ли).

### M8. QUICv2

FOCI 2026, дословно по смыслу: «QUICv2 is not affected… facilitating potential circumvention». ТСПУ матчит QUICv1 (`0x00000001` в поле версии первого пакета); QUICv2 (`0x6b3343cf`) мимо детекта. **Но:** QUICv2 почти не развёрнут на серверах (Google/Cloudflare — v1). Практическое применение — только свои relay sora, говорящие на QUICv2, и только как транспорт sora, не как обход для YouTube в браузере.

### M9. ECH поверх QUIC

Шифрует внутренний ClientHello (включая SNI); снаружи виден cover-SNI (обычно CDN). По измерению TU Dresden 2026 (via №27): 33% из 105.7k ECH-доменов в зоне `.ru` «по-прежнему подвержены ECH-блокировке, развёрнутой в России, **при обращении по QUIC**» — т.е. ТСПУ давит ECH и на QUIC-транспорте. Метод не готов.

### M10/M11. QUIC как камуфляж (не обход QUIC-троттлинга!)

Mullvad 2025.9: WireGuard, завёрнутый в QUIC через MASQUE, — трафик неотличим от обычного HTTP/3; авто-переключение на QUIC при фейлах обычного WG. NymVPN: QUIC transport mode для entry-hop. Hysteria2: `FakeTCP` (UDP-пакеты с мимикрией TCP-хендшейка — против UDP-троттлинга как класса), `UDP-hop`, `WeChat-video` obfs. Для sora это **кандидаты в транспорты**, а не способы починить чужой YouTube по QUIC. Важно не смешивать в одну кучу при проектировании.

### M12/M13. GFW-специфика — [слух для РФ]

Preceding random UDP packet и version-negotiation trick измерены только против GFW. Механика ТСПУ (анализ первого пакета + residual clearance) делает M12 теоретически правдоподобным и для ТСПУ, но замеров нет — не утверждать.

## 4. Надёжность: что реально работает в РФ 2026

### 4.1. Работает (подтверждено измерениями/полем)

1. **M1 fake-QUIC-десинк** — единственный метод с полевым подтверждением 2026 именно для YouTube/HTTP-3 (Riposte/Levelflow 08.2026, СПб: YouTube открылся только через youtubeUnblock/zapret2 с QUIC-десинком). Канон: `--filter-udp=443 --dpi-desync=fake --dpi-desync-repeats=6..11` + `quic_initial_www_google_com.bin`. Но: стратегия обязана подбираться **per-ISP** (урок №27: Meduza открылась через `fake_ttl8`, но не через `disorder_tlsrec`; преконфиги сообщества расписаны по операторам).
2. **M4 TCP-fallback** — работает всегда и везде; цена — потеря преимуществ QUIC (скорость, переживание потерь). Обязательный запасной план, а не «поражение».
3. **M8 QUICv2-невидимость** — измерено FOCI 2026 (не цензурируется); применимость узкая (свои relay).

### 4.2. Умерло / не работает

1. **M6 смена портов** — убита измерением FOCI 2026 (все порты).
2. **M9 ECH по QUIC** — давится в РФ (TU Dresden 2026).
3. **Наивный «просто включить QUIC»** — без десинка SNI виден ТСПУ в открытую (ключи Initial публичны).

### 4.3. Спорное / условное

1. **«Zapret в значительной степени перестал работать с 2025»** (Roskomsvoboda 06.2026) **vs** полевые тесты 08.2026 (работает). Разрешение спора: эффект операторо- и стратегозависим; универсального «работает везде» нет и не было (№30 §2: преконфиги по провайдерам). Для отчётности sora — только честные per-ISP замеры, никаких глобальных заявлений (наследовать запрет маркетинговых цифр из ZAPRET-EVOLUTION-SPEC).
2. **M2/M3** — разумны в связке с M1, соло-доказательств против ТСПУ нет.
3. **Троттлинг не по SNI** (кейс Cloudflare 06.2025, «16 КБ»): M1–M9 бессильны в принципе — триггер не SNI, а IP/направление. Лечится только сменой транспорта/маршрута (M10/M11-класс) или ожиданием снятия волны.

### 4.4. Системный предел (важно для планирования)

Победа над DPI-слоем ≠ доступ к ресурсу. Слоистая оборона 2026 (criticalinfralab 09.2026, via №30): YouTube — SNI-троттлинг (08.2024) → удаление из НСДИ (02.2026); блок по IP (подозрение в полевых тестах: `mail.proton.me` не открылся ни с чем). QUIC-десинк закрывает **только DPI-слой**. Архитектура sora обязана складывать: DoH/DoT + QUIC-десинк + fallback + IP-уровень (проксирование через «чистые» IP).

## 5. Что неизвестно / требует проверки

1. **Реассембли CRYPTO у ТСПУ.** Собирает ли ТСПУ фрагментированный QUIC Initial (M3/M7)? FOCI 2026 не тестировал. Определяет судьбу M3 и M7 одним измерением.
2. **Эвристики без SNI.** Триггерит ли ТСПУ что-то кроме SNI в QUIC (длина первого пакета ≥1001 байт — исторический триггер Period B; частота Initial; паттерны ретрансмитов)? Если да — фейк обязан mimick'ировать и их.
3. **Детект известных фейков по сигнатуре.** `quic_initial_www_google_com.bin` лежит в открытых репозиториях; цензор может внести его в игнор-лист («такие пакеты не считать»). Проверка: A/B — известный бинарник vs свежесгенерированный Initial с тем же белым SNI.
4. **Поведение при проигрыше гонки.** Подтвердить полем: один пропущенный настоящий Initial = дроп 4-tuple ровно на ~420 с с самопродлением? Влияет на стратегию ретраев (смена исходного порта клиента после детекта дропа).
5. **Операторская вариативность QUIC-стратегий.** Поле 08.2026 — СПб, один провайдер. Карты «какой QUIC-пресет у какого оператора» нет (для TCP такая карта в преконфигах сообщества есть).
6. **Мобильные сети.** Все QUIC-замеры — фиксированный ШПД. На мобильных сетях (NAT оператора, плавающий маршрут) гонка фейк-vs-оригинал и 4-tuple-стейт могут вести себя иначе. Не измерено.
7. **M5 migration против ТСПУ.** Переживает ли established-QUIC смену клиентского порта при активном SNI-троттлинге mid-connection? Ноль измерений.
8. **0-RTT и Retry.** Как ТСПУ обрабатывает QUIC Retry и 0-RTT-пакеты (там SNI тоже есть, но в другом месте)? Неизвестно — влияет на полноту M1 (надо ли прикрывать и Retry-ответы).
9. **IPv6.** Все измерения — IPv4. Покрытие QUIC-цензурой v6 — неизвестно (общий пробел, отмечен и в №27).
10. **Направление и unidirectional-цензура.** FOCI: входящий в РФ трафик не цензурируется. Даёт ли это что-то практически (например, server-initiated migration к клиенту в РФ)? Не исследовано.

## 6. Проблемы для тех-агентов

Нумерация P28-N. Зависимости от смежных отчётов указаны явно, дубли не заводятся.

**P28-1. UDP-тракт десинка отсутствует как класс.** sora запускает `tpws` — только TCP; QUIC идёт мимо (ZAPRET-EVOLUTION-SPEC §2). Для M1 нужен перехват UDP/443: NFQUEUE/nftables (Linux, root), WinDivert/WFP-callout (Windows), VpnService (Android, userspace). Это та же проблема, что P27-1, но в UDP-проекции: без нативного хелпера per-OS «встроенный QUIC-десинк» невозможен, остаётся только M4. Требуется архитектурное решение до любых стратегий.

**P28-2. Нет автоподбора QUIC-стратегий.** `blockcheck.sh` завендорен, но не используется; `core/tune` перебирает обфускации без QUIC-пула (ZAPRET-EVOLUTION-SPEC §2). Нужен QUIC-блок автопрофайлера: батарея (`fake`×repeats 6/8/11, `fake`+`udplen-increment`, `disorder2`, без десинка как baseline) против эталонов (`googlevideo.com`, `youtube.com` по UDP/443) с кэшированием per-ISP профиля. Формат профиля и критерий успеха — не определены (урок №27: curl-200 ≠ рендер в браузере).

**P28-3. QUIC-probe + честный TCP-fallback (зависимость от P0.3 ZAPRET-EVOLUTION-SPEC).** Активная проверка достижимости UDP/443 **до** того, как браузер упрётся в Happy-Eyeballs-таймаут. Дополнительно: локальный дроп исходящего UDP/443 как детерминированный триггер fallback (вариант «б» M4) — иначе каждая сессия начинается с медленного таймаута. Не реализовано.

**P28-4. Гонка первого пакета и ретрансмиты Initial.** QUIC-клиент при потере перепосылает Initial; каждый ретрансмит — новый шанс ТСПУ увидеть настоящий SNI первым (особенно при repeats=6 на дропающем канале). Требуется: фейки должны перекрывать не только первый, но и последующие Initial-ретрансмиты в пределах окна (NFQWS_UDP_PKT_OUT уже считает исходящие — проверить достаточность 6+ретраны), либо связка с локальным ретрай-менеджментом.

**P28-5. Окно применимости фейка схлопывается у близких серверов.** Для TCP-фейков критичен TTL (умереть после ТСПУ, но до сервера); для QUIC TTL-трюк обычно не применяют, но проблема та же в другой форме: GGC-ноды YouTube стоят в 2–4 хопах от клиента (№30 §3, риски). Фейковый Initial доходит до реального сервера — последствия: мусор в логах, потенциальный rate-limit/ban по IP за «аномальные» Initial, ответы сервера на фейк (Initial-ответ на чужой CID — лишний трафик клиенту). Требуется оценка: игнорирует ли типичный QUIC-сервер чужой Initial бесшумно и без сайд-эффектов.

**P28-6. Свежесть и сигнатурность fake-пайлоадов.** `quic_initial_www_google_com.bin` — статичный артефакт из публичных репозиториев; ТСПУ может его игнорировать по сигнатуре (тогда M1 молча умрёт). Требуется: (а) полевая A/B-проверка «известный бинарник vs свежесгенерированный Initial с тем же белым SNI»; (б) генератор свежих Initial (валидная структура, белый SNI, свежий CID, актуальная версия QUIC) вместо одного файла на все времена.

**P28-7. Самотравление: фейк не должен стать триггером.** Белый SNI (`www.google.com`) безопасен сегодня; но эвристика «первый UDP-пакет ≥1001 байт с QUICv1» (исторический триггер Period B, FOCI 2026) жива как минимум в коде цензора. Фейк обязан: не превышать типичные размеры, нести QUICv1 (не v2 — иначе см. P28-9, другой путь), не содержать запретных подстрок даже случайно. Нужен валидатор пайлоадов перед включением в пул стратегий.

**P28-8. 420-секундный бан 4-tuple: стратегия ретраев.** Проигрыш гонки = дроп всего 4-tuple на ~420 с с самопродлением каждым пакетом. Клиент, продолжающий долбить ретрансмитами в тот же 4-tuple, продлевает себе бан. Требуется: детект «QUIC-дроп» (паттерн: Initial уходит, ответа нет, TCP до того же хоста жив) → смена исходного UDP-порта (новый 4-tuple, чистый стейт у ТСПУ) → повтор с десинком. Без этого M1 при нестабильной сети превращается в самобан.

**P28-9. QUICv2-relay: оценка реализуемости.** FOCI 2026: ТСПУ не детектит QUICv2. Вопросы: поддерживает ли quic-go (транспорт sora) QUICv2 на сервере; говорят ли клиенты sora на QUICv2; переживёт ли QUICv2-трафик эвристики ТСПУ, не завязанные на версию. Пилот: свой relay с QUICv2 + замеры из РФ. Применимость — только транспорт sora (M8), не пользовательский YouTube.

**P28-10. Точка применения десинка относительно VPN-туннеля.** ТСПУ видит только внешний WG-трафик sora; QUIC внутри туннеля ему невидим — десинк внутри туннеля против ТСПУ бессмысленен. M1 имеет смысл: (а) на трафике до инкапсуляции (split-tunnel, прямые соединения браузера), (б) если транспорт sora сам на QUIC (M10/MASQUE — тогда десинк применяется к внешнему QUIC). Требуется зафиксировать точку в конвейере (связано с F11 «VPN+zapret одновременно») — иначе тех-агенты будут десинкать не тот слой.

**P28-11. Android без root: userspace QUIC-десинк.** Перехват UDP на уровне пакетов без root невозможен; но VpnService отдаёт дейтаграммы в userspace — там можно реализовать M1 (впрыск фейков перед оригиналом) и M4 (дроп UDP/443) без root. Неизвестны: перфоманс (CPU/батарея при обработке каждой дейтаграммы), гонка таймингов в userspace (успеет ли фейк раньше оригинала через TUN-интерфейс). Требуется прототип + замеры, иначе Android остаётся только с M4.

**P28-12. Измерение M5 (migration) против ТСПУ.** Ноль полевых данных. Методика: established QUIC-сессия (например, через quic-go-клиент к своему серверу) → принудительная смена исходного порта mid-connection при активном троттлинге → замер, переживает ли сессия и с какой скоростью. Если да — механизм «тихого переподключения» при деградации без нового хендшейка (и без нового SNI-риска).

**P28-13. Измерение M7 (фрагментация Initial) против ТСПУ.** Firefox 137 / quic-go v0.52.0 уже умеют разбивать CRYPTO. Методика: клиент с включённой фрагментацией → заблокированный по SNI домен по QUIC → факт прохода/блока. Один замер закрывает и вопрос №5.1 (реассембли CRYPTO у ТСПУ).

**P28-14. Честные метрики QUIC-стратегий.** Каждая стратегия в пуле — измерение pass/fail против эталона через `core/probe` (UDP/443, SNI заблокированного домена, фиксация факта прохода трафика, а не «открылось в браузере»). Наследовать запрет маркетинговых цифр из ZAPRET-EVOLUTION-SPEC §P0. Без этого пул стратегий превратится в коллекцию слухов.
