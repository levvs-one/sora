# 30. Fake-пакеты — эффективность

Аналитик №30. Только анализ, без имплементации. Источники: zapret/nfqws/winws документация и код (deepwiki по репозиториям bol-van/zapret, Flowseal/zapret-discord-youtube, Anonym-tsk/nfqws-keenetic), исследование FOCI'26 «On Russia's Early Introduction of QUIC SNI Censorship» (замеры март–апрель 2026, jonsnowwhite.de), отчёт criticalinfralab «TSPU and You» (09.2026), обзор Roskomsvoboda «Runet 2025: Sovereignization» (06.2026). Полевые данные есть только косвенные (конфиги сообщества, blockcheck2); прямых замеров эффективности fake против ТСПУ 2026 в открытых источниках нет — это ограничение отмечено в §5.

## 1. Какие fake-техники известны

Базовая идея одна: отправить DPI пакет, который он проинтерпретирует как начало handshake, но который реальный сервер проигнорирует/отбросит. Дальше — варианты того, *чем* фейк отличается от настоящего трафика.

**1.1. `fake` (TCP): инъекция фейкового ClientHello перед настоящим.** nfqws/winws (`--dpi-desync=fake`) шлёт один или несколько (`--dpi-desync-repeats`, типично 2–11) пакетов с правдоподобным TLS ClientHello до/вместе с настоящим. Полезная нагрузка — либо встроенный шаблон (`--dpi-desync-fake-tls=!`), либо hex (`0x00000000` — нулевые байты, тоже валидная стратегия в blockcheck2), либо файл-шаблон (`tls_clienthello_www_google_com.bin`, `tls_clienthello_4pda_to.bin`, `tls_clienthello_iana_org.bin`). Генеративные модификации (`--dpi-desync-fake-tls-mod`):
- `rnd` — рандомизация полей ClientHello;
- `rndsni` — случайный SNI каждый раз;
- `dupsid` — дублирование session ID (малформированный, но парсируемый пакет);
- `sni=www.google.com` — подмена SNI на белый домен;
- `padencap` — паддинг/инкапсуляция для смены структуры.

Комбинации: `fakedsplit` (фейк + сплит настоящего), `fakeddisorder` (фейк + диспордер), `hostfakesplit` (фейк, подстраивающийся под Host, с модификатором `host=ozon.ru`).

**1.2. Fooling — как сделать фейк невидимым для сервера (TCP).** Параметр `--dpi-desync-fooling`:
- `md5sig` — в фейк добавляется TCP-опция MD5 Signature с невалидной подписью. Почти все реальные серверы молча отбрасывают такие пакеты (RFC 2385/5925: несовпадение подписи = drop). DPI-парсеры опцию, как правило, не валидируют и читают payload.
- `badseq` — фейк с заведомо неверным sequence number (вне окна). Сервер отбрасывает out-of-window сегмент без RST; DPI читает его как начало потока. Требование: seq фейка не должен пересекаться с реальным потоком, иначе сервер ответит RST и убьёт соединение.
- `ts` — нулевой/невалидный TCP Timestamp.
- `hopbyhop` (IPv6) — Hop-by-Hop options header; часть hardware-offload движков пропускает такие пакеты мимо инспекции.

Комбинации в диких конфигах: `md5sig,badseq` (general.bat), `ts,md5sig` (ALT9), просто `badseq` (ALT, ALT8).

**1.3. `syndata` + `wssize`.** `--dpi-desync=syndata`: данные (фейковый ClientHello из `--dpi-desync-fake-syndata`) вкладываются прямо в SYN-пакет. Большинство TCP-стеков данные в SYN игнорируют (обрабатываются только при TCP Fast Open с валидной cookie); DPI, который извлекает handshake из первого же пакета с данными, «отравляется». Рабочие связки из преконфигов Discord (Beeline, Ростелеком): `syndata`, `syndata,split2`, `syndata,disorder2` + `--wssize 1:6` (урезание advertised window до 1–6 байт — сервер вынужден слать крошечные сегменты, что дополнительно ломает реассембли потока у DPI) + fooling `md5sig` + repeats 8–10. Отдельная техника из blockcheck2: дроп пустого ACK хендшейка на первом хопе (`--lua-desync=pktmod:ip4_ttl=1` на empty ACK) — ACK доставляется только в первом data-пакете, что сбивает DPI, ждущий чистый 3-way handshake.

**1.4. QUIC-фейки (UDP/443).** Основная стратегия для QUIC — только `fake` (сплиты для UDP бессмысленны):
- `--dpi-desync-fake-quic=quic_initial_www_google_com.bin` — готовый QUIC Initial с чужим Connection ID. Механика: DPI ведёт состояние по Connection ID; фейковый Initial с другим CID «отравляет» состояние именно этого CID, настоящий Initial с настоящим CID проходит мимо уже запутанного классификатора (по крайней мере, так это работало против старых реализаций).
- `--dpi-desync-repeats` для QUIC ставят выше (6–11 против 2 для TCP) — компенсация ненадёжности UDP.
- Порча UDP-уровня: `--dpi-desync-udplen-pattern=0xCAFEBABE`, `--dpi-desync-udplen-increment=15` — повреждение поля длины UDP; часть DPI отваливается на парсинге, сервер (quic-стек в userspace) пересчитывает/игнорирует.
- `fake,disorder2` для QUIC (CloudflareFix ALT).
- `--dpi-desync-fake-unknown-udp` / `--dpi-desync-any-protocol` — generic UDP-пейлоад для игр (Discord voice, `stun2.bin`), cutoff `n2`/`n3`.

## 2. Где работает / против каких DPI

Fake-техники работают против DPI, который:
1. стоит **in-path раньше сервера** и видит фейк;
2. ведёт **упрощённую state-машину TCP/QUIC**, отличную от стека конечного сервера (не валидирует MD5-опции, sequence numbers, данные в SYN, длину UDP);
3. выносит **вердикт рано** — по первым байтам потока (SNI из первого ClientHello) — и кэширует его.

Это классический «ленивый» DPI: реассемблирует поток дешёво, без полной валидации. Против DPI, который (а) ждёт ServerHello/подтверждения от сервера, (б) валидирует TCP-опции и seq как полноценный стек, (в) инспектирует *все* ClientHello в потоке, а не только первый, — fake не работает.

По операторам: в преконфигах сообщества fake-связки расписаны по провайдерам (Beeline, Ростелеком, Infolink, Cloudflare-направления) — т.е. эффективность операторо-зависима и требует подбора. Универсального «работает везде» нет; это подтверждается и архитектурой ТСПУ: решения ставятся на сети разных операторов, конфигурации различаются.

## 3. Как технически: механика, TTL/autottl, требования, риски

**Почему фейк ломает DPI.** DPI держит per-flow буфер реассембли и извлекает L7-сигналы (SNI, Host) из того, что *он* считает началом handshake. Конечный сервер строит состояние по строгим правилам TCP/QUIC и отбрасывает мусор (плохая MD5-подпись, seq вне окна, данные в SYN без TFO-cookie, мусорный QUIC Initial, который не расшифровывается). Расхождение моделей «что считать handshake» = десинхронизация: DPI анализирует фейк, сервер — настоящий пакет. Второй эффект: DPI, выносящий вердикт по первому ClientHello и кэширующий allow/block на flow, после фейка с белым SNI (`www.google.com`) пропускает настоящий пакет по кэшу.

**TTL — обязательное условие для TCP-фейков.** Фейк обязан умереть до сервера, иначе: (а) сервер может ответить RST (badseq с пересечением seq) или (б) фейк станет детектируемым артефактом на сервере. Схема: TTL фейка > дистанция до DPI, но < дистанция до сервера. DPI стоит in-path на первых хопах (у оператора), сервер далеко — окно существует. Режимы в nfqws:
- `--dpi-desync-ttl=N` — фиксированный TTL;
- `--dpi-desync-ttl=0` — фейк умирает на первом хопе (для UDP/Discord-кейсов);
- `autottl` — автоматический подбор: измеряется дистанция до DPI и до сервера, TTL ставится так, чтобы фейк истёк между ними. В blockcheck2 перебираются `ip4_ttl=1..12` и `ip4_autottl=-delta,3-20` (истечение между хопами 3–20 при дельте 1–5).

Важный нюанс: по criticalinfralab (09.2026) ТСПУ работает как **L2 transparent bridge in-path — не декрементирует TTL и невидим в traceroute**. Это не ломает TTL-трюк (фейк всё равно проходит через ТСПУ на первых хопах и умирает у дальнего роутера по ICMP time-exceeded), но ломает *наивный autottl*, который пытается «нащупать» DPI по хопам: нащупать нечего, устройство прозрачно. Правильная калибровка — «умереть заведомо раньше сервера», а не «умереть сразу за DPI».

**Требования к реализации:**
- перехват пакетов до ухода в сеть (NFQUEUE/tpws/nfqws на Linux, WinDivert на Windows) — фейк должен уйти *раньше* настоящего пакета того же flow;
- точный контроль IP TTL / Hop Limit на каждый фейк;
- для badseq — точный учёт seq/ack текущего соединения, seq фейка строго вне окна и без пересечения с реальными данными;
- для syndata — возможность вложить данные в SYN до connect() (raw-сокеты или перехват на уровне NFQUEUE);
- для QUIC — генерация валидного по структуре Initial (версия, CID, токен) с чужим CID.

**Риски:**
- **Детектируемость.** Сам десинк — сигнатура: повторы фейков, статичные шаблоны (`tls_clienthello_www_google_com.bin` лежат в открытых репозиториях — цензор может внести их в игнор-лист и просто не учитывать такие пакеты), ICMP time-exceeded штормы от умирающих фейков, аномальные TCP-опции (MD5) в исходящем трафике.
- **Ломка соединений** при неверной калибровке: TTL слишком мал — фейк не доходит до DPI, трюк не срабатывает, но соединение живёт; TTL слишком велик — фейк доходит до сервера (RST по badseq, мусор в логах сервера, потенциальный бан по IP за «атаку»).
- **Окно TTL схлопывается**, если сервер близко: CDN/GGC-ноды внутри сети оператора (YouTube через GGC!) находятся в 2–4 хопах — валидного TTL «после DPI, но до сервера» может не существовать в принципе.
- **Производительность**: repeats до 11, обработка каждого пакета через NFQUEUE — на мобильных устройствах это CPU/батарея; плюс рост объёма трафика.

## 4. Надёжность в РФ 2026

Коротко: **деградация сильная, но не до нуля; всё операторо-зависимо и требует постоянного переподбора.**

- Roskomsvoboda, «Runet 2025: Sovereignization» (06.2026): «с 2025 года известные утилиты GoodbyeDPI и Zapret **в значительной степени перестали работать**. В отличие от VPN, они лишь модифицировали пакеты — не шифровали трафик, и оборудование цензуры всё равно могло определить запрашиваемый ресурс». Это самый прямой публичный вердикт по классу fake/split-инструментов.
- Масштаб ТСПУ: на конец 2025 — 1406 комплексов, >132 Тбит/с, >1,2 млн сайтов и 258 VPN-сервисов заблокировано; бюджет РКН +60% в 2027 (31,8 млрд ₽), цель — 954 Тбит/с и блокировка 92% VPN к 2030. Ресурс на «переучивание» у цензора есть.
- QUIC-цензура полностью введена: FOCI'26 (замеры март–апрель 2026, три города РФ) — Россия **расшифровывает QUIC Initial, извлекает SNI и дропает пакеты** с запрещёнными доменами; списки для TLS и QUIC идентичны (2644 домена в выборке Tranco Top 100k); цензор сидит на 3–4 хопе от Москвы. Фейковый QUIC Initial против такого DPI — это гонка именно за state-машину (CID), а не за «невидимость» SNI: SNI в Initial цензор читать умеет.
- Послойная оборона (criticalinfralab, 09.2026): YouTube — SNI-троттлинг googlevideo.com с 08.2024, затем удаление youtube.com из НСДИ (DNS-уровень) в 02.2026; WhatsApp — то же в 02.2026; Telegram — блокировка звонков и троттлинг медиа с 08.2025. Победа над DPI-троттлингом ≠ победа над системой: fake-пакеты закрывают только DPI-слой.
- С другой стороны, сообщество zapret живо: blockcheck2 активно развивает fake-модули (50-fake-multi.sh, 55-fake-faked.sh), преконфиги обновлялись в 2025–2026, пользователи рапортуют о рабочих связках под конкретных операторов. **Слух (пометить):** в чатах встречаются утверждения, что ТСПУ «научился игнорировать» фейки с известными шаблонами — прямых доказательств нет, но статичность шаблонов делает это правдоподобным направлением контрмеры.

Вывод для планирования: fake — это тактика с периодом полураспада в недели-месяцы (что уже зафиксировано в `core/tune/desync/doc.go`: «параметр, выигравший сегодня, может умереть за 5–15 минут; ТСПУ переконфигурируется ночью»), а не стратегическое решение. Долгосрочно цензор выигрывает гонку против нешифрованного десинка — это прямо сказано в обзоре 2025 года.

## 5. Что неизвестно / требует проверки

1. **Строгость state-машины актуального ТСПУ.** Валидирует ли свежий ТСПУ TCP MD5-опцию, отбрасывает ли out-of-window сегменты из анализа, игнорирует ли данные в SYN, как ключирует QUIC-состояние (CID vs 5-tuple)? Открытых данных нет. Это главный неизвестный параметр — от него зависит, работает ли вообще класс fooling.
2. **Реакция на известные шаблоны.** Игнорирует ли ТСПУ фейки, байт-в-байт совпадающие с публичными `tls_clienthello_*.bin` / `quic_initial_*.bin`? Правдоподобно, но не подтверждено. Проверка: A/B тест `fake-tls=!` vs `rnd,rndsni` на одном операторе.
3. **Поведение autottl против L2-прозрачного ТСПУ.** Раз устройство не декрементирует TTL, классический «поиск DPI по хопам» бессмыслен; но работает ли эвристика «истечь между хопами 3–20» на практике в 2026 — требует полевого замера (нужен traceroute + blockcheck2 с реальных точек).
4. **QUIC CID-poisoning в 2026.** После внедрения SNI-цензуры QUIC (FOCI'26) — отравляет ли ещё чужой CID состояние DPI, или классификатор перешёл на 5-tuple + расшифровку каждого Initial? Неизвестно.
5. **Порог детекта десинка как сигнатуры.** Есть ли у ТСПУ эвристики «клиент шлёт фейки» → дроп/шейпинг всего flow? Слухи есть, подтверждений нет.
6. **GGC-случай.** Для YouTube через внутрисетевые GGC-ноды окно TTL может отсутствовать физически — никто не публиковал замер «дистанция до DPI vs дистанция до GGC» по операторам.
7. **IPv6.** Почти все рецепты fake — про IPv4; поведение fooling (hopbyhop) и autottl для IPv6/464NAT в РФ не документировано, а мобильный трафик всё чаще v6.

## 6. Проблемы для тех-агентов

Нумерация P30-N. Привязка к коду sora: `core/tune/desync/{doc.go,params.go}`, `core/engine/bypass` (tpws-исполнитель).

- **P30-1. Нет исполнителя fake в sora.** `Params.RequiresNFQWS()` честно маркирует `MethodFake`, `Fooling`, `TTL`, `AutoTTL`, `Repeats>1` как требующие nfqws; текущий исполнитель — только tpws (`core/engine/bypass`), который умеет split/disorder/oob/tlsrec. Нужен nfqws-исполнитель: Linux — NFQUEUE, Windows — WinDivert-порт, Android — дизайн перехвата (root с NFQUEUE? интеграция через VPNService + userspace TCP/IP стек с возможностью крафта SYN/TTL?). Без этого весь §1 — только теория для тюнера.
- **P30-2. autottl против прозрачного ТСПУ.** `Params.AutoTTL` сейчас — bool без семантики измерения. По criticalinfralab ТСПУ — L2-бридж, TTL не трогает, в traceroute невидим. Значит автокалибровка «найти хоп DPI» невозможна в принципе; реализуемая семантика — «TTL = дистанция_до_сервера − delta», где дистанция измеряется до *сервера*, а не до DPI. Требуется: дизайн измерения (TCP traceroute до canary-эндпоинта? TTL-probing через ICMP?), хранение delta на профиль сети (F5), обработка anycast/CDN (дистанция плавает).
- **P30-3. Схлопывание TTL-окна для близких серверов.** GGC/CDN внутри сети оператора: если сервер в 2–4 хопах, а DPI на 1–2, валидного TTL может не быть. Тюнер должен *измерять* дистанцию до сервера перед применением fake-стратегии и откатываться на split/disorder, когда окна нет. Сейчас в fitness-функции (doc.go: «forbidden content received × TCP not broken × brevity») этого измерения нет — кандидат с fake будет «выигрывать» в лабе и молча умирать на GGC.
- **P30-4. Безопасность badseq: один неверный seq = RST = разрыв.** Требуется попакетный учёт seq/ack соединения в исполнителе; seq фейка — строго вне окна, без пересечения с реальными данными, с учётом ретрансмитов и SACK. На мобильном клиенте с userspace-сетью это отдельный модуль учёта состояния TCP, а не «просто отправить пакет».
- **P30-5. md5sig нельзя подмешивать в настоящий трафик.** Исполнитель должен гарантировать: MD5-опция — только на фейках, никогда на реальных пакетах (иначе сервер начнёт их дропать — странные «необъяснимые» разрывы). Нужен инвариант на уровне кода + тест (property-тест: ни один исходящий не-фейк пакет не несёт MD5-опцию).
- **P30-6. syndata требует крафта SYN.** sing-box и ОС-сокеты не дают вложить данные в SYN до connect(). Реалистичные пути: NFQUEUE-перехват с модификацией SYN на лету (только Linux/root) либо собственный userspace TCP-стек. Для Android/Windows без root это, вероятно, нереализуемо — зафиксировать в матрице возможностей исполнителей, чтобы тюнер не предлагал syndata там, где её нельзя выполнить.
- **P30-7. Статичные шаблоны фейков — детектируемая сигнатура.** Геном тюнера (`seed.go`) должен включать рандомизацию шаблона как ось: `rnd`, `rndsni` per-connection, ротация SNI-белого-списка, `padencap`. Статичный `tls_clienthello_www_google_com.bin` как дефолт — это обучение цензора нашему паттерну. Дополнительно: частота смены шаблона vs стоимость генерации на мобильном CPU.
- **P30-8. QUIC-стратегии в тюнере недоопределены.** `ScopeQUIC` + `FakeProto:"quic"` есть, но нет: repeats 6–11 как отдельной оси, `disorder2` для UDP, udplen-порчи, fake-unknown-udp для игр/Discord voice. QUIC-цензура с расшифровкой Initial (FOCI'26) меняет механику: нужен эксперимент «CID-poisoning vs 5-tuple» (§5.4) до того, как закладывать QUIC-fake в продукт.
- **P30-9. Детект «тихой смерти» именно fake-стратегий.** rotate.go уже умеет ротацию, но отличить «fake перестал работать» от «сеть мигнула» по пассивным сигналам нетривиально: fake-смерть выглядит как внезапный SNI-блок при живом TCP. Нужны различимые пассивные признаки (например, счётчик «SYN+handshake прошли, а первый HTTP/3 запрос получил blockpage/RST») и пороги, иначе ротатор будет крутить стратегии на каждом чихе.
- **P30-10. Стоимость fake в fitness-функции.** Repeats ×11 и фейки на каждый handshake — это мультипликатор трафика и CPU (NFQUEUE per-packet). Член «brevity» в fitness должен учитывать *полную* стоимость (пакеты × CPU-время обработки), иначе тюнер выберет самый «громкий» и самый заметный вариант. На мобильных — отдельный бюджет (батарея).
- **P30-11. Заметность активного зондирования.** doc.go уже требует: только canary-эндпоинты sora, только по явному действию пользователя, rate-limit. Для fake это критичнее, чем для split: ICMP time-exceeded от умирающих фейков и MD5-пакеты видны оператору как аномалия исходящего трафика. Политику probing нужно расширить именно на fake/repeats (лимиты повторов, джиттер, запрет на продовые домены из блоклиста).
- **P30-12. IPv6/nat64.** Весь рецепт fake — IPv4-центричный (TTL, MD5-опция, hopbyhop только упомянут). Мобильный клиент часто на IPv6 или 464NAT; нужны: Hop Limit вместо TTL, эквивалент fooling для v6, проверка, что операторы применяют ТСПУ к v6-трафику так же (не факт). Без этого fake-стратегии будут молча не применяться на половине мобильных сетей.
- **P30-13. Валидация «не навреди» для fooling.** Перед включением fooling в прод нужен стенд, проверяющий, что серверы из топ-N (Google, Cloudflare и т.д.) действительно дропают md5sig/badseq-фейки молча, а не банят IP за «сканирование/атаку». Один неверный сервер — и sora начнёт сжигать IP-адреса пользователей.
