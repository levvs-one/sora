# №27. Обход SNI-фильтрации — что работает

Аналитик №27/50, отдел анализа ТСПУ/блокировок. Дата: 2026-10-20.
Тема: методы обхода SNI-фильтрации, их механика и реальная работоспособность против ТСПУ РФ (октябрь 2026).

Источники: веб-поиск 7 запросов (приоритет 2025–2026), полевые тесты Riposte/Levelflow (08.2026, СПб), FOCI 2025 (Paderborn), CDT, AdGuard, rks.global «Runet 2025». Слухи помечены явно.

---

## 1. Какие методы обхода SNI-фильтрации известны

| # | Метод | Суть в одной строке | Статус |
|---|-------|---------------------|--------|
| M1 | TCP-фрагментация ClientHello (`split`) | Разбить ClientHello на 2+ TCP-сегмента так, чтобы SNI разорвался посередине | Работает (в связке) |
| M2 | Фрагментация TLS-записи (`tlsrec`) | Разбить TLS record, а не TCP-сегмент | Работает (в связке) |
| M3 | Десинк фейковыми пакетами (`fake`, `disorder`, `oob`, `syndata`) | Подсунуть DPI фейковый пакет до/вместо настоящего | Работает — основной метод 2026 |
| M4 | TTL-трюки (`fake` + короткий TTL) | Фейк-пакет доходит до ТСПУ, но умирает до сервера | Работает (в связке) |
| M5 | ECH — Encrypted Client Hello (RFC 9849, 03.2026) | Шифрование внутреннего ClientHello, снаружи виден только cover-SNI | В РФ заблокирован (ноя.2024–…) |
| M6 | ESNI (Encrypted SNI, draft) | Предшественник ECH, шифровал только поле SNI | Мёртв |
| M7 | Domain fronting (SNI ≠ Host) | SNI разрешённого домена, Host заблокированного | Классика мертва на крупных CDN |
| M8 | SNI-спуфинг / REALITY | SNI чужого «белого» сайта, сервер валидирует по-своему | Работает — золотой стандарт для прокси |
| M9 | Direct-to-IP (пустой/отсутствующий SNI) | Подключение по IP без SNI | Нишевый, часто бесполезен |
| M10 | QUIC-десинк | Те же приёмы (fake/split) для QUIC Initial по UDP/443 | Работает там, где UDP/443 жив |

Дополнительно (не SNI-обход в чистом виде, но смежно и влияет на результат): uTLS/JA3-маскировка fingerprint'а ClientHello, DoH/DoT (иначе SNI виден в DNS до TLS).

## 2. Где проверено / против кого работает

### 2.1. Полевые тесты, август 2026 (Riposte / Levelflow)

Тестовая установка: СПб, домашний интернет, инструменты в WSL2 (ByeDPI, zapret2, youtubeUnblock, B4), DoH включён. Методика: baseline без инструмента (11–12 прогонов) vs инструмент (5 прогонов), curl + ручная проверка в браузере.

Результат (сводно):

- **Открылись со всеми 4 инструментами**: Instagram, Facebook, Discord, LinkedIn, Signal, Novaya Gazeta Europe, Deutsche Welle, ProtonVPN.
- **Meduza**: открылась через `fake_ttl8`, youtubeUnblock, zapret2; НЕ открылась через `disorder_tlsrec` (стратегия-зависимо!).
- **YouTube**: только youtubeUnblock и zapret2 (QUIC-десинк). ByeDPI — нет.
- **Telegram**: заблокирован при всех инструментах (не SNI-уровень — см. §4).
- **ProtonMail**: `mail.proton.me` не открылся ни с чем; `account.proton.me` открылся через zapret2. Подозрение авторов: блок по IP, а не по SNI (не проверено отдельно).
- **WhatsApp**: нестабильно со всеми инструментами (причина не установлена — протокол или баг инструментов).

Источник: https://riposte.levelflow.org/2026/08/bypasswithoutavpn/

### 2.2. ECH против ТСПУ РФ

- **Ноябрь 2024**: после включения Cloudflare ECH по умолчанию ТСПУ начал рвать соединения. Условие блокировки: в ClientHello одновременно присутствуют **расширение ECH** и **SNI = `cloudflare-ech.com`** (публичное имя из ECH-конфига Cloudflare). РКН подтвердил блокировку официально (AdGuard: https://adguard-dns.io/sk/blog/encrypted-client-hello-misconceptions-future.html; CDT: https://cdt.org/insights/do-not-stick-out-the-dynamics-of-the-ech-rollout/).
- Полевой симптом (Habr, цит. по Riposte): сайты на Cloudflare с ECH висли до таймаута в браузере (Chrome/Firefox с ECH), но открывались через `wget` (без ECH). После временного отключения Cloudflare TLS 1.3 (= отключение ECH) сайты из РФ открылись за минуты. Вывод: ТСПУ дропает ClientHello с ECH, а не IP.
- **Китай**: блокирует ECH «более гибко» (CDT); плюс блокирует зашифрованный DNS — косвенная цензура ECH (FOCI 2025: https://ris.uni-paderborn.de/record/60503).
- **Иран**: блокировка зашифрованного DNS → косвенное убийство ECH (FOCI 2025).
- Измерение ECH-деплоя (TU Dresden, 2026): до 247 SLD с ECH public names вне Meta/Cloudflare; **NordVPN использует ECH для ~1.5k доменов** (антицензурное применение!); 33% из 105.7k измеренных ECH-доменов — в зоне `.ru`, и они «по-прежнему подвержены ECH-блокировке, развёрнутой в России, при обращении по QUIC». Meta раздаёт ECH без публикации в DNS. Источник: https://netd.cs.tu-dresden.de/papers/mgsw-dechd-26.pdf

### 2.3. Протокольные блокировки (контекст, не SNI, но важно)

- По заявлению оператора инфраструктуры (dev.to, 10.2025 — **анекдот одного оператора, не измерение**): «резня протоколов» — OpenVPN 100% детект за 30 сек, WireGuard душат, Shadowsocks 95%, Trojan пал от active probing (08.2025), VMess — от DPI-сигнатур (09.2025), выжил только VLESS (+TLS+WS+CDN), детект <5%.
- **Декабрь 2025**: волна блокировок VLESS; VPN Guild призвал не паниковать; к началу декабря работоспособность XRay постепенно восстановилась (rks.global «Runet 2025»: https://rks.global/files/research/censorship_review_2025_en.pdf?v=2).
- rks.global утверждает: «с 2025 GoodbyeDPI и Zapret в значительной степени перестали работать». **Конфликт с полевыми тестами 08.2026** — см. разбор в §4.5 (помечаю как спорное).
- Carnegie (05.2026): РКН «теоретически» умеет детектить VPN по сигнатурам, но «не имеет способа» против VLESS+REALITY/XTLS; мощности фильтрации «на пределе»; планируется ИИ. https://carnegieendowment.org/russia-eurasia/politika/2026/05/russia-vpn-usage-political

### 2.4. Domain fronting

- Классика мертва на: AWS и Google (~2018), Cloudflare (ещё ~2015), Azure (кон. 2022), Fastly (~2024). Источник: https://deepstrike.io/blog/what-is-domain-fronting
- Но: рецензированное исследование на ACM Web Conference 2024 протестировало 30 провайдеров — **22 допускали какую-то форму fronting** в tested-конфигурациях, включая крупные имена (Akamai, Fastly). Цит. по: https://www.wizlynxgroup.com/news/domain-fronting-modern-evasion/ — т.е. «мёртв» только в дефолтных конфигах мейджоров; на мелких CDN и self-hosted реверс-прокси жив.
- В 2018 РФ блокировала IP крупных CDN целиком ради убийства fronting — прецедент готовности цензора к collateral damage.

## 3. Как технически: механика каждого метода

### M1. TCP-фрагментация ClientHello (`--dpi-desync=split`, `split2`)

ClientHello (обычно 200–600 байт; с постквантовым key share X25519MLKEM768 — ~1.8 КБ, сам бьётся на 2 сегмента) разрезается на уровне TCP: первый сегмент обрывается **внутри** строки SNI (`--dpi-desync-split-pos=N`, напр. позиция 1–2 от начала payload или внутри hostname: «instag» | «ram.com»). DPI, читающий «на лету» без реассембли TCP-потока, не видит домен целиком → нет совпадения с реестром → пропускает. Сервер собирает сегменты штатным TCP-стеком.

- Против кого работает: DPI без полной TCP-реассембли на скорости линии (классические инлайн-боксы, читающие первые N пакетов).
- Против кого НЕ работает: DPI с реассемблей (современные ТСПУ частично умеют); DPI, триггерящийся на сам факт фрагментации; DPI, смотрящий ServerHello/сертификат (TLS 1.2) или IP.

### M2. Фрагментация TLS-записи (`tlsrec`, ByeDPI `disorder_tlsrec`)

Та же идея, но разрез на границе TLS record (5-байтный header + fragment), а не TCP-сегмента. Иногда комбинируется с перестановкой порядка (`disorder`): второй фрагмент отправляется раньше первого. DPI, ожидающий «TLS record целиком в пакете», ломается; TCP-стек сервера переупорядочивает.

- Работает против DPI, парсящего TLS поверх предположения «1 пакет = 1 record».
- Не работает против DPI с TLS-реассемблей; требует, чтобы сервер терпел disorder (обычно да).

### M3. Десинк фейковыми пакетами (`fake`, `disorder`, `oob`, `syndata`)

Ключевая идея (академическая база — Geneva, CCS 2019): состояние DPI ≠ состояние сервера. Отправляем **фейковый пакет раньше настоящего**:

- `fake`: пакет с мусором/пустым ClientHello и «порчеными, но безвредными» полями (fooling: `md5sig` — опция TCP MD5, `badseq` — неверный seq, `badsum`). DPI обрабатывает фейк как «уже видел сессию» или решает, что всё легитимно, и перестаёт следить. Сервер отбрасывает фейк (неверный seq/контрольная сумма), принимает настоящий.
- `syndata`: данные, впихнутые в SYN-хендшейк (против DPI, анализирующего хендшейк; пресет Rostelekom в zapret-discord-youtube).
- `oob`: out-of-band данные (TCP urgent).
- Fake ClientHello как приманка: `--dpi-desync-fake-tls=tls_clienthello_www_google_com.bin` — фейк выглядит как handshake к google.com.

Против кого: инлайн-DPI с упрощённой TCP-машиной состояний (следит только за первым пакетом/потоком, не валидирует seq как сервер). Не работает против DPI с полной эмуляцией TCP-стека и против терминации TLS на DPI (MITM у корпоративных).

### M4. TTL-трюки (`--dpi-desync-ttl`, `fake` + autottl)

ТСПУ стоит **на пути раньше** сервера (у провайдера). Фейк-пакет отправляется с TTL, которого хватает до бокса DPI, но не до сервера (напр. `--dpi-desync-ttl=6`, `--dpi-desync-autottl`). DPI видит фейк, сервер — никогда. Затем идёт настоящий пакет с нормальным TTL.

- Работает, пока топология стабильна (число хопов до ТСПУ известно/подбирается autottl).
- Не работает: если DPI стоит близко к серверу/далеко непредсказуемо; при смене маршрута (мобильные сети!); если DPI игнорирует TTL-истекшие пакеты и ждёт настоящий.

### M5. ECH (RFC 9849, март 2026; DNS-бутстрап RFC 9848)

Два ClientHello: **outer** (plaintext, SNI = public_name, напр. `cloudflare-ech.com`, виден всем) + **inner** (зашифрован публичным ключом из DNS HTTPS-записи домена, содержит настоящий SNI и чувствительные расширения). Сервер расшифровывает inner своим приватным ключом; при неудаче — достраивает handshake по outer (не рвёт).

Критические слабости против цензора:

1. **Расширение ECH видно в plaintext** — детектируемо само по себе. РФ блочит не «весь ECH», а точечно: ECH-ext + SNI `cloudflare-ech.com` (§2.2). Китай — «гибче» (CDT).
2. **Фиксированный public_name** у Cloudflare (`cloudflare-ech.com` во всех outer) — единая сигнатура. ECH с другим public_name теоретически сложнее детектить массово (CDT).
3. **Зависимость от зашифрованного DNS**: ECH-конфиг берётся из HTTPS-записи → нужен DoH/DoT. Китай и Иран блочат зашифрованный DNS → ECH мёртв без боя (FOCI 2025).
4. **IP не скрыт**: на выделенном IP ECH бесполезен (видно, к кому идёшь по IP).
5. **Fallback**: без ECH-конфига клиент падает в обычный handshake с plaintext SNI.
6. GREASE ECH (фиктивное расширение, когда ECH не нужен) — задумано против ossification, но против цензора, режущего «неизвестные расширения», не испытано (см. §5).

Клиенты: Firefox 119+ по умолчанию, Chrome/Chromium по умолчанию. Серверы: Cloudflare — единственный мейджор (FOCI 2025); NGINX 1.29.4 (02.2026) и OpenSSL 4.0 добавили ECH — self-hosting стал возможен.

### M6. ESNI — мёртв

Шифровал только поле SNI, оставляя остальные расширения видимыми; уязвим к traffic analysis. Cloudflare: «Good-bye ESNI, hello ECH». Браузеры выпилили. Использовать негде и незачем.

### M7. Domain fronting (SNI ≠ Host)

SNI = разрешённый домен (фронт), внутри TLS — HTTP Host = заблокированный. Работало, пока CDN не валидировал соответствие SNI↔Host. Мейджоры закрыли (см. §2.4). Остатки: мелкие CDN, misconfigured distributions, **self-hosted фронт** (свой reverse proxy: SNI свой, Host любой — но тогда «фронт» блочится точечно, нет collateral-damage-защиты).

Для sora практический вывод: как клиентская техника — только со своим фронтом (см. M8).

### M8. SNI-спуфинг / REALITY

Клиент ставит SNI **чужого, заведомо «белого» сайта** (напр. `www.microsoft.com`, `ya.ru`), а сервер (Xray REALITY) завершает handshake так, что active probing возвращает настоящий сайт: «real cert, real chain, real content» (cybernews, 2026: https://cybernews.com/security/ussians-bypass-kremlin-firewall-with-diy-proxies/). Условия:

- Сервер должен держать TLS-fingerprint, неотличимый от прикрытия (uTLS-параноидальный уровень), и проксировать непосвящённых на настоящий origin.
- SNI должен резолвиться/быть правдоподобным; dest-домен — с валидным сертом, желательно на CDN/крупном хостере, который цензор не станет блочить целиком.
- Вариант для whitelist-режимов (мобильные шатдауны 2026): конфиги `[SNI-RU]` — `sni=ya.ru` + IP из белого диапазона; `[*CIDR]` — VPS в подсети VK/Yandex/CDNvideo (community-данные: https://deepwiki.com/igareck/vpn-configs-for-russia/1.1-black-lists-vs-white-lists — **не верифицировано независимо**).

Против кого: любой SNI-реестровый DPI (ТСПУ, GFW) — пока прикрытие бело и fingerprint чист. Не работает против: active probing с поведенческим анализом (Trojan пал именно так, 08.2025); статистического анализа потока (AmneziaWG-разработчики прямо пишут: obfuscation не всегда спасает от behavioral detection); блокировки по IP сервера.

### M9. Direct-to-IP

Подключение на IP без SNI (или SNI = IP). Имеет смысл, только если: у сайта выделенный IP, серт валиден без SNI, а блок — чисто SNI-реестровый. Практика: почти все крупные заблокированные сидят за shared CDN-IP → без SNI сервер не выберет серт/бэкенд. Плюс DPI-правило «нет SNI → дроп» существует как опция (Cloudflare Gateway так и рекомендует корпоратам). Нишево.

### M10. QUIC-десинк

QUIC Initial шифруется ключами, **выводимыми из публичных значений** (RFC 9001) → SNI из Initial извлекаем любым наблюдателем (таблица Vectra: https://www.vectra.ai/topics/encrypted-traffic-analysis). ТСПУ это знает: по данным TU Dresden, ECH-блокировка в РФ применяется и к QUIC. Техника: `--dpi-desync=fake` для UDP/443 с фейковым QUIC Initial (`quic_initial_www_google_com.bin`), `--dpi-desync-udplen-increment` (порча UDP length). Полевые тесты 08.2026: YouTube (HTTP/3) открылся только через QUIC-десинк (youtubeUnblock/zapret2). Ограничение: UDP/443 местами режется целиком — тогда только fallback на TCP.

## 4. Надёжность: что реально работает в РФ (октябрь 2026)

### 4.1. Работает (подтверждено полевыми тестами / надёжными источниками)

1. **Десинк фейками + фрагментация (M1–M4) в связке** — zapret2, ByeDPI, B4, youtubeUnblock открывают SNI-заблокированные домены (Instagram, Facebook, Discord, LinkedIn, СМИ) по состоянию на 08.2026. Стратегия обязана подбираться **per-ISP** (пример: Meduza открылась через `fake_ttl8`, но не через `disorder_tlsrec`; у Rostelekom — `syndata,split2` + repeats=8).
2. **QUIC-десинк** — единственный рабочий путь к YouTube/HTTP/3-ресурсам там, где UDP/443 не зарезан целиком.
3. **VLESS + REALITY (M8)** — handshake неотличим от визита на белый сайт; «транспорт, реже всего ломавшийся от обновлений ТСПУ в 2025–2026» (analysis-atlas). Волна декабря 2025 пережита, работа восстановлена.
4. **DoH/DoT как базовый слой** — без него SNI-обход бессмысленен (домен виден в DNS раньше TLS). Все полевые тесты 2026 шли с DoH.

### 4.2. Умерло

1. **ESNI** — выпилен отовсюду, заменён ECH.
2. **Классический domain fronting на мейджор-CDN** — закрыт провайдерами (2015–2024).
3. **ECH через Cloudflare в РФ** — режется с 11.2024 по сигнатуре (ECH ext + `cloudflare-ech.com`). НЕ режется «весь ECH как протокол» — точечная сигнатура.
4. **Наивная одиночная фрагментация без фейков** против свежих ТСПУ — по совокупности данных, «голый split» 2019 года давно не панацея; работают комбинации.

### 4.3. Спорное / противоречивое

**«Zapret/GoodbyeDPI перестали работать с 2025»** (rks.global, Runet 2025). Против: полевые тесты 08.2026 (все 4 инструмента работают), активная разработка zapret2 (Lua-стратегии), B4, свежие пресеты под ISP. Разбор противоречия: rks.global, вероятно, фиксирует смерть **дефолтных/старых стратегий и GoodbyeDPI-пресетов**, а не метода как такового. Метод жив, но требует per-ISP тюнинга и обновлений под прошивки ТСПУ — это уже не «поставил и забыл». Помечаю утверждение rks.global как **неподтверждённое и противоречащее полевым данным**.

### 4.4. Что НЕ берётся SNI-обходом (важно для скоупа)

- **Telegram** (08.2026: заблокирован при всех инструментах) — уровень IP/протокола, не SNI.
- **Полный IP-блок / route cutoff** — «если IP недоступен даже без TLS — нужен полный туннель, а не десинк» (Riposte).
- **Whitelist-шатдауны мобильной связи** (2026, Москва и др.) — при «белом списке» из госсайтов SNI-десинк не помогает; работают только `[SNI-RU]`/`[*CIDR]`-хаки (community-уровень, см. §5).
- **Протокольный fingerprinting** (JA3/JA4, статистика потока) — десинк SNI его не чинит; нужен uTLS + traffic shaping.

| split/tlsrec+fake (M1–M4) | ✅ работают в связке, per-ISP тюнинг | ⚠️ частично (GFW умнее, active probing) | ⚠️ частично | ❌ whitelist, почти всё убито |
| ECH | ❌ режется (сигнатура CF) | ❌ блочится | ❌ косвенно (нет DoH) | ❌ |
| ESNI | ❌ мёртв везде | ❌ | ❌ | ❌ |
| Domain fronting | ❌ на мейджорах | ❌ | ❌ | ❌ |
| SNI-spoof/REALITY | ✅ осн. метод для прокси | ✅/⚠️ | ✅ | ⚠️ (IP-блоки) |
| Direct-to-IP | ⚠️ нишево | ⚠️ | ⚠️ | ❌ |
| QUIC-десинк | ✅ где UDP/443 жив | ⚠️ | ⚠️ | ❌ |

Легенда: ✅ — подтверждено источниками 2025–2026; ⚠️ — частично/условно; ❌ — не работает. Пустые клетки вне РФ — по открытым данным, полевых тестов у меня нет (см. §5).

## 5. Что неизвестно / требует проверки

1. **Вендорность ТСПУ.** «ТСПУ» — зонтичный термин; боксы разных производителей/прошивок (RDP.ru, EcoFilter и др. — состав не раскрывается) ведут себя по-разному. Нет карты «прошивка × уязвимая стратегия». Все пресеты — эмпирические, per-ISP.
2. **Глубина реассембли.** До какого размера/глубины ТСПУ собирает TCP-поток и TLS-записи в 2026? От этого зависит, какие split-позиции ещё живы. Данных нет — только косвенные (работающие пресеты).
3. **GREASE ECH.** Режет ли ТСПУ ClientHello с «мусорным» ECH-расширением? Если нет — это потенциальный детект-обход для ECH-детекта (но не для SNI-скрытия). Не тестировалось.
4. **ECH с не-Cloudflare public_name.** Блок 11.2024 — точечный (CF-сигнатура). Работает ли ECH через self-hosted (NGINX 1.29.4 / OpenSSL 4.0) с собственным public_name из РФ в 2026? Полевых данных нет; TU Dresden фиксирует рост таких деплоев.
5. **DoH-давление.** Периодические деградации публичных резолверов (1.1.1.1, 8.8.8.8) в РФ — влияет и на ECH (нужен для HTTPS-записей), и на базовый слой. Нет свежих замеров доступности.
6. **Мобильные vs фиксированные.** Большинство пресетов и тестов — фиксированный ШПД. Поведение ТСПУ у мобильных операторов (особенно в режимах шатдауна/whitelist) изучено хуже; `[SNI-RU]`-конфиги — community-уровень.
7. **QUIC Initial parsing в ТСПУ.** Умеет ли ТСПУ извлекать SNI из QUIC Initial (ключи публичные) или блочит QUIC грубо по UDP/443? TU Dresden: ECH-блок применяется и к QUIC — значит, парсинг есть хотя бы частично.
8. **IPv6.** Стратегии тестировались почти исключительно на IPv4; покрытие ТСПУ v6-трафика — неизвестно.
9. **Активный probing против REALITY.** Trojan пал от active probing 08.2025; насколько ТСПУ сейчас зондирует REALITY-серверы — неизвестно.
10. **Региональная вариативность.** Тесты 08.2026 — СПб; VPS в МСК/СПб «большинство доменов открывалось и без инструментов». Карты по регионам нет.

## 6. Проблемы для тех-агентов (требуют решения)

Контекст: sora — Flutter UI + Go-ядро (sing-box/Xray/mihomo), платформы Windows/Linux/Android. Проблемы сформулированы как конкретные технические задачи, а не пожелания.

**P27-1. Десинк на L3/L4 невозможен из userspace Go-ядра напрямую.**
Zapret-стратегии (fake-пакеты с поддельным seq/ttl, `syndata`, `oob`, QUIC-fake) требуют raw sockets / NFQUEUE / WinDivert / VpnService-TUN. Go-ядро sing-box работает на уровне потоков, а не пакетов. Требуется архитектурное решение: (а) отдельный нативный хелпер per-OS (WinDivert-драйвер на Windows, NFQUEUE/nftables на Linux, VpnService на Android), (б) либо userspace TCP/IP-стек поверх TUN с ручной сегментацией, (в) либо отказ от fake-пакетов и реализация только `split`/`tlsrec` на уровне записи (разбивка TLS-фрагмента на несколько `write()` — реализуемо в Go, но покрывает лишь M1/M2). Без решения — никакого «встроенного zapret» в клиенте не будет.

**P27-2. Нет методики per-ISP автоподбора стратегии.**
Полевые тесты 08.2026 показывают: одна и та же стратегия открывает Meduza через `fake_ttl8`, но не через `disorder_tlsrec`; у Rostelekom нужен `syndata,split2` с repeats=8. Клиенту нужен **авто-профайлер**: при первом запуске прогнать батарею стратегий против набора эталонных заблокированных доменов, замерить успех/скорость и закэшировать профиль (ISP, регион, фикс/мобайл). Формат профиля, набор эталонов и критерий «успеха» (curl-200 vs рендер в браузере — см. расхождение curl/браузер в тестах) — не определены.

**P27-3. TTL-автоподбор хрупок на мобильных сетях.**
`autottl` калибруется под число хопов до ТСПУ; на мобильных сетях маршрут плавает (смена базовой станции, NAT оператора). Нужна стратегия периодической рекалибровки и fallback на non-TTL стратегии при дрейфе. Не исследовано.

**P27-4. QUIC-десинк требует UDP raw / TUN на Android.**
YouTube/HTTP/3 без QUIC-десинка не открывается (тесты 08.2026). На Android без root единственный путь — VpnService с перехватом UDP и ручной сборкой QUIC Initial fake-пакетов. Объём работы и влияние на батарею не оценены.

**P27-5. Статус ECH в клиенте: включать или нет?**
Факты: ТСПУ режет связку (ECH-ext + `cloudflare-ech.com`) с 11.2024; браузеры шлют ECH по умолчанию. Если sora просто проксирует браузерный трафик — ECH-пакеты будут молча умирать, и это будет выглядеть как «сайт не открывается». Требуется: (а) полевой тест в 2026 — режется ли *любой* ClientHello с ECH-расширением или только CF-сигнатура; (б) решение — резать/даунгрейдить ECH на клиенте (убирать расширение, форсить plaintext SNI + десинк) или вести через self-hosted ECH с собственным public_name (NGINX 1.29.4+); (в) GREASE ECH — тест, триггерит ли блок.

**P27-6. Зависимость ECH и антицензурного DNS от DoH.**
ECH-конфиг (и вообще резолв без подмены) требует DoH/DoT; публичные резолверы в РФ под периодическим давлением. Нужен встроенный в клиент DoH-клиент с несколькими апстримами + happy-eyeballs + детект подмены, иначе ECH и половина десинк-техник бессмысленны (SNI виден в DNS раньше TLS).

**P27-7. Подбор dest-домена для REALITY/SNI-спуфинга не автоматизирован.**
REALITY жив, пока «белый» dest-домен: валидный серт, правдоподобный TLS-fingerprint, CDN/хостер, который не заблочат целиком, стабильный IP. Сейчас это ручная работа оператора сервера. Для продукта нужен **валидатор прикрытия**: скрипт, проверяющий кандидата (сертификат, fingerprint через uTLS-скан, ASN/хостер, отсутствие в реестре, latency из РФ) и периодически перепроверяющий. Не существует.

**P27-8. Active probing против инфраструктуры.**
Trojan пал от зондирования (08.2025). Насколько ТСПУ зондирует REALITY/VLESS-серверы сейчас — неизвестно. Требуется: серверная гигиена (проксирование непосвящённых на настоящий origin — уже в Xray), плюс мониторинг «странных» handshake-паттернов на серверной стороне. Для клиента — задача серверной стороны, но клиент должен уметь быстро ротировать dest.

**P27-9. Детект режима блокировки (RST-inject vs drop vs IP-cutoff).**
Riposte: «если IP недоступен даже без TLS — десинк не поможет, нужен туннель». Клиент должен сам диагностировать: ICMP/TCP-доступность IP → TLS без SNI → TLS с SNI → классифицировать (SNI-блок / IP-блок / DPI-reset / throttling) и выбирать метод (десинк vs полный туннель vs «не лечится»). Такой автодиагностики ни в одном открытом клиенте нет.

**P27-10. Расхождение «curl говорит 200, браузер показывает битую страницу».**
Полевые тесты: curl-200 при фактически деградированной странице (Signal: не грузятся картинки/скрипты — часть субресурсов режется). Значит, бинарный чек «открылось/нет» недостаточен; профайлер стратегий (P27-2) должен проверять **набор субресурсов/доменов страницы**, а не один URL. Методика не выработана.

**P27-11. SNI-десинк не чинит fingerprint-блокировки.**
Десинк прячет SNI, но JA3/JA4 ClientHello и статистику потока — нет. При переходе цензора на protocol-fingerprinting (тренд 2025–2026: OpenVPN/WireGuard/SS душат по сигнатурам) клиент обязан: uTLS-маскировка ClientHello под Chrome (проверить, что умеют sing-box/Xray из коробки и чего не хватает), плюс shaping трафика. Это отдельный трек, но без него SNI-обход — половина решения.

**P27-12. IPv6 — слепая зона.**
Все пресеты и тесты — IPv4. Если у пользователя включён IPv6 и сайт резолвится в AAAA, десинк-стратегии могут просто не применяться к v6-потокам (или ТСПУ их не смотрит — тогда это, наоборот, лазейка). Требуется замер: что видит ТСПУ на v6 в 2026.

**P27-13. Побочные эффекты fake-пакетов.**
Фейковые RST/SYN с плохим seq — поведение, которое корпоративные IDS и некоторые серверные фаерволы классифицируют как hostile. Для продукта нужен дисклеймер и, желательно, режим «только split/tlsrec» (без фейков) для чувствительных окружений. Юридическая оценка не проводилась.

**P27-14. Telegram и мессенджеры — не обещать.**
08.2026: Telegram заблокирован при всех SNI-инструментах (IP/протокольный уровень). В UI клиента нельзя маркировать SNI-десинк как «обход для Telegram» — только полный туннель/прокси протокола.

**P27-15. Whitelist-режимы (мобильные шатдауны 2026).**
При «белом списке» (госсайты + VK + операторы) классический десинк бесполезен — разрешено только whitelisted. Community-хаки `[SNI-RU]` (sni=ya.ru) / `[*CIDR]` (VPS в подсети VK/Yandex) — не верифицированы независимо, хрупки и, вероятно, уже прибиты. Требуется отдельное исследование, а не перенос в продукт вслепую.
