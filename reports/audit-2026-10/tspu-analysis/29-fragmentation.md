# 29 — Фрагментация против ТСПУ

Аналитик №29. Анализ на основе публичных источников 2025–2026 (измерения и реверсы — в приоритете, блоги — во вторую очередь). Непроверенные утверждения помечены как слухи.

## 1. Какие виды фрагментации применяются

Три разных уровня, не путать:

**1.1. TCP-сегментация ClientHello (самый массовый вид).** ClientHello разрезается на несколько TCP-сегментов так, чтобы ни один пакет не содержал цельный SNI. Инструменты: GoodbyeDPI (`-f/--frag`), zapret (`split2`/`multisplit` в nfqws), SpoofDPI (`--split sni|first-byte|chunk|random`), DPIBreak (разрез по смещению 1: первый байт отдельно), TlsFragment (Python, dual-layer). Также есть «обратная» сегментация (`--reverse-frag` в GoodbyeDPI): сегменты шлются в обратном порядке — ряд DPI-парсеров не умеют переставлять буфер. GoodbyeDPI `-f 2 -e 2 --native-frag` режет прямо на позиции SNI (`--frag-by-sni` — только для доменов из блэклиста); классика: `-f 2` (разрез через 2 байта, чтобы сломать парсинг заголовка TLS-record) и `-e 2/40`.

**1.2. TLS record fragmentation (`tls_fragment` в sing-box / xray).** Работает на уровне TLS-записей, а не TCP: один ClientHello переупаковывается в несколько валидных TLS-записей (content type 0x16 + version + новый length), каждая может уйти своим TCP-сегментом. В sing-box это `common/tlsfragment` с двумя режимами: `splitPacket` (разрез на TCP-сегменты по границам label'ов SNI — «www», «example», «com»; каждый сегмент ждёт ACK перед отправкой следующего, включён `TCP_NODELAY`) и `splitRecord` (переупаковка в отдельные TLS records). Разрез именно по границам label'ов SNI — ключевая деталь: большинство DPI-парсеров SNI извлекают домен как одну строку из одного пакета/записи; разрез внутри label'а эффективнее, чем между полями. В xray-core — эквивалент: `fragment` в настройках `freedom`-outbound (`packets: "tlshello"`, `length`, `interval`), т.е. фрагментация на уровне прокси-транспорта, а не пакетного десинка. Полевые конфиги 2025–2026 для РФ: `fragment=1-3,10-20,tlshello,null` (цепочка `tls-fragment → skip-fragment → full-fragment` в Xray-examples, Iran configs: `tls-fragment` packets=`tlshello` length=`6`; `full-fragment` packets=`1-1` length=`1` interval=`4` — до ~517 сплитов).

**1.3. IP-фрагментация.** Разрез на уровне IPv4-фрагментов (MF-бит, fragment offset), а не TCP-сегментов. Применяется редко: в VPN/прокси-клиентах почти не используется; встречается у низкоуровневых десинк-инструментов и в сканерах (nmap `-f/--mtu`). Зачем упоминать: DPI, который делает IP-риассемблирование, всё равно его обычно делает по-своему (см. раздел 3), и поведение ТСПУ при IP-фрагментах — отдельная поверхность для тестов.

## 2. Где работает / против каких DPI

**ТСПУ/РКН, РФ:** фрагментация — основной рабочий приём GoodbyeDPI/zapret против ТСПУ с 2021 по 2026. Половая практика 2026 (bypasscore.com, 2026): против ТСПУ-троттлинга YouTube «GoodbyeDPI, ByeDPI или Zapret работают для большинства провайдеров»; стандартные стартовые стратегии — GoodbyeDPI `-5 --set-ttl 5`, zapret `split2+disorder2`. Детализация по zapret2 (deepwiki анализ, 2026): `split2`/`multisplit` работают, потому что «простые DPI-движки не умеют TCP-риассемблирование», `disorder`/`multidisorder` ломают stateful-инспекцию, ожидающую линейного прибытия пакетов. Там же: у ТСПУ двухстадийная блокировка (анализ 5–15 мин → обновление списков), против неё zapret2 крутит стратегии по кругу (`--lua-desync=circular`). Отдельный факт 2026: у ТСПУ достигнут паритет инспекции IPv6 (март 2026) — стратегии нужно применять и к IPv6 явно.

**Иран:** Xray-examples документирует целые цепочки фрагментации (`tls-fragment → skip-fragment → full-fragment`) как основу обхода иранского DPI; фрагментация там давно в продакшене в связке с VLESS+Reality.

**Ограничения по операторам:** эффективность фрагментации в РФ неоднородна по операторам и регионам (как и всё остальное в ТСПУ). По отдельным репортам 2025–2026 чистая сегментация на части операторов перестаёт работать — см. раздел 4.

**Где НЕ работает как самодостаточное средство:** фрагментация прячет SNI в ClientHello, но ничего не делает с IP-назначения (блокировки подсетей VPN-хостеров, август–сентябрь 2026), с DNS, с сигнатурами протоколов (WireGuard/OpenVPN детектятся за миллисекунды вне зависимости от фрагментации) и с белыми списками (default-deny при отключениях мобильного интернета — там фрагментировать нечего, всё нер азрешённое падает).

## 3. Как технически: почему фрагментация ломает парсинг DPI, размеры/позиции разрезов, ограничения

**Почему ломает.** Типовой DPI-сенсор ТСПУ (line-rate бокс на стыке оператора) парсит TLS inline: ищет в пакете байт 0x16 (handshake) + 0x01 (ClientHello), дальше по смещениям находит extension server_name и извлекает SNI строкой, сравнивает с блоклистом. Разрез ломает любой из шагов:
- разрез в первые 5 байт (TLS record header: `16 03 01 LL LL`) — сенсор не видит валидного заголовка и вообще не распознаёт пакет как TLS;
- разрез в первые ~50 байт — ломается парсинг структуры ClientHello (версия, random, session id, cipher suites имеют переменную длину, длины закодированы в самих полях — без начала нельзя прыгнуть к SNI);
- разрез внутри самого SNI (`blocked-|site.com`) — сенсор видит обрывок строки, точное совпадение с блоклистом не срабатывает;
- разрез по границам label'ов SNI (подход sing-box splitPacket) — хитрее: парсеры, извлекающие SNI посимвольно из одного буфера, получают куски «www» / «example» / «com» в разных пакетах.

**Размеры и позиции (конкретика из инструментов):**
- GoodbyeDPI `-f 2`: разрез через 2 байта от начала payload — бьёт по record header; `-e 2`: то же для HTTPS; `--native-frag` — фрагментация на уровне TCP-сегментов вместо манипуляции окном; `--reverse-frag` — сегменты в обратном порядке (для серверов, не переваривающих сегментированный ClientHello, и против парсеров без реордеринга).
- zapret `split2`: разрез в позиции, вычисляемой по SNI (`--dpi-desync-split-pos`), обычно 1–3; `multisplit`: несколько разрезов; `disorder2`: первый сегмент шлётся с маленьким TTL (дохнет на сенсоре ТСПУ, не доходя до сервера) + правильный порядок по seqnum — сенсор видит мусор, сервер — чистый поток.
- sing-box splitPacket: разрезы строго на границах DNS-label'ов внутри SNI; каждый сегмент отправляется только после ACK предыдущего (stop-and-wait) — это медленно, но максимально «невинно» выглядит для stateful-парсера: обычный TCP с маленькими сегментами.
- TlsFragment: двухстадийный — сначала TLS-записи режутся на `num_tls_pieces` (2–3), SNI распределяется по записям по 1–5 байт (`len_tls_sni`), затем TCP-сегментация по 1–10 байт SNI на сегмент (`len_tcp_sni`), опционально `send_interval` 0–0.1 с.
- DPIBreak default: разрез по смещению 1 — первый байт отдельно, остальное вторым сегментом.
- xray fragment outbound: `packets: "tlshello"` (фрагментировать только первый TLS-пакет), `length: "100-200"` — случайная длина кусков в диапазоне, `interval: "10-20"` — мс между кусками; цепочки усиливают: `skip-fragment` (первый пакет целиком, задержка 560 мс — сенсор ждёт), затем мелкие куски.

**Ограничения: DPI с реассемблированием.** Фрагментация — не криптография, а экономическая атака на бюджет DPI: реассемблирование TCP-потока на 100 Gbps стоит памяти (буфер на поток), CPU и состояния; большинство сенсоров его не делают полностью. Но ограничения реальны:
- DPI, который буферизует первые N КБ потока (а не один пакет), переживёт простую сегментацию — достаточно собрать первые ~2 КБ, и SNI будет виден целиком. Слух (не подтверждено измерениями): на части российских операторов с 2025 фрагментация без фейков/десинка работает хуже — сообщество отвечает комбинациями `split+fake+disorder`.
- Out-of-order и перекрывающиеся сегменты: у каждого TCP-стека своя политика разрешения перекрытий (BSD vs Linux vs Windows); сенсор, собирающий поток «по-простому» (первый пришедший сегмент побеждает), видит не то, что видит сервер. - IP-фрагментация против DPI: большинство stateful-систем IP-фрагменты реассемблируют (дешёвый буфер: max ~64 КБ на датаграмму, короткий таймаут), либо дропают; как средство сокрытия SNI уступает TCP-сегментации и почти не применяется в клиентских VPN.
