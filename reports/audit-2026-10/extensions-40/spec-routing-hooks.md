# Спека: Routing hooks API (тема 4)

Статус: **спека** (кода нет — сначала контракт).
Связано: `core/ext/manifest_v1ext.go` — поле `routing: {entry}` (contract
pointer, уже добавлен); permission `routing.rules` (dangerous), capability
`routing`.

## 1. Цель

Расширение добавляет правила маршрутизации (домены/диапазоны → direct /
proxy / block) — например, «обход нового DPI» как набор правил. Правила —
декларативные данные, а не код.

## 2. Формат: `routing.json`

```json
{
  "routing_version": 1,
  "rules": [
    {"id": "ads", "match": {"domain_suffix": "ads.example.com"},
     "action": "block", "priority": 80},
    {"id": "corp", "match": {"ip_cidr": "10.0.0.0/8"},
     "action": "direct", "priority": 90}
  ]
}
```

Поля match (ровно один тип на правило): `domain` (точное), `domain_suffix`,
`domain_keyword` (подстрока — с явным предупреждением о широте),
`ip_cidr`, `port` (только в паре с domain/ip — голый `port: 443 → proxy`
запрещён: слишком широко). Action: `direct` | `proxy` | `block`.

## 3. Валидация (install/enable/update, fail closed)

- ≤ 512 правил, `id` уникальны, `^[a-z0-9-]{1,32}$`.
- `domain_suffix`/`domain` — валидные DNS-имена (тот же `normalizeHostPattern`
  подход, что в `network_hosts`); `ip_cidr` — парсится `net.ParseCIDR`,
  одноадресные /32 и /128 разрешены, `0.0.0.0/0` — запрещён (перехват всего
  трафика правилом расширения недопустим).
- `priority` — 0..100, default 50.
- Правило, ломающее валидацию, роняет **весь файл** (не «пропускаем плохое» —
  молчаливое дропание правил это театр: пользователь думает, что защита
  работает).

## 4. Приоритеты и детерминизм

Порядок вычисления для соединения:

1. Правила пользователя (из UI приложения) — всегда выше.
2. Правила расширений: сортировка по `(priority DESC, installed_at ASC,
   rule id ASC)` — полностью детерминирована, воспроизводима, тестируема.
3. Дефолты движка.

Первое совпавшее правило побеждает (first-match). Пересечения логируются в
лог расширения («ваше правило X перекрыто правилом пользователя Y») —
пользователь видит, почему трафик пошёл не так, как ожидало расширение.

## 5. Применение и откат

- Все правила всех включённых расширений компилируются в **одну** таблицу
  маршрутизации при любом изменении набора (install/enable/disable/update).
- Компиляция атомарна: собрали → провалидировали → swap. Ошибка в одном
  расширении → его правила исключаются целиком, остальные работают, в лог —
  ошибка. Предыдущая скомпилированная таблица хранится до успешной замены.
- Откат версии расширения = перекомпиляция из `routing.json` N-1 (файл лежит
  в директории версии — источник правды, как и манифест).
- Отключение расширения → его правила исчезают из таблицы мгновенно
  (тот же one-tap принцип, что отзыв токенов).

## 6. Производительность

Правила компилируются в префиксное дерево (домены — суффиксное trie,
CIDR — radix tree), а не в линейный список: O(длина) на соединение вместо
O(N правил). Лимит 512 правил на расширение — чтобы таблица оставалась
маленькой; движок дополнительно капает суммарный размер.

## 7. Отсеяно и почему

- JS/WASM-колбэки на соединение («динамическая маршрутизация кодом») —
  это произвольный код на горячем пути трафика: латентность, падения,
  невозможность аудита. Декларативных правил достаточно для всех
  заявленных кейсов (DPI-обходы — это списки доменов/IP).
- `action: proxy` с указанием *какого* прокси — выбор outbound остаётся за
  пользователем/движком; расширение говорит «проксировать», а не «куда».
  Иначе расширение тихо уводит трафик на свой сервер.
- Маскировка под системные правила (приоритет > пользовательского) —
  запрещено архитектурно: пользователь всегда выше расширения.
