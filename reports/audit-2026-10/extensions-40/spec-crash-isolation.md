# Спека: Crash isolation — падение расширения не роняет приложение и ядро (тема 9)

Статус: **частично внедрено** (воркеры), остальное — спека с точками
внедрения. Модель процессов зафиксирована по факту кода, а не выдумана.

## 1. Модель процессов (как есть)

| Компонент | Где живёт | Падение роняет |
|---|---|---|
| App (Flutter) | свой процесс | — (это он и есть) |
| Core (Go) | отдельный сервис-процесс (systemd / Windows service), gRPC по unix-socket / named pipe | только себя; app переподключается (`CoreLink.open` ретраится бесконечно) |
| Extension host, Scheduler, net.fetch | внутри core-процесса (Go) | только себя — см. п.2 |
| Панели | WebView в app-процессе, рендер — в изолированном renderer-процессе платформы | renderer — нет; app — нет |
| Воркеры (JS-раннер) | seam `WorkerFunc`; раннер — app side (будет внедрён) | см. п.2 |

Вывод: «расширение роняет ядро» возможно только через панику в Go-коде
расширенческого рантайма внутри core-процесса. Всё ниже — про эту границу.

## 2. Что уже внедрено (этот прогон + ранее)

- Паника в `WorkerFunc` гасится `recover()` в `runOnce`, пишется в лог
  расширения как failed run — планировщик жив.
- Наложение запусков запрещено (atomic guard): зависший ран не порождает
  лавину горутин.
- Circuit breaker: 10 подряд падений/ошибок → задача снята с расписания,
  расширение остаётся установленным; следующий старт приложения
  перерегистрирует (шанс на самовосстановление после фикса).
- Токены расширений — только в памяти: падение core инвалидирует их все;
  app выпускает заново при старте. Отзыв при disable/uninstall/rollback —
  мгновенный (`RevokeByExtension`) + TTL 24 ч как пояс (смежный отдел).
- Панель: `extension.disabled` → экран закрывается (`_onStoreChanged` →
  `maybePop`), loopback-сервер останавливается, кэш WebView чистится.

## 3. Супервизия core-процесса: кто за кого отвечает

- Владельцем рестарта core является **сервис-менеджер ОС** (systemd
  `Restart=`, Windows SCM recovery). Приложение НЕ должно дублировать
  супервизию: два супервизора = флаппинг и гонки за сокет.
- Работа приложения при мёртвом core: `CoreLink.open` уже ретраит с
  бэкоффом; UI показывает честное состояние «ядро недоступно, переподключение…»
  (не «всё хорошо»). Панели расширений в этом состоянии показывают
  `extPanelUnavailable` — уже есть.
- Телеметрия падений core: при переподключении app сверяет uptime/инкарнацию
  core (поле в handshake — добавить) и пишет в диагностику «core restarted»:
  пользователь/разработчик видит, что падения были, а не гадает.

## 4. Панели: падение renderer-процесса

- Современные WebView изолируют renderer: его падение не роняет app.
- Точка внедрения (app side, проверить на dev-машине — Flutter SDK здесь
  нет): обработчик `onRenderProcessGone` → показать в панели экран
  «панель упала» с кнопкой «перезагрузить» (пересоздать контроллер +
  перезапустить loopback-сервер). Без кнопки-«магии»: причина пишется в
  лог расширения.
- Защита от цикла «упала → перезагрузили → упала»: счётчик падений
  renderer за 5 минут; ≥ 3 → панель остаётся в состоянии ошибки до
  ручного тапа (та же философия, что circuit breaker воркеров).
- Bridge-вызовы в момент мёртвого renderer: `runJavaScript` уже обёрнут в
  try/catch с игнором — поведение корректное (панель мёртва, события
  никому не нужны).

## 5. Воркеры: падение JS-раннера (когда будет внедрён)

- Раннер — отдельный Dart isolate на расширение. Падение isolate (uncaught)
  → планировщик получает ошибку run, а не смерть процесса.
- Вотчдог wall-time: превышение `WorkerRunTimeout` → `isolate.kill()`,
  в лог — `run failed: timeout`. Kill, а не «вежливая просьба».
- Изоляция секретов: isolate воркера не получает control token и токены
  других расширений; его `WorkerEnv` — единственный мост наружу.

## 6. Политика рестарта (сводно)

| Событие | Реакция | Порог |
|---|---|---|
| Падение одного run воркера | лог, повторить по расписанию | — |
| N подряд падений run | снять задачу до рестарта app | N = 10 |
| Падение renderer панели | экран ошибки + кнопка перезагрузки | 3 падения / 5 мин → стоп до ручного тапа |
| Падение core-процесса | рестарт — за ОС; app переподключается и честно показывает состояние | — |
| Падение app-процесса | рестарт — за ОС; расширения/состояние восстанавливаются из стора | — |

## 7. Отсеяно и почему

- «Супервизор расширений» отдельным процессом/вотчдогом внутри core —
  лишний процесс ради того, что уже дают recover + circuit breaker +
  сервис-менеджер ОС. Сложность без выигрыша.
- Авторестарт задачи воркера после circuit breaker по таймеру —
  будило бы мёртвое каждые N минут ради ничего; рестарт app — естественная
  и понятная точка.
- Перехват `os.Exit`/фаталов из кода расширения — код расширения не
  выполняется в core-процессе как Go (только WorkerFunc-шлюз), так что
  перехватывать нечего; JS-раннер — в isolate (п.5).
