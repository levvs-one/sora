# Спека: Quotas — лимиты CPU/RAM/сети для расширений (тема 8)

Статус: **частично внедрено** (см. «Что уже в коде»), остальное — спека.
Принцип: квота применяется там, где ресурс реально потребляется, и только
там, где измерение честное. Фальшивая точность (псевдо-CPU-аккаунтинг
горутин в Go) — это театр, её здесь нет.

## 1. Что уже в коде (этот прогон + ранее)

| Ресурс | Механизм | Где |
|---|---|---|
| Сеть (число запросов) | token bucket 30/мин, burst 10 | `netfetch.go` rateLimiter |
| Сеть (объём) | тело запроса ≤ 1 MiB, ответа ≤ 8 MiB | `netfetch.go` |
| Сеть (время) | 30 s на запрос, редиректы ≤ 3 | `netfetch.go` |
| Сеть (диагностика) | счётчики Requests/Denied/BytesOut/BytesIn | `Fetcher.Stats()` (этот прогон) |
| CPU/время воркера | один запуск ≤ 5 мин; пропуск при наложении; circuit breaker 10 падений | `worker.go` (этот прогон) |
| Частота воркеров | интервал клампится в [15 мин, 7 дней] | `worker.go` |
| Память (лог) | ring 256 записей × ≤ 1024 байт | `extlog.go` |
| Память (пакет) | ≤ 64 MiB архив, ≤ 256 MiB распаковки, ≤ 4096 файлов | `package.go` |
| Память (fetch-буферы) | ≤ 8 MiB на ответ, лимит чтения | `netfetch.go` |

## 2. CPU: честная граница

Go не умеет атрибутировать CPU по горутинам — любой «лимит CPU на
расширение» внутри core-процесса был бы выдумкой. Поэтому:

- Воркеры: исполнение ограничено **wall-time** (5 мин) + запрет наложения
  (этот прогон). JS-раннер (app side, когда будет внедрён) запускает скрипт
  в отдельном isolate с вотчдогом: превышение wall-time → terminate isolate,
  в лог — ошибка. Wall-time, а не CPU-time: для фоновой задачи разница
  несущественна, а измерение честное.
- Панели: WebView — отдельный рендер-процесс платформы. Лимит «CPU»
  выставляется средствами ОС (Android: `onTrimMemory`, iOS: приоритет
  процесса, десктоп: ничего — там рендерер уже изолирован). Приложение не
  притворяется, что управляет планировщиком ОС.
- Диагностика вместо прецизионного лимита: лог воркера пишет длительность
  каждого запуска (`run ok (1.2s)` — уже есть); экран деталей показывает
  медиану за 24 ч. Аномалия видна пользователю без фальшивых графиков.

Отсеяно: cgroup-лимиты (непортируемо на Android/iOS/Windows единообразно),
«CPU-квота в процентах» для горутин (неизмеримо — значит, враньё).

## 3. RAM: границы по компонентам

- Core-процесс: все буферы расширений уже капированы (таблица выше).
  Дополнительно: суммарный лимит `Fetcher`-буферов не нужен — 8 MiB × N
  расширений при N ≤ десятков не угроза; если расширений сотни — их столько
  не будет, установка поштучная.
- Панели: при `didReceiveMemoryWarning`/`onTrimMemory` приложение дропает
  фоновые WebView панелей (оставляет только видимую). Это спека на app side:
  хук в `ExtensionPanelScreen.dispose` уже закрывает сервер и чистит кэш —
  добавить реакцию на системный сигнал нехватки памяти.
- Воркер-JS: isolate с лимитом heap (Dart: нет прямого лимита — вотчдог по
  wall-time + ограничение частоты запусков; честно документировать, что
  heap-лимит JS-окружения — вотчдог, а не капа).

## 4. Сеть: что ещё

- Суммарный дневной лимит на расширение (например, 500 MiB/день через
  net.fetch): поверх существующих per-request лимитов. Счётчики уже есть
  (`BytesIn/BytesOut`) — добавить окно 24 ч и мягкий стоп с уведомлением
  пользователю («расширение X исчерпало дневной лимит»). Жёсткий стоп без
  предупреждения — нет: молчаливая поломка функциональности хуже.
- Панели: сеть запрещена полностью (CSP `connect-src 'none'` — внедрено:
  meta при распаковке + заголовок с loopback-сервера).

## 5. Диагностика превышений (обязательно, не опционально)

Квота без видимости — это черный ящик. Экран деталей расширения показывает:

- fetch: Requests/Denied/Bytes за 24 ч (из `Fetcher.Stats()` + окно);
- воркер: последний запуск (ok/failed, длительность), счётчик подряд
  идущих падений, факт срабатывания circuit breaker;
- лог: все отказы уже пишутся с уровнем Warn/Error.

Пользователь, видя «Denied: 412», понимает, что расширение стучится не
туда, — это и есть репутационный механизм из EXTENSIONS-VISION.

## 6. Отсеяно и почему

- Платные/токенные квоты («расширению N мегабайт в месяц») — оверинжиниринг
  для v1; дневного окна и per-request лимитов достаточно.
- Приоритизация трафика расширений vs VPN-трафика — net.fetch идёт через
  тот же туннель без отдельных QoS-классов; делить полосу внутри клиента —
  слоп, который никто не настроит правильно.
