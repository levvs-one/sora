# 48 — Android VpnService: tun fd, per-app VPN, battery impact, always-on; best practices для будущего Android-клиента

Дата: 2026-10-20. Третий проход группы E. Android-клиента у sora пока нет (первый проход: темы 47 — батарея, 46 — упоминание VpnService-лимитов). Здесь — API-механика для проектирования с нуля, чтобы не повторять грабли v2rayNG/NekoBox.

## 1. Tun fd: как это работает (первоисточник — developer.android.com)

`VpnService.Builder.establish(): ParcelFileDescriptor?` (https://developer.android.com/reference/kotlin/android/net/VpnService.Builder):
- Интерфейс работает **на IP-пакетах**: каждое чтение из fd — исходящий пакет, каждая запись — входящий. fd по умолчанию в **non-blocking** режиме; для нативного кода — `ParcelFileDescriptor.detachFd()`.
- Приложение **обязано закрыть fd** при завершении соединения; интерфейс удаляется системой автоматически.
- **Только один активный VPN-интерфейс** в системе. Конкуренция с AdGuard/файрволами/enterprise-VPN — реальная причина «подключился и сразу отвалился» (35vpn.com, 2026).
- `establish()` возвращает `null`, если приложение не prepared или отозвано — обрабатывать как race, а не как фатальную ошибку.
- Бесшовный хендовер: можно создать новый fd, осушить старый, закрыть — старый деактивируется автоматически.

Ключевые параметры Builder: `addAddress()` (виртуальный IP), `addRoute()` (маршруты, `0.0.0.0/0` — весь трафик), `setMtu()` (**жёсткий потолок: VpnService требует MTU ≤ 1500** — грабли MTU 9000 из темы 47 на Android невозможны физически, система не даст), `addDnsServer()`, `setSession()` (имя в системных настройках), `setBlocking(false)` для нативного I/O.

Архитектура для sora: Kotlin/Java `VpnService` только **владеет fd и жизненным циклом**, весь датаплан — в Go-core (sing-box как библиотека через gomobile или отдельный процесс с передачей fd). Паттерн NekoBox/v2rayNG: `protect()` сокетов движка обязателен — иначе трафик движка завернётся в собственный TUN (петля).

## 2. Per-app VPN

- `addAllowedApplication(pkg)` — allowlist: **только** эти приложения идут через VPN, остальные — напрямую. `addDisallowedApplication(pkg)` — denylist: эти — напрямую, остальные — через VPN.
- Списки задаются **до** `establish()`; изменение = пересоздание интерфейса.
- Приложение должно быть установлено на момент добавления (проверять через PackageManager, иначе `NameNotFoundException`).
- `allowBypass()`: разрешить приложениям самим выбирать сеть через `bindProcessToNetwork`/`bindSocket`. Нюанс приватности: bypass-приложения могут увести трафик мимо kill switch.
- Платформенный лимит (из доков sing-box, тема 41): Android VpnService **не переваривает большое число маршрутов** — `route_address_set` с большими списками роняет систему (`DeadSystemException`). Правило: на Android — маршруты `0.0.0.0/0` + `::/0` и вся гранулярность **внутри** движка (правила sing-box), а не системными роутами.

## 3. Always-on и lockdown (системный kill switch)

- Находятся в **системных настройках** (Settings → Network & Internet → VPN → gear): **Always-on VPN** + **«Block connections without VPN»** (Lockdown Mode). Приложение само включить их не может (кроме device owner через `DevicePolicyManager.setAlwaysOnVpnPackage`).
- Что это даёт sora бесплатно: автопереподключение при дропе туннеля и системный kill switch без своего кода. Что нужно от sora: **экран-инструкция**, ведущий пользователя в системные настройки (диплинк `android.settings.VPN_SETTINGS`), и детект состояния («lockdown не включён — предупредить»).
- Trade-off lockdown: ломаются банковские приложения, локальные принтеры, captive portal, enterprise-инструменты — честно предупреждать (перекликается с первым проходом, тема 06).

## 4. Battery impact: что реально жрёт и как проектировать

По первому проходу (тема 47): протокол — главный рычаг (WireGuard ~4%/час, OpenVPN хуже в разы); keepalive — второй (WG молчит в простое — использовать); «тихий убийца» — нестабильный сервер (ре-хандшейки будят радио).

Проектные решения для sora-Android:
1. **Foreground Service + постоянная нотификация** — без этого Doze и вендорные киллеры (Samsung, Xiaomi, OnePlus) убивают туннель через 5–15 минут при выключенном экране. Нотификация — не косметика, а условие выживания процесса (35vpn.com).
2. **Battery optimization exemption**: просить пользователя выставить «Unrestricted» (Settings → Apps → Battery). `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` — под запретом политики Play для большинства кейсов → вести гайдом внутри приложения, а не пермишеном. Плюс vendor-by-vendor гайд как у Mullvad (Samsung «Never sleeping apps» и т.д.).
3. **Умный keepalive**: дефолт адаптивный (25 с за NAT, 0 в простое), не пробрасывать слепо из подписки (уже зафиксировано в теме 47).
4. **Протокольный приоритет**: на мобильных дефолтить WireGuard/AmneziaWG-варианты; тяжёлые цепочки (VLESS+TCP+фрагментация) — только при нужде обхода. Встроить в автовыбор «режим экономии».
5. **Auto-secure по сетям** (Windscribe-паттерн): дома на доверенной сети — VPN выключен (0 расхода), на публичном Wi-Fi — включён. Связка с сетевыми профилями F5.
6. **Не врать про расход**: Android приписывает VPN-приложению трафик всех приложений за туннелем (misattribution) — показывать свой честный замер (CPU/радио-время движка) с объяснением.

## 5. Жизненный цикл и стабильность (частые грабли)

- **Смена сети** (Wi-Fi ↔ LTE): детектить через `ConnectivityManager.NetworkCallback`, пересоздавать сессию движка, осушать старый fd. Тест: заблокировать экран на 10 минут, разбудить, проверить что трафик идёт без ручного переподключения.
- **Captive portal**: детектить (`ConnectivityManager.getNetworkCapabilities` → `NET_CAPABILITY_CAPTIVE_PORTAL` / `isCaptivePortal`), временно выпускать трафик к порталу мимо туннеля (паттерн Speedify из первого прохода).
- **Private DNS** (Android 9+): конфликтует с VPN-DNS — при проблемах советовать «Automatic».
- **Не стакать два VPN**: проверять, не занят ли TUN другим приложением, и говорить пользователю какое именно.
- **Doze**: даже foreground-сервис в Doze ограничен — критичные переподключения делать через `setAndAllowWhileIdle`, не через точные таймеры.

## 6. Вердикт: лучшее или слоп

**Лучшее.** VpnService API зрелый и документированный; все грабли (fd lifecycle, 1500-потолок MTU, DeadSystemException на маршрутах, вендорные киллеры) известны заранее и закрываются проектными решениями, а не хаками. Системные always-on + lockdown дают kill switch бесплатно — не писать свой.

## 7. Рекомендация «внедрить так» (чеклист архитектуры Android-клиента)

1. Kotlin `VpnService`: только Builder + fd + `protect()` + lifecycle. Датаплан — Go-core (sing-box ≥1.15 как библиотека), fd через `detachFd()`.
2. MTU дефолт **1400** (запас под мобильные underlay), hard cap 1500 — проверять в коде, а не надеяться на систему.
3. Маршруты: только `0.0.0.0/0` + `::/0`; вся гранулярность — правилами движка (лимит DeadSystemException).
4. Per-app VPN: `addAllowedApplication`/`addDisallowedApplication` до `establish()`; списки — из существующего split-tunnel UI (переиспользовать, не строить заново).
5. Экран «Защита системы»: диплинк в системные VPN-настройки + детект always-on/lockdown + честные предупреждения о trade-off.
6. Foreground service + нотификация + in-app гайд по battery exemption (vendor-by-vendor) + умный keepalive + протокольный приоритет WG.
7. Тест-матрица перед релизом: Doze 8 часов, смена Wi-Fi/LTE 20 раз, captive portal, конкуренция с другим VPN-приложением, перезагрузка с always-on.
8. На будущее: Android 17 стандартизирует системный split tunneling — заложить абстракцию, чтобы переключиться без рефакторинга.
