# 04. WebSocket транспорт — early data, CDN-фронтинг, лимиты

Дата: 2026-10-20. Источники: официальные доки XTLS Project X (websocket), исходники Xray (`transport/internet/websocket`), sing-box docs (v2ray-transport: `max_early_data`), mihomo `transport/vmess/websocket.go`, полевая практика CDN 2025–2026.

## Early data / «0-RTT»: механика

Это **не TLS 0-RTT**, а early data на уровне HTTP-апгрейда:

- **Xray:** если `path` содержит параметр `ed` (например `/mypath?ed=2560`), включается Early Data. Клиент base64url-кодирует первый пакет (VLESS/Trojan-заголовок) и кладёт его в заголовок `Sec-WebSocket-Protocol` прямо в upgrade-запросе. Сервер извлекает его до завершения апгрейда. Экономия: **1 RTT** на установку соединения — заметно на высоком пинге (RU→EU/US).
- Число — порог длины первого пакета: рекомендуемое **2560**, максимум **8192**. Если первый пакет длиннее порога — early data не включается (молча). Слишком большое значение → проблемы совместимости с некоторыми прокси/CDN (режут длинные заголовки).
- **sing-box:** `max_early_data` (0 = выкл). Отличие: по умолчанию early data кладётся **в path**, а не в заголовок. Для совместимости с Xray-сервером нужно `early_data_header_name: "Sec-WebSocket-Protocol"`. **Должно совпадать с сервером** — иначе хендшейк не сойдётся.
- **mihomo:** та же механика (`websocketWithEarlyDataConn`, base64url без паддинга в заголовке, `transport/vmess/websocket.go` 41–48, 177–203).

**Практический вывод:** early data — реальная, измеримая оптимизация (минус RTT на каждое новое WS-соединение), цена — только корректная настройка обеих сторон. Порог 2560 покрывает типичный VLESS-заголовок.

## Механика CDN-фронтинга

Почему WS — классический CDN-транспорт:

1. **Upgrade проходит через любой HTTP-реверс-прокси** (nginx, Caddy, Cloudflare). Сервер Xray может стоять за nginx с `proxy_pass` или за Cloudflare (порты 443, 2052–2096 и др.).
2. **Разделение SNI и Host (domain fronting):** TLS SNI = легитимный CDN-домен, HTTP `Host` = реальный бэкенд. Цензор видит TLS к «чистому» домену.
3. **security=none за CDN:** TLS терминируется на edge CDN, до origin идёт plain WS — допустимо, т.к. CDN-канал доверенный.
4. `X-Forwarded-For` в Xray имеет приоритет над PROXY-протоколом для определения source IP (важно для серверных логов/лимитов).

## Лимиты — честные

1. **Официальное предупреждение XTLS (DANGER в доках):** «рекомендуется перейти на XHTTP». Причина: у WS-трафика характерный признак — **ALPN `http/1.1`** (WebSocket в Xray не работает поверх h2). Современные браузеры почти всегда negotiates h2/h3 — долгоживущее h1.1-соединение с WS-паттерном выделяется.
2. **WS + REALITY не поддерживается** (таблица совместимости XTLS) — для REALITY есть TCP и XHTTP.
3. **Одно TCP-соединение = один стрим** (без мультиплексирования на уровне транспорта; mux поверх — отдельно). Обрыв = пересоздание всего.
4. **Буферизующие прокси** могут ломать стриминг (лечится SSE-заголовками, но это уже территория XHTTP).
5. **Cloudflare:** проксирует WS, но есть idle-таймауты и троттлинг; длинные сессии могут рваться — нужен heartbeat (`heartbeatPeriod`, Xray; по умолчанию пинги не шлются вообще, `0` = выкл).
6. **heartbeatPeriod** (секунды, клиент/сервер): интервал WS-Ping для keepalive через NAT/прокси. Дефолт-выкл — на мобильных сетях соединение может молча умирать.

## Вердикт: лучшее с оговорками

WS — зрелый, отлаженный, максимально совместимый с CDN транспорт. Early data — настоящее улучшение (1 RTT). Но: XTLS официально двигает всех на XHTTP из-за `ALPN http/1.1`-сигнала; для новых деплоев WS — уже не первый выбор. Слоп-фильтр: «WS невидим за Cloudflare» — неверно (паттерн долгоживущего h1.1-WS виден); «early data = настоящий 0-RTT с его рисками реплея» — неверно, это другой механизм.

## Внедрить в sora так

Состояние sora: `wsSettings` рендерится только с `path/host` (`engine/xray/render.go`); sing-box — `type: ws` с path/headers. Early data, heartbeat — отсутствуют везде.

1. **plan.go:** `Transport` ← `EarlyData int` (порог, 0=выкл, дефолт 2560 при включении), `HeartbeatPeriod int` (сек, 0=выкл).
2. **render.go (xray):** `path + "?ed=<n>"` при включённом EarlyData (ровно так это задаётся в Xray — через path!); `heartbeatPeriod` в `wsSettings`.
3. **render.go (sing-box):** `max_early_data: <n>`, и **автоматически** `early_data_header_name: "Sec-WebSocket-Protocol"` когда сервер — Xray (иначе рассинхрон механики). В UI/диагностике показывать, какой вариант negotiated.
4. **validate.go:** EarlyData > 8192 → ошибка; предупреждение при WS без TLS вне CDN («голый ws по интернету виден полностью»).
5. **UI:** при выборе WS — чекбокс «Early data (минус 1 RTT)» + подсказка про порог; поле heartbeat для мобильных сетей; **баннер**: «XTLS рекомендует XHTTP вместо WS (ALPN http/1.1 — детектируемый признак)» со ссылкой на миграцию в один клик (смена транспорта с сохранением сервера).
6. **Диагностика:** тест «WS через CDN»: проверка upgrade через указанный хост, замер handshake RTT с/без early data — наглядная цифра для пользователя.
7. **Не делать:** автовключение `ed` без проверки серверной стороны (серверы не-Xray его не поймут); позиционирование WS как «стелс» — честно помечать как «совместимый, но с известным сигналом».
