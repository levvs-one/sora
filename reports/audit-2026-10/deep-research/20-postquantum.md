# 20. PQ-гибриды на практике — X25519MLKEM768, серверный PSK WireGuard; что внедрять, что маркетинг

Дата: 2026-10-20. Источники: RFC 10024 (авг. 2026), Cloudflare (апр. 2026), wadebush.com / postquantumsecurity.org (сен. 2026), qntonsol.com (окт. 2026), Chromium PQC roadmap, прецедент AmneziaVPN 11.2024.

## 1. X25519MLKEM768 — статус на октябрь 2026

- **Стандарт**: RFC 10024 (Proposed Standard, август 2026) — гибрид X25519 + ML-KEM-768 (NIST FIPS 203) для TLS 1.3; в IANA-реестре Recommended. Предстандартный `X25519Kyber768Draft00` формально deprecated.
- **Клиенты**: Chrome 131+ (ноя. 2024) — дефолт на всех платформах; Firefox 132+; Safari — iOS 26 / macOS Tahoe; Edge/Brave/Opera (Chromium) — аналогично. QUIC тоже покрыт.
- **Серверы**: Cloudflare — >2/3 human TLS-трафика уже гибрид (апр. 2026); Imperva — дефолт на всех WAF-сайтах (окт. 2026). Серверная сторона — **проблема упаковки, не настройки**: нужен OpenSSL 3.5+ (ниже — нет ML-KEM вообще, включая LibreSSL и старые QuicTLS-форки); nginx использует библиотеку, с которой слинкован, а не системную.
- **Дорожная карта**: сначала key exchange (готово), затем PQ-сертификаты (Merkle Tree Certificates, фазы до Q3 2027), затем отказ от классики.

**Критично для sora**: uTLS-фингерпринт «свежий Chrome» **обязан** предлагать X25519MLKEM768 в key_share. 90%+ реального Chrome-трафика 2026 его имеет; ClientHello «Chrome 155 без PQ» — противоречие, видимое DPI до HTTP (уже зафиксировано в тире S #2). uTLS догнал Chrome 155 (06.10.2026) — проверить, что дефолтный fp включает гибридную группу.

## 2. Что PQ защищает, а что нет — честно

- **Защищает**: key exchange → «собери сейчас, расшифруй потом» (HNDL) для сессионных ключей. Гибрид = безопасность max(классика, PQ): сломать надо обе.
- **Не защищает**: аутентификацию (сертификаты/подписи всё ещё классические — ECDSA/RSA), долгосрочные статические ключи от квантовой атаки в будущем (но их компрометация не расшифровывает прошлые сессии при PFS).
- **Маркетинг, который отсекаем**: «quantum-proof VPN», «полная квантовая безопасность» (пока сертификаты классические — её нет ни у кого), кастомные гибридные схемы вместо стандартного X25519MLKEM768.

## 3. Серверный PSK WireGuard — прецедент AmneziaVPN (11.2024)

WG Noise psk2 уже даёт точку для симметричного PSK в хендшейке. AmneziaVPN добавила серверный PQ-PSK: PSK подмешивается в Noise chaining key → хендшейк квантово-стоек без смены протокола; сервер при этом **принимает и клиентов без PSK** (инкрементальный раскат, старые клиенты не ломаются). Для sora это готовый паттерн: one-click деплой генерирует PSK, клиент хранит его в конфиге, сервер — в режиме «принимать оба».

Дополнительно: **ML-KEM вместо RSA в самоподписанных сертах** (свои CA/серты для локальных нужд) — реальная мера против HNDL там, где мы контролируем обе стороны.

## 4. Что внедрять (ранжировано)

**P0 — дёшево, реально, сейчас:**
1. **PQ key_share в uTLS**: убедиться, что дефолтные фингерпринты (Chrome 155+) предлагают X25519MLKEM768; stealth-check JA4 в диагностике должен проверять наличие гибридной группы (отсутствие = детект-сигнал). Трекинг актуальности отпечатков (уже в тире S #2 — подтверждаю как P0).
2. **WG/AWG PSK-генератор**: `wg genpsk`-эквивалент в UI + поле PSK в конфиге; one-click деплой ставит PSK на сервер в dual-accept режиме (прецедент AmneziaVPN). Подпись: «защита хендшейка от будущего квантового дешифрования; бесплатно по производительности».
3. **REALITY**: ключи уже X25519 — ок; проверить, что uTLS-слой REALITY тоже предлагает PQ-группу (там свой ClientHello).

**P1:**
4. **Тумблер «PQ only»** для параноиков: только гибридные группы в TLS, отказ от классического ECDH. Честная подпись: «может не подключаться к старым серверам; сертификаты всё равно классические».
5. **ML-KEM для своих сертов**: где sora выпускает самоподписанные серты (локальные панели, one-click) — опция ML-KEM вместо RSA.
6. **QUIC**: убедиться, что QUIC-стек (hy2/TUIC/MASQUE) предлагает гибрид — Chrome делает, наши движки должны.

**Не делать:**
- Кастомные «квантовые» протоколы и бейджи «Quantum-Safe VPN».
- ECH+PQ+D2D в одной связке без проверки совместимости (сложность без выигрыша).
- PQ как аргумент против классики до 2029+ (Cloudflare целит full-PQ на 2029; до тех пор гибриды).

## Вердикт: лучшее или слоп

**Лучшее**: X25519MLKEM768 как дефолт везде, где мы формируем ClientHello (uTLS, REALITY, QUIC) + WG-PSK как PQ-слой хендшейка. Всё — отраслевой консенсус (NIST, IETF, Apple/Signal/Mullvad/Cloudflare), гибриды обратимы, цена нулевая. **Слоп**: «quantum-VPN»-маркетинг, собственные гибридные конструкции, PQ-бейдж без PQ в фингерпринте (хуже, чем ничего — это ложь в UI).

## Внедрить так

1. Аудит всех мест формирования ClientHello (uTLS-конфиги, REALITY, QUIC-транспорты): требовать X25519MLKEM768 в поддерживаемых группах; тест в CI: JA4/фингерпринт свежего Chrome содержит гибрид.
2. UI: PSK-поле для WG/AWG + кнопка генерации; one-click: генерация + dual-accept.
3. Диагностика → раздел «Постквантум»: статус по каждому подключению (гибрид да/нет, PSK да/нет).
4. Документация: одна честная страница «что PQ даёт и чего не даёт» (HNDL да, сертификаты нет, 2029 горизонт) — вместо маркетингового тумана.
