# 17. AmneziaWG 3.1 deep — параметры, мимикрия, что нового

Дата: 2026-10-20. Источники: официальные доки docs.amnezia.org (полная таблица параметров 3.1), amnezia.org/blog (анонс 3.1), amneziawg-go исходники (device/send.go, receive.go), GL.iNet доки параметров.

## 1. Полная карта параметров 3.1

| Параметр | Тип | Назначение |
|---|---|---|
| `Jc` / `Jmin` / `Jmax` | uint16 | Junk-train: число мусорных пакетов сразу после I-цепочки, размеры из диапазона |
| `S1`–`S4` | uint16 | Случайные префиксы к Init/Response/Cookie/Data: `len(init)=148+S1`, `len(resp)=92+S2`, `len(cookie)=64+S3`, `len(data)=payload+S4` |
| `H1`–`H4` | range<uint32> | Динамические идентификаторы типов пакетов; диапазоны **не должны пересекаться**; `1/2/3/4` = совместимость (откл.) |
| `I1`–`I5` | CPS-описание | Signature-пакеты перед хендшейком (каждые 120 с): теги `<b hex>`, `<t>` (unix time), `<r N>` (случайные байты), `<rc N>` (буквы), `<rd N>` (цифры) |
| `HeaderProtectionKey` | 32-байтный ключ | **Новое 3.1**: ChaCha20-шифрование служебных частей пакетов после Sx-префикса (Init 148B, Response 92B, Cookie 64B, Data 16B); nonce — первые 12 байт Sx-префикса; требует S1–S4 ≥ 12; при использовании H1–H4 := 1,2,3,4 (тип прячется защитой, не кастомными хедерами) |
| `ContentPaddingAddition` | range<uint16> | **Новое 3.1**: случайное число байт к transport-пакетам (ломает «кратность 16» WG-паддинга); в пределах внутреннего MTU |
| `RekeyAfterTime` / `RekeyTimeout` / `RejectAfterTime` / `KeepaliveTimeout` / `MaxHandshakeAttempts` | range<uint16> | **Новое 3.1**: тайминги как диапазоны — при срабатывании таймера значение выбирается случайно из диапазона |
| `RandomTrailers` | on/off | **Новое 3.1**: случайные трейлеры в конец пакетов (хендшейк — случайные данные, transport — нули к внутреннему IP-пакету); при использовании S1–S4 рекомендуют равными (иначе ошибки определения типа) |
| `DisableCookies` | on/off | **Новое 3.1**: не отправлять Cookie Reply (cookie — отдельный фингерпринт при активном пробинге); входящие cookie обрабатываются как раньше |

Отключение механизма: значение `0`, `off` или диапазон `0-0` = стандартный WireGuard.

## 2. Мимикрия I1–I5 (CPS) — как это работает на практике

I-пакеты шлются **перед** хендшейком, сервер их игнорирует (ждёт настоящий init). Пример из доков: `i1 = <b 0xd100000001><rc 8><t><r 50>` — байты, похожие на QUIC Initial, затем буквы, timestamp, случайные байты. Полевое наблюдение 2026 (dev.to): когда режут на уровне AS (кейс Hetzner AS24940 — хендшейк проходит, данные умирают), generic-рандомный I1 не помогает, а **I1 с QUIC Initial + allowlisted SNI** пробивает; какой SNI — операторо-специфично, нужен перебор. Вывод: пресеты мимикрии должны быть **редактируемыми и тестируемыми**, а не зашитыми.

## 3. Что нового в 3.1 — и зачем

Контекст: летняя волна блокировок 2026 в РФ. Цензор перешёл от анализа отдельных пакетов к анализу **соединения целиком**: размеры и последовательность пакетов, inter-arrival times, паттерны хендшейков, keepalive, объёмы, число соединений, повторяющиеся статпрофили. Ответ 3.1 — бить по всем осям сразу:
- **Header Protection** — прячет незашифрованные служебные части (статичный фингерпринт типов сообщений);
- **Content Padding** — ломает кратность 16;
- **Custom Timings** — ломает фиксированные интервалы rekey/keepalive/timeout (поведенческий детект);
- **Random Trailers** — ломает стабильную пару «init+response»;
- **DisableCookies** — убирает cookie как probing-сигнал.

Криптографическое ядро **не менялось**: Noise_IK, Curve25519, ChaCha20-Poly1305 — те же, что у WireGuard; применимы все WG-аудиты. Header Protection — ChaCha20 **для сокрытия структуры, не пейлоада** (доки это подчёркивают — честность).

## 4. Ограничения — честно

- Китай (GFW 4.0): AWG уже детектится — там VLESS/XHTTP, не AWG.
- Поведенческий детект «по совокупности» (amnezia.org): если IP/подсеть уже под подозрением, смена одного параметра не спасёт — нужна смена «диалекта» целиком (все параметры) + IP.
- Совместимость: конфиг 3.1 требует клиент с поддержкой 3.1; при выключенных параметрах — обычный WireGuard.

## Вердикт: лучшее или слоп

**Лучшее.** 3.1 — первый ответ индустрии на AI-поведенческий DPI, спроектированный по всем осям детекта сразу, с сохранением аудированного криптоядра. Параметры ортогональны и комбинируются в «диалекты». **Слоп**: включать junk «побольше» без контроля MTU (`Jmax` > MTU = фрагментация = подозрительно); копировать чужие наборы параметров один в один (общий «диалект» = общий фингерпринт); HeaderProtectionKey из слабого источника.

## Внедрить так

1. **Параметры 3.1 в plan/validate/render**: все 9 новых полей; валидация: `S1–S4 ≥ 12` при `HeaderProtectionKey`; H-диапазоны не пересекаются; `Jmax < MTU`; `S1+56 ≠ S2` (иначе init и response сравняются по размеру — известный футган); при `RandomTrailers=on` рекомендовать равные S1–S4.
2. **Генератор «диалектов»**: случайный, но валидный набор параметров на сервер (one-click) — как WG Tunnel; кнопка «сменить диалект» при подозрении на детект.
3. **I1-пресеты мимикрии**: QUIC / DNS / SIP + кастомный CPS-редактор с inline-валидацией тегов; полевое правило «I1 с allowlisted SNI» — в подсказку.
4. **UI-редактор AWG** (нет ни у кого из конкурентов в десктопе): все параметры с объяснениями и валидацией; импорт `vpn://` URI + QR.
5. **Критично — проверка движка**: убедиться, что целевой движок **реально применяет** AWG-поля. sing-box upstream AWG не умеет (только форк amnezia-box); если движок молча игнорирует поля — на проводе обычный WG, это обман пользователя. Внедрить capability-check: поле `awg_supported` у движка; если false и выбран AWG — жёсткий варнинг/блок с объяснением.
6. **Честные предупреждения**: «Китай — не AWG»; «при блокировке по IP смените сервер, а не параметры».
