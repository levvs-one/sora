## 1. Методология blockcheck (zapret) — что копировать

`blockcheck` — это не «проверка блокировок», а **автоматический перебор стратегий обхода**: для заданных доменов последовательно поднимает движок (tpws/nfqws/dvtws/winws) с параметрами стратегии и дергает домены через curl, затем считает пересечение успешных стратегий по всем доменам.

Пять фаз (порядок важен):
1. **DNS-валидация** — выявление DNS-отравления, фолбэк на DoH. Без чистого DNS весь перебор стратегий бессмысленен: половина «неуспехов» будет не про DPI.
2. **Подготовка firewall** — временные правила перехвата тестового трафика (iptables/nftables/WFP), после теста — откат.
3. **Инстанцирование движка** — запуск конкретного бэкенда с конкретными параметрами стратегии.
4. **HTTP-клиентский тест** — curl с **заведомо известным TLS-фингерпринтом** (важно: результат зависит от fp; тестить надо и curl-fp, и браузерным).
5. **Сбор и пересечение** — успешные стратегии логируются; итог — пересечение по всем тестовым доменам (стратегия, работающая на 1 из 5 доменов, в прод не идёт).

Что sora берёт: фазу 1 (DNS-check с DoH-фолбэком как обязательный пре-степ любой диагностики), фазу 4 (тестировать **нашим** fp, не curl'ным — иначе диагностика врёт про реальный клиент), фазу 5 (пересечение по нескольким доменам, а не «один домен открылся — всё хорошо»).

Чего НЕ копировать: интерактивный перебор десятков стратегий вручную — в sora это должен делать **авто-режим** (см. ниже), а blockcheck-подход остаётся в «расширенной диагностике» для продвинутых.

## 2. Канареечные эндпоинты (canary)

Термин из практики измерений: **канарейка = пара «тест + контроль»**, позволяющая отличить цензуру от аварии.

Архитектура для sora (по методологии OONI web_connectivity — те же шаги локально и через контроль, сравнение результатов):

- **Контрольные домены (known-clean):** `example.com`, `neverssl.com`-подобные, свой `sora-diag` эндпоинт. Если не открывается и контроль — проблема не в цензуре (сеть/сервер).
- **Канареечные заблокированные:** 2–3 домена, заблокированных в стране пользователя стабильно и давно (напр., для RU — из публичных списков; не порно/экстремизм — нейтральные, напр. заблокированные СМИ/соцсети). Их недоступность напрямую = «цензура на месте, тест валиден»; их внезапная доступность напрямую = «что-то изменилось, перепроверить».
- **Контрольный сервер sora:** свой хост за пределами цензурируемых сетей, отдающий эталонные ответы (echo IP, JA4-приёмник из темы 63, набор «ожидаемых» DNS-ответов). Сравнение локального результата с эталоном — дословно OONI-подход «control request with backend».

Правила честности:
- Никогда не тестировать домены из категории «особо чувствительные» без явного согласия (OONI предупреждает: в их URL-листах есть gambling/sex/hacking — пользователя надо предупреждать).
- Канарейки — только для диагностики по кнопке/авто-режима, не фоновый спам (не палить пользователя регулярными запросами к заблокированным доменам без его ведома — показать в UI, что и зачем тестируется).
- Результат: не «заблокировано/нет», а классификация OONI: `dns_anomaly` / `tcp_anomaly` / `http_anomaly` / `ok` / `inconclusive`.

## 3. Детектор «сибирской заморозки» с автосменой фингерпринта

**Сигнатура атаки (реверс РКН, июнь 2026):** цензор смотрит тройку (подсеть/AS + SNI + uTLS-fp) и **замораживает** соединения при **>3 параллельных TLS с одним SNI**. Заморозка ≠ RST: соединение висит (таймаут), что ломает наивные «проверки доступности». Подозрительные fp: Chrome/Safari/iOS; проходят Firefox/QQ/Edge/Android OkHttp.

**Детектор (активный зонд, по требованию и в авто-режиме):**
1. Открыть N=6 параллельных TCP к нейтральному хосту (свой diag-сервер или известный CDN-домен), на каждом — TLS ClientHello **с нашим текущим uTLS-fp** и одинаковым SNI.
2. Таймаут на handshake: 8 с. Замерять: сколько из 6 зависли (нет ServerHello, нет RST).
3. Контроль: та же процедура с fp `firefox` (из «проходящих»).
4. Вердикт `SIBERIAN_FREEZE`, если: наш fp — зависло ≥4/6, а firefox — ≤1/6. Разница между fp при прочих равных = поведенческая эвристика цензора, а не «плохая сеть» (сеть бы роняла оба).
5. Анти-ложноположительные: повторить 2 раза с паузой 30 с; freeze должен воспроизводиться.

**Автосмена (только в авто-режиме, с согласия пользователя в настройках):**
1. При детекте: переключить uTLS-fp на первый из allowlist'а «проходящих» (firefox → qq → edge → okhttp), пересчитать JA4 (тема 63), переподключить активный туннель/цепочку.
2. Перезапустить детектор для валидации (замер должен стать чистым).
3. Записать событие в журнал диагностики: `siberian_freeze_detected{asn, sni, old_fp, new_fp}` — это же фид для OONI-подобной агрегации (тема 61).
4. Бэк-офф: не чаще 1 автосмены в 10 минут; после 3 неудач — стоп и уведомление «цензор адаптировался, выберите протокол вручную».

**Пассивный детектор (без зондов, всегда включён):** в health-check туннеля считать зависшие handshake'и с одним SNI за скользящие 5 минут; паттерн «много висящих TLS, ноль RST, другие SNI живы» → мягкое предупреждение + предложение запустить активный зонд.

**Связанные обязательные меры (из тира 3, напоминание):** mux по умолчанию для REALITY (режет триггер параллелизма); vision flow обязателен (TLS-in-TLS без vision — детектируемый сигнал); предупреждение при REALITY без vision в UI.

## Вердикт «лучшее или слоп»

**Лучшее:** blockcheck-подход «сначала чистый DNS, потом стратегии, потом пересечение» — дисциплина, убивающая ложные выводы. OONI-методология control/test — золотой стандарт атрибуции. Активный зонд заморозки с fp-контролем — единственный честный способ отличить эвристику цензора от плохой сети.

**Слоп:** (а) «проверка блокировок» одним доменом без контроля; (б) автосмена fp без валидации и без бэк-оффа (флаппинг, который сам становится сигналом); (в) фоновые зонды к заблокированным доменам без ведома пользователя.

## Рекомендация «внедрить так»

1. `core/censor/`: `dnscheck` (с DoH-фолбэком) → `canary` (test+control пары, классификация OONI) → `siberian` (активный зонд N=6 + пассивный счётчик) → `failover` (ротация fp из allowlist с валидацией и бэк-оффом).
2. «Авто-режим обхода»: связка детектор→смена fp/стратегии→перепроверка, журнал событий, экспорт для исследований.
3. Расширенная диагностика для продвинутых: ручной перебор стратегий в духе blockcheck (домены + движок + параметры), но с нашим fp.
4. Все зонды — только явно (кнопка/авто-режим с согласием), в UI видно что тестируется и зачем.
