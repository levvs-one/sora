# 12. Shadowsocks-2022 (SIP022) — AEAD-2022, EIH, UDP relay, формат ключей

Дата: 2026-10-20. Источники: SIP022/SIP023 (shadowsocks-org), исходники shadowsocks-rust, go-shadowsocks2 `shadowaead_2022`, доки mihomo/sing-box.

## 1. AEAD-2022: что внутри (SIP022)

Три метода: `2022-blake3-aes-128-gcm`, `2022-blake3-aes-256-gcm`, `2022-blake3-chacha20-poly1305`.

**Деривация ключа сессии** — BLAKE3 вместо HKDF-SHA1:
```
session_subkey := blake3::derive_key("shadowsocks 2022 session subkey", PSK || session_id[0..8])
```

**Wire format.** Пакет = зашифрованный separate header (16 байт) + AEAD-тело:
- Separate header plaintext: `session_id` (8B, случайный на сессию) + `packet_id` (8B, u64be, счётчик от 0).
- Header шифруется **блочным AES напрямую PSK** (не AEAD!) — `aes_new(psk).encrypt(separate_header)`.
- Тело — AEAD сессионным подключом, nonce = `separate_header[4..16]` (12 байт: младшие 4 байта session_id + packet_id).

**Отличия от legacy AEAD (SIP004/SIP007):**

| Свойство | Legacy AEAD | AEAD-2022 |
|---|---|---|
| Деривация | HKDF-SHA1 | BLAKE3 derive_key |
| Вход | пароль → EVP_BytesToKey | только сырой PSK фиксированной длины (base64), как у WireGuard |
| Replay-защита | не требовалась | обязательна (timestamp ±30 с + пул salt) |
| TCP payload cap | 16383 байта (0x3FFF) | 65535 байт (0xFFFF) |
| UDP nonce | нулевой | из session/packet ID |
| Тип заголовка | нет | есть (различение client/server) |
| Timestamp check | нет | обязателен |

## 2. EIH — Extensible Identity Headers (SIP023)

Опциональное расширение поверх SIP022 для мультитенантности. Двухуровневая иерархия ключей:
- `iPSK` (identity PSK) — идентифицирует уровень маршрутизации (relay или multi-user сервер); каждый хоп добавляет один iPSK.
- `uPSK` (user PSK) — идентифицирует конечного пользователя; последний PSK в цепочке.

Клиент получает список через двоеточие: `iPSK0:iPSK1:uPSK0`. На каждый iPSK генерируется один identity header перед стандартным SIP022-пейлоадом. Каждый узел снимает ровно один header и форвардит остаток без изменений — **полная прозрачность**. Применение: один порт обслуживает многих пользователей и цепочки relay без инспекции внутреннего пейлоада. В shadowsocks-rust: секция `users` на сервере, у клиента `password` формата `iPSK:uPSK`.

## 3. UDP relay

- Клиент держит **сессию на каждый source address** локального приложения: случайный `session_id`, монотонный счётчик пакетов, запоминание target address; таймаут по неактивности.
- **Сервер маршрутизирует по `client_session_id`, а не по source IP** — сессия переживает смену IP клиента (роуминг Wi-Fi→LTE бесплатно, как у WireGuard/QUIC).
- Формат тот же, что TCP: `AES(separate_header) + AEAD(body)` для request и response.

## 4. Формат ключей (важно для UI!)

- AEAD-2022 принимает **только криптографически стойкий ключ фиксированной длины** (16 или 32 байта), закодированный в **base64**. Парольная фраза запрещена спекой.
- Генерация: `openssl rand -base64 32` (для 256-битных методов).
- SIP002 URI-правила для 2022: `ss://<base64(method:password)>@host:port`, где password — уже base64 ключа. Клиент обязан валидировать длину после декодирования.

## 5. Чем 2022 лучше legacy — честно

1. **Replay-защита из коробки** — главный практический выигрыш против активного зондирования (GFW-style replay-атаки, убивавшие legacy SS).
2. **Нет слабого KDF** — парольные фразы с EVP_BytesToKey были вектором словарных атак; теперь только сырой PSK.
3. **BLAKE3 быстрее** HKDF-SHA1 на деривации каждой сессии.
4. **UDP-роуминг** по session_id — для мобильных клиентов.
5. **EIH** — мульти-пользователь и relay-цепочки без костылей плагинов.
6. **Больше TCP-чанки** (64K) — меньше оверхед на bulk-трафике.

Ограничение честно: SS-2022 — это «шифрованный блоб», у него нет анти-probing на уровне протокола (в отличие от Trojan-fallback или REALITY). Против DPI, умеющего в энтропийный анализ + active probing, один SS-2022 слаб — нужны плагины/obfs или другой протокол.

## Вердикт: лучшее или слоп

**Лучшее** — для сценариев «простой PSK, UDP-игры/звонки, self-hosted». AEAD-2022 закрывает реальные криптографические дыры legacy (replay, слабый KDF), а не «добавляет фич». EIH — элегантное решение мультитенантности без инспекции трафика. **Слоп** — навешивать поверх 2022 обфусцирующие плагины «для стелса», не понимая, что энтропийный блоб всё равно виден; и использовать legacy-методы (`aes-256-gcm` с паролем) в новых деплоях.

## Внедрить так

1. **Метод по умолчанию** для новых SS-подключений: `2022-blake3-aes-256-gcm`; legacy-методы — в секцию «устаревшие» с варнингом (replay-атаки, слабый KDF).
2. **Генератор ключей в UI**: кнопка «сгенерировать» (`openssl rand -base64 32` эквивалент), валидация длины base64 при ручном вводе, понятная ошибка «нужен base64-ключ 32 байта, а не пароль».
3. **Поддержка EIH**: парсинг `password` формата `iPSK:uPSK`, UI для multi-user (список users на серверной стороне one-click деплоя).
4. **UDP relay**: использовать нативный UDP (не UoT) по умолчанию; в health-check учитывать session_id-роуминг (смена сети ≠ разрыв).
5. **Импорт/экспорт**: корректный SIP002 для 2022 + QR (де-факто стандарт распространения).
6. **Не позиционировать** SS-2022 как анти-DPI решение в одиночку — в UI честная подсказка: «против активного зондирования используйте Trojan (fallback) / VLESS+REALITY».
