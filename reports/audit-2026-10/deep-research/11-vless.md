# 11. VLESS — deep-dive по спеке протокола

Дата: 2026-10-20. Источники: официальная спека XTLS (xtls.github.io, автор протокола), исходники Xray-core `proxy/vless/encoding/encoding.go`, `inbound.go`, `outbound.go`.

## 1. Структура протокола (авторитетная спека)

VLESS — stateless, лёгкий, без встроенного шифрования. Формат запроса:

```
1B Protocol Version | 16B UUID | 1B Addons Length (M) | M Bytes Addons (ProtoBuf) |
1B Command | 2B Port | 1B Address Type | S Bytes Address | X Bytes Request Data
```

Формат ответа: `Version | Addons Length (N) | Addons (ProtoBuf) | Response Data`.

- **Protocol Version**: 0 в тестовых, 1 в официальных версиях. Дизайн сервера — «switch version»: сервер поддерживает все версии одновременно; при апгрейде структуры версию поднимают, сервер обновляется за месяц до клиентов. У Trojan версии протокола нет вообще.
- **UUID (16 байт)**: идентификатор-аутентификатор. Автор сознательно оставил 16 байт (у Trojan пароль — 56 печатных символов, т.е. 56 байт). Сервер проверяет UUID на каждом соединении, поэтому критична скорость валидатора: переписан несколько раз, `sync.Map`, держит очень много пользователей, динамическое добавление/удаление через API безболезненно. UUID — это НЕ ключ шифрования.
- **Addons (ProtoBuf)**: опциональные расширения, TLV. Когда не нужны — `Addons Length = 0`, оверхеда сериализации нет («splicing», байты почти как без ProtoBuf). Сейчас несут только Flow (Scheduler/SchedulerV). Задел на будущее: динамические порты и т.п.
- **Command**: 1 = TCP, 2 = UDP, 3 = Mux. Часть «Command → Address» идентична VMess, Mux поддерживается.
- **Шифрование делегировано транспорту**: `encryption: none` / `decryption: none` — вся криптография на TLS/REALITY. Это осознанное решение, а не упрощение.

## 2. Роль UUID — точно

UUID — только аутентификация, не секретность канала. Проверяется каждое соединение серверным валидатором. Практические следствия для клиента:
- UUID v4 достаточно; генерация — `xray uuid`, не «красивый» руками.
- Один UUID = один пользователь; шеринг UUID между людьми = шеринг аккаунта (сервер это видит по параллельным сессиям).
- Утечка UUID из логов/скриншотов = компрометация (эквивалент пароля).

## 3. XTLS-расширения: что реально живёт в Addons

- **Flow `xtls-rprx-vision`** — единственное массово используемое расширение. Решает макроскопическую характеристику трафика (тайминги), а не микроскопическую (её решает шифрование). Авторская мотивация: Socks5-over-TLS выглядит для наблюдателя как «другой протокол», даже если содержимое зашифровано.
- Vision **обязателен** для VLESS+REALITY+TCP: без него TLS-in-TLS — детектируемый прокси-сигнал (подтверждено полевыми тестами 2026, см. тир S #3 в WEB-RESEARCH).
- `xtls-rprx-vision-udp443` — вариант для UDP/443.
- Остальное из XTLS-стека — это уже не VLESS-расширения, а транспорты/безопасность: REALITY, XHTTP (с `downloadSettings`), uTLS-фингерпринты.

## 4. Что в протоколе лишнее (по словам самого автора и по факту)

1. **«Response Authentication»** — убрана ещё в ALPHA 2, заменена версией протокола в начале. Автор: генерация псевдослучайных чисел была лишним оверхедом, версия даёт и аутентификацию ответа, и апгрейдабельность.
2. **VMess-наследие «metadata obfuscation» при хендшейке** — автор прямо пишет: не давало ничего поверх TLS, только снижало производительность; в VLESS выпилено. Слово «obfuscation» он считает вредным (путают с camouflage).
3. **Schedulers как «Zstd compression / dynamic data expansion»** — анонсированы в BETA 2, по факту не взлетели; жив только vision-flow. Не тащить в продукт.
4. **Поле `encryption` со значениями `ss_aes-128-gcm` и т.п.** — бета-идея «согласованного шифра поверх UUID», мейнстримом не стала (есть VMessAEAD, хватает). В UI держать `encryption` как текстовое поле с дефолтом `none` (указание автора спеки), не как селект.
5. **Mux-команда (0x7f)** — поддерживается, но на практике почти не используется; мультиплексирование решают xmux/sing-mux на уровень выше.

## Вердикт: лучшее или слоп

**Лучшее.** VLESS — эталон минимализма: версия + UUID + опциональный ProtoBuf + команда. Всё, что автор выпилил (obfuscation-хендшейк, response-auth), выпилено по измеренным причинам, а не по вкусу. Стек VLESS+REALITY+vision — главный рабочий антицензурный стек 2026, подтверждённый полевыми тестами (nDPI: 5/6 коммерческих VPN детектятся за <1.5 с, VLESS+REALITY — нет).

## Внедрить так

1. **Жёсткая связка в UI/валидации**: `security=reality` + `type=tcp` ⇒ требовать `flow=xtls-rprx-vision`, иначе варнинг «TLS-in-TLS детектируется». Запретить/варнить пару XHTTP+vision (несовместимы; защита через xmux + сплит up/down).
2. **Поле `encryption`** — текстовый инпут, дефолт `none`, автоподстановка при пустом (по гайдлайну автора).
3. **Идентификатор в UI строго «VLESS»** (указание автора спеки, не VLess/vless).
4. **UUID-менеджмент**: кнопка генерации, предупреждение о шеринге/утечке; импорт `vless://` с разбором всех query-параметров (`flow`, `pbk`, `sid`, `fp`, `sni`, `alpn`, `type`, `path`, `host`, `mode` для xhttp).
5. **Не внедрять**: свои «улучшения» поверх VLESS (кастомные schedulers, дополнительное шифрование UUID) — это слоп, ломающий совместимость с экосистемой.
6. **Версионный риск XHTTP**: требовать одинаковые версии Xray на клиенте и сервере — варнинг в диагностике (уже отмечено в тире 12 WEB-RESEARCH, подтверждаю).
