# 69. Reproducible builds + аудиты безопасности: что проверяют аудиторы, как готовить код

Дата: 2026-10-20. Группа G, третий проход.

## Первоисточники

  - Cure53 «Pentest-Report Mullvad VPN & Servers» 11–12.2020 (публ. 01.2021) — серверы, инфраструктура, веб.
  - Cure53 «Pentest-Report Mullvad Apps, Clients & API» 05.2020 — клиенты всех платформ.
  - Assured «Mullvad VPN relay server audit» MUL006 v1.0 (06.2022).
  - Radically Open Security (08.2023, отчёт на GitHub).
  - Cure53 «Relay-Infrastructure» 06.2024 (Ansible-репо + стейджинг-хосты).
  - X41 D-Sec (10–11.2024): 30 человеко-дней, все 5 платформ.
  - Cure53: аудит WireGuard-демона (фаззинг).
- Практика подписей: minisign (trusted comment против даунгрейда), Tauri updater, `minio/selfupdate` (Go `Verifier`).
- Сверка с sora (read-only): `docs/security.md` уже описывает модель хранения/логирования/kill switch/проверку сборок (SHA256SUMS + minisign, fail-closed без ключа). Публичных аудитов не было.

## 1. Что реально проверяют аудиторы (по отчётам Mullvad)

**Клиент (Cure53 Apps 2020, X41 2024):**
1. **IPC-привилегии.** Находка MUL-02-007: Windows named pipe с доступом everyone read/write, при «рыхлой» сетевой конфигурации торчал наружу через SMB; через браузер можно было уронить демон. Проверка: ACL на каждом IPC-эндпоинте, кто может подключиться.
2. **Kill switch — не по конфигу, а сниффером.** Аудиторы ставили сниффер и смотрели реальный исходящий трафик в состояниях connect/disconnect/reconnect. Исключения контролировались двухуровневыми firewall-правилами.
3. **Логирование.** Поиск PII в логах, конфигах, краш-дампах. У Mullvad — «no leaks of PII» как отдельная строка вердикта.
4. **Фаззинг демона** (WireGuard-аудит): malformed inputs, rate limiting против repeated invalid attempts.

**Инфраструктура (Cure53 2020/2024, Assured 2022, ROS 2023):**
5. **Обход аутентификации** (MUL-03-002: OpenVPN user-auth bypass, Medium) и **DoS через отключение чужих пользователей** (MUL-03-005, High).
6. **Харденинг контейнеров** (MUL-03-010: insecure Docker → breakout, High); **устаревшие зависимости от root** (shadowsocks-libev outdated + runs as root, Low).
7. **Секреты:** Ansible Vault/GPG — корректно; но все плейбуки лежали на стейджинг-хостах (лишняя экспозиция, MUL-04-002); **в стейджинге не должно быть продовых ключей** — отдельная проверка.
8. **No-logging:** конфиги + форензика диска тестовых машин; честная оговорка всех отчётов: «не можем подтвердить, что прод настроен так же».

**Веб/платёжная поверхность:** DOM-XSS через устаревший Swagger UI (Medium), unrestricted PayPal webhook → DoS (Info), timing-unsafe сравнение в аутентификации (Low).

**Процесс:** у Mullvad аудиты **раз в два года с 2018** (2018/2020/2022/2024), отчёты публикуются полностью. Реальный стресс-тест — обыск полиции 04.2023: изымать было нечего.

## 2. Reproducible builds: зачем и как

Смысл: любой может пересобрать релиз из исходников и получить **бит-в-бит тот же бинарь** — тогда аудит кода покрывает и бинарь, который ставит пользователь. Прецеденты: Tor Browser, Debian.

Для sora (реалистичный план по компонентам):
- **Go core + движки:** достижимо. `go build -trimpath`, `SOURCE_DATE_EPOCH`, зафиксированные версии тулчейна, `go.sum`; проверка `go version -m` (buildinfo). Публиковать инструкцию «как пересобрать» + ожидаемые SHA256.
- **Flutter-приложение:** сложно (Dart/Flutter не детерминирован полностью) — честно зафиксировать как «best effort», а не обещать.
- **SLSA provenance + SBOM:** подпись не только артефакта, но и аттестации «собрано из коммита X на раннере Y» — закрывает оговорку аудиторов «не можем подтвердить прод» хотя бы для клиентских сборок.
- Связка с темой 68: minisign-подпись ставится **поверх** воспроизводимой сборки; trusted comment несёт версию (анти-даунгрейд).

## 3. Чеклист «как готовить код к аудиту» (для sora)

1. **Threat model документом** (тема 70) — аудиторы начинают с него; без него они аудируют «всё», находят мелочи, пропускают главное.
2. **Scope-пакет:** архитектура (`docs/architecture.md` уже есть), границы доверия, инвентарь секретов, инструкция развёртывания стейджинга.
3. **Self-audit по находкам Mullvad:** ACL IPC (сокет/канал только локальная сессия — в `docs/security.md` уже заявлено, перепроверить кодом), kill switch сниффером на всех платформах (автотест!), grep логов на PII, зависимости от root, Swagger/веб-панели.
4. **Чистый стейджинг:** продовые ключи/подписи — никогда в тестовых окружениях и CI-логах.
5. **Фикс-SLA:** критические — до публикации отчёта; отчёт публикуется **целиком**, с «исправлено/запланировано» по каждой находке (практика Mullvad).
6. **Каденс:** первый аудит — до заявления «best in the world»; дальше раз в 1–2 года + аудит после крупных архитектурных изменений (новый движок, sync).
7. **Warrant canary** (практика IVPN — ежемесячная публикация «не получали запросов»): дёшево, честно, принято в индустрии.

## Вердикт «лучшее или слоп»

**Лучшее:** публикация полных отчётов (а не «аудит пройден» бейджем), аудит kill switch сниффером, разделение стейджинг/прод ключей, reproducible builds для Go-компонентов, честные оговорки о границах проверки.

**Слоп:** (а) «независимо проверено» без ссылки на отчёт; (б) аудит только веб-сайта при заявлении про клиент; (в) обещание reproducible builds для Flutter без доказательства; (г) скрытие неисправленных находок.

## Рекомендация «внедрить так»

1. Дописать threat model (тема 70) → заказать первый аудит (клиент: IPC, kill switch сниффером, логи, обновления; инфра: серверная часть one-click).
2. Reproducible builds для `core/` и движков: `-trimpath`, `SOURCE_DATE_EPOCH`, док «пересобери сам», SLSA-провенанс в релизах.
3. Автотест «kill switch под сниффером» в CI (Linux/Windows) — то, что аудиторы делают руками.
4. Опубликовать `docs/security.md` как Trust Center + завести warrant canary.
5. Церемония minisign-ключа (всё ещё открыта!) — без неё вся цепочка подписей декларативна.
