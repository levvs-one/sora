# 68. Фреймворки обновлений: Sparkle, Tailscale, staged rollout, автооткат, update-over-VPN, лимитные соединения

Дата: 2026-10-20. Группа G, третий проход.

## Первоисточники

- Sparkle 2: `github.com/sparkle-project/Sparkle` (README, фичи), доки appcast (`sparkle:edSignature`, `SUFeedURL`, `SUPublicEDKey`).
- Atlassian: open-source инструмент phased releases для Sparkle-приложений (SourceTree).
- Tailscale: пакет `clientupdate` (`tailscale.com/clientupdate`, опенсорс) — треки stable/unstable, `LatestTailscaleVersion(track)`, `Updater{Confirm, ForAutoUpdate}`, platform-specific установка; на Windows — копирование бинаря + re-exec подкоманды `update`.
- minisign: `jedisct1.github.io/minisign`, man-страница; trusted comment (подписан, можно вшить версию против даунгрейда) + untrusted comment.
- Практика: Tauri auto-updater (minisign-верификация), `minio/selfupdate` (Go, `Verifier`).
- Сверка с sora (read-only): `app/lib/src/updates.dart` — `AppUpdater`: проверка GitHub releases (`/repos/levvs-one/sora/releases/latest`), детект пакетного менеджера (dpkg/rpm/pacman), верификация SHA256SUMS сигнатуры через привилегированный хелпер. **Нет:** staged rollout, minisign для обновлений приложения, автоотката, учёта лимитных соединений, политики update-over-VPN.

## 1. Что взять у каждого

**Sparkle 2 (macOS, эталон UX):**
- Подписи **EdDSA (Ed25519)** + Apple Code Signing; публичный ключ вшит в `Info.plist` (`SUPublicEDKey`), сигнатура в appcast (`sparkle:edSignature`).
- **Delta updates** (патчится только изменившееся) + **атомарная установка**.
- **Каналы** (бета), **phased rollouts**, метки critical/major.
- Appcast = RSS с enclosures — де-факто стандарт, читаемый сторонними трекерами.
- Вывод для sora: даже не на macOS — идея «фид релизов + Ed25519 + дельты + атомарность» переносима.

**Tailscale `clientupdate` (образец для Go-клиента):**
- Треки `stable`/`unstable`; сервер версий (`pkgs.tailscale.com`) отдаёт latest per track.
- `Confirm(newVer) bool` — хук согласия; `ForAutoUpdate` — отдельный режим фоновых обновлений.
- Платформенно-специфичная установка инкапсулирована; Windows: «скопируй себя → re-exec `update`» — надёжный приём самообновления занятого бинаря.
- `tailscale update` как CLI-команда — то же API, что у автоапдейта.

**minisign (подписи без GPG-зоопарка):**
- Один ключ, один формат; `minisign -Vm file -P <pubkey>`.
- **Trusted comment подписан** — вшивать `version=1.2.3` прямо в подпись: верификация одновременно проверяет и подлинность, и **защиту от даунгрейда** (атакующий не может подсунуть старую подписанную версию с другим комментарием).
- У sora minisign уже используется для **расширений** (`.soraext`) — тот же механизм естественно распространяется на обновления движков/ядра.

**Atlassian phased releases:** раскатка Sparkle-приложения инкрементальными группами как safety valve — раскатка идёт серверной логикой поверх стандартного appcast.

## 2. Staged rollout 1% → 100%: дизайн для sora

Раскатка — серверное решение, клиент только честно сообщает когорту:

1. Релизный фид (`releases.json`, свой хост, не только GitHub API): на версию — `rollout: {percent, started_at}` + minisign-сигнатуры артефактов.
2. Когорта клиента: `hash(machine_id || version) % 100 < percent` — детерминированно, без трекинга пользователя.
3. Лестница: 1% (24 ч) → 5% → 25% → 100%; переход — правкой `percent` в фиде, без нового релиза.
4. **Стоп-кран:** в фиде `blocked_versions: [...]` — клиент, увидевший свою версию в списке, откатывается (см. ниже) и больше не предлагает битую.
5. Критические security-фиксы — `critical: true`: пропускают очередь (100% сразу), но автооткат для них ещё важнее.

## 3. Автооткат (то, что все забывают)

1. Перед установкой — снапшот текущей версии (бинарь + конфиг-миграции с даунгрейд-путём).
2. После установки — **health-check**: core стартует, отвечает на control socket, пробный коннект к diag-эндпоинту ≤60 с.
3. Провал health-check или креш в первые N минут → **автооткат** на снапшот + запись в фид телеметрии (без PII: версия, ОС, код health-check'а).
4. Порог: если доля откатов когорты > X% — авторелес **автоматически ставит версию в `blocked_versions`** (стоп-кран без человека).

## 4. Update-over-VPN и лимитные соединения

**Update-over-VPN** (специфика VPN-клиента, у обычных приложений проблемы нет):
- Проверка обновлений и скачивание **не должны идти в обход туннеля**, когда он активен (иначе — прямой лик «пользователь sora, версия X, IP»).
- Но и рвать туннель ради апдейта нельзя. Правило: апдейт-трафик идёт через **тот же outbound**, что и пользовательский трафик (в TUN-режиме — автоматически); при `strict` kill switch — апдейт ждёт окна или идёт через туннель, но никогда напрямую.
- Исключение: **bootstrap-кейс** — обновление нужно, чтобы починить сломанный обход цензуры, а сеть режет всё кроме VPN. Тогда — явный UI-выбор «скачать обновление напрямую» с предупреждением (как captive portal: осознанный, видимый пользователю шаг).

**Лимитные (metered) соединения:**
- Windows: `NetworkInformation` / NLM `GetCost()`; Linux: NetworkManager `Metered`; Android: `ConnectivityManager.isActiveNetworkMetered()`.
- Политика: на metered — только **проверка** (байты), скачивание — по явному согласию или на unmetered; delta-обновления в первую очередь для таких сетей.
- Установщик/пакетный менеджер: если sora поставлена из deb/rpm — **не качать бинарь в обход пакетного менеджера** (текущий `AppUpdater` это уже учитывает — сохранить).

## Вердикт «лучшее или слоп»

**Лучшее:** Ed25519-подписи с trusted-comment (анти-даунгрейд бесплатно), детерминированные когорты для staged rollout, health-check + автооткат как часть установки, апдейт-трафик через туннель, уважение к metered.

**Слоп:** (а) «обновление» = скачать zip по HTTP без подписи; (б) staged rollout на клиенте без серверного стоп-крана; (в) автоапдейт, рвущий VPN или текущий мимо туннеля; (г) GPG-связка ключей там, где хватает одного Ed25519.

## Рекомендация «внедрить так» (аудит текущего `updates.dart`)

1. Фид `releases.json` со схемой: версия, артефакты, minisign-сигнатуры (trusted comment `version=`), `rollout.percent`, `blocked_versions`, `critical`.
2. Клиент: когорта `hash(machine_id)%100`, проверка подписи **до** распаковки, установка атомарно, health-check 60 с, автооткат на снапшот.
3. `sora update [--check|--apply]` в management CLI (тема 65) — тот же код, что автоапдейт.
4. Апдейт-трафик — через активный туннель; bootstrap-исключение — только явным действием пользователя.
5. Metered: проверка всегда, скачивание — с согласия; дельты — приоритет.
6. Minisign-ключи: церемония как для расширений (ключ офлайн, публикация pubkey в репо + на сайте).
