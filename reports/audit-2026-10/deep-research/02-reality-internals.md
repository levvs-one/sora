# 02. REALITY internals — исходники Xray

Дата: 2026-10-20. Источники: `transport/internet/reality/reality.go` (Xray-core), REALITY.ENG.md (Xray-examples), DeepWiki-разборы с привязкой к коду, mihomo `component/tls/reality.go` (кросс-проверка механики), полевая практика 2025–2026.

## Handshake: что происходит на проводе

REALITY — не TLS с чужим сертификатом, а отдельный протокол, мимикрирующий под TLS 1.3:

1. **ClientHello** — клиент отправляет обычный ClientHello с uTLS-фингерпринтом выбранного браузера, SNI = `serverName`. Ключевое отличие от TLS — поле **Session ID** (32 байта): клиент вычисляет ECDH на X25519 с `publicKey` сервера, получает shared secret и **AEAD-шифрует им (timestamp || shortId)** в Session ID. Сервер — единственная сторона, способная это расшифровать.
2. **Сервер** расшифровывает Session ID своим `privateKey`, проверяет временное окно (защита от реплея) и что `shortId` есть в списке `shortIds`. Успех → сервер отвечает специально подписанным handshake (HMAC-SHA512 производным ключом) и выдаёт временный сертификат → клиент продолжает как прокси.
3. **Провал аутентификации** (неверный/пустой shortId, кривой ключ) → сервер **прозрачно проксирует TLS-сессию на `dest`** и отдаёт настоящий сертификат dest-сайта. Клиент, увидев genuine-сертификат вместо ожидаемого, входит в **spider mode**: ведёт себя как веб-краулер, делая HTTP-запросы по `spiderX`-пути (дефолт `/`), чтобы не выделяться.
4. **Невалидный сертификат вообще** → клиент рвёт соединение с TLS alert (защита от MITM).

Итог: пассивный наблюдатель видит обычный TLS 1.3 хендшейк к легитимному сайту; активный пробер без ключа получает настоящий сайт. Серверного TLS-фингерпринта нет в принципе — нечего фингерпринтить.

## shortId

- Hex-строка, до 16 символов (чётная длина), список на сервере до десятков значений. Семантика: идентификатор клиента/группы — можно ротировать и отзывать без смены ключей.
- Пустой shortId валиден: клиент аутентифицируется только ключом. Удобно, но теряется гранулярность (не отличить «свой» клиент от чужого с украденным ключом).
- Клиентский `shortId` обязан совпадать с одним из серверных `shortIds`, иначе — spider mode.

## spiderX

Начальный путь, который клиент запрашивает в spider mode (например `/` или `/dns-query/`). Механика: поддерживает иллюзию «я браузер/краулер», если сервер не узнал клиента. Практический смысл — глубина правдоподобия при активном зондировании; на everyday-работе не влияет. Дефолт `/` достаточен для большинства dest.

## Требования к dest (жёсткие, из кода и документации)

1. **TLS 1.3 обязателен** — REALITY мимикрирует именно под 1.3-хендшейк; сайт без 1.3 ломает иллюзию.
2. **HTTP/2** — ALPN `h2` в хендшейке dest; отсутствие H2 — маркер «не тот сайт».
3. **X25519 key exchange** на dest — иначе несоответствие криптопараметров видно пассивному наблюдателю.
4. **Зарубежный популярный сайт**, географически близкий к VPS (расхождение RTT клиент→VPS vs VPS→dest — детектируемая аномалия при большой разнице).
5. **НЕ anycast/CDN-фасад типа Cloudflare** в качестве dest для серьёзных сценариев: IP dest резолвится в anycast-сеть, а VPS имеет свой IP — несоответствие видно; плюс Cloudflare-домены — самые зондируемые.
6. **serverNames** — имена из сертификата dest; клиентский SNI обязан входить в список.

Дополнительно 2026: постквантовый key share (X25519MLKEM768) — 90%+ трафика Chrome 2026 его предлагает; dest без PQ при «свежем» uTLS-фингерпринте — противоречие, заметное DPI (см. тир S #2 сводки).

## Защита от traffic theft (кражи трафика)

Проблема: неаутентифицированный клиент получает прозрачный TLS-прокси до `dest`. Если `dest` — публичный сервис, **любой может использовать сервер как бесплатный forwarder** (кража трафика/абуз IP).

Решение «without being stolen» (официальный паттерн Xray-examples):
1. `dest` REALITY-inbound → локальный `dokodemo-door` (например `127.0.0.1:4431`).
2. `dokodemo-door` настроен на реальный `dest`.
3. **Routing-правила**: трафик с тега dokodemo-door разрешён только при совпадении домена с ожидаемым `serverNames`, всё остальное → `blackhole`.

Итого: чужой клиент упирается в стену, свой — проходит.

## Вердикт: лучшее

Механика подтверждена кодом двух независимых реализаций (Xray, mihomo). Spider mode, AEAD-SessionID, no-steal архитектура — продуманные ответы на реальные атаки (active probing, traffic theft), а не маркетинг.

**Отсеяно фильтром:** «REALITY невидим» — неверно; детект идёт по поведению (сибирская волна РКН: параллельные TLS с одним SNI, см. тир S #3), а не по протоколу. «Любой сайт подойдёт как dest» — неверно, требования жёсткие. Анекдоты «мой dest не палится год» — нерепрезентативно.

## Внедрить в sora так

Состояние sora: `realitySettings` рендерится (`serverName/publicKey/fingerprint/shortId/spiderX`), `Flow` — сквозной из URI без авто-логики. Пробелы: нет валидации dest, нет no-steal в шаблонах сервера, нет авто-vision (тема 03).

1. **Диагностика dest (клиент):** при добавлении REALITY-сервера — проверка dest: TLS 1.3 ✓, ALPN h2 ✓, X25519 ✓, PQ key share ✓, IP не anycast/CDN (предупреждение, не блок), гео-близость к серверу (RTT-сравнение, эвристика). Красный/жёлтый/зелёный индикатор «качество dest».
2. **spiderX:** дефолт `/` в UI; поле редактируемое, подсказка «путь для spider mode».
3. **shortId:** генератор случайных shortId в UI деплоя; предупреждение при пустом shortId («все клиенты неразличимы»).
4. **One-click сервер:** шаблон «REALITY без кражи» из коробки — dest → локальный dokodemo-door + routing (SNI-фильтр → blackhole). Уникальные X25519-ключи на инстанс (`xray x25519` на сервере при деплое, не один ключ на всех — иначе компрометация одного = компрометация всех).
5. **ml-dsa65:** упомянуть в advanced (PQ-подписи REALITY, `xray mldsa65`) — опционально, не дефолт.
6. **Не делать:** «автоподбор dest» перебором популярных сайтов — шумный и этически сомнительный; вместо этого — курированный список проверенных dest с результатами диагностики.
