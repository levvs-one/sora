# 60. Captive portals: детект, временный выпуск мимо туннеля, поведение при strict

Группа F «Маршрутизация и файрвол», проход 3. Дата: 2026-10-20.
Не дублирует WEB-RESEARCH §13 (там — Speedify как референс и порядок внедрения): здесь — механика детекта и модель исключений.

## Находки

### 1. Как ОС детектят портал (первоисточники)
- **RFC 8910**: DHCP Option 114 — сеть напрямую анонсирует URL портала; iOS 14+ и Android 11+ поддерживают нативно. Долгосрочный стандартный путь — не перехват HTTP.
- **RFC 8908**: Captive Portal API (`/captive-portal/api/home`) — опрос состояния портала.
- Canary-пробы ОС: Android — `connectivitycheck.gstatic.com/generate_204`; Windows — `msftconnecttest.com` / `www.msftconnecttest.com/redirect`; Apple — `captive.apple.com`. Портал определяется по редиректу/не-204 ответу.
- **Дедлок с VPN** (purple.ai, 2026): VPN шифрует всё → шлюз не видит HTTP-пробу → страница логина не появляется → «гость видит: нет интернета». Штатный совет персоналу отелей — «первый вопрос: выключен ли VPN».

### 2. Модель Speedify (единственный внятный референс среди VPN)
- Детект портала → **уведомление** «хотите войти?» → при согласии трафик к/от страницы логина временно идёт **мимо туннеля**, остальной трафик продолжает идти защищённо (у Speedify — через bonding с cellular; у sora — через уже поднятый туннель на другом интерфейсе, если есть, иначе просто ждёт).
- После успешного логина — автоматический возврат всего трафика в туннель.
- Плюс: `split-tunneling Bypass` для постоянных исключений отдельных сервисов.
- Честная цена: окно, когда трафик к порталу идёт открыто, — уязвимость; Speedify её минимизирует скоупом (только портал) и временем.

### 3. Что НЕ делать (анти-референс)
- **NordLayer «temporary internet access»**: выключить VPN ровно на 3 минуты на логин. Окно уязвимости — весь трафик, а не только портал; пользователь под атакой в открытой сети. Это слоп как модель, хотя как костыль понятно.
- **Молчаливые дыры**: авто-выпуск к порталу без ведома пользователя при strict kill switch — предательство уровня Strict.

### 4. Поведение при strict kill switch — проект решения
- Strict по определению не должен сам открывать исключения. Модель:
  1. Core детектит портал (свои canary-пробы мимо туннеля — см. §5).
  2. UI: баннер «Обнаружен портал входа в сеть. Разрешить временный доступ только к странице входа?» + честная подпись про strict.
  3. При согласии — **scoped exception**: только IP/хост портала (из DHCP Option 114 или из редиректа пробы), только TCP 80/443, TTL 10–15 минут, видимый таймер в UI.
  4. Re-probe после логина → портал пропал → exception снимается автоматически, трафик возвращается в туннель.
  5. Без согласия — strict остаётся strict, интернет «не работает» с объяснением причины (честность вместо молчаливого фейла).
- Standard: то же, но с меньшим трением (авто-предложение, один тап).

### 5. Техническая реализация детекта в sora-core
- Canary-пробы из core **мимо туннеля** (через detour/direct, не через VPN): HTTP GET к `generate_204`-аналогам + проверка DHCP Option 114. Частота — только при событии «подключение к новой сети» / «туннель не устанавливает соединение», не постоянный поллинг.
- Временное правило: sing-box — `{"domain": ["<portal-host>"], "outbound": "direct"}` с TTL; mihomo — временное правило в начало; Xray — аналогично. DNS на время: портал-домен резолвить системным резолвером (split-DNS исключение), hijack-dns для него off.
- Интеграция с trusted networks: сеть с порталом = untrusted по определению; после логина — переоценка.

### 6. Связка с DNS (WEB-RESEARCH §18 подтверждает)
- При детекте портала DoH/DoT ломают резолв страницы входа → временно обычный системный DNS **только для портала**. После логина — возврат к DoH3-first.

## Вердикт: лучшее или слоп
- **Лучшее:** Speedify-модель — детект → явное согласие → scoped exception (портал-only, TTL) → авто-возврат; при strict — без согласия ничего не открывается.
- **Слоп:** «выключи VPN на 3 минуты»; молчаливый авто-bypass при strict; вечные исключения портала без TTL.

## Рекомендация «внедрить так»
1. **Captive-state machine в core:** `IDLE → PROBING → PORTAL_DETECTED → AWAITING_CONSENT → BYPASS_ACTIVE → VERIFYING → IDLE`. События — в UI и в лог диагностики.
2. **Детект:** canary-пробы при смене сети/фейле коннекта + DHCP Option 114 (RFC 8910). Не поллить постоянно.
3. **Bypass:** scoped exception с TTL 15 мин, только хост/IP портала, только 80/443; видимый баннер с таймером и кнопкой «закрыть досрочно».
4. **Strict:** никакого авто-bypass; явный consent-экран с предупреждением; без согласия — объяснение «интернет заблокирован strict kill switch: войдите в портал».
5. **После логина:** re-probe → снятие exception → возврат DNS-политики (DoH3-first). Залогировать событие для per-network memory (Windscribe-паттерн): «в этой сети был портал».
