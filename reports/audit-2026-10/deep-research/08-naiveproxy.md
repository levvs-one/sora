# 08. NaiveProxy — интеграция cronet в sing-box, padding, active probing, цена

Дата: 2026-10-20. Источники: sing-box `protocol/naive/outbound.go` + `docs/configuration/outbound/naive.md` (build-тег `with_naive_outbound`), cronet-go (0x676e67), klzgrad/naiveproxy README (padding-протокол, known limitations), sing-box changelog (QUIC/ECH/UoT в naive), amnezia-box (кросс-проверка интеграции).

## Интеграция cronet в sing-box

- **Механика:** sing-box `protocol/naive/outbound.go` использует Go-биндинги **cronet-go** к нативному движку Chromium **Cronet** (C++). `cronet.NaiveClient` — главный клиентский интерфейс. TLS-хендшейк, HTTP/2 и HTTP/3-запросы выполняются **внутри Cronet** — то есть на проводе настоящий сетевой стек Chromium, а не имитация.
- **Следствие:** TLS-фингерпринт побайтово равен актуальному Chrome (ClientHello, порядок расширений, GREASE, HTTP/2 frame ordering, flow control) — то, что uTLS лишь имитирует и где отстаёт на версии (см. тир S #2).
- **Build-тег:** `with_naive_outbound` (`protocol/naive/outbound.go:1`). В официальных релизах sing-box тег включён по умолчанию. Для sora: при сборке sora-core из исходников тег нужно передавать явно, иначе outbound `type: naive` не зарегистрируется.
- **Платформы:** Apple (iOS/macOS), Android, Windows (`libcronet.dll` рядом с бинарником / в PATH), Linux amd64/arm64 (`libcronet.so`; варианты purego, glibc≥2.31, musl). sora — десктоп (Windows/Linux) — покрыто.
- **Новое в свежих sing-box (changelog):** naive outbound теперь поддерживает **QUIC**, **ECH**, **UDP-over-TCP** и настраиваемый QUIC congestion control. UDP — только через UoT (не нативный UDP).
- **Inbound тоже есть:** sing-box имеет Go-реализацию naive-сервера (`protocol/naive/inbound.go`, `naive.RegisterInbound`) с паддингом — то есть sora может деплоить naive-сервер своим же движком.

## Padding-протокол

- **Механика (klzgrad/naiveproxy):** случайный паддинг добавляется к **первым 8 read/write каждого стрима**. Цель — сломать length-based traffic analysis (анализ длин пакетов).
- **Opt-in:** паддинг включается только если обе стороны прислали `padding`-заголовок; иначе обе стороны его отключают. Следствие: naive-клиент interoperable с обычными HTTP/2-прокси, naive-сервер — с обычными браузерами.
- **Application fronting:** сервер прячется за обычным веб-фронтендом (Caddy + forwardproxy-плагин с форком под паддинг, или HAProxy). Фронтенд отдаёт нормальный веб-контент браузерам и роутит аутентифицированные запросы на прокси. Активный пробер без credentials видит обычный сайт.

## Устойчивость к active probing

Архитектура «фронтенд → naive» даёт сильную защиту от активного зондирования: пробер получает корректные HTTP-ответы неотличимые от легитимного сайта (в отличие от REALITY, где пробер получает настоящий dest-сайт — тоже хорошо, но здесь сайт свой). TLS-фингерпринт — настоящий Chrome, а не эмуляция.

**Честные ограничения (документированы самим проектом, README 153–161):**
- Fast Open-паттерн (back-to-back H2-пакеты) — необычен, потенциальная сигнатура.
- TLS-over-TLS: больше round trips, инфляция длин пакетов, превышение MTU — «нет мелких пакетов, типичных для user agent».
- Долгоживущие туннели — поведенческая сигнатура (неизвестно оптимальное время жизни).
- Проект **явно не заявляет** полную необнаружимость.

**Внешний риск (10.2026):** госзакупка КНР показывает, что DPI-оборудование уже заявляет идентификацию NaiveProxy. Позиционировать как «anti-probing», не как «невидимость».

## Цена

1. **Размер:** libcronet — десятки МБ в дистрибуции (на каждую платформу свой бинарник). Для sora — заметный прирост установщика.
2. **Свежесть Chromium:** фингерпринт равен версии встроенного Cronet. klzgrad ребейзится под каждый Chromium (10.2026 — ~v153/154). **Устаревший libcronet = устаревший фингерпринт = детект-сигнал** (та же проблема, что с uTLS, тир S #2). Значит: процесс обновления libcronet синхронно с Chromium — обязательная часть релизного цикла sora, иначе фича превращается в антифичу.
3. **UDP только через UoT** — не для игр/VoIP с жёсткими требованиями к задержке; честно помечать.
4. **TLS-over-TLS тяжелее VLESS** — выше CPU и latency на хендшейке.

## Вердикт: лучшее (с ценником)

Настоящий Chrome-стек вместо имитации — качественно другой уровень маскировки, чем uTLS. Padding-протокол и application fronting — продуманные, документированные механизмы. Цена честно посчитана выше. Окно дифференциации реально: ни у кого из десктопных конкурентов нет нативного naive.

**Отсеяно фильтром:** «NaiveProxy необнаружим» — сам проект это опровергает списком limitations; «достаточно включить — и всё» — без свежего libcronet и fronting-деплоя это просто тяжёлый TLS-прокси.

## Внедрить в sora так

Состояние sora: naive отсутствует полностью (парсер, план, рендеры — ноль).

1. **Сборка:** включить тег `with_naive_outbound` в пайплайн сборки sora-core; в дистрибуцию класть `libcronet.dll`/`libcronet.so` под каждую платформу; проверка наличия библиотеки при старте с понятной ошибкой.
2. **Парсер:** `naive+https://user:pass@host:port` (де-факто формат) → `Outbound{Protocol: "naive", ...}`.
3. **plan/render (sing-box):** `{"type": "naive", "server", "server_port", "username", "password", "tls": {...}}` — сверить с `docs/configuration/outbound/naive.md` актуальной версии.
4. **Релизный процесс:** пункт «обновить libcronet до актуального Chromium» в чеклисте каждого релиза sora; диагностика «версия Cronet vs актуальный Chrome» с варнингом при отставании >2 версий.
5. **One-click деплой:** Caddy + forwardproxy@naive (xcaddy-сборка) — самый простой серверный деплой; шаблон с application fronting (дефолтный сайт-заглушка).
6. **UI:** протокол «NaiveProxy» с честной пометкой: «настоящий Chrome-стек; UDP — через UoT (не для игр); требует свежий libcronet». Capabilities: скрывать протокол, если сборка без тега/библиотеки.
7. **Не делать:** позиционировать как «невидимый»; включать без fronting на сервере одной кнопкой без предупреждения (голый naive-сервер без фронтенда проще пробовать).
