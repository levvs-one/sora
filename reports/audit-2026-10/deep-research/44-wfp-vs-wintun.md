# 44 — WFP callout-драйверы vs WinTun: компромиссы Windows-датаплана sora

Дата: 2026-10-20. Третий проход группы E. Новая тема первого прохода не покрыта (там WFP упоминался только вскользь). Вопрос: стоит ли sora вместо/вместе с WinTun строить датаплан на WFP callout-драйвере.

## 1. Что такое WFP callout и чем он отличается от WinTun

- **WinTun** — виртуальный L3-адаптер (NDIS miniport). ОС видит «сетевую карту»: на неё вешаются IP-адреса, маршруты, DNS, метрики. Трафик приложений попадает в драйвер через обычный роутинг ядра, дальше — shared-memory кольца в userspace (тема 43).
- **WFP (Windows Filtering Platform)** — фреймворк фильтрации в сетевом стеке ядра. **Callout** — kernel-драйвер, регистрирующий колбэки на слоях WFP (ALE — Application Layer Enforcement, транспортный, сетевой, stream/datagram). Callout может разрешать/блокировать/перенаправлять пакеты и соединения.
- Критичное различие: **WFP callout сам по себе не создаёт интерфейс и не умеет «туннелировать»**. Это инспектор/фильтр, а не транспорт. Чтобы гнать трафик в туннель через WFP, нужно: перехватить пакет на слое → скопировать в userspace → зашифровать → вернуть через `FwpsInjectNetworkSendAsync` или через сокет — с ручным переписыванием адресов и аккуратным избеганием рекурсии (свой же инжект снова попадает в callout). Это сложно, гонкоопасно и медленно.

## 2. Что WFP умеет хорошо (и где ему место в sora)

1. **Kill switch**: WFP-фильтры на ALE-слое (`FWPM_LAYER_ALE_AUTH_CONNECT_V4/V6`) с action=block — решение принимается **один раз на соединение**, пер-пакетного оверхеда почти нет. Важно: **фильтры не требуют драйвера** — их добавляет userspace через `FwpmFilterAdd` (нужны админ-права, но не подпись kernel-драйвера). Mullvad/Proton/IVPN делают kill switch именно так.
2. **Per-app split tunneling**: ALE видит AppId процесса — можно разрешать/блокировать по приложению без виртуального адаптера. Но роутинг «это приложение — в туннель, это — мимо» всё равно требует интерфейса-получателя (WinTun) для туннелируемой части.
3. **Блокировка утечек**: `strict_route` в sing-box на Windows + WFP-фильтры против «ordinary multihomed DNS resolution behavior» Windows (официальная дока sing-box, тема 41).

Производительность по слоям (copyprogramming, гайд WFP 2026): ALE-фильтрация — минимальный импакт (решение на соединение); транспорт/сетевой слой — выше (решение на каждый пакет); stream/datagram-инспекция с копированием полезной нагрузки — самый дорогой вариант. Вывод: WFP для policy — дёшево, WFP для datapath — дорого.

## 3. Компромиссы: таблица

| Критерий | WinTun (виртуальный адаптер) | WFP callout-драйвер |
|---|---|---|
| Роль | Полноценный датаплан: интерфейс + роутинг ОС из коробки | Фильтр/инспектор; туннелирование — костыль через inject |
| Подпись драйвера | Нужна (WinTun.sys подписан zx2c4/Microsoft) | Нужна **своя** (attestation через Partner Center) |
| Зависимость от Microsoft | Используем готовый подписанный драйвер | Свой драйвер → своя подпись → риск истории апр. 2026 (приостановка аккаунта WireGuard в Hardware Program) |
| Per-packet cost | ~0 syscall (shared memory кольца) | Перехват в ядре + копия в userspace + inject обратно |
| Роутинг/метрики/DNS | Нативно через ОС | Вручную, вне модели ОС |
| Kill switch | Возможен, но грубее | Идеален (ALE-фильтры, дёшево) |
| Per-app policy | Через userspace-мэппинг сокет↔процесс | Нативно (AppId на ALE) |
| Сложность кода | Низкая (зрелый API) | Высокая (рекурсия inject, состояния TCP) |
| Отладка | tcpdump/Wireshark на интерфейсе | Только kernel-отладка |

Вывод из dev.to-разбора per-process networking на Windows (2026): «Option A — Kernel-driven: WFP drivers, virtual adapters… Powerful, but heavy and fragile. Option B — User-space reconstruction: capture via Wintun… More flexible». Индустрия сошлась на гибриде: **датаплан — виртуальный адаптер, политика — WFP-фильтры**.

## 4. Что делают другие

- WireGuardNT — третий путь: полноценный kernel-датаплан (не WFP callout, а NDIS-протокол-драйвер). Быстрее WinTun, но требует своей подписи и несёт риски поставки (тема 45).
- AdGuard для Windows — WFP-драйвер для **фильтрации** (не туннелирования): показывает, что WFP-драйвер оправдан, когда задача — инспекция, а не транспорт.
- OpenVPN DCO (hide.me дефолт с 3.15): kernel-датаплан для OpenVPN — опять же не WFP callout, а специализированный драйвер под протокол.

## 5. Вердикт: лучшее или слоп

**WFP callout как датаплан — слоп** (переусложнение: свой подписанный драйвер ради худшего перфа, чем готовый WinTun). **WFP-фильтры (без драйвера) как policy-слой — лучшее** (kill switch, per-app policy, блокировка DNS-утечек — дёшево и нативно).

## 6. Рекомендация «внедрить так»

1. **Датаплан Windows остаётся WinTun** — не писать WFP callout-драйвер. Это архитектурное решение зафиксировать в доке (чтобы не возвращаться).
2. **Kill switch на WFP-фильтрах** (user-mode `FwpmFilterAdd`, без своего драйвера): ALE connect-блок при активном Strict-режиме + персистентность через ребут (перекликается с темой kill switch первого прохода). Проверить, что это делает/может sing-box `strict_route`, и добавить своё поверх при необходимости.
3. **Per-app split на Windows**: ALE видит AppId — использовать WFP для policy, WinTun для транспорта. Не пытаться определять «какое приложение» через userspace-сниффинг сокетов (хрупко).
4. **Не подписывать свой kernel-драйвер** без крайней нужды: урок апреля 2026 (Microsoft приостанавливала аккаунт WireGuard в Hardware Program) — для опенсорсного проекта это экзистенциальный риск цепочки поставок.
5. Долгосрочный watch: WireGuardNT как опциональный kernel-датаплан **только** когда стабилизируется поставка подписей; WFP callout — никогда как датаплан.
