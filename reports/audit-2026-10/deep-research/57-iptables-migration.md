# 57. iptables legacy: что использует sora-legacy, путь миграции на nftables

Группа F «Маршрутизация и файрвол», проход 3. Дата: 2026-10-20.

## Находки

### 1. Факт по репо: sora-legacy уже на nftables, iptables — только вендорный
- Поиск по `sora-legacy`: `iptables` встречается **только** в `third_party/zapret/` (скрипты `common/ipt.sh`, `common/fwtype.sh`, `common/linux_fw.sh`, `blockcheck.sh`) — это внешний вендорный код zapret, который сам детектит бэкенд (fwtype.sh выбирает между iptables/nftables/ipfw).
- Собственный код: `core/guard/nftables.go`, `nftables_linux.go`, `nftables_test.go` — kill switch на nftables; `core/testdata/coexist/run.sh` — тест сосуществования. То есть «миграция» собственного кода уже состоялась в ходе аудит-фиксов; задача темы — зафиксировать путь и добить остатки.

### 2. Путь миграции iptables → nftables (проверенная практика, 2026)
- **Транслятор:** `iptables-translate` / `iptables-restore-translate -f` — конвертирует существующие правила в nft-синтаксис для ревью. Не слепо применять: вывод требует ручной проверки (семантика цепочек и приоритетов отличается).
- **Окружение:** Ubuntu 24.04 / Debian 12 — nftables нативный бэкенд по умолчанию, `iptables` = `iptables-nft` compat-слой поверх nf_tables. Отдельный legacy-бэкенд держать не нужно нигде, где ядро ≥3.13 (2014) — то есть везде, что поддерживает sora.
- **Что меняется архитектурно:**
  - `iptables` + `ip6tables` → одна таблица `inet` (v4+v6 в одних правилах — заодно закрывается класс IPv6-утечек);
  - `ipset` → нативные `set`/`map`/`vmap` в nft;
  - цепочки `INPUT/OUTPUT/FORWARD` → `type filter hook input/output/forward`;
  - маркировка для policy routing: `iptables -t mangle -j MARK` → `nft ... meta mark set`.
- **Откат:** бэкап `iptables-save` перед миграцией; `nft flush ruleset` + `iptables-restore` — план отката на случай регрессии.

### 3. Конфликты при сосуществовании
- nftables мультитабличен: таблицы `inet sora`, `inet firewalld`, `ip filter` (docker) живут рядом. Конфликт — не в таблицах, а в **порядке hook'ов и чужих drop-политиках**. Правило: своя таблица с уникальным именем + проверка `nft list ruleset` на пересечения при установке (уже рекомендовано в теме 55).
- UFW/firewalld поверх nftables: либо дружить (своя таблица), либо честно требовать отключения — молчаливое «не работает» недопустимо.

### 4. Что осталось доделать в sora-legacy
- Вендорный zapret: оставить как есть (upstream сам мигрирует; `fwtype.sh` уже предпочитает nftables где доступно), но зафиксировать в документации, что sora вызывает zapret-скрипты с ожиданием nft-бэкенда и тестирует этот путь.
- Убедиться, что ни один собственный скрипт/инсталлятор не дёргает `iptables` напрямую (поиск показал — не дёргает; зафиксировать grep-тестом в CI).

## Вердикт: лучшее или слоп
- **Лучшее:** один бэкенд — nftables везде; `iptables-translate` как инструмент разовой конвертации с ручным ревью; CI-тест сосуществования с firewalld/docker.
- **Слоп:** держать два бэкенда «на всякий случай» (удвоение тестовой матрицы, рассинхрон правил); слепое применение вывода транслятора без ревью.

## Рекомендация «внедрить так»
1. **Зафиксировать:** nftables — единственный поддерживаемый бэкенд Linux-файрвола sora. Удалить/запретить прямые вызовы `iptables` в собственном коде (grep-гейт в CI).
2. **zapret:** не трогать вендорный код; в документации sora зафиксировать, что zapret запускается в nft-режиме (`fwtype.sh` это умеет), и покрыть интеграционным тестом.
3. **Миграция пользовательских систем:** если у пользователя уже есть iptables-правила — не затирать молча: своя таблица `inet sora` + предупреждение о найденных чужих drop-правилах.
4. **Тесты:** расширить `testdata/coexist/run.sh`: firewalld включён, docker включён, ufw включён — kill switch работает и не ломает их.
5. Fallback: если `nft` недоступен в системе (экзотика) — явная ошибка с инструкцией, а не тихий no-op без защиты.
