# 47 — MTU/MSS: PMTUD black holes, MSS clamping, диапазон 1280–1420, почему MTU 9000 — баг

Дата: 2026-10-20. Третий проход группы E. Первый проход зафиксировал баг (MTU 9000) и диапазон. Здесь — механика поломки, арифметика оверхедов и точные значения для конфигов sora.

## 1. Арифметика: откуда берутся 1280–1420

Каждый слой инкапсуляции отъедает от path MTU (обычно 1500):

- WireGuard поверх IPv4: 20 (IP) + 8 (UDP) + 32 (WG) = **60 байт**; поверх IPv6: **80 байт**. Отсюда дефолт WG-интерфейса **1420** = 1500 − 80 (худший случай): «fits the worst case on a 1,500-byte path» (https://www.aicassindra.com/blogs/networking/understanding_mtu_and_fragmentation.html).
- Типовые связки (mustafaerbay.com.tr, 2026): WireGuard 1420/1380 (v4 MTU/MSS), IPsec 1400/1360, OpenVPN-UDP 1360/1320. MSS = MTU − 40 (IPv4) или − 60 (IPv6, заголовок 40 вместо 20).
- **1280** — минимальный MTU IPv6 (RFC 8200): ниже нельзя, иначе ломается v6 вообще. Поэтому практический VPN-диапазон: **1280–1420**.
- PPPoE-подключения (часто в РФ): underlay 1492 → WG-интерфейс 1412. Мобильные сети: underlay бывает 1400 → интерфейс 1340.

## 2. Почему MTU 9000 на TUN — баг (механика)

sora рендерит `"mtu": 9000` в sing-box TUN (`core/engine/singbox/render.go:641`). Что происходит:

1. ОС видит интерфейс с MTU 9000 и отдаёт в TUN пакеты до 9000 байт (TCP-сегменты до ~8960).
2. Движок (userspace) должен этот 9000-байтный пакет запихнуть в реальный путь с MTU 1500. Варианты: фрагментировать в userspace (дорого, и многие стеки этого не умеют корректно), либо слать как есть с DF — и получать дроп.
3. Реальный интернет **не поддерживает 9000**: jumbo frames работают только внутри дата-центра, где каждый свитч и NIC настроены. «The risk is a single device left at 1,500: then large packets are silently dropped for exactly the bulk flows that motivated the change» (aicassindra.com).
4. Итог: фрагментация/ретрансмиты, рост CPU на сегментацию, а при обрезанном ICMP — PMTUD black hole (см. ниже). Замеры OpenVPN (1500→48000 даёт 158→510 Мбит/с) — это **лабораторный гигабит без фрагментации**, к реальному интернет-пути неприменимо.

Отдельный нюанс sing-box: в официальном примере конфига `"mtu": 9000` — видимо, оттуда значение и перекочевало в sora. Пример — для идеального пути, не дефолт для продукта.

## 3. PMTUD black holes: механика и диагностика

Path MTU Discovery: отправитель ставит DF (Don't Fragment), роутер с меньшим MTU отвечает ICMP `Type 3 Code 4` (Fragmentation Needed) / ICMPv6 `Type 2` (Packet Too Big), отправитель уменьшает размер. Ломается, когда ICMP режут фаерволы («block all ICMP» — частая и вредная практика):

- Симптом: **маленькие пакеты ходят, большие висят**. Классика: «VPN works until I hit a website with a big certificate chain» — ClientHello влезает, цепочка сертификатов (несколько сегментов) — нет; первый сегмент, требующий фрагментации, дропается молча (https://www.valtersit.com/guides/networking/the-mtu-nightmare-why_your_vpn_connection_is_fragmenting_to_death/).
- IPv6-специфика: роутеры v6 **не фрагментируют вообще** (только отправитель), поэтому обрезанный ICMPv6 Type 2 убивает v6-путь полностью — «dual-stack VPN freezes on IPv6» (mustafaerbay.com.tr).
- QUIC-особенность: QUIC делает **свой PMTUD поверх UDP** и **игнорирует MSS clamping**. Clamping чинит TCP, но не QUIC — для него нужен рабочий ICMP end-to-end, иначе QUIC падает на консервативный MTU и теряет скорость (valtersit.com).

Диагностика: `ping -M do -s <size>` — бинпоиск максимального нефрагментируемого размера; +28 (IP+ICMP заголовки) = path MTU. В sora это должен делать автоматический MTU-probe, а не пользователь.

## 4. MSS clamping: как чинит 90% случаев

Механика: перехватывать TCP SYN (и SYN-ACK) и переписывать MSS на `tun_mtu − 40` (v4) / `− 60` (v6). Тогда TCP изначально сегментирует под туннель — PMTUD не нужен, фрагментации нет.

Рецепты (https://oneuptime.com/blog/post/2026-03-20-configure-tcp-mss-clamping/view):
```
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu
iptables -t mangle -A OUTPUT  -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu
```
`--clamp-mss-to-pmtu` читает MTU выходного интерфейса динамически — работает при смене сети. Нужны обе цепи (FORWARD для транзита, OUTPUT для локально-генерируемого трафика) и обе версии протокола (v4 и v6 отдельно, значения различаются на 20).

Для userspace-движка (sing-box TUN): clamping должен делать сам движок на SYN, проходящих через его TCP-стек (новый стек 1.15 — проверить наличие; если нет — фича-реквест/патч). На уровне ОС это тоже возможно, но движок надёжнее (видит все SYN).

## 5. Вердикт: лучшее или слоп

**Лучшее.** MTU 9000 — объективный баг с понятной механикой поломки; MSS clamping — дешёвое (одна опция/правило) исправление 90% «медленного VPN»; диапазон 1280–1420 — арифметика, а не вкусовщина.

## 6. Рекомендация «внедрить так»

1. **Дефолт TUN MTU: 1500 → нет; ставить 1420** (худший случай WG-over-v6 на пути 1500). Для AWG оставить 1280 (уже так в `render.go:342` — правильно: junk-пакеты Jmax < MTU, запас нужен). mihomo 1420 — уже правильно. Xray unset→1500 — проверить, не надо ли 1420.
2. **MSS clamping — обязательно**: либо опцией движка (проверить поддержку в sing-box 1.15 / mihomo / Xray TUN), либо своими iptables/nftables-правилами на Linux и WFP-фильтром на Windows. Clamp = MTU_туннеля − 40 (v4), − 60 (v6). Без этого смена MTU — полумера.
3. **MTU-probe в диагностике**: автоматический бинпоиск `ping -M do` до шлюза/популярных хостов при жалобах на скорость; результат — в лог и в UI («path MTU 1412, применён clamp 1372»).
4. **Не позволять пользователю ставить MTU > 1500** на TUN без явного «я понимаю» (валидация в UI: варнинг при >1500).
5. **QUIC отдельно**: в доке зафиксировать, что clamping не чинит QUIC — для него нужен нефильтрованный ICMP; при проблемах с QUIC-скоростью проверять ICMP-проходимость, а не крутить MTU.
6. Убрать 9000 из всех примеров/документации sora — значение расползается копипастой.
