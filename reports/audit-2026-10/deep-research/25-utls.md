# 25. uTLS — конструкция ClientHello, HelloChrome_Auto=Chrome 155, JA3/JA4, CVE-2026-27017/26995, вред рандомизации

Дата: 2026-10-20. Группа C «DPI-обход», третий проход. Первоисточники: репозиторий refraction-networking/utls, XTLS/Xray-core issue #7131 (окт. 2026), CVE-записи (INCIBE/Tenable/Wiz/Ubuntu), justbrowser.app (JA4 vs рандомизация), crawlex.net (каталог ClientHello). Тир S #2 и отчёт 26 покрывали «что случилось» — здесь «как устроено и почему ломается».

## 1. Конструкция ClientHello в uTLS

- uTLS — форк Go `crypto/tls`: handshake настоящий, но ClientHello собирается по программируемому **ClientHelloSpec** — упорядоченный список TLS-расширений с точными байтами (порядок расширений, GREASE-значения, cipher suites, кривые, ALPN, key shares).
- **Паритеты («parrots»):** `HelloChrome_120`, `HelloChrome_131`, `HelloChrome_133`, … — каждый сверяется с реальным браузером побайтово.
- **Коммит 06.10.2026 (`6ebdceb`):** добавлен `HelloChrome_155`, сверенный с реальным Chrome 155, и он стал `HelloChrome_Auto`. Замер JA4: Xray 26.10.10 с `chrome` → `t13d1516h2_8daaf6152771_d8a2da3f94cd`; uTLS 6ebdceb → `t13d1517h2_8daaf6152771_cb7bf5808d99` — идентично реальному Chrome 155 (Linux). Отличаются только рандомизированные значения (GREASE, ключи, ECH payload, порядок расширений).
- **Вехи фингерпринта:** Chrome 100+ — ALPS/application_settings + compress_certificate; Chrome 120+ — ECH/GREASE ECH; Chrome 131+ — **X25519MLKEM768** (post-quantum hybrid key share; ~90%+ трафика Chrome к 2026).

## 2. Почему старые/«почти правильные» фингерпринты детектятся

- **Поле (Xray-core #7131, окт. 2026):** в РФ `chrome`-паритет (Chrome 133) детектится и блокируется ТСПУ: Chrome 133 → TLS timeout, Chrome 155 / Firefox / QQ → OK. Устаревший фингерпринт — активная причина блокировки, не «старый, но рабочий».
- **CVE-2026-27017** (опубл. 19.02.2026, фикс uTLS 1.8.1, CVSS 5.3): Chrome-parrot в uTLS 1.6.0–1.8.0 при **GREASE ECH** случайно выбирал ChaCha20 для ECH при AES в outer ClientHello — комбинация, **невозможная в настоящем Chrome** (Chrome выбирает консистентно по hardware AES support). 50% соединений — детект пассивным наблюдателем. Фикс-коммит `24bd1e0`.
- **CVE-2026-26995** (фикс uTLS 1.8.2; CVE Program **отклонил** запись — сочли проблемой зависимости, не uTLS): в `HelloChrome_120` было удалено padding-расширение, хотя настоящий Chrome убирает его только при отправке PQ keyshare. Только non-PQ вариант Chrome 120 задет; новее — PQ по дефолту, старше — расширение на месте.
- **Вывод:** DPI ловит не только «старый», но и «почти правильный» фингерпринт. Любая деталь (padding, GREASE, порядок расширений, консистентность cipher-выбора) — вектор. Ручные подкрутки фингерпринта опасны; безопасен только точный паритет со свежим браузером.

## 3. JA3/JA4

- **JA3** = MD5(SSLVersion, Ciphers, Extensions, EllipticCurves, ECPointFormats). Чувствителен к порядку; ТСПУ-слой 2 (по habr 1009542) сверяет первые байты + JA3-хэш с базой.
- **JA4** (FoxIO, 2023) — менее чувствителен к порядку расширений, **устойчив к рандомизации** (спроектирован так). Промышленные DPI переходят на него. Следствие: «перемешаем расширения — и нас не узнают» не работает против JA4.
- Для sora: JA4 — инструмент **самопроверки**, не маскировки: stealth-check «наш ClientHello == реальный Chrome 155» в диагностике.

## 4. Почему randomized-фингерпринты вредны (консенсус 2025–2026)

- Случайных TLS-фингерпринтов в реальной популяции браузеров **не существует** — рандомный отпечаток сам по себе аномалия, делающая клиента *более* детектируемым.
- JA4 спроектирован устойчивым к рандомизации — рандом не ломает классификатор.
- uTLS `HelloRandomizedALPN`/`HelloRandomizedNoALPN`, xray `random`/`randomized` — это трюк «не засветиться дважды подряд», а не способ стать незаметным.
- Правильная стратегия для обхода цензуры: **точное совпадение с самым популярным браузером** (Chrome Auto свежий), а не рандом. Доказательства: поле Xray #7131 (Chrome 155 проходит, 133 — нет), CVE-пары выше (отклонение от Chrome = детект).

## 5. Вердикт: лучшее или слоп

**Лучшее — свежий точный паритет; слоп — всё остальное.** uTLS с HelloChrome_Auto=155 — лучшее из доступного (побайтовый паритет, JA4 совпадает). Слоп: дефолт `chrome` без контроля версии (сейчас = Chrome 133 = блок в RU); randomized-фингерпринты как «фича приватности»; ручные правки ClientHello; ECH+uTLS без проверки консистентности (урок CVE-2026-27017).

## 6. Рекомендация «внедрить так»

1. **Пин uTLS ≥1.8.2** во всех движках; трекинг актуальности: CI-джоба сверяет `HelloChrome_Auto` с последним релизом uTLS, алерт при отставании >N недель.
2. **Убрать дефолт `chrome`** (sora-legacy `render.go:269` ставит его молча) — в UI явный выбор фингерпринта с пометкой свежести («Chrome 155, сверен 06.10.2026»).
3. **Авто-fallback при TLS-timeout:** при симптоме из #7131 (timeout на handshake) — перебор fp (Chrome Auto → Firefox → QQ → Edge) с запоминанием рабочего на профиль сети.
4. **Stealth-check JA4 в диагностике:** клиентский замер собственного ClientHello vs эталон реального Chrome; красный флаг при расхождении.
5. **PQ-консистентность:** если паритет заявляет Chrome 131+, key share обязан включать X25519MLKEM768 — иначе «свежий Chrome без PQ» виден DPI до HTTP.
6. **Не делать:** randomized-fp как опцию «стелс»; ручной конструктор ClientHello для пользователей; ECH без GREASE-консистентности (регрессионный тест на кейс CVE-2026-27017).
