# 50 — Методология замера throughput через TUN: как честно бенчмаркать и ловить регрессии

Дата: 2026-10-20. Третий проход группы E. Первый проход дал набросок (тема 46, п.6; ssdnodes-методология). Здесь — полный протокол стенда: что мерять, как не врать себе, как автоматизировать.

## 1. Почему «просто speedtest» врёт

Типовые источники лжи в замерах через TUN:
1. **Один TCP-поток упирается в окно/RTT, а не в TUN.** На пути 50 мс один поток не насытит даже 100 Мбит/с без тюнинга буферов. Результат «медленный VPN» при исправном датаплане.
2. **Направление.** Аплоад и даунлоад асимметричны (особенно через NAT/мобильные сети). Замер в одну сторону — половина картины.
3. **Короткий тест** (5 с дефолта iperf3): slow start и прогрев занимают большую часть замера на длинных путях.
4. **Тепловой/CPU-фон**: замер на ноутбуке под нагрузкой меряет планировщик, а не TUN.
5. **Endpoint — бутылочное горлышко**: на 1+ Гбит/с iperf3-клиент/сервер сам может не успевать (Intel: на ≥25G нужны CPU-pinning и несколько инстансов; то же верно для слабых VPS).
6. **Смешение метрик**: «скорость VPN» = min(канал, сервер, датаплан клиента, протокол). Без контрольного замера напрямую нельзя сказать, что именно тормозит.

## 2. Протокол честного замера (база — iperf3)

Источники: cordero.me (чеклист iperf3), Intel Ethernet perf-tuning guide, learnlinux.tv, surfercloud (Google Cloud, янв 2026).

**Стенд**: iperf3-сервер за туннелем (на VPS рядом с VPN-сервером или на самом VPN-сервере в обход — см. п.4), клиент — машина с sora. Фиксировать: версии iperf3, ОС, железо, дату, направление, TCP/UDP, число потоков, длительность, RTT, CPU.

**Прогон (каждый — минимум 30 с, `-t 30`, пропуск slow start `-O 3`, JSON-вывод `-J`):**
```
# 1. Контроль: напрямую, без туннеля
iperf3 -c <server> -t 30 -O 3 -J
iperf3 -c <server> -t 30 -O 3 -J -R        # реверс
# 2. Через TUN, один поток, оба направления
iperf3 -c <server-via-tun> -t 30 -O 3 -J
iperf3 -c <server-via-tun> -t 30 -O 3 -J -R
# 3. Через TUN, 4 потока, оба направления
iperf3 -c <server-via-tun> -P 4 -t 30 -O 3 -J
iperf3 -c <server-via-tun> -P 4 -t 30 -O 3 -J -R
# 4. UDP: джиттер и потери (VoIP/игры)
iperf3 -c <server-via-tun> -u -b 200M -t 30 -J
# 5. MTU-лестница: повторить п.2-3 при MTU 1280/1400/1420/1500
```

**Смотреть не только битрейт**: `Retr` (ретрансмиты TCP — маркер MTU/фрагментационных проблем), `Cwnd`, CPU клиента (`mpstat`: `%usr` vs `%soft` — userspace-датаплан vs kernel), pps (малые пакеты: `iperf3 -l 256`).

**Правило интерпретации** (cordero.me): «Begin with one TCP stream… Test both directions… Add streams gradually… one stream shows the flow, parallel streams show the path's aggregate potential — the difference between them is where the troubleshooting begins».

## 3. Матрица «что ловим»

| Симптом | Диагноз | Проверка |
|---|---|---|
| 1 поток низко, 4 потока — норма | Ограничение окна/RTT или single-thread TUN (тема 45) | Сравнить напрямую vs TUN; `-P` лесенка 1/2/4/8 |
| Низко в обе стороны и на всех потоках | Канал/сервер/CPU-крыша | Контроль напрямую; `mpstat` — какое ядро в 100% |
| Down норм, up в разы ниже | Асимметрия пути/NAT | `-R` оба направления всегда |
| Ретрансмиты >1% | MTU/фрагментация/PMTUD black hole | MTU-лестница + `ping -M do` (тема 47) |
| UDP потери/джиттер при живом TCP | UDP-путь движка (gVisor-legacy!) | Аргумент за снятие `stack` (тема 41) |
| Просадка только на мелких пакетах | pps-потолок датаплана | `iperf3 -l 256`, сравнить pps, не bps |

## 4. Архитектура стенда для sora (регрессионный)

1. **Встроенный бенч в sora-core** (развитие идеи первого прохода): Go-реализация iperf-подобного замера (TCP upload/download, 1 и 4 потока, UDP loss/jitter) **через активный TUN** к эталонному серверу sora (контролируемый VPS). Результат — в диагностику и в историю замеров.
2. **Эталонный сервер**: известный, неменяющийся (тот же VPS, тот же iperf3) — иначе регрессии движка неотличимы от «сервер проседает».
3. **CI-матрица**: на каждый релиз движка/пины — прогон матрицы (1/4 потока × 2 направления × TCP/UDP) на Linux/Windows, сравнение с бейзлайном прошлого пина. Отклонение >10% — красный флаг, блокирующий обновление пина.
4. **Разделение «канал vs датаплан»**: замер «напрямую» и «через TUN» рядом, показывать обе цифры (честность из первого прохода, тема 04).
5. **Публикация цифр**: Trust Center / changelog движка — «sing-box 1.15: +X% к 1.14 на нашем стенде». Никто из конкурентов не публикует свои TUN-бенчи — готовый дифференциатор.

## 5. Типовые антипаттерны (не делать)

- Замер одним потоком 5 секунд и вывод «VPN режет скорость в 3 раза» — меряет TCP-физику, не VPN.
- Замер до speedtest.net через браузер — меряет CDN/провайдера/TCP-стек браузера, невоспроизводимо.
- Сравнение движков на разных серверах/в разное время суток — шум больше эффекта.
- Игнорирование CPU: «движок А медленнее движка Б» при 100% одного ядра — это не про движок, а про single-thread TUN.
- UDP-замер с `-b` выше своего аплоада — loss-колонка врёт (пакеты не вышли из машины).

## 6. Вердикт: лучшее или слоп

**Лучшее.** Методология — дешёвая (iperf3 + скрипт), а ловит дорогие ошибки: регрессии пинов движков, MTU-баги, UDP-деградацию. Без стенда все выводы тем 41–49 — «вроде стало лучше».

## 7. Рекомендация «внедрить так»

1. Скрипт `bench-tun.sh` в репозитории (не в прод): матрица выше, JSON-вывод, сравнение с бейзлайном, exit code по порогу регрессии — гонять руками и в CI при смене пина движка.
2. Встроенный замер в диагностику клиента: «потолок клиента» (через TUN к эталонному серверу) рядом с «потолком канала» (напрямую) — 1 и 4 потока, оба направления.
3. Бейзлайны хранить версионированно (движок/версия/ОС/железо); порог регрессии 10%.
4. Первым прогоном зафиксировать эффект снятия `"stack": "mixed"` и MTU 9000→1420 — это и есть доказательство для пользователя, а не «стало лучше, поверьте».
5. Отдельный UDP-прогон — обязателен: именно UDP-путь страдал в `mixed` (gVisor) и именно он важен для QUIC/игр.
