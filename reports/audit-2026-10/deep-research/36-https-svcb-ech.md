# 36. HTTPS/SVCB-записи + ECH — DNS как enabler

Дата: 2026-10-20. Группа D «DNS», третий проход. Тезис: для VPN-клиента ECH нельзя «включить», но можно **не сломать** — и это нетривиально, потому что ECH полностью зависит от DNS.

## 1. Механика (RFC 9460 + RFC 9849)

**RFC 9460** вводит типы 64 (SVCB) и 65 (HTTPS). Два режима:
- **AliasMode** (priority 0): алиас на другое имя — работает на apex зоны (в отличие от CNAME);
- **ServiceMode** (priority > 0): target + SvcParams: `alpn` (h2/h3), `port`, `ipv4hint`/`ipv6hint`, **`ech`**.

**ECH (RFC 9849, Standards Track, 2025):** клиент берёт `ech` (ECHConfig — публичный ключ) из HTTPS-записи, делит ClientHello на внешний (публичное имя, видимое) и **шифрованный внутренний** (реальный SNI, ALPN, cipher suites). Серверная сторона — в основном Cloudflare (для своих зон) и крупные хостеры.

**Критическая зависимость:** Firefox 119+ и Chromium 117+ включают ECH **по умолчанию, но только если HTTPS-запись получена через DoH** (позиция Mozilla: «ECH relies on DNS over HTTPS; ECH delivers the most privacy benefit when DNS records are fetched via an encrypted transport»). Причина: через plaintext-DNS цензор/провайдер может **вычистить `ech`-параметр** из ответа — клиент решит, что ECH не поддерживается, и пойдёт с открытым SNI. Это тихая деградация, которую пользователь не заметит.

## 2. Что это значит для sora

VPN-клиент не выполняет TLS-хендшейки за приложения — ECH делает TLS-стек браузера. Но sora контролирует **DNS-путь**, от которого ECH зависит:

1. **Не фильтровать QTYPE 65.** Любой «DNS-фильтр»/adblock на уровне DNS в клиенте обязан пропускать HTTPS/SVCB-записи как есть. Проверка: `dig example.com HTTPS` через туннельный DNS возвращает `ech=` — в диагностику.
2. **HTTPS-записи — только через шифрованный транспорт.** Если DNS идёт plaintext (или через провайдера для .ru — см. 35), `ech` может быть вычищен. Для доменов, где приватность важна, — DoH/DoH3.
3. **FakeIP и HTTPS-записи:** fakeip-сервер отвечает только на A/AAAA; запросы прочих типов (TXT, MX, HTTPS/SVCB) должны уходить на upstream — в sing-box это поведение по умолчанию для не-A/AAAA? Нет: правило `query_type: [A,AAAA] → fakeip` уже ограничивает catch-all, остальные типы идут на `final` — текущая схема sora корректна, зафиксировать тестом.
4. **Sniffing + ECH:** при ECH SNI в ClientHello зашифрован — TLS-sniffing домена не даст. Значит правило «домен для маршрутизации» обязано браться из DNS (fakeip-реверс), а не из sniffing. Это усиливает аргумент за FakeIP-first под TUN.

## 3. Что резолвить и где (конкретика)

- В DNS-менеджере: опция «Запрашивать HTTPS-записи» не нужна отдельная — они запрашиваются автоматически TLS-стеками; нужно **не мешать**: не блочить QTYPE 65 в rcode-правилах, не отбрасывать в кэше.
- В диагностике: проверка «ECH-конфиг для домена» — резолв HTTPS-записи через туннельный DoH, показать `ech=` present/absent. Это честный, проверяемый индикатор вместо тумблера «ECH вкл».
- Для RU-пресета: DoH3 через туннель для HTTPS-записей критичен вдвойне — ТСПУ заинтересован вычищать `ech` именно у неугодных доменов.

## Вердикт: лучшее (как enabler), слоп — как «фича»

«Переключатель ECH» в VPN-клиенте — слоп: клиент не владеет хендшейком. Лучшее — гарантировать доставку HTTPS-записей через шифрованный DNS + диагностика `ech`. Это невидимая, но настоящая работа.

## Рекомендация: внедрить так

1. Инвариант: QTYPE 65/64 никогда не фильтруются и не уходят в fakeip; покрыть тестом рендера обоих движков.
2. Диагностика: «ECH-readiness домена» — HTTPS-запись через туннельный DoH, парсинг `ech=`; показать в DNS-диагностике.
3. Документировать: ECH работает только в связке «браузер с ECH + DoH»; sora обеспечивает вторую половину.
4. Не делать: попытки терминировать/проксировать ECH на клиенте, собственные ECH-конфиги.
