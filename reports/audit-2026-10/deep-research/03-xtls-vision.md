# 03. XTLS Vision — исходники Xray

Дата: 2026-10-20. Источники: `proxy/vless/vision/` (conn.go, vision.go, common.go) Xray-core, `transport/vless/vision/` mihomo (кросс-проверка), Xray-examples (VLESS-TCP-XTLS-Vision), полевые данные RU 2025–2026.

## Механика flow

`flow=xtls-rprx-vision` — не «уровень шифрования», а режим обработки VLESS-поверх-TLS. Работает только в связке **VLESS + TCP + (TLS | REALITY)**.

Как устроен код:

1. **Обёртка соединения.** `vision.NewConn` оборачивает VLESS-соединение в `vision.Conn`. Через `reflect` + `unsafe.Pointer` достаёт из `tls.Conn` внутренние буферы `input` и `rawInput` — Vision буквально подглядывает в кишки TLS-стека, чтобы видеть записи до их расшифровки/обработки.
2. **Сканирование первых пакетов.** `FilterTLS` инспектирует первые ~8 пакетов, идущих через туннель, в поисках **внутреннего** TLS-хендшейка (трафика пользователя — например, его HTTPS к сайту).
3. **Паддинг до ApplicationData.** Пока внутренний TLS не дошёл до стадии `Application Data` (байты `0x17 0x03 0x03`), Vision добавляет паддинг (`ApplyPadding`), скрывая VLESS-заголовок и выравнивая размеры записей под профиль обычного браузерного HTTPS.
4. **Direct mode.** Как только зафиксирован переход внутреннего TLS в application data, клиент и сервер переключаются в «прямой» режим (`commandPaddingDirect`): `ExtendedWriter` заменяется на сырой `net.Conn` — дальше байты идут **напрямую, без повторного шифрования и без VLESS-фрейминга**. Это одновременно:
   - **убирает TLS-in-TLS сигнал** (внутри внешнего TLS едет «плоский» поток, а не второй TLS со своей структурой записей),
   - **даёт прирост производительности** (снятие двойного шифрования — кратный выигрыш CPU/throughput, задокументированный XTLS).

Требование кода: внешний TLS обязан быть **1.3** (проверяется в `NewConn`); внешний security — только TLS или REALITY.

## Почему обязателен с REALITY+TCP

Без Vision стек выглядит так: `[TCP [outer TLS 1.3 (REALITY) [VLESS header [inner TLS 1.3 (сайт пользователя)]]]]`. Внутренний TLS имеет характерную структуру записей (handshake → change cipher → application data с типичными размерами), вложенную во внешний TLS. DPI видит **матрёшку**: TLS внутри TLS. Российский ТСПУ этот паттерн детектирует (зафиксировано в полевых отчётах 2025–2026) — это самый дешёвый и надёжный сигнал «это прокси», не требующий расшифровки.

С Vision: после хендшейка внутренний TLS «растворяется» — снаружи виден один TLS 1.3-поток с естественным профилем. Плюс VLESS-заголовок скрыт паддингом на старте.

## Что ломается без него / при неправильном применении

- **REALITY+TCP без flow** — работает, но несёт детектируемый TLS-in-TLS сигнал. В RU это разница между «работает» и «режется».
- **Vision с WS/gRPC/XHTTP** — несовместим (у этих транспортов свой фрейминг; Vision требует «голого» TCP). Xray проигнорирует или сломает соединение — в sora это должно быть ошибкой валидации, а не молчаливым конфигом.
- **Vision без внешнего TLS 1.3** — код откажет (проверка версии). REALITY всегда 1.3 — ок.
- **UDP/QUIC** — Vision только TCP.
- Тонкость: Vision требует `fingerprint` (uTLS) на клиенте — без него внешний хендшейк выглядит «не как браузер», и весь маскарад теряет смысл.

## Вердикт: лучшее

Механика элегантна и подтверждена кодом: один механизм закрывает и детект (TLS-in-TLS), и производительность (снятие двойного шифрования). Обязательность с REALITY+TCP — не вкусовщина, а требование выживания в RU.

**Отсеяно фильтром:** «Vision ускоряет всё в 10 раз» — ускорение только для TLS-трафика внутри (прямой режим); для нет-TLS трафика выигрыш скромнее. «Vision нужен везде» — нет, только TCP+TLS/REALITY.

## Внедрить в sora так

Состояние sora: `flow` берётся из URI как есть (`parser.go:405`, `render.go:207` — `o.Flow`), **авто-включения нет**, валидации пар (vision+ws, vision без reality) нет.

1. **Авто-vision:** в `plan.go`/валидаторе — если `protocol=vless|trojan`, `transport=tcp`, `security=reality|tls` и `flow` пуст → установить `xtls-rprx-vision` автоматически (дефолт для новых конфигов). Явный `flow=none` пользователя — уважать, но с варнингом.
2. **validate.go:** `flow=xtls-rprx-vision` + `transport != tcp` → **ошибка** (не варнинг: конфиг сломан по построению); `reality+tcp` без vision → варнинг «обнаружимый TLS-in-TLS» с кнопкой «исправить».
3. **UI:** при выборе REALITY+TCP — бейдж «Vision: включён (защита от TLS-in-TLS)», тултип с объяснением в одно предложение; при ручном отключении — confirm-dialog с честным текстом последствий.
4. **Диагностика:** проверка «vision активен?» по фактическому конфигу движка + тест: хендшейк-тест, подтверждающий отсутствие двойного TLS-паттерна (эвристика по размерам записей — опционально, P2).
5. **Движки:** vision поддерживается Xray и mihomo (`transport/vless/vision`); для sing-box — сверить реализацию перед заявлением паритета (sing-box поддерживает `flow` для vless — проверить версию).
6. **Не делать:** автовключение vision для trojan без проверки — trojan+vision валиден в Xray, но сверить с версией движка; не применять к XHTTP (у него своя защита через xmux+сплит, тема 01).
