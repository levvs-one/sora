# 62. Speedtest-методология: Ookla, LibreSpeed — как мерить честно через туннель

Дата: 2026-10-20. Группа G, третий проход.

## Первоисточники

- Ookla, официальная методология: `speedtest.net/help/guides/how-does-speedtest-measure-my-network-speeds`.
- LibreSpeed: `github.com/librespeed/speedtest` (LGPL-3.0) — `speedtest_worker.js`, `doc.md`, параметры; `librespeed/speedtest-cli` — `defs/server.go` (алгоритм jitter).
- CAIDA: «Empirical Characterization of Ookla's Speed Test Platform» (выбор сервера: 10 ближайших по гео → минимальный RTT).
- Square Chrometric (адаптация LibreSpeed): документированный `pingTest`.

## 1. Ookla: что говорит сама Ookla

**Latency/Jitter:** клиент шлёт запрос, сервер отвечает, меряется RTT. Повторяется многократно — **итогом берётся минимальное значение**.

**Download (TCP):**
1. Несколько соединений на порт 8080, запрос начального чанка.
2. Клиент считает скорость в реальном времени и **динамически подстраивает размер чанка и буфера**, чтобы насытить канал.
3. В первую половину теста **дооткрывает соединения**, если решает, что потоков не хватает для точного замера.
4. Тест идёт фиксированное время.

**Расчёт результата (ключевое):** все сэмплы сортируются по скорости; **два самых быстрых удаляются, нижняя четверть из оставшихся (~22%) тоже удаляется**; остальное усредняется. Т.е. это усечённое среднее, а не пик и не «вся кривая».

**Upload:** несколько соединений, динамический чанк; **до 4 HTTP-потоков; чанки сортируются по скорости, усредняется быстрейшая половина** (устойчивость к выбросам вверх при старте).

**Число потоков:** до 4 HTTP-потоков для download/upload (в нативных клиентах до 16 параллельных TCP — отраслевой диапазон 4–16, динамически).

**Выбор сервера (CAIDA):** из ~10 ближайших по IP-геолокации выбирается сервер с минимальным RTT, затем параллельные HTTPS/TCP-соединения.

**Warmup:** первая половина теста — фаза «раскачки» (slow start, дооткрытие потоков); в зачёт идёт усечённое среднее, которое де-факто отсекает и стартовый разгон, и провалы.

## 2. LibreSpeed: открытая реализация (что копировать дословно)

Параметры по умолчанию (проверены по вики/коду):
- `count_ping = 10` — число пингов в ping+jitter тесте.
- `dl_graceTime = 1.5` с, `ul_graceTime = 1.5` с — **warmup, данные выбрасываются** (у DL — на подстройку TCP-окна, у UL — на сброс начального всплеса буферизации).
- `overheadCompensationFactor = 1.06` — компенсация транспортного оверхеда.
- `test_order = "IP_D_U"` — порядок: IP, пинг, даунлоад, аплоад.
- `time_auto = true` — длительность DL/UL адаптируется под измеренную скорость.

**Ping:** последовательные GET к `empty.php`; в JS-воркере — минимум из всех замеров; в CLI — **первый замер выбрасывается** (TCP-handshake), остальные усредняются.

**Jitter (точный алгоритм, `defs/server.go` speedtest-cli; тот же в `speedtest_worker.js`):**
- Второй пинг: `jitter = |ping1 − ping2|`.
- Дальше — **асимметричное взвешенное сглаживание**:
  - если мгновенный джиттер > текущего: `jitter = jitter*0.7 + inst*0.3` (всплески учитываются быстро);
  - если ≤ текущего: `jitter = inst*0.2 + jitter*0.8` (стабильность сглаживается медленно).
- Первый джиттер-замер в воркере отбрасывается. Это не простое среднее |Δ| — алгоритм подавляет одиночные выбросы, но реагирует на устойчивую деградацию. Копировать как есть.

## 3. Как мерить честно через туннель (специфика sora)

Главная ловушка: замер «не через тот интерфейс». Честный замер = трафик обязан идти через активный туннель, и это должно быть проверяемо, а не «мы так думаем».

Методология для sora-core (Go, без вебвью):

1. **Привязка к туннелю.** Тестовые соединения открываются через тот же dialer/сокет-путь, что и пользовательский трафик (в sing-box — через outbound активного конфига; в TUN-режиме — обычный сокет, т.к. системный маршрут уже через TUN, но с проверкой).
2. **Контрольная проверка.** Перед тестом — запрос к `ip-echo` эндпоинту через туннель и сверка egress-IP с IP сервера/подписки. Не совпал → тест не запускаем, в UI «тест невозможен: трафик не в туннеле».
3. **Фазы (порядок `P_D_U`):**
   - Ping: 10× HTTP-RTT к тестовому серверу через туннель; первый отброс; итог = min; jitter — асимметричное сглаживание LibreSpeed.
   - Download: 10–15 с, старт 4 потока → динамическое дооткрытие до 16 по насыщению; grace 2 с отброс; усечённое среднее Ookla (минус топ-2, минус нижние 22%).
   - Upload: 4 потока, 10 с, grace 1.5 с; усреднение быстрейшей половины чанков.
4. **Парный замер.** «Через VPN vs напрямую» рядом (как ExpressVPN): тот же сервер, тот же метод, разница — это и диагностика («режет провайдер или сервер»), и доверие пользователя.
5. **Массовый тест серверов:** параллельно с лимитом (8–12 одновременных), per-server таймаут, Speed Index = взвесь (DL 50%, UL 20%, ping 20%, jitter/loss 10%) — веса конфигурируемы.
6. **История:** каждый замер — в локальную БД (время, сервер, протокол, DL/UL/ping/jitter/loss, через VPN/прямо). Это топливо для автовыбора и графиков; ни у кого из конкурентов истории нет.

**Серверная сторона:** не обязательно своя — протокол LibreSpeed открыт, можно поднять свои `garbage.php/empty.php`-совместимые эндпоинты рядом с one-click серверами sora. Чужие Ookla-серверы для встроенного теста не использовать (ToS, нестабильность).

## Вердикт «лучшее или слоп»

**Лучшее:** усечённое среднее Ookla (устойчиво к выбросам с обеих сторон) + grace-период LibreSpeed + асимметричный jitter — всё это десятилетия полевого опыта, закодированные в числа. Копировать дословно.

**Слоп:** (а) «пиковая скорость» на циферблате; (б) один поток (M-Lab NDT-стиль) для оценки канала; (в) замер мимо туннеля — цифра, которая врёт; (г) jitter как простое среднее |Δ| — шум вместо сигнала.

## Рекомендация «внедрить так»

1. `core/speedtest/`: Go-пакет с фазами P/D/U, конфигом (потоки, grace, окна), привязкой к активному outbound'у, egress-проверкой.
2. Серверный мини-протокол, совместимый с LibreSpeed-бэкендом (`empty`/`garbage`), на one-click образах.
3. UI: кнопка «Проверить скорость» в карточке сервера + массовый тест списка + история с графиком + пара «VPN/прямо».
4. Speed Index кормит автовыбор сервера и движка; веса — в настройках для продвинутых.
