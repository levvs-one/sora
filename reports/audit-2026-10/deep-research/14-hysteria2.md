# 14. Hysteria2 internals — brutal CC, salamander, port hopping, баг «stall без обрыва»

Дата: 2026-10-20. Источники: hysteria.network docs (Full Server Config, Troubleshooting), исходники hysteria2/mihomo/sing-box (`adapter/outbound/hysteria2.go`, `transport/hysteria/congestion/brutal.go`), dev.to-разбор stall-бага (окт. 2026, PR #1703 upstream), clashopen-бенчмарк 2026.

## 1. Brutal congestion control — как работает

Обычные CC (Cubic/BBR) — реактивные: смотрят на потери/RTT и ужимают окно. Brutal — **статeless fixed-rate**: шлёт фиксированный объём байт за тик планировщика, вычисленный из заданного оператором таргета:

```
Bytes to Emit = R_target × Δt
```

Сигналы потерь ядра (SACK, RTO) инъекционным циклом **не наблюдаются**; ретрансмиты QUIC идут отдельным out-of-band потоком, инъекция продолжает идти на `R_target`. Итог: при 5% потерь и таргете 100 Мбит полезная пропускная способность ~95 Мбит; Cubic на тех же потерях схлопывается до ~20–40 Мбит после первого multiplicative decrease. Разрыв 30–50 п.п. — единственная причина существования протокола.

**Включение**: заданы `up_mbps` + `down_mbps` (sing-box) / `up` + `down` (mihomo). Не заданы → откат на BBR → hy2 работает в самом слабом режиме, без главного преимущества. Это сейчас и происходит в sora (передаются только type/password/obfs).

**Семантика** (источник путаницы): `up` сервера = `down` клиента и наоборот. Значения — хинты для CC, не жёсткие лимиты. Завышенный `up` деградирует канал (перегрузка → потери → ретрансмиты поверх fixed-rate = мелтдаун). `disableLossCompensation` (сервер): при потерях слать чуть быстрее таргета для компенсации — иногда помогает, иногда вредит; опция локальна для направления upload этой машины. `ignoreClientBandwidth` (сервер): игнорировать хинты клиента, использовать не-Brutal — для операторов, не доверяющих клиентам.

## 2. Salamander obfuscation

`obfs: { type: "salamander", password: "..." }`. Маскирует QUIC-пакеты: защита от active probing и от DPI-классификации по паттерну QUIC. Пароль обязателен, если тип задан (mihomo/sing-box падают при пустом). Не шифрует заново — именно обфускация слоя. Совместима с port hopping и brutal.

## 3. Port hopping

Клиент ротирует destination UDP-порт из списка/диапазона (`server_ports` / `ports: "20000-30000"`) каждые `hop_interval` (дефолт 30 с, минимум 5 с). QUIC-соединение при этом **не рвётся** (connection ID не привязан к порту). Сервер слушает весь диапазон. Прямой ответ на троттлинг долгоживущих UDP-флоу у ISP (типичная практика: шейпить QUIC-флоу старше N секунд). Реализация в mihomo: `UDPHopClientPacketConn`.

## 4. Известный баг «stall без обрыва» (сервер, актуален 2026)

**Механизм** (разбор colitu, окт. 2026, воспроизведено на v2.11.0):
1. Клиент аплоадит через hy2-поток; сервер `io.Copy` в TCP-таргет.
2. Таргет перестаёт читать, но не закрывается (типично для speedtest-аплоада: серверу хватило данных). TCP-буфер таргета полон → блокирующий `Write` сервера встаёт.
3. Непрочитанные байты потока продолжают занимать **connection-level receive window** QUIC (дефолты hysteria: 8 МБ на поток, 20 МБ на соединение). Несколько таких потоков съедают всё окно.
4. Клиент не может слать **ни на одном потоке**, включая новые. Писатель клиента тоже заблокирован тем же окном — клиент никогда не «отпускает» поток. Сигнал «stream given up» приходит только при убийстве клиентского процесса.
5. UDP-дейтаграммы (не flow-controlled) продолжают идти — соединение выглядит живым.

Симптом: «подключено, но ничего не грузится; реконнект лечит». **Фикс upstream** (PR #1703): `TCPStallTimeout` — каждая запись в TCP-таргет получает бюджет (10 с); запись без прогресса дольше бюджета → таргет закрывается, нормальный cleanup освобождает окно; при «сдаче» потока клиентом таргет закрывается сразу. Медленный, но живой таргет не режется (таймер обновляется на каждый Write).

**Вывод для клиента**: детектить «stall без обрыва» нельзя только по состоянию сокета — нужен **throughput watchdog**: соединение established, а байт 0 в обе стороны N секунд при активном спросе → принудительный реконнект (новая QUIC-сессия). Плюс требовать от one-click деплоя сервер hysteria ≥ версии с фиксом.

## Вердикт: лучшее или слоп

**Лучшее.** Brutal — единственный CC, выигрывающий у потерь, а не проигрывающий им; port hopping — дешёвый ответ на UDP-шейпинг; salamander — базовая гигиена против пробинга. Stall-баг реален, задокументирован с фиксом — замалчивать его значит получить «мистические зависания». **Слоп**: hy2 без `up/down` (BBR-режим — протокол-кастрат); завышенный `up_mbps` «побольше» (вредит); port hopping без открытого диапазона на сервере (молча не работает).

## Внедрить так

1. **Прокинуть `up_mbps`/`down_mbps`** (sing-box) и `up`/`down` (mihomo) из плана в конфиг; UI-поле «скорость тарифа» + **авто-калибровка brutal по встроенному speedtest** при первом подключении (ручной ввод почти все выставляют неверно — завышают).
2. **Port hopping в UI**: список/диапазон портов + `hop_interval`; one-click деплой открывает диапазон в фаерволе и ставит `server_ports`.
3. **Stall-watchdog в health-check**: `established && bytes==0 && demand>0` в течение 15–20 с → пометить «stall», разорвать QUIC-сессию и переподключиться; событие в диагностику («Hysteria2 stall detected, reconnected»). Серверный one-click — hysteria с `TCPStallTimeout` (версия с PR #1703+).
4. **Salamander**: тумблер + автогенерация пароля в one-click деплое.
5. **Честные подписи**: «завышенный up вредит», «brutal агрессивен к чужому трафику — на shared VPS ставьте по тарифу».
6. Проверить маппинг Xray: Xray маппит hy2 на устаревший v1-outbound — для hy2 предпочитать sing-box/mihomo (уже отмечено в тире 7, подтверждаю как P0).
