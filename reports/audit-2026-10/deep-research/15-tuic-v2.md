# 15. TUIC v2 — QUIC-протокол, 0-RTT, congestion control, честные замеры против Hysteria2

Дата: 2026-10-20. Источники: исходники mihomo `transport/tuic/{v4,v5,pool_client}`, доки Surge (HonKit), бенчмарк clashopen.com «Hysteria2 vs TUIC v5: 2026 Speed Benchmarks», sing-box `option/tuic.go`.

## 1. Протокол

TUIC — прокси поверх QUIC, **всегда TLS 1.3 поверх QUIC**, ALPN `h3`. TCP и UDP relay с мультиплексированием.

**Две несовместимые версии:**
- **v4**: аутентификация статическим `token` (32-байтный SHA256 строки), UDP assoc id — `uint32`.
- **v5**: `UUID` + `password`; токен — time-based, генерируется `GenToken` из состояния TLS (привязка к сессии); UDP assoc id — `uint16`; есть фрагментация UDP-пейлоадов больше path MTU (`deFragger`).

Сервер диспетчит по байту версии в потоках/дейтаграммах (`EarlyListener`). Клиент обязан использовать ключевое слово версии (Surge: `tuic` vs `tuic-v5`) — перепутать = не подключится.

**UDP relay — два режима:**
- `native` (дефолт): QUIC DATAGRAM frames (RFC 9221) — максимальная производительность;
- `quic`: UDP поверх однонаправленных QUIC-потоков — для сетей, где дейтаграммы душат;
- плюс `udp-over-stream` (UoT-протокол) как крайний fallback, и `udp-relay-mode` выбор.

**0-RTT**: QUIC 0-RTT через `DialEarly` (опция `reduce-rtt`); поверх — `PoolClient`: пул активных QUIC-сессий, при dial сначала ищется сессия со свободными стримами (`max-open-streams`, дефолт 100), новая поднимается только при переполнении. После idle — resume с 0-RTT, если тикеты валидны: −1 RTT на первом запросе. Для мобильного клиента с частыми переподключениями это реальный выигрыш латентности.

**Congestion control**: выбираемый (`congestion-controller`): cubic / bbr / bbrv2 (профили conservative/standard/aggressive в mihomo) / brutal (через общий с hy2 селектор в sing-box/mihomo). Дефолт разумен из коробки — в отличие от hy2, не требует ручного таргета для приличной работы.

**Прочее**: `heartbeat-interval` (дефолт 10 с), `max-udp-relay-packet-size` (1252), port hopping поддерживается клиентами (Surge: `port-hopping` + `port-hopping-interval`, как у hy2).

## 2. Честные замеры против Hysteria2 (clashopen, 2026)

Методология вменяемая: отброс первых трёх хендшейков после idle, NTP-синхронизация для 0-RTT-экспериментов, тесты на двух PoP (география контролируется).

- **Чистый канал, интерактив**: медиана HTTPS GET — hy2 с консервативным brutal 126 мс, TUIC v5 118 мс; p95 — 198 мс vs 221 мс в пользу TUIC. Разница 8 мс медианы испаряется при смене PoP — **география доминирует над выбором протокола**.
- **Настройка**: «Hysteria2 rewards careful tuning whereas TUIC v5 is more forgiving out of the box» — при завышенном brutal-таргете hy2 проигрывает в хвостах; при таргете по реальному каналу разница → статшум.
- **Bulk/lossy**: преимущество brutal hy2 (см. тему 14) — TUIC со стандартным CC проигрывает на потерях.
- **Cold start**: TUIC иногда выигрывает за счёт 0-RTT resume; hy2 быстрее пересоздаёт состояние, но редко бьёт TUIC на первом пакете.

**Честный итог**: универсального победителя нет. TUIC v5 — лучший «из коробки» для интерактива/браузинга и мобильных переподключений; Hysteria2 с настроенным brutal — лучший для bulk-трафика и сетей с потерями. Заявления «TUIC быстрее hy2» без указания сценария — маркетинг.

## Вердикт: лучшее или слоп

**Лучшее** — держать оба протокола как взаимодополняющие: TUIC v5 дефолт для «повседневного» профиля (прощает отсутствие тюнинга, 0-RTT для мобильных), hy2+brutal для «скорость/потери». **Слоп**: v4 в новых деплоях (устаревшая auth-модель); `reduce-rtt`/0-RTT как маркетинговый бейдж без пула сессий; выбор «победителя» по одному синтетическому тесту.

## Внедрить так

1. **TUIC v5 как протокол**: `uuid`+`password`, `udp-relay-mode` селектор (native дефолт, quic при душащихся дейтаграммах — автоопределение по потере дейтаграмм), `congestion-controller` выбор (bbr дефолт), `reduce-rtt` тумблер, heartbeat 10 с.
2. **URI**: `tuic://uuid:password@host:port?congestion_control=..&udp_relay_mode=..&sni=..&alpn=h3&version=5` — полный парсинг; явно различать v4/v5 в UI (несовместимы).
3. **Автовыбор транспорта**: speedtest-матрица «TUIC vs hy2» на одном сервере (уникальные данные, которых нет в открытых источниках — отмечено в тире 12, подтверждаю): bulk-тест → hy2, интерактив/мобильность → TUIC; результат — в рекомендации движка/протокола.
4. **Port hopping** для TUIC прокинуть так же, как для hy2 (опции есть у клиентов).
5. В one-click деплое — TUIC v5 рядом с hy2 на том же UDP-порту (практика sb-nodejs: мультиплекс портов).
