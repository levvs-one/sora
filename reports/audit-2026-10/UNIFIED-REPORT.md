## 3. Топ критичных: sora (8 High)

1. **H1 — неподписанные релизные артефакты.** Вся цепочка доверия обновлений = TLS +
   самопубликуемые SHA-256 (`packaging/README.md:11`, CI `repository.yml:512-516`,
   `app/lib/src/updates.dart`, `packaging/linux/sora-update`). `sora-update` работает как root
   через pkexec и сверяет пакеты с `SHA256SUMS` из записываемого пользователем каталога.
   Компрометация релиза или локальная подмена = бэкдор с правами root всем пользователям сразу.
   Главный вектор массовой компрометации VPN-клиента обхода блокировок.
2. **H2 — polkit `allow_active=yes`** (`service/linux/sora.policy:22`). Любой активный локальный
   пользователь без пароля → `Handshake` отдаёт токен (`core/control/server.go:459`) → полный API
   ядра: подмена туннеля, стирание секретов, дамп чужого трафика (см. H3).
3. **H3 — `ExportDiagnostics` возвращает сырой нередкатированный трафик** вопреки docstring
   «already-redacted» (`core/control/server.go:1192-1235`): 10-секундный PCAPNG/EVTX захват
   TUN-трафика. В связке с H2 — межпользовательская утечка.
4. **H4 — kill switch не блокирует root-трафик.** `meta skuid <engineUID> accept`
   (`core/guard/nftables.go:45`), а `EngineUID = os.Getuid()` без понижения привилегий →
   при запуске от root (типовой сценарий для TUN) весь root-трафик, включая DNS, идёт мимо
   kill switch. Тихая утечка при уверенности пользователя, что «всё заблокировано».
5. **H5 — подмена бинарника движка через PATH.** `Prober.Discover` падает в `exec.LookPath`
   (`core/engine/supervise/binary.go:83-112`), аутентификация — только строка `version`;
   `VerifyDigest` — мёртвый код вопреки комментарию. «Движок» стартует с привилегиями сервиса
   (Windows: LocalSystem) и получает все credentials подписок через stdin.
6. **H6 — panic в журнале событий** (`core/session/journal.go:108-186`): `Append` отпускает
   мьютекс перед отправкой, отписка закрывает канал → send on closed channel роняет весь core
   из штатной ситуации (закрытие UI во время сессии). Туннель и kill switch — в неопределённом
   состоянии.
7. **H7 — `Session.Stop` без таймаута** (`core/session/runner.go:253-295`): поле `StopGrace`
   объявлено, но нигде не используется → зависший движок вешает `Stop` навсегда, `m.busy=true`,
   все Connect/Disconnect отклоняются до рестарта процесса.
8. **H8 — потеря `sora://add/...`-ссылок на Linux**, если приложение уже запущено
   (`app/linux/runner/my_application.cc:93-163` — `command-line`/`open` не реализованы;
   на Windows тот же кейс закрыт).

Проверено и признано корректным (не баги): SSRF-защита фетчера подписок (HTTPS-only,
`dialChecked` против DNS-rebinding, лимиты); секреты движкам только через stdin + `SafeEnv()`;
redaction логов движков; DPAPI user-scope на Windows; hardening systemd-юнита; TOCTOU-защита
`sora-update`; отсутствие setState-after-dispose в Dart; race-устойчивость connect/disconnect.

## 4. Топ критичных: sora-legacy (8 High)

1. **Обновление движков без проверки подписи/хэша** (`UpdateHandle.cs:120-168,496-567`) —
   скачанный `xray.exe` запускается как есть, downgrade не запрещён → RCE при компрометации релиза.
2. **Handshake отдаёт control-токен любому допущенному пиру** (`core/control/server.go:459`) —
   документация утверждает защиту «от процессов того же аккаунта», по коду граница только
   транспортная. Любой локальный процесс получает полный контроль над VPN.
3. **Локальный privesc в C#-клиенте** (`MainForm.Community.cs:868-891`,
   `TunModeController.cs:17-90`): per-user установка (`%LOCALAPPDATA%`) + `runas`-рестарт TUN
   исполняет подменённые бинарники как администратор, проверки целостности нет.
4. **Кнопка «Edit» выполняет произвольные файлы** (`AddServer2Form.cs:109-153`): `Process.Start`
   с `UseShellExecute=true` на `.exe` из «конфига», пришедшего по социнженерии.
5. **Discovery движков доверяет `SORA_*_BIN`/PATH без проверки digest** (`binary.go:81-112`):
   `VerifyDigest` существует, но нигде не вызывается; version-probe подделывается строкой shell.
6–8. Три архитектурных гэпа: в `app/` (Android) код отсутствует вообще — UID-авторизация туннеля
   только на бумаге, манифест не написан (exported/backup/cleartext), хранилище токена не определено.

Ключевое из Medium: несогласованная авторизация методов control API; пустой session ID обходит
проверку сессии; архив диагностики маскирует секреты, но НЕ host:port серверов (а в `summary.json`
пишется `"values_masked": true`); `Rotate()` не персистит токен; парсер не применяет `MaxItems`
к JSON/YAML/WireGuard → вредоносная подписка = OOM ядра; мёртвый handshake-timeout + нет лимита
соединений → локальный FD/goroutine DoS; probe — неограниченный TCP-сканер приватных сетей.

Сверка с `docs/audits/2026-10-02-*`: исправлены №12–19 (№17 — архитектурно); **№20 расходится**
(в коде намеренно `0666` + `SO_PEERCRED`, аудит писал «0660» — формулировку стоит поправить);
пункты №6 и №11 прошлых аудитов **завышают** реальное состояние.

Проверено и чисто: systemd-юнит (образцовый hardening), `fetch.sh` (HTTPS-only + SHA-256),
SSRF-защита подписок, secret store (AEAD, wipe, atomic write), защита Windows pipe от squatting,
устойчивость `SoraMarkdownView` к XSS, отсутствие отключения TLS-валидации в C#.

## 5. Системные выводы по безопасности

Оба проекта страдают от **одной системной болезни — цепочки доверия обновлений и discovery
движков** (H1/H5 в sora, №1/№5 в legacy). Это главный вектор массовой компрометации и чинить
его надо первым делом в обоих репозиториях: подпись релизов офлайн-ключом (minisign),
вшитый публичный ключ в установщики/апдейтеры, вызов `VerifyDigest`, отказ от PATH-fallback.

Второй системный узел — **локальная граница доверия IPC**: polkit `allow_active=yes` (sora H2)
и токен «для всех допущенных» (legacy №2) фактически открывают управление туннелем любому
локальному процессу/пользователю. Нужна раздельная polkit-политика и привязка авторизации
к peer credentials, а не к факту подключения.

## 6. Конкуренты: главное

**Дыры sora (приоритет):**
- P0: Android заявлен, но кода нет; нет QR-импорта/шеринга конфигов; нет выбора сервера по
  пропускной способности; слабый DNS-менеджер без проверки утечек; нет экрана активных соединений.
- P1: синхронизация устройств, override-слой поверх подписки, цепочки прокси, сетевые профили, iOS/macOS.
- P2: развёртывание своего сервера из клиента, расширения, виджеты.

**Уникальные сильные стороны (защищать и развивать):** мульти-движок с автовыбором под
подключение, бессерверный zapret-режим, kill switch до старта ядра, диагностика уровня
HAR/PCAPNG/EVTX, 31 язык.

**«Функции будущего» (полный список из 15 — в отчёте):** умный выбор связки «сервер+движок»
по живым замерам; авто-тюнинг фрагментации под DPI конкретного провайдера; детектор цензуры
с упреждающим failover; сетевые профили с автоопределением; E2E P2P-синк без облака;
captive-portal handling; ML-маршрутизация по классу трафика; one-click развёртывание
мультипротокольного сервера; opt-in краудсорсинговая карта DPI; ротация серверов; stealth-оценка
конфига; режим «штопор». Roadmap Must-have / Differentiators / Future bets с оценкой
сложности S/M/L — в [competitor-analysis.md](sandbox://workspace/bug-hunt/reports/competitor-analysis.md).

## 7. Рекомендуемый порядок действий

**Безопасность (P0):**
1. Подписать релизные артефакты (minisign, офлайн-ключ), вшить публичный ключ в `install.sh`,
   `install.ps1`, `sora-update`, встроенный апдейтер; запретить downgrade — оба проекта.
2. Разделить polkit-action (sora H2), привязать IPC-авторизацию к peer credentials (legacy №2).
3. Вызывать `VerifyDigest`, убрать PATH-fallback в discovery движков (sora H5, legacy №5).
4. Починить kill switch для root-трафика (sora H4); перепроверить гарантии redaction
   диагностики (sora H3, legacy M).
5. Устранить panic в журнале событий (sora H6) и клин `Session.Stop` (sora H7).

**Надёжность (P1):** handshake-дедлайны и лимиты соединений IPC; backoff при флэппинге сети;
идемпотентность `Nftables.Arm/Disarm`; `MaxItems` для всех форматов парсера; персист токена
после `Rotate()`.

**Продукт (P0 из gap-анализа):** QR-шеринг, выбор сервера по пропускной способности,
DNS-менеджер с проверкой утечек, экран активных соединений, Android.

**Процесс:** прогнать `go test -race` и `flutter analyze` в CI (в аудите тулчейнов не было);
зафиксировать формулировки прошлых аудитов №6, №11, №20 под реальный код.
