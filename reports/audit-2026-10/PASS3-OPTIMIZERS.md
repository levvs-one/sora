# PASS3-OPTIMIZERS — отдел оптимизаторов финального аудита, проход 3/3

Дата: 2026-10-20. Ветка `bugfix/audit-2026-10-19`, пуша нет.
Базы замера: sora tip `66d9e26a`, sora-legacy tip `a769346`.
Методология — та же, что в OPTIMIZERS.md / PASS1 / PASS2: VM зашумлена
параллельными агентами, критерий — детерминированные B/op и allocs/op;
ns/op — медианы многопрогонных A/B на одном дереве (benchtime 20000x,
count=3, если не указано иное). Слоп-фильтр: выигрыш <5%, нестабильный
или ценой читаемости / fail-closed семантики → отклонение. Принятое и
отклонённое проходов 1–2 не пересматривалось, кроме регрессионных
проверок по заданию.

## Принятые оптимизации (2 коммита)

### 1. Редактор логов: per-pattern гейты без аллокаций — sora `8cdcb6d9`, legacy `3480d86`

Проход 1 (`e60f9854`) дал редактору один общий гейт: строка без «://»,
ключевых слов и ≥4 дефисов пропускает все пять regexp-проходов. Замер
этого прохода показал два остатка:

1. Сам гейт — `strings.ToLower` всей строки: **80 B/op, 1 alloc на
   каждую строку**, включая чистые (это вся цена чистой строки).
2. Гейт бинарный: строка, прошедшая по одному слову, платила **все
   пять** проходов. URL-строка без единого ключа платила
   `keyValuePattern` (самая большая alternation, ~16 µs из ~33 µs
   строки); token-строка платила userInfo/tokenLink/UUID-проходы
   впустую (каждый `ReplaceAllString` аллоцирует копию и без совпадений).

Фикс: для ASCII-строк (норма логов движков) — один безаллокационный
проход, считающий **отдельное необходимое условие на каждый паттерн**:
`://` для userInfo/tokenLink; подстрока из keyGateWords для keyValue
(каждая ветка alternation содержит одну: все `*_key` — «key»,
obfs_param — «param», auth_str — «auth», username — «user» и т.д.);
«user»/«login» для strict; ≥4 дефисов для UUID. Запускаются только
проходы, которые могут совпасть. Не-ASCII строки идут по старому пути
байт-в-байт (в sora — гейт прохода 1 + полный конвейер, в legacy —
безусловный конвейер): Unicode-фолдинг наблюдаем ((?i) различает,
например, U+212A KELVIN SIGN → «k»), и срезать там проходы нельзя.

Флаги считаются один раз на входе; это остаётся надмножеством для
строки, которую получает каждый следующий паттерн: замены только
удаляют спаны и вставляют `[masked]`/`[masked]@`, чьи скобки ни одно
гейт-слово пересечь не может, а keyValue сохраняет ключ и сепаратор
дословно — ни один проход не создаёт триггер (схему, ключевое слово,
user/login, дефисы), которого не было на входе. Пропущенный паттерн
доказуемо не может совпасть; выход байт-идентичен безусловному
конвейеру, что запинено дифференциальным тестом
`TestMaskPatternsDifferential` (~1000 входов: одиночные фрагменты и
все попарные комбинации, включая KELVIN и кириллицу) в обоих репо.

### Регрессионная проверка M1 (гейт после объединения alternation)

По заданию проверено, что гейт держится после M1-суперсета
(`7a217630`/`a769346`: `pre[_-]?shared[_-]?key`, `public[_-]?key`,
`spider[_-]?x` с обеих сторон):

- Гейт — надмножество и после слияния: каждая новая ветка содержит
  гейт-подстроку (`pre_shared_key`/`public_key` — «key», `spider_x` —
  «spider»); parity-тесты M1 в обоих репо зелёны.
- Цена слияния — **ноль**: A/B на одном дереве, паттерн до M1 против
  после M1: token-строка 1009 B/op / 18 allocs в обеих версиях,
  URL-строка 961/16 в обеих; ns в пределах шума VM (27.7–40.9 µs против
  28.2–29.5 µs на зашумлённой VM). Слияние заменило две ветки
  (`preshared…|pre-shared-key`) одной — alternation не выросла.
- Аномалия первого замера: один ранний прогон `BenchmarkRedactLines`
  дал 971 B/op / 15 allocs (значение «до гейта» из PASS1). В девяти
  последующих прогонах (benchtime 10000x и 20000x, count=3) не
  воспроизвелось: стабильно 536–541 B/op / 9 allocs, что совпадает с
  PASS1 «после» до байта. Зафиксировано как невоспроизводимый выброс
  (дерево общее, WIP соседей), а не как регрессия.

## Отклонённые в этом проходе (с замерами и причинами)

- **BuildCapabilities: убрать/закэшировать клон Features** — цена
  клона 984–1 432 B и ~1–2 µs на вызовах, каждый из которых холодный
  (старт сессии, раунд замеров); суммарный потолок выигрыша ~0.6 ms
  на раунд из 200 серверов против секунд сети. Клон защищает от
  мутаций вызывающих (xraytun bridge). Отклонено.
- **`Supervisor.admit`: двойной `Capabilities()`** — слияние в один
  вызов экономит один клон (~1 µs, ~1 KB) на старт/валидацию сессии;
  путь холодный, выигрыш под слоп-фильтром. Отклонено (цифры — в
  разделе каталога).
- **mihomo render: pre-size / замена yaml.v3** — 91% аллокаций внутри
  эмиттера yaml.v3; наш код — 1.3%. Замена отклонена ещё в OPTIMIZERS
  (байт-идентичность), pre-size даёт <2%. Отклонено.
- **Ext SetSettings: кэшировать распарсенную схему настроек** —
  перепарсинг схемы — малая часть 34–41 µs дискового вызова по тапу
  пользователя; кэш в Store = инвалидация при смене манифеста ради
  микросекунд на холодном пути. Отклонено.
- **Первая итерация гейта редактора (per-word сканы)** — замер ns
  чистой строки ушёл вверх (~2.1 µs против 0.71 µs старого гейта) при
  нулевых аллокациях: 15 наивных сканов проигрывают `ToLower`+`Contains`
  по времени. Переписана в однопроходный скан с диспетчером по первой
  букве до коммита (~0.33 µs, 0 B/op); в дерево вошла только вторая
  итерация.

## Инциденты

- **CAS-коммит оставляет общий индекс «устаревшим» (не отравление
  чужими staged-удалениями).** Оба коммита этого прохода садились
  temp-index + `commit-tree` + CAS `update-ref` (первая попытка в
  обоих репо, ровно по файлам коммита). После сдвига HEAD общий индекс
  продолжал держать blob'ы старого HEAD по трём файлам редактора,
  из-за чего `git status` показывал их как staged-обратный-дифф
  коммита (`MM` + «staged deletion» нового bench-файла в legacy).
  Проверка `git diff --cached` показала: staged-содержимое — байт-в-
  байт инверсия собственных коммитов, чужих staged-правок по этим
  путям нет. Нейтрализовано `git restore --staged -- <3 пути>` в обоих
  репо (индекс = HEAD, worktree не тронут); финальный
  `git diff --cached --stat` пуст в обоих репозиториях. Чужих
  staged-удалений за этот проход не наблюдалось (счётчик проходов
  1–2: ≥17 — в этом проходе эпизодов с чужими файлами не было;
  единственный эпизод — собственный stale-index выше).
- **Пре-существующий env-фейл legacy**:
  `TestTunAndFakeIPAvoidLANAndEachOther` падает и на чистом HEAD
  `a769346` (fake-IP пул пересекается с реальным интерфейсом VM,
  `tun_test.go:77`) — проверено отдельным worktree на чистом HEAD, с
  правками прохода не связан. В sora тот же класс фейла исторически —
  `TestDetectCensorshipEventsWithoutOffsetsStayUnknown` при длинном
  TMPDIR; в этом проходе control прогнан при `TMPDIR=/tmp` и зелён.
