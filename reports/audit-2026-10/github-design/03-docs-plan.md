Дизайн №3 (архитектор документации). Только чтение репозитория, без изменений.
Дата: 2026-10-19.

## 1. Текущее состояние: что не так (конкретно)

Инвентарь `docs/` сейчас: `README.md` (индекс), `install.md` (87 строк), `usage.md` (122), `providers.md` (65), `troubleshooting.md` (89), `architecture.md` (78), `development.md` (153), `sync-threat-model.md` (119), `extensions/manifest-v1.md` (199), `images/` (2 скриншота). Всего ~1200 строк, 9 страниц.

### P0 — структурные дефекты

1. **Осиротевшая страница.** `docs/sync-threat-model.md` не связан ниоткуда: ни `docs/README.md`, ни корневой `README.md`, ни `architecture.md` на него не ссылаются. Найти его можно только перебором файлов. Проверка: `grep -rn "sync-threat-model" --include="*.md"` по репозиторию — ноль совпадений.
2. **Полуосиротевшая страница.** `docs/extensions/manifest-v1.md` связан только из `examples/hello-panel/README.md`. В индексе документации его нет — разработчик расширений, пришедший через главную страницу, его не найдёт.
3. **Лишняя вложенность.** `docs/extensions/` — каталог ради одного файла, при том что расширения ещё не реализованы (статус «Скоро появится» в `usage.md`, P1 в `PLANS.md`). Один уровень вложенности не оправдан.
4. **Смешение языков без правила.** Шесть страниц на русском, две — на английском (`sync-threat-model.md`, `extensions/manifest-v1.md`). При этом `README.en.md` честно предупреждает: «These guides are in Russian» — то есть конвенция «доки на русском» заявлена, но два документа её нарушают молча.

### P1 — битые и протухшие ссылки

5. **Битая ссылка в CONTRIBUTING.md.** «Старый клиент для Windows 7 находится в ветке [`legacy`](https://github.com/levvs-one/sora-client/tree/legacy)» — репозитория `sora-client` больше нет; legacy живёт отдельно в `levvs-one/sora-legacy` (это подтверждает и корневой README). Ссылка ведёт в 404.
6. **Протухшие версии в инструкциях.** `install.md` и `development.md` содержат хардкод `1.0.6` (`Sora-Setup-1.0.6-x64.exe`, `SORA_VERSION=1.0.6` в командах nfpm/flutter). Текущая версия по CHANGELOG — 1.0.12. Инструкции копипастятся пользователями как есть — номер версии в команде это ловушка.

### P2 — дублирование и пробелы

7. **Два индекса.** `docs/README.md` дублирует раздел «Документация» корневого `README.md` почти один в один. Один из них лишний как сущность; индекс должен быть один (в `docs/`), а README ссылаться на него.
8. **Дубль «обновление» в двух местах.** Раздел «Обновление и трей» в `usage.md` пересказывает то, что уже есть в `install.md` («Обновление: запустите установщик новой версии поверх…»). Достаточно ссылки.
9. **Архитектура неполна.** `architecture.md` не упоминает `sora-sync` (синхронизация устройств, F9) вообще — ни словом. Новый сервис существует, threat model существует (осиротевший), а в картине архитектуры его нет.
10. **Нет страницы про приватность/безопасность для пользователей.** Позиционирование — «no hidden telemetry», открытый код как витрина. Сейчас гарантии раскиданы: шифрование хранилища — в `architecture.md`, маскирование логов — там же, проверка SHA256 — в `install.md`, «Sora не отвечает за серверы провайдеров» — в `SECURITY.md`. Единого места, куда ткнуть недоверчивого пользователя или исследователя («что Sora собирает и чего не делает»), нет. `SECURITY.md` в корне — только про процедуру репорта уязвимостей, не пересекается.
11. **Нет FAQ.** Вопросы про продукт («чем TUN отличается от прокси», «что видит мой VPN-провайдер», «прячет ли zapret IP», «собирает ли Sora телеметрию», «почему установщик не подписан») сейчас либо раскиданы по `usage.md`, либо отсутствуют, либо неизбежно осядут в issues.

Что **не** является проблемой: сами тексты написаны хорошо — плотно, по-русски, без воды; перекрёстные ссылки внутри (`usage.md → providers.md`, `usage.md → install.md`) корректны и ведут на существующие файлы; скриншоты на месте и подключены.

## 2. Целевая структура

Принципы: плоская структура (все страницы в `docs/`, один уровень), английские имена файлов (текущая конвенция), русский язык текстов (текущая конвенция, заявлена в `README.en.md`), каждая страница оправдана своей аудиторией.

```
docs/
├── README.md            — индекс: карта документации по аудиториям
├── install.md           — установка, обновление, удаление (Win + Linux)
├── usage.md             — руководство пользователя: подключение, режимы, правила, DNS, журнал
├── faq.md               — частые вопросы о продукте (НЕ про поломки)
├── troubleshooting.md   — «сломано → чиним»: по сообщениям об ошибках и симптомам
├── providers.md         — для VPN-провайдеров: форматы подписок, заголовки, группы, кнопка «Добавить в Sora»
├── extensions.md        — для разработчиков расширений: формат .soraext, manifest v1 (нормативный текст)
├── architecture.md      — как устроена Sora: приложение, служба, ядра, TUN, kill switch, хранение + раздел про sora-sync
├── security.md          — модель приватности: какие данные где хранятся, что шифруется, чего Sora НЕ делает (телеметрия, логи)
├── sync-threat-model.md — детальный threat model sora-sync (для исследователей безопасности)
├── development.md       — сборка, тесты, контракт, ядра, пакеты, CI, выпуск
└── images/              — скриншоты для README и доков
```

Описание каждой страницы (1–2 строки):

- **README.md** — единственная входная точка: 4 блока по аудиториям (Пользователям / Провайдерам / Разработчикам / Безопасность), по 2–4 ссылки в каждом. Без пересказа содержимого.
- **install.md** — установка одной командой, ручная установка, что куда ставится, обновление, удаление, трей. Поглощает раздел «обновление» из `usage.md`.
- **usage.md** — как пользоваться после установки: подписки, серверы, режимы (TUN/прокси/без сервера), kill switch, правила и маршруты, DNS, уведомления, скорость, журнал, горячие клавиши. Без дубля про обновление — только ссылка на `install.md`.
- **faq.md** — новый, короткий (10–15 вопросов): режимы и их отличия, что видит провайдер VPN и провайдер интернета, прячет ли zapret IP, телеметрия, неподписанный установщик и SmartScreen, зачем службе постоянная работа, sora vs sora-legacy. Каждый ответ — 2–4 строки + ссылка вглубь.
- **troubleshooting.md** — без изменений по сути: диагностика по текстам ошибок и симптомам. Чёткая граница с FAQ: здесь только «что-то сломалось».
- **providers.md** — без изменений по сути: форматы подписок, заголовки, группы серверов, deeplink-кнопка. Целевая аудитория — владельцы панелей (Remnawave и др.).
- **extensions.md** — плоский перенос `extensions/manifest-v1.md` (нормативная спецификация). Один файл вместо каталога.
- **architecture.md** — текущий текст + новый раздел «Синхронизация устройств (sora-sync)»: 5–8 строк о протоколе и ссылка на `sync-threat-model.md`. Сейчас сервис в архитектуре отсутствует.
- **security.md** — новая страница: хранилище подписок (AES-256-GCM, DPAPI/файл), что в логах маскируется, сетевые границы (только https для подписок), kill switch как гарантия, проверка сборок по SHA256, «Sora не видит ваш трафик и не отправляет телеметрию». Для пользователей и исследователей; `SECURITY.md` в корне остаётся про процедуру репорта.
- **sync-threat-model.md** — остаётся отдельным детальным документом, связывается из `architecture.md` и `security.md`. Язык — см. раздел 6.
- **development.md** — без изменений по сути, минус хардкод версий (п. 6 в разделе 1).

Порядок в индексе — по убыванию частоты обращения: install → usage → faq → troubleshooting → providers → extensions → architecture → security → sync-threat-model → development. Внутри `docs/README.md` группировать по аудиториям, а не плоским списком.

Связи между страницами (минимум, только оправданные):

- `usage.md` → `install.md` (обновление), `providers.md` (группы серверов)
- `architecture.md` → `sync-threat-model.md`, `security.md`
- `security.md` → `sync-threat-model.md`, `architecture.md`
- `faq.md` → `usage.md`, `security.md`, `troubleshooting.md` (по вопросам)
- `troubleshooting.md` → `install.md` (переустановка), issues
- `extensions.md` → `examples/hello-panel/` (пример)
- `development.md` → `core/README.md`, `app/README.md` (уже есть)

Корневой `README.md`: раздел «Документация» превращается в 4 строки по аудиториям со ссылкой на `docs/` как полный индекс (убрать дублирующий плоский список из 8 пунктов). `README.en.md` — аналогично. `CHANGELOG.md`, `PLANS.md`, `CONTRIBUTING.md`, `SECURITY.md` остаются в корне: changelog и планы — витрина проекта (видны на главной), contributing/security — стандартные места, которые ищет GitHub.

## 4. Wiki vs in-repo: решение

**Решение: всё в репозитории (`docs/`), wiki не заводить.**

Обоснование:

1. **Версионирование вместе с кодом.** У sora частые релизы и инструкции, зависящие от версии (флаги `sora-core`, структура настроек). Дока в репозитории всегда соответствует коду в том же коммите; дока в wiki рассинхронизируется молча.
2. **Атомарные PR.** Изменение поведения + обновление доки — один pull request, одно ревью. CONTRIBUTING уже требует тестов к фиксам; доки ревьювятся тем же процессом.
3. **Масштаб не требует wiki.** ~1200 строк, 11 страниц — GitHub рендерит это из коробки. Wiki окупается на порядок большем объёме.
4. **Дверь к сайту остаётся открытой.** Когда понадобится сайт документации — генерировать его из `docs/` (mkdocs / docusaurus), как делает sing-box: доки лежат в репозитории (`docs/` + `mkdocs.yml`), а сайт — лишь рендер. Плоская структура из раздела 2 к этому готова заранее.

## 5. FAQ: решение

**Решение: отдельный `docs/faq.md` — нужен.**

Обоснование: `troubleshooting.md` и FAQ отвечают на разные вопросы. Troubleshooting — «сломалось, чиним» (симптом → действие). FAQ — «вопросы о продукте» (вопрос → объяснение): чем режимы отличаются, что видит провайдер, собирает ли Sora данные, почему SmartScreen ругается, что такое zapret и его ограничения. Смешивать их в одном файле — значит заставлять пользователя с вопросом продираться через диагностику поломок и наоборот. Раздельные страницы короче и точнее находятся поиском.

Граница: всё, где ответ — «сделайте X», идёт в troubleshooting; всё, где ответ — «потому что / вот как это работает», идёт в FAQ. Стартовый набор вопросов собирается из того, что уже раскидано по `usage.md`/`install.md` (режимы, zapret и IP, SmartScreen, телеметрия) — нового исследования не требуется, только перенос в одно место.

Референсы подтверждают разделение: у Tailscale troubleshooting вынесен в отдельные KB-статьи, у sing-box FAQ живёт отдельно от диагностики в wiki.

## 6. Референсы: что подсмотрено

1. **sing-box** (SagerNet/sing-box): документация — это wiki (сайт sing-box.sagernet.org), в репозитории только `docs/` + `mkdocs.yml` как источник для сайта; README ссылается на сайт, а не на файлы. Вывод для sora: при текущем объёме внешний сайт/wikи — избыточны; но структура «доки в репо → сайт как рендер» — правильный задел на будущее (раздел 4, п. 4). Отдельный FAQ в wiki — подтверждение разделу 5.
2. **Tailscale** (tailscale.com/docs + tailscale.com/kb/): разделы по задачам — установка по платформам, концепции («что такое»), KB-статьи для troubleshooting с номерами. Вывод: группировка по аудиториям/задачам вместо плоского списка (индекс из раздела 2), troubleshooting отдельно от объяснений.
3. **Hiddify** (hiddify.com): документация как сайт-руководство с туториалами по платформам + FAQ; мультиязычность. Вывод: для VPN-клиента с нетехнической аудиторией критичны install/usage/faq как первые три страницы — именно такой порядок задан в индексе.

## 7. Языковой вопрос (вытекает из п. 4 раздела 1)

Конвенция «документация на русском» уже заявлена (`README.en.md`: «These guides are in Russian») — её сохранить. Исключение: два нормативных документа оставить на английском и явно пометить в индексе:

- `docs/extensions.md` (manifest v1) — спецификация для разработчиков расширений, международная аудитория;
- `docs/sync-threat-model.md` — threat model для исследователей безопасности, международная аудитория.

Переводить нормативные спеки на русский — значит поддерживать две версии нормативного текста, что для минимализма неприемлемо. Пометка «(in English)» в индексе снимает вопрос.

## 8. Что НЕ делать

- Не заводить wiki, Discussions-шаблоны доков и прочие сущности «на вырост».
- Не дробить страницы мельче (например, `install-windows.md` / `install-linux.md`): 87 строк `install.md` — нормальный размер, дробление добавит навигационного шума.
- Не дублировать CHANGELOG в доках и не тащить версии в инструкции (п. 6 раздела 1).
- Не писать доки к нереализованным функциям из PLANS.md — только к тому, что shipped (исключение: нормативный manifest расширений, он нужен разработчикам заранее).
