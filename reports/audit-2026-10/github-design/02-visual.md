# 02 — Визуальная подача репозитория sora

Дизайнер №2 (визуальная подача). Статус: план и спеки, не реализация.
Репозиторий не трогать; картинки не генерировать и не скачивать.

Принцип: минимализм. Каждый бейдж, каждый скриншот, каждый пиксель — с обоснованием.
Владелец любит минимализм; продукт позиционируется как лучший VPN-клиент вообще.

---

## 1. Badges — минимальный набор

### Что вешают конкуренты (факты, проверено 2026-10-19)

| Проект | Бейджи | Вердикт |
|---|---|---|
| v2rayNG | API level (статич.), Kotlin version (статич.), commit activity, CodeFactor, GitHub Releases (скачивания), Telegram chat — **6 шт.** | Шум. Половина — девелоперская trivia для конечного пользователя |
| Nekoray | GitHub All Releases downloads — **1 шт.** | Минимализм. Один бейдж = социальное доказательство, которое реально читают |
| AmneziaVPN client | GitHub Actions build status (dev), Gitpod ready-to-code — **2 шт.** | Минимально, но для разработчиков, не для пользователей |

Вывод: «лучший клиент в мире» не нуждается в шести бейджах. Хватит трёх — каждый отвечает на вопрос пользователя, а не тешит эго мейнтейнера.

### Оставляем: 3 бейджа

1. **Release (версия)** — `github/v/release/levvs-one/sora`
   Обоснование: главный CTA страницы — «скачать последнюю версию». Бейдж показывает номер версии и ведёт на страницу релизов. Обновляется сам (shields.io тянет из GitHub API).
2. **Downloads (скачивания)** — `github/downloads/levvs-one/sora/total`
   Обоснование: единственное социальное доказательство, которое имеет смысл для десктопного клиента (звёзды GitHub и так видны в шапке). Некорёвый прецедент подтверждает: один такой бейдж — норма жанра.
3. **License (лицензия)** — `github/license/levvs-one/sora` → покажет `GPL-3.0`
   Обоснование: сигнал доверия «это действительно open source», стандарт для OSS-репо. Статичен, ничего не стоит.

Стиль: дефолтный shields.io (flat), **без кастомных цветов и без логотипов-иконок внутри бейджей** — цветной винегрет убивает минимализм. Все три — нативные `img.shields.io/github/...`, ноль ручного обслуживания.

### Убиваем (и почему)

- **Build status** — в репо нет workflow, который собирает приложение (есть `repository.yml` «Repository checks», `security.yml`, `autofix.yml`; релизы драфтятся по тегу `v*`). Бейдж сборки лил бы в заблуждение.
- **Commit activity / code frequency** — vanity-метрика для мейнтейнера, пользователю не говорит ничего.
- **CodeFactor / Codecov / coverage** — шум для конечного пользователя; качество кода доказывается аудитами, а не бейджем.
- **Платформы (`Windows | Linux`)** — дублирует секцию «Установка»; статичный бейдж врёт при расширении платформ.
- **Версия Flutter/Go/SDK, API level** — девелоперская trivia (грех v2rayNG). Не в README для пользователей.
- **Chat (Telegram/Discord)** — ссылка на сообщество живёт в docs/подвале, не в шапке. Бейдж чата = приглашение флудить в шапке репо.
- **Stars, watchers** — GitHub показывает сам в шапке страницы.
- **«Made with …», hits/посещения, произвольные shoutout-бейджи** — мусор по определению.

### Готовый markdown-сниппет (вставить под H1, в оба README)

```markdown
[![Release](https://img.shields.io/github/v/release/levvs-one/sora)](https://github.com/levvs-one/sora/releases)
[![Downloads](https://img.shields.io/github/downloads/levvs-one/sora/total)](https://github.com/levvs-one/sora/releases)
[![License](https://img.shields.io/github/license/levvs-one/sora)](LICENSE)
```

Требование: все бейджи — ссылками (релиз/скачивания → страница релизов, лицензия → `LICENSE`). Бейдж без ссылки — мёртвый пиксель. Порядок: release → downloads → license (важность убывает слева направо).

## 2. Скриншоты

### Текущее состояние (факты)

- `docs/images/home-1440x900-light.png` — 1440×900, PNG RGBA, 136 КБ
- `docs/images/home-1440x900-dark.png` — 1440×900, PNG RGBA, 142 КБ
- Именование уже хорошее (`<экран>-<размер>-<тема>.png`). Размер файлов отличный.

### Спека

| Параметр | Спека | Обоснование |
|---|---|---|
| Формат | **PNG**, без WebP | Файлы уже ~140 КБ — выигрыш от WebP ничтожен, а PNG безопаснее для чёткости UI-шрифтов и консистентен с текущими ассетами |
| Размер окна | **1440×900**, строго одинаковый для всех скриншотов | Визуальный ритм: скриншоты разной ширины в README выглядят как слоп |
| Retina | Экспорт 1440×900 достаточен (GitHub рендерит README шириной ~1012 px). 2x (2880×1800) — опционально, только если файл останется < 400 КБ | Не гнаться за пикселями ценой веса страницы |
| Вес | Каждый файл **< 300 КБ** | Тяжёлые скриншоты тормозят первый экран — первое впечатление |
| Контент окна | Чистое состояние: дефолтная подписка-пример, без реальных серверов пользователя, без персональных данных | Скриншот — витрина, а не дамп чьего-то конфига |
| Папка | `docs/images/` — оставить как есть | Рядом с доками, не в корне, не в `.github/` |

### Какие экраны (максимум 4 в README, иначе — галерея-шум)

1. **Главное окно, светлая тема** — hero, уже есть. Первый экран README.
2. **Главное окно, тёмная тема** — уже есть. Подача: см. ниже про `<picture>`.
3. **Экран серверов/подписок** (новый) — ключевой дифференциатор: список серверов с задержкой, выбор лучшего. Снять в светлой теме 1440×900.
4. **Экран подключений или сплит-туннеля** (новый, опционально) — вторая фишка после серверов. Только если скриншот читается без пояснений; если требует легенды — не снимать.

Файлы 3–4 именовать по той же схеме: `docs/images/servers-1440x900-light.png`, `docs/images/connections-1440x900-light.png` (+ `-dark` при наличии).

### Тёмная тема без аккордеона

Сейчас тёмный скриншот спрятан в `<details>`. Это лучше, чем два скриншота подряд, но есть чище:

```html
<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/home-1440x900-dark.png">
  <img src="docs/images/home-1440x900-light.png" alt="Главное окно Sora" width="1440">
</picture>
```

GitHub рендерит `<picture>` с `prefers-color-scheme` — скриншот сам подстраивается под тему зрителя. Один визуальный элемент вместо двух + аккордеона. Alt-текст — на языке README (`README.md` → русский, `README.en.md` → английский).

Для экранов 3–4 (где тёмной версии может не быть) — обычный `![alt](path)`.

### Demo-GIF: не делать

Вердикт: **GIF в README не нужен**.

- Подключение в Sora — это один клик; GIF «подключение за 10 секунд» не сообщает ничего, чего не говорит статичный скриншот.
- GIF тяжёлый, зациклен (отвлекает при чтении), деградирует в качестве, утяжеляет страницу.
- Если когда-нибудь понадобится демо — немой ролик ≤10 сек приложить **ассетом к релизу** и ссылкой из `docs/usage.md`, а не в README. Но и это — только по явному запросу, не «на всякий случай».

## 3. Social preview (og:image, 1200×630)

Настройка: Settings → Social preview в репозитории (загружается PNG, в репо файл не кладётся).

**Композиция (минимализм):**

- Фон: сплошной, тёмный — цвет фона тёмной темы приложения (или `#0E1116`, если точного токена нет; взять из `logo.dart`/темы). Никаких градиентов, никаких «абстрактных волн».
- Центр: знак логотипа (~160–180 px) → под ним вордмарк «sora» строчными, кегль ~64 px, начертание — как в приложении.
- Под вордмарком, одна строка, приглушённый серый, ~28–30 px: `The best open-source VPN client` (английский — превью глобальное).
- Воздух: отступы минимум по 120 px со всех сторон. Никаких скриншотов, бейджей, буллетов фич, QR-кодов, «звёздочек GitHub».

**Файл для дизайнера:** `social-preview-1200x630.png`, ровно 1200×630, sRGB, < 500 КБ.
**Чего не должно быть:** коллаж из скриншотов (выглядит как реклама 2012 года), список фич, призыв «Star us on GitHub».

## 4. Логотип и айдентика в README

**Факт:** сейчас в README логотипа нет вообще — только текстовый `# Sora`. Файла логотипа в репо тоже нет: знак живёт в коде (`app/lib/src/design/logo.dart`), иконка — `app/windows/runner/resources/app_icon.ico`.

**Спека:**

1. Экспортировать знак из `logo.dart` в `docs/images/logo-512.png` (512×512, PNG, прозрачный фон; SVG — если знак векторный и GitHub его отрисует корректно — предпочтительнее, но PNG надёжнее).
2. Шапка README (оба языка):

```html
<p align="center">
  <img src="docs/images/logo-512.png" width="96" alt="Логотип Sora">
</p>
<h1 align="center">Sora</h1>
```

- Размер: **96 px** ширина. Не 200, не 256 — логотип в шапке README это маркер, а не постер.
- Отступы: один `<p>` достаточно; пустая строка до H1 и после. Никаких `<br>`-лесенок.
- H1 центрируется вместе с логотипом — шапка становится единым блоком. Бейджи — под H1, тоже по центру? Нет: бейджи оставить **по левому краю** под центрированной шапкой — так делают GitHub-старожилы; центрированные бейджи + центрированный заголовок = свадебный торт. Решение: шапка (лого+H1+описание) по центру, бейджи и весь остальной контент — по левому краю, как сейчас.

3. **Favicon-подход для docs:** сейчас не нужен. Доки — это markdown в репо, у них нет своего сайта и вкладки браузера. Favicon появится только если доки переедут на статический сайт (GitHub Pages / отдельный домен) — тогда `favicon.ico` + `apple-touch-icon.png` из того же знака. Не делать заранее.

## 5. Чёрный список: чего НЕ делать

Конкретный перечень визуального шума — не добавлять, а при появлении — удалять:

1. **Больше 3 бейджей** в шапке. Каждый четвёртый бейдж должен пройти защиту «какой вопрос пользователя он закрывает».
2. **Бейджи без ссылок** — мёртвые пиксели.
3. **Кастомные цвета/иконки в бейджах** — винегрет вместо системы.
4. **Скриншоты разного размера** в одном README — визуальный слоп; все 1440×900.
5. **Скриншоты с реальными пользовательскими данными** (настоящие подписки, IP, серверы) — витрина, не дамп.
6. **Demo-GIF в README** — тяжело, зациклено, ничего не добавляет (см. §2).
7. **Коллаж «все экраны сразу»** одним изображением — нечитаемо, выглядит дёшево.
8. **Эмодзи в заголовках секций README** (🚀 ✨ 🔥) — маркетинговая пыль; продукт для взрослых.
9. **«Star us on GitHub»-баннеры и кнопки-«звёздочки»** в теле README.
10. **Таблицы сравнений «мы vs конкуренты» с галочками** в README — хвастовство; пусть сравнивают другие.
11. **Скриншоты терминала установки** — команды в code-блоке читаются лучше и копируются.
12. **Логотипы технологий** («Built with Flutter», «Powered by Go») — пользователю всё равно, разработчик и так видит код.
13. **Счётчики посещений / hits-бейджи** — vanity-мусор.
14. **Автоподставляемые «красивые» таблицы фич с иконками** вместо спокойного списка — список уже есть и он хорош.
15. **Social preview с текстом мельче 24 px** — на превью в соцсетях его всё равно не прочитать; только знак + название + одна строка.
