## 1. About / description + topics

**Готовая строка description (английский, 138 символов):**

```
Open-source VPN client for Windows and Linux. sing-box, Xray and mihomo cores, kill switch, split tunneling, DPI bypass.
```

Почему так: первое слово — суть (open-source VPN client), дальше — платформы, дальше — дифференциаторы из README (ядра, kill switch, split tunneling, zapret). Без воды («best», «fast», «simple») — не слоп, а факты, проверяемые кодом.

**Готовый набор topics (8 шт., копировать как есть):**

```
vpn, proxy, sing-box, xray, mihomo, flutter, dpi-bypass, open-source
```

Обоснование каждого:
- `vpn` — главный поисковый топик категории; без него репозиторий невидим в поиске по VPN-клиентам.
- `proxy` — половина функциональности (системный прокси, proxy chains F8) — это прокси-клиент тоже.
- `sing-box`, `xray`, `mihomo` — три ядра в поставке; именно по этим словам ищут клиентские GUI (так же делают Clash Verge Rev: `clash`, `clash-meta`, `mihomo`).
- `flutter` — стек UI; привлекает контрибьюторов и правильно классифицирует проект.
- `dpi-bypass` — zapret-режим без сервера; ниша обхода блокировок, по которой ищут именно такие инструменты.
- `open-source` — сигнал прозрачности; часть позиционирования («public showcase, no hidden telemetry»).

Что НЕ брать: `windows`, `linux` (платформы уже в description, тратить слоты топиков на них не стоит), `dart`, `go` (внутренняя кухня, не поисковые слова), `kill-switch`, `tun` (слишком узко, поиск по ним мёртвый).

## 2. Формат GitHub Releases

**Версионирование сейчас:** semver, теги вида `v1.0.12`, история тегов в клоне — `v0.1.0 … v1.0.12`. Так и оставить. Правила: MAJOR — ломающие изменения формата подписок/протокола; MINOR — новые функции (волны F1–F11); PATCH — фиксы. Тег `vX.Y.Z` обязан совпадать с `version:` в `app/pubspec.yaml` (сейчас `1.0.12+13` — совпадает, это хорошо).

**Шаблон release notes** (язык — русский, аудитория русскоязычная; структура — по образцу Clash Verge Rev: категории → платформы → загрузки):

```markdown
## Sora 1.0.13

**✨ Новое**
- …

**🐞 Исправления**
- …

**🖥️ Windows**
- …

**🐧 Linux**
- …

**🔒 Безопасность**
- (только если есть; иначе раздел опустить)

## Проверка подлинности

Все файлы подписаны. Сверьте контрольные суммы и подпись:

```powershell
# Windows (PowerShell)
minisign -Vm SHA256SUMS -p <публичный ключ из docs/security.md>
```

```sh
# Linux
minisign -Vm SHA256SUMS -p <публичный ключ из docs/security.md>
```

## Загрузка

| Платформа | Файл |
| --- | --- |
| Windows 10/11 x64 | `Sora-Setup-1.0.13.exe` |
| Linux (deb) | `sora_1.0.13_amd64.deb` |
| Linux (rpm) | `sora-1.0.13.x86_64.rpm` |
| Linux (Arch) | `sora-1.0.13-x86_64.pkg.tar.zst` |

Полный список изменений: [CHANGELOG.md](https://github.com/levvs-one/sora/blob/main/CHANGELOG.md)
```

Что взять у других (проверено):
- **Clash Verge Rev**: структура «🐞 Исправления / ✨ Новое / 🚀 Оптимизации» + подсекции по платформам (🖥️ Windows / 🍎 macOS / 🐧 Linux), блок «## 下载地址» с таблицей файлов по ОС и битности, подписи `.sig` рядом с каждым артефактом, теги с GPG-верификацией, RC-пререлизы отдельно от stable. Взять: категоризацию и таблицу загрузок.
- **AmneziaVPN**: короткие notes + ссылка «Full Changelog: X...Y» на сравнение тегов; инструкции по установке прямо в notes (какой файл для какой ОС). Взять: «какой файл качать» прямо в notes — у sora это критично, т.к. install-скрипты тянут `latest/download`.
- У обоих: один релиз = один «latest». Sora уже так устроена (install.ps1/install.sh тянут latest) — правило: **пререлизы всегда помечать как pre-release**, иначе скрипты установки подхватят бету.

Дополнительно: подпись тега (GPG/SSH, «Verified» бейдж как у Clash Verge Rev) — дешёвый сигнал прозрачности, соответствует позиционированию проекта.

## 3. CHANGELOG.md

**Текущий формат:** заголовок `# Изменения`, секции `## 1.0.12 (15 октября 2026)`, внутри — плоский список пуль без категорий (новое и фиксы вперемешку, см. 1.0.8 и 1.0.6). Даты — словами по-русски. Это *почти* Keep a Changelog, но не он.

**Оценка:** содержание отличное (подробные, честные записи; пометка про 1.0.1–1.0.3 «собраны, но не выпущены» и про переезд репозитория — образцовые), формату не хватает трёх вещей: категорий, машиночитаемых дат, секции Unreleased.

**Что улучшить (минимум правок):**
1. Категории внутри версии: `### Добавлено`, `### Исправлено` (по Keep a Changelog: Added / Fixed; Changed — по необходимости).
2. Даты в ISO: `## [1.0.13] — 2026-10-19` вместо `(15 октября 2026)`. Русские даты словами ломают парсинг и сортировку.
3. Секция `## [Unreleased]` сверху — куда PR-шаблон уже требует добавлять записи («Если поведение изменилось, обновлён CHANGELOG.md» — сейчас некуда добавлять, т.к. секций под будущую версию нет).
4. Заголовок `# Changelog` вместо `# Изменения` — файл читают и не-русскоязычные (README.en.md существует); тело записей пусть остаётся русским.

**Эталонная запись:**

```markdown
# Changelog

## [Unreleased]

## [1.0.13] — 2026-10-19

### Добавлено
- Менеджер DNS: выбор серверов и проверка утечек для всех режимов (F3).

### Исправлено
- Ложный отказ при смене сервера с работающим Xray TUN: проверка конфигурации использует отдельный временный адаптер.

## [1.0.12] — 2026-10-15
…
```

## 4. Pinned (закрепить)

GitHub позволяет закрепить до 3 issue/PR. Кандидаты:

1. **«Добро пожаловать: с чего начать»** (новый issue, закрепить) — одна страница: что такое Sora, кому подходит (есть подписка от провайдера), ссылки на установку / troubleshooting / SECURITY.md, просьба не постить секреты подписок (уже есть в шаблоне бага — продублировать). Обоснование: снижает поток мусорных issue, первое, что видит новичок.
2. **«Дорожная карта»** (новый issue со ссылкой на PLANS.md, закрепить) — живой список P0–P2 из PLANS.md с чекбоксами прогресса. Обоснование: PLANS.md сейчас лежит в корне и его никто не видит; закреплённый issue превращает его в публичный роадмап и точку сбора фидбека.
3. **Анонс переезда `levvs-one/sora`** (существующий issue/PR о переезде, если есть; иначе — раздел в #1) — в changelog 1.0.10 уже есть пометка про перенос репозитория и канала обновлений. Обоснование: старые пользователи/форки ищут проект по старому адресу; закреп спасает от потерянных issue не туда.

Discussions: если включены — закрепить там вместо issue #2 (роадмап как discussion «Announcements»). Проверить в настройках: Settings → General → Features → Discussions.

## 5. Мелочи гигиены

**`.gitattributes`** — в порядке: `* text=auto eol=lf` + явный список binary. Замечание: добавить `*.minisig binary` и `SHA256SUMS* -text` (артефакты подписи из workflow), иначе diff подписи будет мусорить. Одна строка, не срочно.

**`.gitignore`** — в порядке: покрыты Go, Flutter/Dart, Android/keystore (`*.jks`, `key.properties` — правильно, ключи не уедут в репо), `/dist/`, `.env`. Замечаний нет.

**FUNDING.yml — не нужен.** Обоснование: у проекта нет заявленной модели монетизации/донатов, README и позиционирование — «открытый showcase, no hidden telemetry»; кнопка Sponsor без настроенного получателя — мёртвый UI и ложное ожидание. Если донаты появятся — добавить тогда, одной строкой.

**Issue labels** (сейчас из шаблонов: только `bug`, `enhancement`). Минимальный добор, каждый оправдан:
- `security` — уязвимости должны визуально отличаться от обычных багов; связан с SECURITY.md.
- `question` — чтобы отличать вопросы от багов и не портить статистику.
- `good first issue` — стандартный магнит для контрибьюторов, дешёвый.
- `windows` / `linux` — платформенная triage-метка; у проекта две ОС с сильно разной спецификой (WFP vs nftables).
- `docs` — правки документации отдельно от кода.

Не добавлять: `wontfix`, `duplicate` (это действия, не категории), `priority/*` (приоритеты уже в PLANS.md как P0–P2).

**Найденный баг шаблонов:** `.github/ISSUE_TEMPLATE/01_bug_report.yml` в dropdown «Система» предлагает «Windows 7 SP1 x86» — это из legacy-репозитория. Sora поддерживает Windows 10 1809+. Заменить опции на `Windows 11`, `Windows 10`, `Linux (указать дистрибутив в описании)`. И placeholder версии `0.2.2` устарел — поставить `1.0.12`.

**Branch protection для `main`** (репозиторий с одним владельцем, CODEOWNERS = @levvs-one):
- Require status checks to pass before merging: workflow `repository.yml` (сборка/линт) — обязательно.
- Block force pushes, block deletions — обязательно.
- Require linear history — желательно (история сейчас линейная и чистая, сохранить).
- Require pull request before merging — для соло-владельца избыточно; оставить прямые пуши, но с обязательными чек-статусами. Если появятся контрибьюторы — включить.
- Tag protection: правило `v*` — теги только из main (сейчас теги уже только релизные, закрепить правилом).

**Прочее из проверки:**
- Dependabot включён (есть `dependabot.yml`, видны dependabot-ветки) — ок.
- PR-шаблон хороший: чек-лист «нет секретов», «обновлён CHANGELOG.md» — оставить как есть.
- Секреты: `.gitleaks.toml` в корне — ок; workflow подписывает SHA256SUMS через minisign — ключ церемонии остаётся за владельцем (уже в FIX-REPORT как owner action).
