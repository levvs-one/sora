# Community-файлы: анализ и решения (дизайн №4)

## Что было не так

**01_bug_report.yml — критично.** Поле «Система» предлагало только «Windows 7 SP1 x86» и «Другая версия Windows». Находка подтверждена: это наследие legacy-клиента. Для основного репозитория (Windows 10+/11, Linux, Android) список бесполезен — пользователь с Ubuntu вынужден выбирать «Другая версия Windows», а мейнтейнер теряет ключевое поле для триажа. Форму нельзя использовать в текущем виде.

**CONTRIBUTING.md — две проблемы.**
1. Ссылка на legacy-ветку вела на `github.com/levvs-one/sora-client/tree/legacy`. Репозиторий переименован в `levvs-one/sora` (GitHub отдаёт редирект), а ветка `legacy` существует именно в `sora` — проверено локально (`remotes/origin/legacy`). Ссылка формально открывается, но указывает на несуществующее имя репозитория; это выглядит неряшливо для проекта, претендующего на «лучший».
2. Противоречие с README: CONTRIBUTING обещал в `legacy` «исправления безопасности и серьёзных ошибок», README говорит «только исправления безопасности». Два документа — два правила приёма; исправлено в пользу README (более строгая и свежая формулировка).

**SECURITY.md — почти хорошо.** Не хватало одной строки: явного запрета обсуждать уязвимость публично до выхода исправления. Без неё добросовестный репортер может «добить» отчёт комментариями в открытом issue. Добавлена одна строка, больше ничего не трогал — файл и так минималистичен.

**PULL_REQUEST_TEMPLATE.md — хорошо.** Все четыре пункта чек-листа оправданы (тесты, тест на багфикс, отсутствие секретов, CHANGELOG). Единственное изменение: подсказка про `Closes #123` в комментарии под «Зачем» — убирает лишний вопрос «куда ссылку на issue».

**02_feature_request.yml — хорошо.** Структура «проблема → решение → альтернативы» уже правильная, сокращать нечего. Оставлена без изменений.

**CODE_OF_CONDUCT.md отсутствовал.** Для проекта с амбицией «лучший опенсорс-VPN» это пробел: у крупных проектов кодекс есть, а его отсутствие у нового амбициозного репозитория считывается как «сообществу не думали». Решение: добавить, но короткий.

## Что взято у лучших

Изучены приёмы issue-форм крупных проектов (tailscale, vscode-экосистема, Ghost, WSL, плюс разборы на deepwiki и материал про AI-friendly баг-репорты):

1. **Обязательный чекбокс «поискал похожие issues»** — у всех. Уже был в sora, сохранён в обеих формах.
2. **Автоматические лейблы** (`bug`, `enhancement`) — стандарт, уже был, сохранён.
3. **Окружение — короткий выпадающий список вместо свободного текста** (приём из шаблонов WSL/LiveTileHost: версии Windows списком). Взято, но без перебора: 8 опций покрывают все платформы из README (Windows 10 1809+/11; Debian/Ubuntu, Fedora, openSUSE, Arch; Android). Свободный ввод для ОС не взят — он даёт мусор в триаже, а dropdown даёт фильтруемость.
4. **Поле «движок» (sing-box / Xray-core / mihomo)** — специфика sora: три движка под одним ядром, и без этого поля половина багов подключений недиагностируема. Первый пункт списка — «Не знаю», чтобы не заставлять гадать. Поле необязательное: для багов интерфейса оно лишнее, трение при заполнении формы должно быть нулевым.
5. **«Версия ядра»** — только для Linux/Android (kill switch на nftables, tun-режим), необязательное, с явным указанием области в description. На Windows поле не нужно — dropdown ОС уже достаточен.
6. **«Что вы увидели и что ожидали увидеть» в одном поле** — уже было в sora, и это правильно: приём из AI-friendly шаблона (Expected vs Actual), но без раздувания формы до двух отдельных полей.
7. **Предупреждение о секретах вверху формы** — уже было, сохранено как есть: для VPN-клиента это не бюрократия, а защита пользователей от публикации подписок и UUID.
8. **Ghost-подход к feature request** — «опишите ситуацию пользователя, а не кнопку» — уже был в sora, усилен не был, потому что и так точен.
9. **Не взято сознательно:** severity-dropdown (проект маленький, приоритет ставит мейнтейнер, а не репортер); отдельные поля «ожидаемое/фактическое поведение» (удваивают форму без выигрыша); `blank_issues_enabled: false` в виде отдельного config.yml — рекомендую добавить позже одной строкой, но это уже за рамками черновиков.

## Обоснование решений по файлам

- **CODE_OF_CONDUCT.draft.md** — написан с нуля, короткий (3 раздела), на русском. За основу взяты принципы Contributor Covenant (ожидания / недопустимое / применение), но без копирования его длинного текста: владельцу важен минимализм, а полный Covenant — это ~40 строк юридического английского. Канал для жалоб — личное сообщение мейнтейнерам в GitHub: не выдуман новый email, использован существующий механизм.
- **Система в баг-репорте** — список собран строго по таблице платформ из README репозитория: Windows 10/11 (README: 10 1809+), Debian/Ubuntu, Fedora, openSUSE, Arch (README: Debian 12+, Ubuntu 22.04+, Fedora 39+, openSUSE), Android (8.0+, отдельная платформа — пропуск был бы дырой). macOS нет в списке осознанно: это не релизная платформа по README, для неё есть «Другое».
- **CONTRIBUTING** — первая строка про кодекс поведения добавлена, чтобы новый файл не висел сиротой. Пункт 1 слегка переформулирован (условие вынесено вперёд, добавлено «сначала» — исходный порядок слов читался как инструкция открывать issue всегда). Остальное не тронуто: команды проверок и правило про тест на багфикс уже точные.
- **SECURITY** — добавлена только строка про непубличное обсуждение. Сроков реакции не выдумывал: обещать SLA без владельца нельзя.
- **Формы issue** — русский язык сохранён как в текущих файлах; префиксы заголовков `[Ошибка]:` / `[Идея]:` и лейблы сохранены для совместимости с существующим триажем.

## Рекомендация вне черновиков

Добавить `.github/ISSUE_TEMPLATE/config.yml` с `blank_issues_enabled: false` — пустые issues обходят всю проделанную работу по формам. Одна строка, но это уже изменение поведения, поэтому оставил на решение владельца, а не в черновики.
