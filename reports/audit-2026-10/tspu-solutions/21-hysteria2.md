# 21. Hysteria2: довести до ума (brutal, hopping, salamander, QUIC-фингерпринт, TCP-фолбэк)

Дата: 2026-10-20. T021 (High), TSPU-ANALYSIS ← P23 (отчёт `tspu-analysis/23-hysteria2-detect.md`).
Статус кода: net-R&D уже приземлил plumbing up/down и port hopping (sing-box `up_mbps`/`down_mbps`/`server_ports`/`hop_interval`, mihomo `up`/`down`/`ports`/`hop-interval`, парсинг `mport`/`ports`/`upmbps`/`downmbps` из hy2-ссылок, `FeatureHy2PortHop` в каталоге движков — Xray для hopping-планов исключён).
Мои коммиты: `[tspu-fix]` T021 (Xray `hysteriaSettings.up_mbps/down_mbps`) — НЕ сел из-за горячей ветки, патч: `tspu-solutions/21-xray-hy2-brutal.patch`.
Эта спека — остаток: UI тарифа, авто-калибровка brutal, TCP-фолбэк, salamander-тест, QUIC ClientHello-аудит.

## 1. Проблема

Hysteria2 в sora работал «вхолостую»: без `up/down` brutal CC никогда не включался (падение на BBR) — терялось главное преимущество протокола (замеры 2025–2026: hy2 выигрывает по throughput именно за счёт агрессивного CC). Детект hy2 идёт не по имени, а по QUIC Initial (SNI/ALPN/fingerprint quic-go), нестандартному порту и туннельному профилю; при резке UDP целиком протокол мёртв в принципе — без TCP-фолбэка сервер недоступен.

Проверка маппинга Xray (пункт (е) исходной задачи): **маппинг НЕ устаревший**. `protocol: "hysteria"` + `settings.version: 2` — это и есть нативный Hysteria2 в Xray (upstream требует version == 2, доки: xtls.github.io/en/config/outbounds/hysteria.html). ## 3. UI «скорость тарифа» (Dart, бэклог — SDK нет)

- В карточке hy2-сервера (addserver/servers): два числовых поля **«Upload тарифа, Мбит/с»** и **«Download тарифа, Мбит/с»**, плюс поле **«Диапазон портов»** (формат `20000-50000` или список через запятую) и **«Интервал hopping, с»** (дефолт 30, мин 5).
- Значения уходят в credential document как `upmbps`/`downmbps`/`hop_ports`/`hop_interval` — дальше plumbing уже есть.
- **Честное предупреждение в UI** (обязательно): «Завышенный upload деградирует канал: brutal шлёт в лоб и перегружает маршрут. Указывайте реальный тариф, не “побольше”. Если провайдер включил `ignoreClientBandwidth`, настройка игнорируется сервером».
- Валидация на клиенте: числа > 0, ≤ 100000; диапазон портов — валидный `validateHopPorts`-формат; интервал ≥ 5.

## 4. Авто-калибровка brutal по speedtest (Go + UI)

Ручной ввод тарифа почти все выставляют неверно (исследование 24). Механизм:

1. **Триггер**: первое успешное подключение к hy2-серверу, у которого `upmbps`/`downmbps` не заданы.
2. **Замер**: `probe.Benchmarker` (уже есть, `core/probe/bandwidth.go`) прогоняет download-бенчмарк через временный движок. Upload напрямую не меряется (бенчмарк — download-only): для upload использовать эвристику — запросить у пользователя тариф один раз ИЛИ взять `down * 0.1` с явной пометкой «оценка».
3. **Применение**: `down = measured * 0.9` (запас 10% — brutal не должен упираться в потолок), `up = min(userTariff, measured_down * 0.1)` с пометкой источника. Запись в credential document сервера; в UI — бейдж «авто (замер 20.10)».
4. **Перепроверка**: не чаще раза в 7 дней и только по кнопке «Перезамерить»; тихие фоновые замеры — нет (трафик заметен, замер сам влияет на сеть).
5. **Честные ограничения**: замер меряет путь сервер→клиент в момент замера, а не тариф; CGNAT/вечерняя конгестия дадут заниженное значение — поэтому коэффициент 0.9, а не 1.0; если сервер включил `ignoreClientBandwidth` — калибровка бессмысленна, в UI показать хинт.

Сложность: средняя (бенчмарк есть, нужна только оркестрация + UI). Эффект: high — brutal наконец работает у всех, а не у тех, кто правильно вбил тариф.

## 5. TCP-фолбэк при резке UDP (Go, бэклог)

- При создании/импорте hy2-сервера предлагать (opt-out, не opt-in) **spare-группу**: hy2 primary + VLESS/Trojan TCP spare через `GroupFallback` (mihomo) / selector (sing-box).
- Health-check: UDP-недостижимость hy2-порта (QUIC handshake timeout) → автоматический переход на spare без ручного переключения; возврат на hy2 — по кнопке или при следующем подключении, не тихим флипом (флип туда-сюда — фингерпринт).
- Запрет слепого TCP-фолбэка для сценариев, где он вреден (отчёт 23 §3.4: для YouTube-quic fallback на TCP иногда хуже) — фолбэк per-сервер, не глобальный.

## 6. Полевой тест salamander и QUIC ClientHello-аудит (исследование, не код)

- **Salamander**: скрывает SNI от пассивных парсеров (XOR всего пакета), но вывод — псевдослучайный поток без QUIC-заголовка → попадает под GFW-эвристики «полностью шифрованного трафика». Полевых подтверждений эффективности/детекта в 2026 нет. Нужно: стенд с замерами из RU-ASN (salamander on/off, детект по энтропийным эвристикам Wu et al.) — задача полевой инфраструктуре, не клиенту. В UI: тогл «Salamander» с варном «сервер должен поддерживать; несовместим с маскировкой под сайт на том же порту».
- **QUIC ClientHello**: sora не контролирует ClientHello напрямую — движки внешние бинарники (sing-box → quic-go, Xray 26.10+ имеет Chrome-parrot QUIC-режим). Аудит = pcap-сравнение ClientHello движков vs Chrome 155 (JA4, GREASE, порядок расширений). В `core/go.mod` quic-зависимости нет вообще — менять нечего; если аудит покажет расхождение, рычаг — обновление движка в `packaging/engines/engines.lock` или опция фингерпринта, если движок её поддерживает. Gecko (sing-box/mihomo не поддерживают) — отложить до появления поддержки в движках.

## 7. Сложность / эффект / риски

- **Сложность**: низкая–средняя. Plumbing готов; остались Xray-патч (применить), UI (4 поля + варны), оркестрация калибровки, spare-группы.
- **Эффект**: high. Brutal — главная причина использовать hy2; сейчас большинство пользователей его не получают.
- **Риски**:
  - Завышенный up → деградация канала и остального трафика (митигация: UI-варн + калибровка с запасом 0.9).
  - `ignoreClientBandwidth` у провайдера делает тюнинг плацебо (митигация: честный хинт в UI).
  - Hopping бесполезен, если режется UDP целиком (митигация: TCP-фолбэк, §5).
  - Авто-замер жрёт трафик (~100 МБ) — только по первому подключению и по кнопке, с предупреждением.
