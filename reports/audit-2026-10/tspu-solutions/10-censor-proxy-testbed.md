# 10. Стенд «прокси цензора»: эвристики + ML для regression-тестов релиза

Дата: 2026-10-20. Пучок: T027 (High, TSPU-ANALYSIS.md ← P20-1…10, P37).
Статус: спека (крупное). Связано: 09 (pcap-харнесс — измерение), 02 (JA4 — один из сигналов стенда), 11 (GFW-профиль — что эмулируем).

## 1. Проблема

- У sora нет способа ответить на вопрос «а что увидит цензор?» до того, как цензор это увидит. Все проверки — постфактум, по жалобам.
- Известные эвристики детекта VPN/прокси (Wu et al.: размер/тайминг/энтропия первых пакетов; website-fingerprinting семейства k-FP/DF) — это опубликованные, воспроизводимые алгоритмы. Не прогонять их на своих транспортах — оставлять бесплатную проверку на столе.
- Нужен regression-стенд уровня релиза: каждый релиз прогоняется через «прокси цензора», деградация метрик — красный флаг.

## 2. Дизайн стенда

### 2.1. Архитектура

```
┌─────────────┐   pcap/поток   ┌──────────────────────┐
│ sora-core   │ ────────────► │  censor-proxy стенд  │
│ (стенд:     │                │  ┌────────────────┐  │
│  loopback + │                │  │ L1: эвристики  │  │
│  netem)     │                │  │ L2: JA4/JA3    │  │
│             │                │  │ L3: wavelet-RF │  │
└─────────────┘                │  │ L4: DF-CNN     │  │
                               │  └────────────────┘  │
                               │  verdict + отчёт     │
                               └──────────────────────┘
```

Стенд — отдельный пакет `core/testutil/censorproxy` + CLI `sora-censor-proxy` для ручных прогонов. Вход: pcap или живой поток со стенда 09. Выход: вердикт по каждому детектору + сводный скор.

### 2.2. Детекторы

1. **L1 — эвристики Wu et al.**: пороговые правила по первым N пакетам — энтропия payload (Shadowsocks AEAD vs TLS), размеры handshake, соотношение in/out, длительность quiet-периодов. Дешёвые, детерминированные, объяснимые. Каждый провал — конкретная строка «почему».
2. **L2 — JA4/JA3 сверка**: ClientHello из потока vs эталон (переиспользовать `core/diagnostics` JA4-код, §02). Отдельный детектор «SNI-консистентность»: SNI == Host == dest-линейка (см. T032).
3. **L3 — wavelet-RF**: вейвлет-признаки размерно-временного ряда → RandomForest «наш транспорт vs baseline». Легче DF-CNN, обучается за минуты, достаточно для regression (ловит «мы отъехали от baseline»).
4. **L4 — DF-CNN** (опционально, nightly): глубокая модель как у цензора; см. спеку 09 §2.3.

Порядок важен: L1/L2 — всегда в CI (секунды), L3 — на релиз (минуты), L4 — nightly.

### 2.3. Квартальная сверка мимикрии с «нормой»

Раз в квартал (чеклист в OWNER-PLAYBOOK):
1. Обновить baseline pcap'ы (новые версии Chrome/Firefox).
2. Прогнать все транспорты sora через стенд.
3. Сравнить скоры с прошлым кварталом: деградация > δ → задача в бэклог с приоритетом.
4. Проверить новые публикации (эвристики Wu et al. и последователи): добавить детектор, если воспроизводим.

### 2.4. Вердикт и пороги

- Каждый детектор: `score ∈ [0,1]` + `explain: string` (почему сработал).
- Сводный: взвешенная сумма; пороги: `≥0.7` — блокер релиза, `0.4–0.7` — warning с обязательным разбором, `<0.4` — ок.
- Пороги калибруются на первых 2–3 прогонах, затем фиксируются. Изменение порога — отдельным коммитом с обоснованием (иначе метрика «поплывёт» под результат).

## 3. Что НЕ делает стенд (честные ограничения)

1. **Не эмулирует активного цензора**: probing, throttling, SNI-блоклисты, поведенческие эвристики на уровне ISP — вне стенда. Это пассивный классификатор трафика.
2. **Не знает про out-of-band**: ASN/IP-репутацию, DNS-сигналы, временные паттерны пользователя — стенд видит только поток.
3. **Ложные срабатывания**: эвристики Wu et al. на коротких потоках шумят; стенд требует минимальной длины потока (напр. ≥50 пакетов) и помечает короткие как «недостаточно данных», а не «чисто».
4. **Гонка версий**: детекторы отстают от цензора по определению; стенд ловит регрессии относительно baseline, а не «невидимость».
5. **Производительность**: L3/L4 на CPU в CI — минуты; на каждый коммит — только L1/L2.

## 4. Сложность / эффект / риски

- **Сложность**: высокая. L1/L2 — средняя (эвристики + переиспользование JA4); L3 — средняя (вейвлеты + RF — стандартные библиотеки); L4 — высокая (см. 09); инфраструктура стенда + калибровка — средняя.
- **Эффект**: high. Превращает «надеемся, что не палимся» в измеряемый regression-контроль; каждый релиз выходит с протоколом «прокси цензора».
- **Риски**:
  - Стенд становится «театром безопасности» → митигация: пороги + обязательный разбор warning'ов + §3 в документации.
  - Переобучение детекторов под свои же транспорты (L3/L4 учатся отличать «нас сегодняшних») → митигация: baseline — только реальные браузеры, никогда свои старые захваты как «норма».
  - Поддержка: каждая новая фича транспорта требует прогона → митигация: стенд в CI делает это автоматическим.
