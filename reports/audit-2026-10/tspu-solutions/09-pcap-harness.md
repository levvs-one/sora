# 09. pcap-харнесс: собственные отпечатки + baseline браузеров + метрика отличимости

Дата: 2026-10-20. Пучок: T026 (High, TSPU-ANALYSIS.md ← P42-1…14).
Статус: спека (крупное). Связано: 02 (JA4 self-test — побайтовый уровень), 10 (стенд «прокси цензора» — поведенческий уровень), 11 (GFW — целевой профиль).

## 1. Проблема

- Сегодня sora проверяет фингерпринт только на уровне ClientHello (JA4, спека 02). Цензор смотрит шире: размеры и тайминги первых пакетов, pacing handshake'а, паттерны multiplexing'а. DF-CNN (Deep Fingerprinting, Sirinam et al.) классифицирует трафик по первым ~5000 пакетам с точностью >90% даже против «похожего» трафика.
- Нет baseline'а: не с чем сравнивать. «Мы похожи на Chrome» — утверждение без измерения.
- Нет acceptance-критерия для релиза: «не стало хуже» нечем померить.
- Cold start не защищён: первые пакеты (TCP handshake, ClientHello, первые data-пакеты) уходят до того, как включается любая обфускация — «защита с пакета №1» отсутствует как требование.

## 2. Дизайн харнесса

### 2.1. Что измеряем

Три слоя, от дешёвого к дорогому:
1. **L1 — ClientHello** (уже есть, спека 02): JA4/JA4+ собственного uTLS vs эталон браузера. Дёшево, в CI.
2. **L2 — размеры/тайминги первых K пакетов**: захват pcap первых ~16 КБ (порог «фриза» ТСПУ!) каждой конфигурации транспорта; признаки: последовательность размеров, inter-arrival times, направления. Сравнение с baseline браузеров.
3. **L3 — DF-CNN отличимость**: обученный (или предобученный) классификатор «наш транспорт vs baseline». Метрика = accuracy отличимости. Acceptance: accuracy ≤ порога (см. §4).

### 2.2. Baseline браузеров

- Набор эталонов: Chrome 155 (дефолт), Firefox, Edge — реальные захваты: TLS handshake + первые 16 КБ типичной сессии (загрузка страницы, video chunk). Источники: собственные захваты в лабе + публичные датасеты (ISCX, CIC). Версионировать как артефакты (`testdata/pcap/baseline/chrome155/*.pcap`), с метаданными (дата, версия браузера, сценарий).
- Baseline пересматривается раз в полгода или при смене мажорного Chrome: браузеры тоже меняют поведение.

### 2.3. Харнесс

Новый пакет `core/testutil/pcapharness` (имя рабочее):
- `Capture(config TransportConfig, scenario) → pcap`: поднимает локальный стенд (клиент sora-core ↔ тестовый сервер через loopback/namespace), пишет pcap первых N пакетов/K байт. Без внешней сети — воспроизводимо в CI.
- `Features(pcap) → vectors`: размеры, IAT, направления первых K пакетов.
- `Distinguishability(ours, baseline) → float`: расстояние/accuracy простого классификатора (наивный baseline: kNN по признакам; DF-CNN — следующий шаг, §5).
- Интеграция: `go test ./core/testutil/pcapharness/ -run TestReleaseGate` — падает, если метрика хуже порога.

### 2.4. Cold-start shaping («защита с пакета №1»)

Требование к каждому транспорту: первые пакеты сессии уже должны лежать внутри браузерного профиля:
- Размеры первых пакетов (включая TCP SYN/ACK — MSS, window scale!) соответствуют baseline.
- Паддинг первых data-пакетов до браузерных размеров (mimicry-padding, не random — см. T016).
- Тайминги: без «мгновенного» handshake (признак скрипта), pacing в пределах человеческого.
- Харнесс проверяет это явно: отдельный subtest `TestColdStartShape` на первые 16 пакетов.

## 3. Acceptance-критерии релиза

1. L1: JA4 собственного uTLS == эталон (уже gate, спека 02).
2. L2: расстояние до baseline Chrome ≤ X (порог калибруется на первых прогонах; стартовая цель — не хуже текущего релиза, затем ужесточение).
3. L3 (цель): DF-CNN accuracy «наш транспорт vs Chrome» ≤ 0.60 (близко к случайному угадыванию 0.50 для бинарной задачи).
4. Cold-start: первые 16 пакетов внутри браузерного коридора размеров/таймингов.

## 4. Честные ограничения

1. **DF-CNN в CI — дорого.** Полноценное обучение — вне CI; в CI — предобученная модель + инференс, или kNN-прокси. Порог 0.60 — цель, не обещание: реальный цензор использует ансамбль и out-of-band сигналы.
2. **Baseline — это лаба, не дикая природа.** Реальный Chrome за NAT, с расширениями, с QUIC — отличается от лабораторного. Харнесс ловит регрессии («мы стали дальше от baseline»), а не доказывает невидимость.
3. **Loopback ≠ интернет.** Тайминги на loopback стерильны; для IAT-признаков нужен impairment (netem: задержка/джиттер/потери). Харнесс обязан эмулировать RTT 30–150 мс, иначе метрика врёт.
4. **«Защита с пакета №1» не покрывает TCP/IP-уровень**: SYN-фингерпринт (p0f) ОС остаётся; харнесс это фиксирует, но не чинит (нужен per-OS тюнинг сокетов — отдельный бэклог).
5. Pcap'ы baseline — артефакты с реальными SNI/временем: хранить redacted (SNI → example.com), иначе сами становимся источником утечек.

## 5. Сложность / эффект / риски

- **Сложность**: высокая. L1 готов; L2 — средний (pcap-захват, признаки, netem); L3 — высокий (модель, обучение/инференс, калибровка порога). Поэтапно: L2 в первую очередь.
- **Эффект**: high. Единственный честный ответ на «а мы точно похожи на браузер?»; ловит регрессии до релиза; cold-start shaping закрывает самый дешёвый вектор цензора (первые пакеты).
- **Риски**:
  - Метрика становится самоцелью (гонка за цифрой вместо реальной стойкости) → митигация: порог + ручная экспертиза расхождений, не только число.
  - Ложное чувство безопасности («DF-CNN не отличил») → митигация: §4 в документации харнесса, рядом с цифрой.
  - Тяжёлый CI → митигация: L2 — всегда, L3 — nightly/на релиз.
