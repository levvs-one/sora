# T040 — Мультистратегический движок (per-ASN кэширование внедрено)

Тех-спека. Статус: per-ASN кэш — внедрено и покрыто тестом; мультистратегия —
спека.

## Внедрено: per-ASN кэширование

`tune/cache.go:networkKey` = `SSID \x1f Gateway \x1f ASN`: стратегия,
подобранная тюнером, привязана к сети **и** оператору. Обоснование:
поведение ТСПУ операторо-зависимо (преконфиги сообщества расписаны по
провайдерам; FOCI: Москва/СПб/Новосибирск различаются), стратегия с
одного ASN на другом — не валидна.

Тест `TestCacheSeparatesASNs` (`core/tune/tune_test.go`): один SSID +
gateway, два ASN — кэши не пересекаются ни в одну сторону. Победа
тюнера тоже per-ASN: `Candidates(current, cached)` подставляет
запомненную стратегию второй после текущей.

## Спека: мультистратегический движок

### Проблема

Сейчас одна стратегия = один процесс (tpws) или один набор фильтров
(nfqws). Реальность 2026: разным классам трафика нужны разные стратегии
одновременно — TLS 443 (десинхронизация handshake), HTTP 80 (тамперы),
UDP 443 (QUIC fake), Discord voice UDP 50000–50099 (STUN fake). Один
профиль на всё — это либо дыры, либо лишние фейки на всём трафике
(заметность + CPU).

### Решение

nfqws поддерживает `--new`: несколько независимых профилей
(фильтры L3/L4/L7 + hostlist/ipset + своя стратегия), первый совпавший
применяется. Движок sora должен:

1. **Модель**: `BypassStrategy` сейчас — одна стратегия на outbound.
   Ввести `BypassProfile { Name, FilterTCP, FilterUDP, FilterL7,
   HostList, Strategy }` и `BypassChain []BypassProfile` на план (или на
   outbound — решение за control plane; на план проще: десинхронизация
   идёт ниже движка, per-outbound ей не нужна).
2. **Рендер**: один процесс nfqws, argv = profile1 `--new` profile2
   `--new` … Типовой набор 2026:
   - TCP 80: `fake,split2` + http-тамперы, hostlist веба;
   - TCP 443: `syndata,split2` / `fake,multidisorder` + `fooling=badseq`;
   - UDP 443: `fake,disorder2` + `fake-quic` + `repeats=8`;
   - UDP 50000–50099: `fake` + `filter-l7=discord,stun`.
3. **Перехват**: один NFQUEUE на профиль или один на всё с
   `--dpi-desync-fwmark`; аллокатор очередей уже внедрён
   (`core/engine/bypass/nfqws_queue.go`).
4. **Тюнер**: `tune/desync` подбирает профиль **по классам**, а не одну
   стратегию на всё; кэш — per-ASN × класс трафика. Профили протухают
   независимо (QUIC-стратегия умерла — TCP-профиль не трогаем).
5. **Ротация** (идея `circular` из zapret2): профиль, поймавший N
   фейлов за M минут, временно отключается, остальные продолжают.
   Без этого одна мёртвая стратегия тянет за собой весь chain.

### UX

- Экран «Обход»: список профилей chain'а с per-профиль статусом
  (работает/деградировал/выключен) и кнопкой «переподобрать».
- Никаких «активных методов вызова bypass» (P49): автоподбор — только
  пассивные сигналы + явная кнопка пробы; вызывать DPI на себя
  активным зондированием — юридический риск, запретить в UI.

### Риски и честные ограничения

- Сложность: высокая. Модель, рендер, перехват, тюнер, UI — затрагивает
  control plane и executor (см. `NFQWS-MIGRATION.md`).
- Каждый профиль — отдельная поверхность протухания: chain из 4
  профилей требует в 4 раза больше полевых замеров, иначе это
  коллекция слухов (наследовать запрет маркетинговых цифр).
- Fake-профили заметнее split-профилей: тюнер обязан предпочитать
  тихий профиль, когда он работает (fitness «brevity» уже учитывает
  стоимость — расширить на per-профиль).
- Windows: WinDivert-фильтры per-профиль — отдельный синтаксис,
  тестировать отдельно.

## Сложность / эффект

Per-ASN кэш: внедрено (низкая сложность). Мультистратегия: высокая
сложность, высокий эффект — это архитектура, на которой держится
«подключил — работает» против ТСПУ 2026. Делать после исполнителя
nfqws (T005), не до.
