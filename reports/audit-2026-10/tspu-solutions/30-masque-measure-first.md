# 30. MASQUE: замерить, потом внедрять

Дата: 2026-10-20. T030 (High) из `TSPU-ANALYSIS.md`. Источники:
`tspu-analysis/46-masque-blocks.md` (P46-1…10), `reports/web-research/28-masque-adoption.md`.
Статус: спека (крупное). Принцип задачи: **полевые замеры → stage-gates → только потом код**.
Кода нет — сознательно: без замеров (P46-1) любые заявления о stealth MASQUE — спекуляция.

## 1. Проблема

- Ни GFW, ни ТСПУ не выделяют MASQUE как цель — для цензора это «ещё один QUIC/HTTP3»
  (отчёт 46, §1). Ценность не в MASQUE-over-QUIC (наследует все QUIC-блокировки), а в
  **MASQUE-over-HTTP/2 (TCP) + CONNECT-IP** (RFC 9484, полноценный L3-туннель).
- Полевых данных «ТСПУ vs MASQUE-сессия» нет ни у кого (отчёт 46, §5.1). Внедрять
  вслепую — строить на вере.
- Ранняя постановка «MASQUE как транспорт VLESS» технически неточна (см. §2) —
  спека фиксирует корректную модель до написания кода.

## 2. Коррекция модели: MASQUE — протокол/endpoint, не транспорт VLESS

Проверка по движкам (октябрь 2026):

- **sing-box 1.15.0-alpha.7**: «MASQUE client and server support» — это **endpoints**
  (CONNECT-IP, IP-проксирование поверх HTTP/1.1–3), не stream-транспорт для outbounds.
- **Xray-core**: `proxy/masque`, `infra/conf/masque.go` — MASQUE как **inbound/outbound-протокол**,
  не как `streamSettings.network`. VLESS поверх «transport: masque» в Xray не существует.
- **mihomo ≥1.19.32**: `masque` как тип outbound-прокси (релизные заметки).

Вывод для sora: MASQUE моделируется как **отдельный протокол** (уровень endpoint,
как WireGuard в sing-box: `endpoints`, не `outbounds`), а «VLESS поверх MASQUE» —
как **композиция через proxy chains** (sora уже умеет `Via`/`dialer_proxy`, F8):
VLESS-outbound, диаллящий через MASQUE-endpoint. Ноль нового транспортного кода,
честная архитектура. Спека 07-naive-masque.md (прошлый пучок) фиксировала то же —
здесь закрепляется как решение T030.

Следствие для gating: sora шиппит sing-box-lx 1.14.3 (engines.lock) — MASQUE-endpoints
нужен 1.15+. Внедрение заблокировано до стабилизации 1.15 в поставке sora; Xray-ветка —
до подтверждения версии с `proxy/masque` в engines.lock.

## 3. Stage 0 — полевые замеры (обязательно до кода)

P46-1. Без этого — никаких заявлений о stealth.

- **Стенд:** MASQUE-endpoint'ы (H3 и H2 отдельно) на «чистом» домене с высоким
  collateral damage; сервер неотличим от обычного веб-сервера (405 на неудачную
  аутентификацию — штатный anti-probing дизайн MASQUE).
- **Вантеджи:** 3+ точки в РФ — мобильные (большая тройка) + фиксированные,
  обязательно Сибирь/ДФО (можно переиспользовать опорную сеть T014).
- **Сценарии:** долгоживущие сессии с дейтаграммным трафиком vs обычный браузинг
  к тому же домену; отдельно H3-сессии, отдельно H2-сессии.
- **Метрики:** дропы/stalling/троттлинг по времени; срабатывание residual-бана 420 с;
  сравнение с baseline (обычный HTTPS к тому же домену в тот же час).
- **Серии 10–15 мин** (двухстадийность, методика T041) — короткие сессии дадут
  false negative «всё чисто».
- **Артефакты:** pcap'ы, временные ряды, вердикт по каждому вантеджу. Хранить как
  baseline для регрессионных тестов релизов (связка с T027 «стенд прокси цензора»).

## 4. Stage-gates: условия перехода к внедрению

| Gate | Условие | Иначе |
|---|---|---|
| G1 | H2-MASQUE к чистому домену живёт 24ч+ на всех вантеджах без дропов | не внедрять как транспорт; только R&D |
| G2 | H3-MASQUE деградирует только там, где деградирует весь QUIC (нет *целевого* детекта MASQUE) | если есть целевой детект — редизайн, не шиппинг |
| G3 | Поведенческий профиль (долгая ровная сессия) не триггерит дроп за 7 дней | иначе — сначала поведенческая маскировка (§6), потом код |
| G4 | TCP-in-TCP деградация CONNECT-IP-over-H2 измерена и приемлема для интерактива | иначе H2-режим — только для бровзинга/фонового |

Провал любого gate — не «отложить», а «вернуться к замерам с изменённым дизайном».
Внедрение без G1–G4 — нарушение принципа задачи.

## 5. План внедрения (после gates)

Приоритет — **MASQUE-over-HTTP/2 (TCP) + CONNECT-IP** (RFC 9484):

1. **Клиент:** MASQUE-endpoint в sing-box-конфиге (тип `masque`, CONNECT-IP);
   TUN на клиенте (CONNECT-IP — L3, нужны привилегии — как у WireGuard-endpoint'а,
   уже есть прецедент в рендере).
2. **Автофолбэк H3→H2 с сохранением сессии** (P46-3): Happy Eyeballs — старт H3 и H2
   параллельно; при деградации UDP — перепривязка CONNECT-контекста на TCP без
   разрыва туннеля. Continuous path-quality monitor (RTT/loss/jitter по сессии,
   P46-10) → авто-переключение H3↔H2 + сигнал в UI «сеть режет UDP».
3. **Probe-resistant сервер** (P46-4): неотличимость от веб-сервера, 405 на
   неавторизованные, отсутствие MASQUE-специфичных ошибок, rate-limit на зонды;
   отдельный пентест active-probing'ом (ср. отчёт 19).
4. **QUIC-фингерпринт стека** (P46-6): для H3-режима — SNI-slicing обязателен
   (quic-go ≥0.52.0, pcap-acceptance против эмулятора цензора); сверка отпечатка
   quic-go с Chrome/Firefox (JA4-аналог для QUIC).
5. **Поведенческая маскировка** (P46-7): QUIC padding, variable keepalive, фоновые
   GET к тому же домену («декойный» веб-трафик), jitter таймингов. Измеримый
   критерий: сдвиг собственного ML-классификатора (T027).
6. **Стратегия фронтов** (P46-8): пул доменов с высоким collateral damage, ротация,
   мониторинг SNI в блоклистах; ECH — только там, где не заблокирован как класс
  (в RU — нет, см. спеку 38).

Что НЕ внедрять: MASQUE-over-H3 как основной транспорт для RU/CN (наследует
QUIC-цензуру); позиционирование «недетектируемый» (поведенческий детект остаётся).

## 6. Честные ограничения (из отчёта 46, §4)

- MASQUE-over-H3 в RU/CN бессмыслен без SNI-slicing и чистого домена — QUIC Initial
  декодируется обеими системами.
- Поведенческий детект (долгая ровная bidirectional-сессия) — главный внешний маркер;
  паддинг — частичная митигация, не решение.
- Весь stealth держится на домене/IP с collateral damage — та же игра, что Reality и
  fronting; MASQUE не отменяет задачу фронтов.
- TCP-фолбэк = TCP-over-TCP meltdown для туннелируемого TCP (gate G4).
- iOS: MASQUE в публичных NetworkExtension API — частично; вероятно, свой Go-core
  через gomobile, без приватных API.
- Apple Private Relay (крупнейшее внедрение MASQUE) самоотключён в RU/CN/BY/KZ —
  прецедент: регуляторное давление бьёт по endpoint'ам, не по протоколу.

## 7. Интерфейсы с другими T-ID

- T014: опорные вантеджи — общие; риск-скор MASQUE появится в матрице только после G1–G4.
- T027: стенд «прокси цензора» — потребитель baseline-замеров §3.
- T038: QUICv2-canary — смежный мониторинг (QUIC-парсер цензора влияет на H3-режим).
- T006 (probe-resistant fallback): серверные требования §5.3 — тот же класс.
- T009 (XHTTP в sing-box): архитектурный родственник — оба про «HTTPS-маскировку»;
  не дублировать, сравнивать в одном ревю.

## 8. Статус

- **Статус:** спека готова; следующий шаг — Stage 0 (полевые замеры), не код.
- **Сложность:** высокая (стенд, вантеджи, pcap-анализ; затем клиент+сервер+фолбэк).
  Замеры — месяцы; внедрение — кварталы после gates.
- **Эффект:** высокий при проходе gates — стандартизированный «прокси за сайтом»
  с UDP/L3 внутри одного соединения и probe-resistance из коробки; ниша, где
  конкуренты (13 продуктов) отсутствуют.
- **Риски:** замеры покажут целевой детект (→ редизайн); sing-box 1.15 не
  стабилизируется (→ Xray/mihomo-ветка или свой клиент на quic-go);
  поведенческий ML закроет окно (→ маскировка §5.5 как обязательная часть, не опция).
- **Чего НЕ делать:** шиппить до G1–G4; называть «невидимым»; строить H3-first
  для RU.
