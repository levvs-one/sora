# T024 — ECH: честная стратегия

## Проблема
ECH жив (RFC 9848, Cloudflare по дефолту), но sora его не использует.
Соблазн — включить «для галочки» и продать как «невидимость». Реальность из
отчёта 13: блокируют не протокол, а пару (outer SNI `cloudflare-ech.com` +
расширение ECH); GREASE ECH сам по себе проходит. ECHConfig приезжает по DNS
(HTTPS RR) — без зашифрованного DNS его подменят. ECH+REALITY несовместимы.
RUSTSEC-2026-0347: rustls тёк на ECH reject.

## Что уже сделано (коммит)
`cb87078` — `core/engine/validate.go`: fail-closed валидация ECH:
- ECH + REALITY → reject (несовместимы);
- ECH без TLS → reject;
- `QueryServerName`, не отрендеренный ни одним движком → reject;
- ECH без пиннутого конфига требует зашифрованный DNS-транспорт в плане,
  иначе reject (конфиг из открытого DNS = подмена).
8 тестов, весь engine-suite зелёный.

## Решение (остаток работы)

### 1. Outer SNI — не cloudflare-ech.com
- Стратегия outer SNI: реальный посещаемый домен на том же ECH-провайдере
  (fronting-подобное поведение без fronting'а как сервиса), ротация из пула.
  `cloudflare-ech.com` как outer — в чёрном списке: пара
  (этот SNI + ECH-расширение) — известная сигнатура блокировки.
- Пул outer SNI — в конфиге плана, обновляемый (не хардкод).

### 2. Защищённый канал ECHConfig
- ECHConfig только из: (а) зашифрованного DNS (DoH по IP-литералу, T010);
  (б) пиннутого конфига из плана/подписки. Никогда из plain DNS.
- Кэш ECHConfig с TTL; при reject — повторный fetch по защищённому каналу
  перед fallback (исключаем отравленный кэш).

### 3. Корректный fallback при reject
- ECH reject → пробуем: свежий ECHConfig → другой outer SNI → fallback на
  обычный TLS (с явной пометкой в журнале «ECH отклонён, SNI видим»).
  Никакого бесконечного ретрая ECH (палит паттерн).
- Метрика reject'ов → в матрицу ТСПУ (если reject'ы массовые — провайдер
  режет ECH, стратегия меняется глобально).

### 4. Threat model в UI — честно
- Переключатель «ECH» с подписью: «Скрывает имя сайта (SNI) от провайдера.
  **Не скрывает**: IP сервера, сам факт VPN, объём трафика».
- Вклад в privacy score — низкий (SNI — лишь один из сигналов).
- ECH — opt-in, не дефолт: выгода спорна там, где ТСПУ режет по IP/паттернам.

## Сложность
Средняя. Валидация готова. Рендер outer-SNI-пула в sing-box/mihomo (~100
строк), fetch ECHConfig по DoH (~80 строк), UI-переключатель (Dart).

## Эффект
Закрывает SNI-фильтрацию там, где она — единственный рубеж (часть
провайдеров, KZ). Не панацея, но дешёвый дополнительный слой.

## Риски
- Неправильный outer SNI хуже, чем никакого ECH (известная сигнатура).
- ECH-флуд reject'ами может триггерить rate-limit у провайдера.

## Честные ограничения
- **ECH скрывает SNI, не IP.** Против IP-блоков и поведенческого анализа —
  бесполезен. В UI это написано прямо, не мелким шрифтом.
- ECH не «невидимость» и не замена обфускации; в privacy score — низкий вес.
- Без зашифрованного DNS (T010) ECHConfig — подделка: связка обязательна,
  поодиночке не включается (валидация это гарантирует).
- ECH+REALITY не комбинируются — выбор одного.
