# 44. Событийный троттлинг: канал сигналов

Дата: 2026-10-20. T044 (Medium) из `TSPU-ANALYSIS.md`. Источники:
`tspu-analysis/40-time-of-day-throttling.md` (P40-1…7), вывод №6 («ECH мёртв» — контекст),
OONI throttling-дизайн. Статус: спека (канал сигналов + клиентское поведение, не
дифференциальный замер как таковой).

## 1. Проблема

Главный вывод отчёта 40: **подтверждённых случаев сознательного троттлинга «по
расписанию» в РФ нет**. Наблюдаемая суточная вариативность — конгестия деградировавших
направлений + **событийный троттлинг** (БПЛА-отключения 2025, протесты, 9 мая).
Проектировать надо под событийный, а не суточный троттлинг — а канала сигналов
о событиях у sora нет (P40-4): детекция сегодня только локальная и постфактум.

Три механизма, которые нельзя смешивать (отчёт 40, §3):

- **а) Сознательный policer/shaper на ТСПУ** — сходимость к фиксированному плато
  (130–150 кбит/с Twitter, 128 кбит/с YouTube), триггер — SNI. Постоянен после включения.
- **б) Конгестия** — высокая дисперсия, возможно с суточной корреляцией (OONI-дизайн:
  суточная корреляция = признак *отсутствия* намеренного шейпера).
- **в) Событийный троттлинг/шатдаун** — те же механизмы, триггер — команда/событие.
  Для VPN-клиента — главный источник внезапной деградации «по времени».

Канал сигналов T044 — про (в) с различением от (а) и (б). Дифференциальный замер
throughput (P40-1) — зона T018; сюда T018 отдаёт классифицированные исходы,
а не сырые замеры.

## 2. Архитектура канала сигналов

```
Источники ──► нормализация ──► классификация ──► подписанный фид ──► клиент
   │               │                 │                  │               │
   ▼               ▼                 ▼                  ▼               ▼
 OONI API/MAT   дедуплика,      policer /          CDN, TTL        event-mode
 DPIdetector    привязка        конгестия /        минуты          (§5)
 vpn-status     к ASN/времени,   событие            подпись         журнал
 новостные      вес источника                        sora          пользователя
 ленты
 opt-in маяки
 парка (ниже)
 локальные
 эвристики
```

**Источники и их вес:**

| Источник | Сигнал | Вес | Задержка |
|---|---|---|---|
| OONI MAT/API: всплеск anomaly/confirmed по RU-ASN | давление на сеть | высокий | часы |
| DPIdetector / аналоги | пространственно-временная неоднородность | средний | часы–дни |
| vpn-status.site (голосования по операторам) | пользовательские жалобы | средний | минуты–часы |
| Новостные ленты / соцсети (БПЛА-угрозы, протесты, даты) | событие-триггер | средний | минуты |
| Opt-in маяки парка sora (§3) | синхронный провал в ASN | высокий (при N) | минуты |
| Локальная эвристика клиента (§4) | резкий синхронный провал направлений | низкий сам по себе | мгновенно |

**Правило двух независимых источников** (как в спеке 25): событие объявляется при
подтверждении из двух плеч (напр. маяки парка + новостная лента, или OONI + локальные
эвристики). Один источник — максимум «подозрение», не событие.

## 3. Opt-in маяки парка (crowd-сигналы без телеметрии)

Позиция продукта: zero hidden telemetry. Значит:

- Маяки — строго opt-in (тот же тумблер, что в спеке 14, §6; один consent —
  два потребителя).
- Маяк = агрегат, не событие: `{asn, hour, transports_ok: n, transports_degraded: m,
  control_ok: bool}`. Без идентификаторов пользователя, серверов, сессий, геоточности
  ниже ASN.
- Клиент отправляет маяк не чаще раза в 15 мин и только при изменении картины.
  Сырые замеры/тайминги/логи — никогда.
- Серверная агрегация: синхронный провал `transports_degraded` у ≥K независимых
  маяков одного ASN за 30 мин при живом `control_ok` = кандидат в событие.
  K зависит от размера парка (старт: K=5, пересмотр по данным).
- Анти-игры: медианы, а не суммы; маяки без `control_ok` (контрольный хост тоже
  лёг) классифицируются как «лежит сегмент», не как «режут VPN» — иначе конгестия
  будет выглядеть как событие.

## 4. Локальные эвристики клиента (без сети — первый рубеж)

До прихода фида клиент детектирует сам, но честно (низкая уверенность):

- **Синхронный провал:** несколько направлений/транспортов деградируют одновременно
  в одном ASN, контрольный хост жив → «похоже на событие» (не «событие»).
- **Плато vs дисперсия** (OONI-дизайн): замер пары «цель vs контроль» (P40-1/T018);
  сходимость к фиксированному плато в любое время суток = policer (механизм а);
  дисперсия с вечерним провалом на обоих хостах = конгестия (механизм б).
- **История:** вердикты `core/censor` + локальная история (CENSORSHIP-METER-SPEC P1.3)
  в разрезе (ASN, час) — внезапное отклонение от профиля сильнее, чем абсолютное
  значение.
- Локальный вердикт — только для локальных действий (переключение транспорта);
  в общий канал уходит только через opt-in маяки §3.

## 5. Поведение клиента при событии (event-mode)

- Источник истины — подписанный фид; локальная эвристика — только до его прихода.
- При событии: консервативный выбор транспорта (по матрице T014, min risk),
  учащённый re-probe, отмена «ночного окна» как эвристики (отчёт 40, §4.1 —
  ставка на «ночью слабее» = проектирование под слух).
- Фоновые задачи (обновления, E2E-синк): планировщик по измеренной доступности,
  retry с экспоненциальной паузой + джиттер — не «запуск в 3 часа ночи» (P40-5).
- UX: честный статус «зафиксированы ограничения в вашей сети (событие), подбираем
  обход» + различение «троттлится VPN» vs «деградирует весь сегмент» (P40-7):
  разные советы пользователю.
- Снятие event-mode — только по сигналам отбоя (два независимых источника),
  не по таймеру и не по часам.

## 6. Формат фида и распространение

- Фид: `{event_id, asn_list|"RU", kind: throttle|shutdown|wave, confidence,
  sources: [...], started_at, updated_at, expected_end|null}`. Подпись sora,
  доставка через CDN, TTL — минуты (события — быстрые).
- Версионирование и отзыв: событие может быть отозвано (ложная тревога) —
  клиент обязан обработать отзыв так же, как событие.
- Ложные тревоги — главный репутационный риск: порог объявления высокий,
  в UX — формулировки вероятностные («зафиксированы», не «цензура доказана»).

## 7. Честные ограничения

- Атрибуция «событие vs конгестия» принципиально трудна: часть ночных отключений
  2025 пользователи описывали как «по расписанию» — без сверки с лентой событий
  будет ложная атрибуция (отчёт 40, §5.6).
- Нет полевых измерений с часовым разрешением по RU за 2024–2026 (отчёт 40, §5.1):
  baseline для «нормального» суточного профиля строится с нуля — первые месяцы
  пороги будут грубыми.
- Умеет ли контур ТСПУ политики по расписанию — неизвестно; канал не должен
  искать расписание там, где его нет.
- Поведение ТСПУ под пиковой нагрузкой (деградация inline-DPI в прайм-тайм) —
  гипотеза без измерений; не классифицировать как событие без второго источника.

## 8. Интерфейсы с другими T-ID

- T014: OONI-агрегация — источник §2; матрица скоров — baseline для §4.
- T018: дифференциальный замер throughput — поставщик классификации (а)/(б);
  T044 — потребитель, не дубль.
- T025: волны — потребитель событий канала (L2/L3); T044 — транспорт доставки.
- T035/CENSORSHIP-METER-SPEC: локальные вердикты и история — входы §4.
- P40-2 (часовые профили), P40-3 (time-aware выбор), P40-6 (метки часа в замерах) —
  требования к хранилищу и форматам, которые этот канал потребляет; реализация —
  бэклог клиента.

## 9. Статус

- **Статус:** спека готова. Очередность: формат фида + локальные эвристики §4
  (недели–месяц) → opt-in маяки §3 (месяц, нужен consent-UX) → внешние источники §2
  (параллельно, аналитик) → event-mode §5.
- **Сложность:** средняя (канал), высокая (достоверная атрибуция — итеративно).
- **Эффект:** высокий — единственный честный ответ на «вечером VPN медленный»;
  убирает класс ложных диагнозов и неверных действий (смена протокола при конгестии).
- **Риски:** ложные тревоги (митигация — два источника, высокие пороги, отзывы);
  малая плотность маяков на старте (митигация — внешние источники как первичные);
  соблазн искать «расписание» (митигация — §7, отчёт 40).
- **Чего НЕ делать:** «ночное окно» как фичу; объявления событий по одному источнику;
  тихие маяки без consent; смешивание policer/конгестии/события в один «троттлинг».
