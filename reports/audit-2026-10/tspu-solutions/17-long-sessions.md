# 17. Длинные сессии: duration-гигиена

Дата: 2026-10-20. T017 (High), TSPU-ANALYSIS ← P39 (`tspu-analysis/39-long-session-detect.md`).
Статус кода: коммит `[tspu-fix]` T017 `de2b254` — `core/session/rehandshake.go`: `RehandshakePolicy` (дедлайн с джиттером) + `KeepaliveInterval` (±25%), тесты с негативными кейсами. Эта спека — проводка в менеджер сессий и телеметрия.

## 1. Проблема

Прямых замеров «сессия старше N минут → RST» нет нигде, но duration — дешёвая эвристика в связке признаков, а «сибирская» волна уже использует счётчики handshake. Критично: **возраст сессии = now − SYN; keepalive, TLS KeyUpdate и WireGuard rekey его не сбрасывают — только новый handshake**. Регулярный keepalive 25 с — сам по себе фингерпринт. Port hopping для UDP частично решает (новый 4-tuple = новый «первый пакет»), но для TCP-транспортов нужен плановый re-handshake.

## 2. Что уже сделано (коммит de2b254)

| Элемент | Поведение |
|---|---|
| `RehandshakePolicy{MaxAge, Jitter}` | Дедлайн = establishedAt + MaxAge ± uniform(Jitter); Jitter > MaxAge клемпится; нулевая политика = выключено (fail-closed); источник джиттера — session-local `*rand.Rand`, не глобальный |
| `Overdue(now, deadline)` | Проверка дедлайна; нулевой дедлайн никогда не overdue |
| `KeepaliveInterval(base, r)` | base ±25%; неположительный base = 0 (выкл); nil-источник = base без джиттера |

## 3. Проводка в менеджер сессий (Go, бэклог)

1. **Учёт возраста.** `session.Manager` фиксирует `handshakeAt` при установлении транспорта (не при старте приложения, не при resume — resume старого соединения возраст не сбрасывает). Каждое плановое пересоздание транспорта обновляет `handshakeAt`.
2. **Плановый re-handshake.** Воркер менеджера тикает раз в минуту: для сессий с `Overdue(now, deadline)` — graceful пересоздание транспорта (новый handshake, старый держится до готовности нового — без разрыва пользовательского трафика). Дефолт политики: `MaxAge=45m, Jitter=10m` (настраивается; 0 = выкл).
3. **Рандомизированный keepalive.** Все keepalive-интервалы (WG persistent keepalive, внутренние пинги) идут через `KeepaliveInterval`. Дефолт 60 с ±25% вместо 25 с метронома. Значение — per-транспорт, не глобальное.
4. **Port hopping для UDP.** Для hy2/TUIC-сессий старше порога — принудительный hop (смена 4-tuple) как лёгкая форма re-handshake: дешевле полного переподключения, бьёт residual-баны (T008, 420 с).
5. **Запрет re-handshake во время заморозки.** Если `censor`/`probe` сигналит «сибирскую» заморозку (T007) — плановые handshake откладываются до её конца: новые handshake во время заморозки продлевают бан и тратят бюджет.

## 4. Локальная телеметрия обрывов (Go, бэклог)

Журнал сессии (кольцевой буфер, только локально, без отправки): для каждого обрыва — `RST vs timeout vs NAT-timeout`, возраст сессии на момент обрыва, транспорт, ASN/сеть. Агрегаты за 24ч/7д в UI «Здоровье»: «средний возраст обрыва 52 мин, 80% — timeout». Это же — вход для T014 (риск-скор транспортов) и раннее предупреждение волн (T025). Никакой телеметрии наружу без явного opt-in.

## 5. Честные ограничения

1. Re-handshake не делает сессию «невидимой» — он лишь не даёт duration стать тривиальным признаком. Поведенческий анализ длинных туннелей остаётся.
2. Слишком частые re-handshake (MaxAge < ~15 мин) сами становятся признаком («сибирский» счётчик handshake). Дефолт 45 мин — компромисс, не догма.
3. Graceful пересоздание удваивает соединения на секунды — на строгих NAT это может выглядеть как port scan при агрессивных настройках.
4. Keepalive ±25% — не панацея от timing-анализа (см. T026, pcap-харнесс).

## 6. Сложность / эффект / риски

- **Сложность**: средняя. Ядро готово и покрыто тестами; проводка — handshakeAt в менеджере, воркер, graceful пересоздание, журнал.
- **Эффект**: medium-high. Убирает дешёвую эвристику duration и метрономный keepalive — два самых дешёвых признака для цензора.
- **Риски**: re-handshake во время заморозки усугубляет бан (митигация §3.5); слишком агрессивные дефолты → заметность (митигация: консервативный дефолт + настройка).
