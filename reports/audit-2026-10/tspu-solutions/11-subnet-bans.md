# 11. Ковровые баны подсетей: репутация, сегрегация, миграция

Дата: 2026-10-20. Проблема **T011** (Critical, Tier S12; матрица: `reports/TSPU-ANALYSIS.md`).
Тип: спека, инфра/продукт. Кода нет — решения архитектурные и процессные.

## 1. Проблема

ТСПУ банит не отдельные IP, а **подсети целиком** («ковровые» баны /24 и шире): достаточно одному шумному пользователю/серверу засветиться, и умирают все серверы провайдера в префиксе. Следствия для sora как продукта:

- Пользователь не различает «сервер лёг» и «подсеть убита» — тыкает нерабочие серверы, винит клиент.
- Миграция вручную — дни; ТСПУ перебанивает за часы.
- Зависимости от RU-ASN (трафик/управление через российскую юрисдикцию) и от Cloudflare (единая точка сигнатурирования и бана) умножают blast radius.

Ни один из 13 конкурентов из `competitor-analysis.md` не показывает пользователю репутацию подсети и не мигрирует автоматически — это окно для отрыва.

## 2. Репутация серверных подсетей

**Модель данных** (на стороне сервиса подписок/инфры sora, не в клиенте):
- Агрегат: `ASN → префикс (BGP-announced) → /24 (или /48 для v6)`.
- Сигналы на /24: доля успешных handshake за окно (пассивные пробы с RU-вантеджей, §4), жалобы пользователей (кнопка «не работает» с привязкой к серверу), факт бана (все хосты префикса недоступны с ≥2 вантеджей, а с внешних — доступны).
- Скор: `healthy / degraded / dead` + `since`. Деградация — скользящее окно 15 минут (типичное время перебана ТСПУ), не мгновенный флип по одному фейлу.

**В клиенте** (Dart, бэклог): индикатор в карточке сервера — «подсеть: в порядке / деградирует / мертва», без технических деталей (пользователю не нужен номер ASN). При `dead` — сервер уходит вниз списка/в серый, автоподключение его пропускает.

**Честно**: репутация — лаггинг-индикатор; первый бан всегда бьёт до того, как скор обновился. Это не предсказание, а быстрая констатация.

## 3. Сегрегация инфраструктуры

- **Никаких shared префиксов** между юзерскими VPN-нодами и чем-либо ещё (сайты, API, панели). Один скомпрометированный сосед по /24 топит всех.
- **Одна нода — один /24-бакет риска**: не сажать 50 серверов в один /24 у одного хостера. Распределение: N хостеров × M префиксов, лимит плотности (например, ≤8 нод на /24).
- **Разделение плоскостей**: управляющий трафик (API подписок, обновления) — отдельные домены/IP от трафика VPN; бан юзерской подсети не должен убивать обновления клиента.
- **IPv6**: отдельные /48 на ноду там, где доступно — баны v6 пока реже и уже.

## 4. Автоматизация миграции (часы, не дни)

Целевой SLA: от детекта смерти подсети до пересадки активных пользователей — **< 4 часов**, без ручной работы.

1. **Детект** (§2): `dead` по ≥2 RU-вантеджам → триггер.
2. **Подготовка**: пул «тёплых» нод в чистых префиксах (прогретые заранее: подняты, замерены, в подписке помечены `standby`). Холодный подъём с нуля в SLA не укладывается — держать резерв 20–30%.
3. **Пересадка**: сервер подписки помечает мёртвые ноды `retired`, продвигает `standby → active`; клиент на следующем обновлении подписки (или пуше, если есть канал) получает новый список. Активные сессии не рвутся принудительно — доезжают на старой ноде, новые коннекты идут на новую.
4. **DNS/домены**: фронтовые домены для XHTTP/WS — на отдельных IP, ротация через DNS с коротким TTL (60–120с) на время миграции.
5. **Пост-мортем**: префикс уходит в карантин на 30 дней (баны иногда снимают), потом — повторная проба малой долей трафика (канарейка 5%), не сразу всем.

Ручной override всегда доступен (инцидент-менеджмент), но дефолтный путь — автоматический.

## 5. Фид статусов с RU-вантеджей

- **Вантеджи**: ≥3 точки внутри RU на разных ASN (не свои же серверы — независимость измерения). Пробы: TCP-handshake + TLS ClientHello с SNI ноды + полный VLESS-handshake (без авторизации — только достижимость).
- **Каденс**: базовый — раз в 5 минут; при деградации — раз в минуту до вердикта.
- **Фид для клиента**: лёгкий поллинг статуса префиксов (не самих проб) — раз в 15 минут, кэшируется; в офлайне — последний известный статус с меткой времени.
- **Анти-абьюз**: фид подписывается (minisign, как каталог расширений); клиент не доверяет неподписанному.
- **Приватность**: вантеджи меряют только свои ноды; никаких замеров пользовательских соединений.

## 6. Отказ от RU-ASN и Cloudflare-зависимостей

- **Хостинг**: ноды — только вне RU-ASN (см. также спеку 34). Биллинг/панели — тем более.
- **Cloudflare**: не использовать как фронтьер для VPN-трафика (единая сигнатура, единый выключатель; CF IP-баны бьют по всем клиентам разом). Допустимо для статики сайта/доков, но не для транспорта.
- **DNS**: NS для фронтовых доменов — вне CF; DNSSEC включён.
- **Честно**: «вне RU-ASN» ≠ «небанится» — ТСПУ банит и зарубежные префиксы; речь о снижении коррелированного риска, а не о неуязвимости.

## 7. Сложность / эффект / риски

- **Сложность**: высокая. Тёплый резерв 20–30% — прямые деньги; вантеджи — операционка; автоматика миграции — самый сложный кусок (состояние, гонки, откат).
- **Эффект**: главный продуктовый дифференциатор против всех 13 конкурентов: sora переживает ковровый бан за часы без участия пользователя, остальные — за дни с ручной вознёй.
- **Риски**: ложноположительный `dead` (флап вантеджа) → ненужная миграция; mitigations — кворум ≥2 вантеджей + гистерезис. Утечка списка нод через фид — отдавать только статусы префиксов, не инвентарь. Автоматика без kill-switch — обязателен ручной стоп.
