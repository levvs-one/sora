# T042 — Подписная ссылка как единица устойчивости: атомарные обновления при волнах

Статус: код — в ветке `bugfix/audit-2026-10-19` (коммит `[tspu-fix] T042`,
см. «Что сделано»); триггерная обвязка (UI/RPC/детектор волн) — ниже.

## Проблема

При волне блокировок провайдер ротирует эндпоинты (IP, домены, SNI),
а клиент сидит на мёртвом списке до следующего планового обновления
(`minUpdateInterval = 1h`, `defaultUpdateInterval = 24h`). Подписка как
единица устойчивости не работает: обновление есть, а «досрочного»
обновления по сигналу беды — нет.

## Что уже было (аудит)

Атомарность уже есть и трогать её не надо:
- `applyUpdateLocked` → `persistLocked` → `secrets.Apply(puts, deletes)`
  атомарно: список серверов заменяется целиком, «наполовину обновлённого»
  состояния не бывает;
- при проваленном fetch сохраняется last-good (`fetchLocked` не трогает
  `lists[id]` при ошибке), пользовательские правки переживают refresh
  через `overrides`.

Не хватало только досрочного запуска.

## Что сделано (Go-ядро)

`core/control/subscriptions_expedite.go` + точечные правки
`core/control/subscriptions.go`:

- `ExpediteUpdate(id string) bool` — планирует ближайшее обновление «как
  можно скорее» (через `poke()` планировщика). Возвращает `false`, если:
  подписка неизвестна, fetch уже идёт (никаких перекрывающихся fetch),
  с прошлого expedite прошло меньше `expediteCooldown = 15 мин`.
- `nextUpdate` учитывает pending expedite через `expeditedDue`:
  запрошенное обновление бьёт регулярное расписание (работает даже при
  выключенном AutoUpdate — явный сигнал важнее расписания).
- После отработки refresh pending-маркер стирается, а `expediteLast`
  продолжает держать cooldown — волна не превращается в fetch-loop
  против провайдера.
- Состояние expedite — только in-memory: рестарт откатывается к
  регулярному расписанию (консервативно).

Тесты `core/control/subscriptions_expedite_test.go` (на `bookServer`+`panel`
харнессе, с подменённым `b.now`):
- `TestExpediteUpdate` — без expedite следующее обновление через ~24 ч;
  первый expedite → true и «due now»; повторный и чужой id → false;
  после отработки refresh маркер стёрт, cooldown держит; после
  `expediteCooldown` — снова true.
- `TestExpediteUpdateWhileFetching` — expedite во время идущего fetch →
  false (fetch блокируется на `release`-канале панели).

## Триггерная обвязка (не в ядре — спека)

Ядро даёт примитив; сигналы — снаружи:
1. **Сигнал смерти активного сервера** (health-check сессии): сервер из
   подписки X умер → `ExpediteUpdate(X)` — провайдер, вероятно, уже
   ротировал список.
2. **Ручная кнопка** «Обновить подписку сейчас» в UI подписок — должна звать
   `ExpediteUpdate`, а не прямой `refresh` (cooldown защищает провайдера).
3. **Детектор волн** (T025, отдельная задача): при коррелированных смертях
   серверов — expedite всех подписок разом.

RPC: добавить `ExpediteSubscriptionUpdate(id)` в control API; UI показывает
«обновление через N» с пометкой «досрочное» и время до конца cooldown.

## Честные ограничения

- Expedite не создаёт новые серверы — он лишь раньше забирает то, что уже
  выложил провайдер. Если провайдер не ротировал список, expedite ничего
  не чинит (и именно поэтому cooldown 15 минут, а не 15 секунд).
- Подписка остаётся точкой отказа: один URL, один провайдер. Устойчивость
  «по-настоящему» — это несколько подписок + ручные серверы; expedite
  лишь сокращает окно неработоспособности одной.
- In-memory состояние: после рестарта приложения только что запрошенный
  expedite теряется — приемлемо, т.к. регулярное расписание сохраняется.
