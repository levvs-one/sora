# 19. IPv6: kill-switch с перепроверкой, leak-тест, защита от RA/DHCP-инъекций

Дата: 2026-10-20. T019 (High), TSPU-ANALYSIS ← P35 (`tspu-analysis/35-ipv6-vectors.md`).
Статус: спека полностью (Go-часть — `core/guard`, который правит другой отдел; координация обязательна).

## 1. Проблема

Асимметрия IPv6 — в пользу пользователя (часть блокировок IPv4-only: кейс tuta.com), но **утечки IPv6 — главный риск деанона**: 41% consumer-VPN проваливают защиту; CVE-2025-59691 показывает, что «блокировка IPv6» должна переживать reconnect/resume — проверять надо после каждого сетевого события, а не только при connect. Отдельный вектор — TunnelVision-класс: инъекция RA / DHCP option 121, уводящая трафик мимо туннеля.

## 2. Решение

### 2.1. Firewall-level IPv6-блок с перепроверкой после каждого reconnect

- Блок — на уровне firewall (iptables/nftables/pf/WFP), а не отключением стека: на Windows отключение IPv6 через реестр ломает функции ОС; корректный путь — drop, не disable.
- **Перепроверка-триггеры**: каждое событие `networkWatch` (смена fingerprint сети, resume из сна, reconnect, смена default route) → `guard` переприменяет IPv6-правила и верифицирует их (пробный пакет / чтение таблицы). Результат — в журнал сессии; провал верификации = kill-switch с уведомлением, а не тихий fallback.
- Проверка должна быть быстрой (<1 с) и идемпотентной: переприменение тех же правил — no-op.

### 2.2. Встроенный leak-тест

- После каждого (пере)подключения и периодически (раз в 15 мин, джиттер) — активная проверка: DNS AAAA через туннель + HTTP-запрос к dual-stack канарейке с эхо IP. Если ответ пришёл с реального IPv6 клиента — утечка: рвём соединение, показываем красный баннер, пишем в журнал.
- Канарейка — свой endpoint sora (не сторонний сервис с трекингом). Тест идёт внутри туннеля, не мимо.
- На Android: `VpnService.Builder.allowBypass()` и split-tunnel исключения могут открывать IPv6 мимо туннеля независимо от настроек — leak-тест обязан покрывать и этот путь; при обнаружении — явное предупреждение «split-tunnel пропускает IPv6».

### 2.3. Защита от DHCP option 121 / RA-инъекции

- Мониторинг таблицы маршрутов: появление more-specific маршрутов (option 121) или RA с флагом «default route», указывающих не на туннель, во время активной сессии — триггер: (а) алерт пользователю, (б) опционально — переустановка маршрутов туннеля поверх, (в) запись в журнал для T014.
- Детерминированный Happy Eyeballs: при dual-stack — предсказуемый порядок попыток (сначала туннельный IPv6, затем IPv4), без гонок, которые могут увести handshake мимо туннеля. Таймауты короткие и фиксированные, не адаптивные (адаптивность — источник недетерминизма).

### 2.4. Dual-stack как опция (не дефолт)

Корректный IPv6 через туннель (ULA/временные адреса RFC 4941, AAAA от резолвера внутри туннеля, IPv6-egress сервера) — отдельная настройка «IPv6 через VPN». Дефолт — блок с перепроверкой (§2.1): безопаснее для большинства, у кого нет нужды в IPv6-ресурсах.

## 3. UI (Dart, бэклог)

- Переключатель «IPv6»: Блокировать (дефолт) / Через VPN. Под ним — статус последней проверки («проверено 12:03, утечек нет») и кнопка «Проверить сейчас».
- Красный баннер при провале верификации/leak-теста с кнопкой «Переподключить».

## 4. Честные ограничения

1. Firewall-блок не защищает от вредоносного локального ПО с правами выше — threat model: цензор и сеть, не rootkit.
2. На некоторых Android-прошивках OEM режет `VpnService` API — перепроверка может быть недоступна; тогда честный статус «не могу проверить», а не зелёная галочка.
3. Dual-stack VPN умирает вместе с IPv4, если цензор начнёт банить IPv6-префиксы хостеров крупными кусками — диверсификация egress обязательна (T011).
4. RA-мониторинг на мобильных сетях шумит (операторы шлют RA регулярно) — нужны allow-list паттерны per-ASN, иначе ложные алерты.

## 5. Сложность / эффект / риски

- **Сложность**: высокая. Per-OS firewall-код (уже частично в `core/guard` — координация), RA/DHCP-мониторинг, канарейка, UI. Верификация после каждого события — аккуратная идемпотентность.
- **Эффект**: high. Деанон через IPv6 — худший исход для VPN-клиента; 41% конкурентов проваливают.
- **Риски**: ложные срабатывания kill-switch на шумных сетях (митигация: верификация перед разрывом, не после одного события); сломанный IPv6-стек Windows при грубом disable (митигация: только firewall-drop).
