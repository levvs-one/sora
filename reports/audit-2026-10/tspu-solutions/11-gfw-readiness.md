# 11. GFW-готовность: профиль «белого списка», шейпинг, handshake, анти-реплей

Дата: 2026-10-20. Пучок: T032 (High, TSPU-ANALYSIS.md ← P37-1…15).
Статус: спека (крупное). Связано: 09 (pcap-харнесс — измерение), 10 (стенд — проверка), 02 (JA4/uTLS — часть профиля).

## 1. Проблема

- GFW (и, по тренду, ТСПУ) движется к модели «белый список протоколов»: проходит только то, что выглядит как обычный HTTPS-браузинг; остальное режется или уходит в active probing.
- sora сегодня оптимизирован под «не палиться как прокси», но не под «выглядеть как браузер с первой секунды»: шейпинга первых 16 КБ нет, handshake'и некоторых транспортов (Hysteria2, TUIC) — кастомные UDP, SNI-консистентность не проверяется, анти-реплея нет.
- Нет плана на день, когда «всё, кроме браузерного TLS» начнёт резаться по умолчанию.

## 2. Профиль «браузинг» (целевой)

Каждый исходящий транспорт в hostile-режиме обязан укладываться в профиль обычного HTTPS-браузинга:

1. **TCP/443 first**: первый SYN — на 443/TCP. UDP-транспорты (Hysteria2, TUIC, QUIC) — только после успешной TCP-фазы или явного выбора пользователя (с предупреждением).
2. **Первые 16 КБ под профиль**: размеры пакетов, pacing, направления — внутри коридора baseline Chrome (см. 09 §2.4). Mimicry-padding вместо random.
3. **Handshake**: только TLS 1.3 с актуальным uTLS (02); никаких кастомных UDP-handshake'ов в первые секунды сессии.
4. **SNI-консистентность**: SNI == HTTP Host == домен из ALPS/ALPN-контекста; SNI резолвится в IP назначения (anti-mismatch); SNI — из пула «живых» доменов с валидным HTTPS (не парковочных, не свежезарегистрированных).
5. **Поведение**: разумные интервалы между «загрузками» (не сплошной поток с первой секунды — браузер грузит страницу чанками); keepalive с джиттером, не метроном.
6. **Анти-реплей**: каждая сессия — свежие эфемерные ключи/токены; повтор ClientHello/пакетов не должен давать серверу повода ответить одинаково дважды (защита от replay-probing цензора).

## 3. Пробоустойчивый handshake

- Серверная сторона (one-click, T006): любой inbound обязан иметь fallback на реальный сайт (probe-resistant): активный пробер получает валидный HTTPS-ответ, а не тишину/прокси-ошибку.
- Клиентская сторона: при подозрении на probing (повторные handshake'и без трафика, HRR-аномалии) — backoff и смена профиля, не долбёжка.
- Reality dest-чеклист (уже в кодовой базе как идея): TLS 1.3 + H2 + крупный домен, не Cloudflare; spiderX включён.

## 4. Симулятор цензора в CI

Расширение стенда 10 отдельным пресетом `gfw-strict`:
- Детекторы: «не TLS 1.3 на 443 в первые 3 секунды» → fail; «SNI mismatch» → fail; «первые 16 КБ вне браузерного коридора» → fail; «кастомный UDP-handshake» → fail.
- Каждый транспорт sora прогоняется в двух режимах: `normal` и `hostile` (профиль §2). В `hostile` провал любого детектора — блокер релиза.
- Отдельный subtest: replay-probing — повторная отправка записанного ClientHello не должна давать отличающийся ответ сервера.

## 5. План на «белый список протоколов»

Если/когда цензор включает default-deny (T004):

1. **Фаза 0 (сейчас)**: все транспорты имеют `hostile`-режим, соответствующий §2. Без него транспорт помечается в UI «не для строгой цензуры».
2. **Фаза 1 (детект)**: рантайм-детектор whitelist-режима (T004): характерные признаки — режется всё кроме 443/TLS, даже «чистые» handshake'и; триггер — новый Kind в `censor` (T003).
3. **Фаза 2 (реакция)**: автопереключение всех outbound'ов в `hostile`-профиль; TCP/443-first; ротация SNI из пула; пользователь уведомляется («сеть в режиме белого списка, включён строгий профиль»).
4. **Фаза 3 (долгосрочно)**: полноценная поведенческая мимикрия (T016) — уже не «похоже на TLS», а «похоже на пользователя»: чанки, паузы, multiplexing-паттерны HTTP/2/3.

## 6. Честные ограничения

1. **Профиль «браузинг» — это тоже фингерпринт.** Идеальная мимикрия недостижима; цель — поднять цену детекта, а не обнулить её. Цензор с ML на NetFlow всё равно видит отличия на длинных сессиях (см. 10 §3).
2. **Шейпинг стоит пропускной способности и задержки**: паддинг и pacing режут скорость. `hostile`-режим — opt-out по умолчанию вне цензуры, opt-in (авто) при детекте.
3. **UDP-транспорты в hostile-режиме деградируют**: Hysteria2/TUIC за TCP-обёрткой теряют смысл; честно — в строгом whitelist их место занимает VLESS+REALITY+TCP.
4. **Анти-реплей не защищает от активного MITM**: если цензор терминирует TLS — это уже другая угроза (T028).
5. **SNI-консистентность требует живого пула доменов**: пул протухает (домены умирают, меняют IP); нужен процесс обновления (research-watch, владелец).

## 7. Сложность / эффект / риски

- **Сложность**: высокая. Шейпинг первых 16 КБ — средняя (паддинг/pacing в транспортах); hostile-режим per-transport — средняя; симулятор в CI — средняя (на базе 10); whitelist-детектор — высокая (T004); поведенческая мимикрия — очень высокая (T016).
- **Эффект**: high. Это единственный архитектурный ответ на тренд «белых списков»; без него sora в один день может просто перестать работать в RU/CN целиком.
- **Риски**:
  - Переусложнение: hostile-режим ломает нормальные сети → митигация: строгий opt-in по детекту, а не дефолт.
  - Ложный детект whitelist → пользователь в медленном режиме без причины → митигация: высокий порог детекта + ручной override + явный UI-статус.
  - Шейпинг как новый фингерпринт («все sora-клиенты шейпятся одинаково») → митигация: параметры шейпинга из диапазона, не константы; джиттер обязателен.
