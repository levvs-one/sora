Репозиторий: `sora-legacy`, ветка `bugfix/audit-2026-10-19`, коммит

(`vmessBlob`/`mapVMessJSON` в `core/parser/parser.go`).
Ревью независимое: отчёту исполнителя не доверял. Все пробы прогнаны
в изолированных `git archive HEAD(031e4eed)` / `git archive HEAD(sora)`

## Вердикт: ПРИНЯТЬ С ЗАМЕЧАНИЯМИ

Коммит полностью и корректно портирует классический vmess-путь:
`vmessBlob`, `mapVMessJSON`, `jsonBool`, `checkVMessAlterID` и сигнатура
`parseVMess(raw, u)` — **байт-в-байт идентичны sora**, расхождения только
в двух комментариях (ссылка на AUDIT-PARITY вместо WAVE-INTEGRATION и
пометка про G2). Поведенческий паритет доказан не чтением, а пробами:
43 граничных случая прогнаны в обоих репозиториях, выводы **идентичны
построчно** (probe2: 25 случаев, probe3: 18 случаев, `diff` пуст).
Замечания ниже — не блокеры: одно про пробел в тестах исполнителя
(поведение при этом правильное, проверено моей пробой) и два про
унаследованные от эталона странности, чинить которые в этом коммите
означало бы сломать паритет.

## 1. Маршрутизация — ✅

- Блоб извлекается из сырого текста: `parseLink` теперь зовёт
  `parseVMess(raw, u)`, `vmessBlob` режет всё после `://` из исходной
  строки. Старый путь (`u.Opaque`/`u.Path`) удалён. Критичный частный
  случай подтверждён пробой: блоб, чей base64 содержит `/`
  (StdEncoding), импортируется (`slash.example.com`) — именно этот
  символ старый код терял на сплите `u.Path`.
- Диалектное ветвление: присутствие ключа `add` **или** `id` →
  `mapVMessJSON`, иначе `mapJSONSpec(v, "vmess")`. Sing-box-форма
  внутри vmess-ссылки не сломана — проба:
  `{"type":"vmess","server":"sb.example.com","server_port":8443,
  "uuid":…,"network":"ws","security":"tls"}` импортируется через
  `mapJSONSpec` (host/port/uuid/transport/security на месте), а тот же
  документ с `alter_id:64` отказывается (`ErrUnsupported`).
- URL/query-форма не проглатывается блоб-веткой: блоб URL-формы
  содержит `:`/`@`, `decodeBase64` его не декодирует (в legacy —
  доспустимый `:`-shortcut, семантически эквивалентен: `:` нет ни в
  одном base64-алфавите), выполнение падает в URL-ветку.
  `TestParseVMessURLStyleStillWorks` зелён, плюс пробы
  `VMESS://` (верхний регистр схемы) и RawURLEncoding-блобы — импорт
  работает.
- Классическая ссылка с хвостом `?foo=bar#Frag%20Name`: query срезана,
  фрагмент работает запасным именем и URL-декодируется (`Frag Name`).
- Битые блобы — честная ошибка, без паник. Мои пробы (все —
  `parseLink → ErrInvalid`, `Parse → servers=0, Invalid=1`):

  | Вход | Итог |
  |---|---|
  | `vmess://` пустой payload, только `#frag`, только `?type=ws` | Invalid=1 |
  | base64 от JSON-массива / `[]` / `"строки"` / `123` / `null` / `true` / `{}` | Invalid=1 |
  | `add` без port (±id), port `"0"`/`"99999"`/`"abc"` | Invalid=1 |
  | `id` без адреса; `{"v":"2","ps":"empty"}` без endpoint | Invalid=1 |
  | не-base64, base64-не-JSON, усечённый JSON | Invalid=1 |
  | 100 000 симв. base64-мусора; base64 от 50 КБ не-JSON | Invalid=1, без паники |
  | валидный классический с `ps` в 50 000 симв. | импортируется |

  Механистическая оговорка: не-объектный/битый JSON не отсекается
  явной веткой, а проваливается в URL-форму и умирает уже на её
  `validate()` (port=0). Итог для пользователя и Report честный,
  текст ошибки — общий `ErrInvalid`. Так же устроена и sora
  (код идентичен), менять в этом коммите не требовалось.
  Отдельный fuzz-прогон `FuzzParseLink` в отведённое время не
  завершился (перегруженная VM, пустой лог при timeout) — не заявляю
  его как пройденный; seed-корпус фуззера при этом исполняется
  обычным `go test` и зелён.

## 2. Полнота полей mapVMessJSON против эталона — ✅ ничего не потеряно

Построчный diff с sora: тело функции идентично. По полям:

| Поле JSON | Куда | Проверка |
|---|---|---|
| `add` → Host, fallback `address` | ✅ | проба: пустой `add` + `address` → импортируется с `address` |
| `port` число/строка | `portNumber` | ✅ оба варианта в тесте исполнителя |
| `id` | UUID | ✅; битый UUID → `ErrInvalid: invalid UUID` (проба) |
| `ps` → DisplayName, fallback — фрагмент | ✅ | оба случая в тесте исполнителя |
| `scy` → Cipher, default `auto` | ✅ | |
| `aid` → `checkVMessAlterID` | ✅ | §3 |
| `net` → Transport | ✅ | включая `grpc` (проба) |
| `tls`: `""`→`none`, `"tls"`→`tls`, прочее — как есть | ✅ | проба `tls:"reality"` → `Security="reality"` (поведение эталона) |
| `sni` → ServerName, `host` → HostHeader | ✅ **не перепутаны** | тест исполнителя пинит различными значениями (`sni=vmess.example.com` vs `host=cdn.example.com`); моя проба — второй парой (`sni.example.com` vs `hh.example.com`) |
| `path`, `fp` → Path, Fingerprint | ✅ | |
| `alpn` | split по `,` | ✅ |
| `insecure`/`allowInsecure` → AllowInsecure | `jsonBool` | ✅ поведение: пробы `true`/`1`/`"1"`/`"true"`/`"TRUE"` → true; `false`/`"yes"` → false. **Но тестами исполнителя не пинится** — см. замечание З1 |
| CountryCode из DisplayName | ✅ | |

`Options` сырым JSON классический путь не заполняет (в отличие от
`mapJSONSpec`) — это тоже паритет с sora, а не потеря: классические
ключи `v`/`type` («none» — тип заголовка, не транспорт) в рендеры не
должны попадать.

## 3. G2 на классическом пути — ✅ достижима, прогнано

Тест исполнителя `TestParseClassicVMessAlterIDRefusedEndToEnd`:
`aid:"64"` и `aid:64` → `parseLink` возвращает `ErrUnsupported`,
`Parse` даёт `Imported=0, Unsupported=1`. В моём независимом прогоне
пакета — зелён. Дополнительные пробы форм `aid` (все исходы **идентичны
sora**): `"0"`/`0`/`0.0` проходят; `"00"`, `" 0"`, `"abc"`, `64.5` —
отказ `ErrUnsupported`; `true`, `-1` проходят (см. замечание З2).

## 4. Тесты исполнителя и гигиена — ✅

- Не тавтология: `TestParseClassicVMessJSON` конструирует документ
  независимо и пинит конкретные различные значения по всем полям
  (endpoint, UUID+cipher, transport/security/SNI, host-header/path/fp,
  ALPN из 2 элементов, эмодзи-имя с CountryCode-контекстом),
  числовой вариант port/aid, RawURLEncoding-блобы.
- Смешанный импорт есть: классический vmess + vless в одном списке →
  2 сервера (зеркалит пробу эталона).
- Сверх эталона legacy добавляет: fallback-имя из фрагмента,
  `TestParseClassicVMessBrokenBlob` (4 битых блоба × parseLink+Parse+
  Report) и end-to-end G2 — в sora этих тестов нет, порт здесь
  **сильнее** оригинала.
- Гигиена: ровно 3 файла по делу (`parser.go` +124/−…, новый
  `vmess_classic_test.go`, `vmess_alterid_test.go`). Правка
  alterid-теста — **только комментарий** (10 строк): старый текст
  утверждал, что классический путь недостижим, — после G4 это ложь,
  обновление комментария корректно и честно, ни одного утверждения
  теста не ослаблено.
- «Имена 1:1 с эталоном» — **подтверждено**: `parseVMess(raw, u)`,
  `vmessBlob`, `mapVMessJSON`, `jsonBool`, `checkVMessAlterID`;
  хелперы `stringValue`/`portNumber`/`number`/`countryCode`/
  `fragmentName` также идентичны. Имена тестов
  `TestParseClassicVMessJSON`/`TestParseVMessURLStyleStillWorks`
  совпадают с sora; два новых теста — legacy-добавки, имён эталона
  не занимают.

## Замечания (не блокеры)

- **З1 (тестовый пробел, паритетный).** `AllowInsecure` на классическом
  пути не пинится ни тестом исполнителя, ни тестом sora, хотя поле
  входит в заявленную полноту G4. Поведение я проверил пробами
  (8 форм, §2) — оно правильное. Рекомендация: одним ассертом
  (`"insecure":true` в основном документе) закрыть в любом следующем
  касании файла, в обоих репозиториях.
- **З2 (унаследованные странности эталона, НЕ чинить в этом коммите).**
  Идентичны в sora построчно по пробам: (а) классический документ
  с `add`+`port`, но без `id`, импортируется с пустым UUID
  (`validate()` проверяет UUID только если непустой) — сервер без
  креды формально «импортирован»; (б) `aid:true` и `aid:-1` проходят
  G2-гейт (`number()` для bool/отрицательных даёт 0), а `aid:"abc"`
  отказывается. Всё это — поведение эталона; расхождение с ним было
  бы дефектом порта. Если владелец решит ужесточать — делать это
  отдельным коммитом в обоих репозиториях.
