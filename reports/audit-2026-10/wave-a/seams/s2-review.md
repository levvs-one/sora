# S2 (seams) — независимое ревью фиксов кластера S2

Ревьюер: независимый (не автор). Объекты — коммиты как объекты
(`git show`), прогоны — на чистых снимках (`git worktree` от нужного
коммита в /tmp, после ревью сняты). Грязное рабочее дерево чужих
отделов (в т.ч. не собирающийся `core/control` в WT, удалённые в WT
тест-файлы обоих коммитов, `MM refs.go/validate.go`) в ревью не
входило и дефектом коммитов не является; в главном дереве ничего не
трогалось, коммитов ревьюер не делал.

Оговорка об источнике: файл автора `s2-engines-zapret.md` на диске
физически обрезан — последняя строка (233) — литеральный маркер
`...[truncated 8067 chars]`; хвост раздела S2-Z1 (после первого
буллета) и задача 4 в файле отсутствуют. Утверждения по этим частям
сверялись с сообщениями коммитов и кодом, а не с фрагментом.

Итог: **оба коммита приняты с замечаниями; оснований для отклонения
не найдено.** Ни одного легитимного продюсера, ломаемого фиксами, не
существует (проверено перебором, см. ниже).

## 1. `acfcab37` — XPaddingBytes-only планы требуют FeatureXHTTPXmux (S2-C1)

**Вердикт: ПРИНЯТ С ЗАМЕЧАНИЯМИ** (замечания — к покрытию авторского
теста и к гипотетическому краю `"0"`, не к поведению фикса).

### Состав коммита — чисто

`git show --stat`: ровно 2 заявленных файла —
`core/engine/refs.go` (+10/−1) и новый
`core/engine/xpadding_gate_test.go` (40 строк). Чужих ханков нет.

Про «чужой servers-ханк в refs.go» — проверено особенно тщательно:
ханка `Group.Selected` в коммите **нет**. Он существует только как
незакоммиченная WT-правка поверх коммита (WT-blob refs.go
`77a29676` = blob коммита `1c052e40` + блок `Group.Selected` в
`Group.validate()`); коммит `91e50755`, названный автором, refs.go
вообще не трогал. Утверждение автора «чужой ханк не тронут и не
включён» — правда; в WT ханк к тому же безвреден для фикса (другой
метод файла, `RequiredFeatures` не пересекается).

### (а) Фикс ровно в заявленном месте; посылка верна

- До фикса (родитель `934ce3e7`): `RequiredFeatures` требовал
  `FeatureXHTTPXmux` только за 4 `XmuxMax*` поля. Фикс добавляет
  `|| o.Transport.XPaddingBytes != ""` в ту же ветку
  `Transport.Type == "xhttp"` — ровно заявленное место, ничего
  лишнего.
- Посылка «рендеры молча роняли» подтверждена по коду снимка:
  `git grep XPaddingBytes acfcab37 -- core/` — поле потребляет
  только mihomo (`mihomo/proxy.go`: `x-padding-bytes`); Xray-кейс
  xhttp эмитит mode/path/host/headers/downloadSettings, sing-box —
  mode/host/path/headers. Комментарий в `plan.go` («validated here
  and dropped at render time») на месте.
- Каталог снимка: `FeatureXHTTPXmux` не клеймит **ни один** движок
  (осознанно, до `mihomo -t` верификации — пинит предсуществующий
  `engine_test.go:463`). Следствие фикса на этом коммите: padding-
  only план честно получает missing на всех движках — та же политика,
  что уже действовала для xmux-планов; не регрессия, а закрытие
  «тихой потери» ценой честного отказа.

### (б) Воспроизведение на снимке (своя проба, не авторский тест)

Проба `TestReviewProbeXPaddingSelection` (временный файл в worktree,
в коммит не входил), снимок `acfcab37`:

- padding-only план (`Transport{Type:"xhttp", XPaddingBytes:"100-1000"}`,
  единственный аутбаунд vmess из `validPlan()`):
  `Catalog[kind].Missing` содержит `feature xhttp-xmux` для **всех
  трёх** движков (mihomo, sing-box, Xray);
- `SelectEngine` при всех трёх движках installed+usable (версии
  1.19.32 / 1.14.3 / 26.3.27) возвращает ошибку, называющую
  `xhttp-xmux`, по каждому движку;
- синтетический набор capabilities с клеймом `FeatureXHTTPXmux`:
  `Missing` xmux не содержит — «с xmux принимается» на уровне
  контракта `Capabilities.Missing`. На уровне каталога этого
  коммита принимающего движка нет (см. выше) — это заявленное
  автором состояние, а не дефект фикса.

Та же проба на снимке до фикса (`ba625cf3`, родитель обоих
коммитов): `SelectEngine(padding-only)` возвращал **nil** (план
селектился на Xray, который поле не рендерит) — дефект автора
воспроизведён дословно: вход → ожидаемое (отказ) → фактическое до
фикса (выбор движка, padding потерян молча).

### (в) Легитимные комбинации не сломаны

- `XPaddingBytes` + `XmuxMaxConcurrency:8` → гейт требуется (как и
  должен);
- только xmux-поля → гейт как раньше;
- `XPaddingBytes == ""` (plain xhttp) → гейта нет, и plain xhttp
  по-прежнему селектится `SelectEngine` успешно;
- padding на не-xhttp транспорте → `RequiredFeatures` не гейтит
  (эту форму отдельно отвергает `validate()`, как и до фикса).

### Замечания

1. Авторский тест уже утверждения: пинит `Missing` только для Xray
   и sing-box (не для mihomo, который на этом коммите клейма тоже не
   имеет), не пинит `SelectEngine`-уровень и комбинацию
   padding+xmux. Поведение при этом правильное — пробел закрыт
   пробой ревьюера, но в репозитории пина на mihomo/селекцию нет.
2. Край `"0"`: поле строковое, нулевое значение — только `""`.
   Строка `"0"` — валидный явный диапазон по `validate.go`
   (`lo==hi==0`) и гейтится. In-repo продюсера, пишущего `"0"` как
   sentinel «выключено», не существует (grep по parser/control/app:
   продюсеров поля вне engine-тестов нет), поэтому легитимной
   поломки нет; замечание — на будущее, если такой продюсер
   появится.
3. Гейт бандлит padding в фичу xmux целиком: если позже sing-box
   рендерер научат эмитить только `x_padding_bytes` (движок это
   умеет, каталог так и комментирует), padding-only планы всё равно
   не попадут в sing-box до отдельного клейма. На этом коммите
   бандл верен рендерерам (mihomo эмитит оба, остальные — ни
   одного).

Прогоны на снимке `acfcab37`: авторский
`TestXPaddingBytesRequiresXmuxCapability` — PASS; полные пакеты
`./engine/ ./engine/bypass/ ./engine/registry/ ./tune/...
./control/ ./engine/mihomo/ ./engine/xray/ ./engine/singbox/` —
все ok, `go vet` чист.

## 2. `934ce3e7` — validateDesync отвергает микс tpws-полей с nfqws (S2-Z1)

**Вердикт: ПРИНЯТ С ЗАМЕЧАНИЯМИ** (замечания — неполный кейс в
авторском тесте; второй тест коммита шире заявленного пункта;
соседний предсуществующий дефект конвертера геномов — не этого
коммита).

### Состав коммита — чисто

Ровно 2 заявленных файла: `core/engine/validate.go` (+34) и новый
`core/engine/bypass/nfqws_legacy_mix_test.go` (93 строки). Родитель
— `ba625cf3`; отсутствие гейта до фикса подтверждено
(`grep tpws-only` по родителю — пусто).

### (а) Отвергается ровно теряемое; потребляемое проходит

Полный состав `BypassStrategy` на снимке — 29 полей.
`NFQWSArgs` потребляет 11: `Desync, SplitPos, Fooling, TTL, AutoTTL,
Repeats, FakeTLS, FakeQUIC, FilterTCP, FilterUDP, FilterL7`.
Legacy-only полей — 18: `Disorder, DisorderScope, OOB, OOBScope,
OOBData, TLSRecord, HostCase, DomainCase, MethodEOL, HostDot,
HostTab, HostNoSpace, MethodSpace, UnixEOL, SplitAnyProtocol,
TamperStart, TamperCutoff, MSS` (все рендерятся tpws-`Args`, ни
одно — `NFQWSArgs`; сверено построчно по обоим рендерерам).

Фикс отвергает при `len(Desync) > 0` все 18, сгруппировав в 15
записей (`disorder = Disorder||DisorderScope`,
`oob = OOB||OOBScope||OOBData`, остальные по одному). Ни одно из 11
потребляемых полей гейтом не затронуто; `SplitPos` — единственное
legacy-поле, которое `NFQWSArgs` рендерит
(`--dpi-desync-split-pos`), — разрешён. Сверка полная, расхождений
нет. (В задании и фрагменте фигурирует «17 полей» — это число
кейсов авторского теста; полей фактически 18, см. замечание 1.)

Собственная проба `TestReviewProbeNFQWSMixMatrix` (20 кейсов:
каждое из 18 полей по отдельности + `DisorderScope` соло +
`OOBData` соло; 10 легальных nfqws-миксов):

- снимок `acfcab37` (фикс в силе): все 20 legacy-кейсов отвергнуты;
  все 10 легальных миксов (splitpos/fooling/ttl/autottl/repeats/
  faketls/fakequic/filtertcp/filterudp/filterl7) и
  `DefaultStrategy()` валидны;
- снимок до фикса `ba625cf3`: ровно 18 legacy-кейсов **проходили**
  валидацию (дефект воспроизведён, включая дословный пример автора
  `{Desync:[fake], Disorder:true, SplitPos:[1], FilterTCP:"443"}`);
  2 соло-кейса (scope/oobdata без родителя) отвергались и раньше —
  более ранними проверками `validate()`.

### (б) Легитимного продюсера микса в репозитории нет

Перебраны все продюсеры `BypassStrategy` на снимке коммита:

- `bypass.DefaultStrategy()` — `Desync + AutoTTL + FilterTCP/UDP/L7
  + FakeQUIC`, legacy-полей нет. Валиден после фикса (проба +
  пакетные тесты).
- F11-путь `control.applyZapretWithVPN`: nil-стратегия →
  `DefaultStrategy()`; клиентская стратегия собирается только из 7
  legacy-полей proto. Proto `BypassStrategy` на этом коммите
  desync-полей **не имеет вовсе** (pb: split_pos, disorder, oob,
  tls_record, host_case, domain_case, method_eol) — клиентский
  микс недостижим в принципе. `outboundFromProto` — тот же набор
  из 7 полей, `Desync` не выставляет.
- `tune.ZapretAlternatives()` — 8 стратегий, все чисто legacy без
  `Desync`.
- Геномы `tune/desync.Params.BypassStrategy()` — перебор сеткой
  пробой ревьюера: 6 методов × fooling × fakeProto × scope = 144
  комбинации, 84 конвертируются (`ok=true`). Конвертер сам
  отказывает (`ok=false`) для OOB/TLSRec/HTTPShuffle на nfqws-пути
  и для disorder выставляет `Desync=[disorder2]`, а не legacy-
  `Disorder`. Ни одной стратегии, отвергнутой **новым** гейтом,
  конвертер не производит (см. замечание 3 про предсуществующий
  отказ по другой причине).

Оснований для отклонения по пункту (б) нет: фикс прод не ломает.

### (в) Тесты на снимке

Авторский `TestDesyncStrategyRefusesTPWSOnlyFields` — PASS на
чистом снимке коммита; полные пакеты `./engine/ ./engine/bypass/
./tune/... ./control/` — ok.

### Замечания

1. Авторский тест пинит 17 кейсов из 18 полей: нет отдельного
   кейса `OOBScope` (есть `OOB` и `OOB+OOBData`), `DisorderScope`
   идёт только вместе с `Disorder`. Код при этом покрывает все 18
   (группировки `||`), что подтверждено пробой ревьюера; пин в
   репозитории уже факта.
2. Коммит шире заявленного пункта S2-Z1: тот же тест-файл несёт
   второй тест `TestShippedFakePayloadsExist` (задача 4 автора —
   пин имён fake-пейлоадов против vendored `third_party/zapret`).
   Он заявлен в сообщении коммита, на снимке проходит, файлов вне
   заявленных не добавляет — безвреден, но при атрибуции коммита
   только к Z1 о нём надо знать.
3. **Соседний предсуществующий дефект (не этого коммита, не
   основание для отклонения).** Сценарий: вход — геном
   `tune/desync.Params{Method: split|disorder, FakeProto: "tls"|"quic"}`
   → `BypassStrategy()` возвращает `ok=true` со стратегией
   `{Desync:[split2|disorder2], FakeTLS/FakeQUIC: ...}` → ожидаемое:
   стратегия валидна → фактическое: `Outbound.Validate()` отвергает
   «fake payloads need the fake desync method». На сетке пробы —
   32 такие комбинации; множества отказов на снимках до и после
   `934ce3e7` **идентичны** (diff пуст), ошибка — предсуществующая
   проверка `validateDesync`, новый гейт в этих стратегиях не
   срабатывает (legacy-полей нет). Поведение fail-closed
   (кандидат тюнера недостижим, а не молча искажён). Рекомендация:
   отдельной задачей отделу tune — конвертер должен возвращать
   `ok=false` для `FakeProto` при методе не-`fake`, либо валидация
   должна принимать fake-пейлоады с split2/disorder2.
