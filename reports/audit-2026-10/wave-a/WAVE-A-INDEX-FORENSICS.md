**Следователь:** лид форензики волны A. **Дата:** 2026-10-20.
**Объекты:** `~/workspace/bug-hunt/sora` и `~/workspace/bug-hunt/sora-legacy`,

## 0. Вердикт (кратко)

**Единый «атакующий процесс» НЕ СУЩЕСТВОВАЛ — и это доказано, а не
предположено.** На VM нет никакой автоматики, способной трогать git вне
агентских сессий: нет хуков, нет cron, нет кастомных systemd-таймеров, нет
фоновых watcher-процессов, в обоих репозиториях нет ни одного скрипта,
выполняющего git-мутации (единственное совпадение — CI-workflow
`.github/workflows/autofix.yml`, он исполняется на GitHub, не здесь).

**Подтверждённый механизм — системный, а не персональный.** «Атаки» —
механический продукт совокупности открыто применявшихся отделами опасных
техник на ОДНОМ общем индексе и дереве:

1. `git checkout <старая ревизия|stash> -- <пути>` как способ «восстановить
   файл» — команда пишет старое содержимое и в worktree, и в индекс; для
   путей, тронутых свежими коммитами, staged-результат неотличим от
   прицельного staged-revert'а этих коммитов. Поименно зафиксированы
   6 агентов и ≥11 таких операций в общем клоне, включая одну за 2 минуты
   до обнаружения атаки №6 и по её же классу файлов.
2. `git stash push/pop` в общем клоне как рутина ревьюеров и фиксеров
   (≥8 агентов), включая `stash push -m "tmp: oth…"` — сташ ЧУЖИХ изменений.
3. CAS-коммиты из устаревших слепков, приземлявшие деревья без свежих
   файлов, — они провоцировали «восстановления» из п.1 (петля обратной
   связи), а defusal-`git reset` лидов уничтожал легитимный стейдж владельцев
   и провоцировал пере-стейдж из сташей и старых ревизий.

**Остаточная неопределённость (честно):** привязка каждого из 18 ночных
эпизодов к конкретной команде невозможна — эта инсталляция рантайма не
сохраняет полные тексты команд (`runtime.tool_calls` и транскрипты в БД
пусты; в журнале прогресса описания команд обрезаны на ~75 символах, пути
целей не видны). Утверждение «эпизод X сделал агент Y командой Z» было бы
выдумкой. Доказано другое: (а) внеагентского актора нет; (б) техники,
механически производящие ровно наблюдавшийся почерк, применялись массово,
открыто и поименно; (в) HEAD за всю историю ни разу не двигался назад без
документированной причины.

## 2. Аудит автоматики: кто вообще может трогать git

Проверено 2026-10-20, оба клона и VM целиком:

| Источник | Результат |
|---|---|
| `.git/hooks/` обоих клонов | только `*.sample`, активных хуков НЕТ |
| `.git/config` обоих клонов | обычный; ничего исполняемого. В sora `extensions.worktreeConfig=true` — безвредно |
| cron | бинаря `crontab` на VM нет; `/etc/cron.d/` — только стоковый `e2scrub_all` |
| systemd timers | только стоковые Ubuntu (apt, dpkg, e2scrub, fstrim, motd, tmpfiles-clean) |
| процессы VM | `hatch daemon`, `hatch-execd` и шеллы текущих агентов; стоящих watcher'ов/демонов нет |
| Скрипты в обоих репо | единственный файл с git-мутациями — `.github/workflows/autofix.yml` (CI на стороне GitHub; на этой VM не исполняется; к индексу локальных клонов отношения не имеет) |
| Скрипты в `~/workspace/bug-hunt` | исполняемых департаментских скриптов не сохранилось — только упоминания в отчётах (.md). Рецепты жили в эфемерных `/tmp/*.sh` конкретных агентов (CAS-обёртки вида `tcommit_*.sh`) и исполнялись только их владельцами |
| Linked worktrees | 24 шт. (`~/workspace/.review-*`, detached HEAD, остались от ревьюеров оптимизаторов). У каждого СВОЙ индекс (`.git/worktrees/<id>/index`) — главный индекс они трогать не могут; как вектор отравления исключены |

**Вывод раздела:** единственные процессы, когда-либо выполнявшие git-мутации
в этих клонах, — шеллы агентов через `hatch-execd`. Постороннего актора на
уровне ОС не существует.

## 3. Форензика по журналу рантайма и reflog

### 3.1. Доступные источники и их пределы

- `runtime.tool_calls` (полные тексты вызовов) — **пуста** в этой
  инсталляции; `agent.context_text_segments` (транскрипты) — **пуста**.
  Полные команды агентов не сохранены нигде.
- `agent.subagent_progress_tool_events` — 48 628 exec-событий всех
  субагентов программы; описание команды обрезано (~75 символов: виден
  префикс `cd <клон> && git <глагол> <начало аргументов>`, пути целей —
  как правило, НЕТ). Этого достаточно для инвентаризации глаголов и
  атрибуции по агенту/времени, недостаточно для доказательства путей.
- Родительская сессия (main-агент) в эту таблицу не попадает; её команды
  аудитируемы по транскрипту, унаследованному следствием: все её
  `checkout <rev> -- …` — восстановления собственных файлов отделов с
  последующей проверкой staged-состава; все `restore --staged`/`reset` —
  обезвреживания. Ничего revert-образного против чужих свежих коммитов.

## 4. Контролируемый эксперимент (ловушка)

- fanotify недоступен: `fanotify_init: Operation not permitted` даже под
  root — песочница рантайма блокирует. Зафиксировано как ограничение среды.
- Развёрнут опросный монитор `monitor.py` (50 мс): (а) sha256+mtime

## 7. Рекомендации

1. **Запрет для общих клонов** (дополнить AGENTS.md/SWARM-DIRECTIVES):
   `git stash push/pop/apply`, `git checkout <rev> -- <пути>`,
   `git restore --source=<не-HEAD>` в общем клоне — запрещены без
   исключений. Восстановление файла — только `git show <rev>:<путь>` в
   /tmp + temp-index apply по CAS-рецепту, либо отдельный worktree.
2. **Ревьюерам — только worktree.** Проверка чужих коммитов «на чистом
   дереве» делается в `git worktree` (как уже делали ревьюеры
   оптимизаторов), а не сташем чужих изменений.
3. **Монитор — постоянной ловушкой** на время любых роёв: даёт то, чего не
   хватило ночью, — атрибуцию за <1 с с полным текстом команды.
4. **Pre-commit guard** (устанавливать осознанно, владельцем/лидом роя —
   следствие не устанавливает): хук, который блокирует коммит, если
   staged-blob пути равен его blob'у в HEAD~1 при том, что HEAD этот путь
   менял (почерк staged-revert'а свежего коммита), либо если staged-пути
   выходят за объявленный агентом список. Черновик:

```sh
#!/bin/sh
# pre-commit guard: block staged reverts of the freshest commit and
# staging outside the agent's declared path set (SORA_AGENT_PATHS).
set -eu
staged=$(git diff --cached --name-only)
[ -z "$staged" ] && exit 0
if [ -n "${SORA_AGENT_PATHS:-}" ]; then
  for p in $staged; do
    case " $SORA_AGENT_PATHS " in *" $p "*) ;; *)
      echo "guard: $p outside declared paths" >&2; exit 1;; esac
  done
fi
for p in $(git diff --cached --name-only HEAD~1 2>/dev/null || true); do
  : # paths changed by HEAD itself are checked below
done
for p in $staged; do
  head_blob=$(git rev-parse -q --verify "HEAD:$p" 2>/dev/null || echo none)
  prev_blob=$(git rev-parse -q --verify "HEAD~1:$p" 2>/dev/null || echo none)
  idx_blob=$(git ls-files -s -- "$p" | awk '{print $2}')
  if [ "$prev_blob" != "none" ] && [ "$idx_blob" = "$prev_blob" ] \
     && [ "$head_blob" != "$prev_blob" ] && [ "${ALLOW_REVERT:-}" != "1" ]; then
    echo "guard: $p staged as exact revert of HEAD; set ALLOW_REVERT=1 if intentional" >&2
    exit 1
  fi
done
exit 0
```

   Ограничения честно: хук не видит `commit-tree`-CAS (тот идёт мимо
   `git commit`) — для CAS-скриптов та же проверка встраивается в обёртку
   перед `update-ref` (сравнение write-tree результата с деревом HEAD~1 по
   путям HEAD). Guard — предохранитель от случайности, не от умысла.
5. **Рантайму на будущее:** сохранять полные тексты exec-команд агентов
   (сейчас — обрезка на ~75 символах и пустые таблицы полных вызовов).
   Ночная форензика упиралась именно в это.
