# WAVE-INTEGRATION — отдел интеграции и превосходства

Дата: 2026-10-20. Ветка `bugfix/audit-2026-10-19` (без пуша — родитель батчами).
Зона отдела: связность системы как целого и превосходство над Happ.
Метод: живой стенд на этой машине (реальные серверы + настоящее ядро sora-core),
вердикты — только по факту трафика и логов серверов, не по «RPC вернул OK».

---

## 0. Итог одной строкой

Сквозной E2E нашёл и закрыл **четыре продуктовых дефекта, каждый из которых
полностью хоронил заметную фичу на дефолтном пути** (REALITY через mihomo,
бенчмарк серверов, импорт классических VMess, пароли trojan/hysteria2), плюс
добавлен недостающий REALITY-пин в interop-матрицу. Все фиксы — с независимым
ревью (по багам 1–4: 5 из 5 коммитов APPROVE; ревью interop-пина — отдельным
агентом, при расхождении доложу родителю дополнительно). Все заявленные
сценарии после фиксов проходят по факту трафика.

## 1. Happ: матрица превосходства

Полный разбор — отдельный отчёт **WAVE-INTEGRATION-happ.md** (35 осей, источники
по каждому факту о Happ; здесь — сводка вердиктов).

- **sora лучше (16 осей):** протоколы и транспорты; 3 движка против 1 Xray;
  форматы подписок (тело); авто-выбор серверов и группы (bandwidth-скоринг);
  realtime-статистика и экран соединений; anti-DPI сверх ядра (фрагментация,
  zapret, детектор цензуры); открытый код GPL-3.0; E2E-синк без облака
  (оговорка E4); цепочки прокси; подписанные расширения; kill switch уровня ОС;
  AmneziaWG/WireGuard/TUIC; безопасность локальных интерфейсов; диагностика;
  локализация (32 языка); проверяемость «нет телеметрии».
- **Паритет (8 осей):** заголовки/userinfo подписок; несколько подписок и
  автообновление; пользовательская маршрутизация; онбординг на десктопе; пинг;
  QR/буфер; uTLS по факту ядра; монетизация (оба бесплатны).
- **Отстаём (7 осей):** HWID-лимиты провайдеров; зашифрованные подписки
  `happ://crypto…`; провайдерская маршрутизация `happRouting`; `fallback-url`
  подписки; Android (нет платформы); iOS/macOS/TV; рыночный масштаб
  (10M+ установок Happ).
- **Не подтверждено:** скорость запуска/подключения обеих сторон (публичных
  замеров нет — наши внутренние цифры в §4), «платный Happ Plus», телеметрия
  Happ (конфликт источников), автовыбор сервера у Happ.

**Важно из E2E этого отдела:** две оси матрицы («протоколы/подписки» и
«bandwidth-автовыбор») на старте волны были фактически НЕ верны — классический
VMess не импортировался, trojan/hy2 теряли пароль, а BenchmarkServers падал для
любого сервера (§3, баги 2–4). После фиксов вердикты матрицы подтверждены живым
трафиком, а не только чтением кода.

Планы закрытия гэпов кодом (C1 HWID, C2 crypto-подписки, C3 happRouting,
C4 fallback-url, C5 stealth-пресеты, C6 публичный стенд скорости, C7 LAN-раздача)
и эскалации владельцу (E1 Android, E2 E2 iOS/macOS, E3 доступ к crypto-спеке,
E4 sora-sync в пакетах, E5 key ceremony, E6 дистрибуция, E7 TV) — в
WAVE-INTEGRATION-happ.md §4–5. Отдел поддерживает порядок: C1 → C3 → C4
(дёшево, провайдерская экосистема), дальше решение владельца по Android.

Контекст конкурентов: v2RayTun (тот же класс, уже умеет HWID и SOCKS-auth —
планка сегмента), Streisand iOS (шире Happ по протоколам: TUIC/WG/SSH —
преимущество sora по протоколам не уникально само по себе; уникальна связка
«протоколы × 3 движка × десктопный kill switch × zapret»).

## 2. Стенд E2E (как проверялось)

- Серверы (sing-box из `packaging/engines`): VLESS+REALITY :24443 (dest —
  локальный TLS :28443, SNI www.microsoft.com ≠ адрес), Shadowsocks-2022 :28388,
  хоп SS-2022 :29388 → REALITY, VMess+TLS :24444 (SNI vmess.example.com),
  Trojan :24445 (SNI trojan.example.com); троттлящий реле :29389 (~64 КБ/с) для
  бенчмарка; HTTP-цель :28080 (`/marker/*` пишет в журнал попаданий, `/big` 4 МиБ);
  подписка по HTTPS :28444 (локальный CA в системном хранилище), plain-HTTP
  вариант для проверки отказа.
- Клиент: настоящее ядро `sora-core` (сборка из дерева ветки), управление —
  собственный gRPC-драйвер по контракту 1.11; трафик — curl через локальный
  прокси ядра; каждый сценарий — с негативным контролем (убить сервер → curl
  обязан упасть, счётчик цели не двигаться).
- Движки стенда обновились по ходу волны отделом движков: утренние прогоны —
  sing-box-lx.14 / Xray 26.3.27, дневные — lx.22 / Xray 26.10.17, mihomo 1.19.32
  весь день (WAVE-A-ENGINES.md).

## 3. Дефекты, найденные E2E и исправленные

### Баг 1 — REALITY мёртв на дефолтном пути (mihomo ронял SNI) — `8df15468`
Дефолтный план (PrivateControl) несёт mihomo (PrivatePreference, sing-box
отфильтрован по capability). Рендерер mihomo клал TLS server name под ключ
`sni` для всех протоколов, но адаптеры **vless и vmess в mihomo 1.19.32
читают только `servername`** (проверено по исходникам пина:
`adapter/outbound/vless.go:89`, `vmess.go:70`; trojan/anytls/hy2/tuic/http
читают `sni`). Ключ молча игнорировался: имя не попадало в handshake,
сертификат проверялся против адреса дозвона — каждый VLESS/VMess+TLS/REALITY
сеанс через mihomo падал. Дыра покрытия: в interop-матрице REALITY-кейсов
было **ноль**. Фикс: свитч по протоколу в `applyTLS` + поле `servername` +
`TestRenderServerNameKeyPerProtocol`. Ревью: APPROVE.

### Баг 2 — BenchmarkServers мёртв полностью (два дефекта в одном пути)
F2 (выбор сервера по пропускной способности) падал для **любого** сервера:
- **2а `69c410ed`:** замыкание SelectKind в `cmd/sora-core/main.go` звало
  `SelectEngine(plan, availability, nil)` — SelectEngine итерирует именно
  переданный порядок, nil = ни одного движка → всегда ErrNoEngine.
  Фикс: `benchmarkSelectKind` с `engine.DefaultPreference` + тест в
  `wiring_test.go`. Ревью: APPROVE.
- **2б `f7a830b7`:** `probe/bandwidth.go` целил match-all правило в display-имя
  `"benchmark"`, а цели правил резолвятся по ID outbound'ов — каждый реальный
  движок отклонял план `unknown target "benchmark"`. Тестовый движок-дабл
  валидацию пропускал — дефект виден только живьём. Фикс: Target = ID +
  `TestBenchmarkPlanPassesEngineValidation` (план через настоящий
  Plan.Validate). Ревью: APPROVE.
После фиксов бенчмарк на стенде различает серверы честно: SS-2022 —
137,5 МБ/с, REALITY — 63,1 МБ/с, троттленый реле — 0,13 МБ/с (ровно
пропускная способность реле ×2 направлений).

### Баг 3 — классические VMess-ссылки не импортировались — `408ad878`
Самый массовый формат VMess в мире, `vmess://<base64 JSON>` (v2rayN), падал
целиком: `parseVMess` читал блоб из `url.URL.Opaque/Path`, а `url.Parse`
кладёт блоб в `Host` — ветка base64 была недостижимым мёртвым кодом; одна
такая ссылка хоронила импорт, в смешанном списке сервер исчезал **молча**.
Плюс `mapJSONSpec` не знает v2rayN-полей (`add`/`id`/`ps`). Фикс: блоб из
сырого текста ссылки + `mapVMessJSON` (add/port/id/scy/net/tls/sni/host/
path/alpn/fp/insecure); sing-box-стиль остался фолбэком; URL-стиль не тронут.
Тесты: `TestParseClassicVMessJSON`, `TestParseVMessURLStyleStillWorks`.
Ревью: APPROVE.

### Баг 4 — trojan/hysteria2 теряли пароль при импорте — `1b094621`
Канонические формы `trojan://<password>@host` и `hysteria2://<password>@host`
несут креду в userinfo-username; `parseLink` парковал её в UUID, Password
оставался пустым, а все три рендерера аутентифицируют trojan/hy2 из Password.
Итог: импортированный сервер без креды, mihomo отклонял план
(`unset fields: password`). Фикс: явная ветка password-only протоколов в
parseLink + `TestParsePasswordOnlyCredentials`. Ревью: APPROVE.

### Пин — REALITY в interop-матрице — `5ba2d079`
`TestRealityThroughEveryEngine`: sing-box REALITY-сервер (живой TLS dest,
SNI ≠ адрес), трафик через все три движка — зелёный на новых пинах
(lx.22 / 26.10.17). Xray как REALITY-сервер в пин сознательно не взят:
в этой песочнице hand-rolled Xray REALITY inbound падал даже между двумя
вендорными бинарями (post-handshake `payload[0]: 8, padding: -4` при
совпадающих AuthKey — клиент Xray 26.10.17 ↔ сервер Xray 26.10.17,
ключи от `xray x25519`); к sora дефект отношения не имеет, но как
наблюдение — отделу движков на заметку.

## 5. Скорость как факты (эта машина, 2 ядра)

- **Холодный старт ядра:** процесс → `core listening` — **59–118 мс**;
  `BenchmarkNewWarmPopulated` (New() in-process, населённый data dir) —
  **71,7 мс/op**. Утверждение OPT40 «238 мс» относилось к New(); регрессии нет,
  текущее дерево быстрее.
- **Первый RPC после старта:** 0,76–1,36 с — одноразовая цена ленивого
  обнаружения движков (version-пробы трёх бинарей) на первом акцессоре;
  с пустым engines dir первый RPC — 20 мс, последующие RPC — 25–35 мс
  (включая ~20 мс спавна клиента). Дизайн lazy-warm осознанный (UI успевает
  раньше Connect); не регрессия, протоколирую как характеристику.
- **Connect → CONNECTED (RPC, включая старт движка):** mihomo 150–498 мс,
  xray 421–619 мс, цепочка 234 мс, троттленый реле не влияет. До первого
  байта на loopback — в пределах того же окна (curl сразу после Connect).
- **Overhead туннеля (goodput, loopback):** SS-2022 137,5 МБ/с против
  REALITY 63,1 МБ/с — цена Vision/REALITY-обработки на слабом CPU;
  абсолютные цифры стендовые, не маркетинговые.

## 6. Эскалации (не закрывается в этой песочнице / не кодом отдела)

1. **Kill switch + TUN end-to-end** — нужен непривилегированный пользователь
   и/или dev-машина без sandbox-guard: прогнать TUN-сессию, kill движка,
   проверить nft-изоляцию по факту отсутствия direct-трафика.
2. **Xray как REALITY-сервер** — вендорная пара Xray↔Xray в стенде не
   заработала (см. §3, пин); если продукт заявит поддержку чужих
   Xray-серверов как эталон, нужен отдельный разбор с dest уровня
   реального сайта (www.microsoft.com недостижим из песочницы).
3. **Happ-гэпы владельцу:** E1 Android, E2 iOS/macOS, E3 crypto-спека,
   E4 sora-sync в пакетах, E5 key ceremony, E6 дистрибуция, E7 TV
   (детали — WAVE-INTEGRATION-happ.md §5).
4. **Известные ограничения вне фиксов:** VMess `aid > 0` не проброшен
   (рендереры пишут alterId=0 — pre-existing, доля таких серверов мала);
   `sora-sync` демон по-прежнему не в пакетах (E4).
